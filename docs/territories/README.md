# The Territory Protocol

PACE is built by **nine territories**. Each one is a team with a border, a set of
laws it enforces, a memory of its own, and a formal way of asking another team for
something. This file is the protocol they all follow. It is short on purpose — every
agent loads it, so every line here costs context nine times over.

---

## Why this exists

Before this, one conversation held the whole product. That meant:

- every new chat re-read `CLAUDE.md` (1,172 lines) and `CONTEXT_WINDOW.md` (265)
  before it could do anything;
- context filled with detail that had nothing to do with the task — a CSS fix
  carrying the entire send-queue ordering rationale;
- and returning to an old piece of work meant rebuilding the state of it out loud.

A territory carries **only its own memory**. The frontend agent does not know how
the send queue orders itself, and does not need to. When it does need to, it asks.

## The three files

| File | What it is | Who writes it |
|---|---|---|
| `docs/territories/<name>.md` | One territory's **living memory** — what is true there now, what is fragile, what is open | that territory's agent, at the end of every job |
| `docs/territories/_contracts.md` | The **border ledger** — every request one territory has made of another, and its status | the asking agent opens it; the answering agent closes it |
| `docs/territories/_map.json` | The **machine-readable map** — territories, paths, edges, sizes. Drives the island view | regenerated by `node scripts/territory-map.mjs` |
| `docs/territories/CAPABILITIES.md` | **What PACE can already do.** Grep it before building anything user-facing — the job may be EXTEND, not build | whoever adds or supersedes a capability, in the same change |
| `docs/territories/DECISIONS.md` | **What the OWNER chose**, and what must not be re-raised. Read before proposing anything | the orchestrator, the moment a decision is made |
| `docs/territories/INTAKE.md` | **How to read the owner** — their four kinds of input, the eight rules, and where a sentence goes | rarely; it changes when a new *kind* of report appears |

`CLAUDE.md` remains the constitution — the laws that bind every territory. A
territory memory file never repeats it; it points at it.

## The working loop

Every territory agent runs the same five steps. This is the whole discipline.

0b. **Grep `docs/territories/CAPABILITIES.md` for the CAPABILITY, not the
   feature name.** "Email a candidate about a job" is a capability; "candidate
   outreach generator" is a name, and searching for a name finds nothing.
   If it exists, the job is **EXTEND** or **REPLACE**, never a second copy —
   and a replacement removes the old entry points in the same change.
   **Two live paths to one outcome is the bug**, and borders make it MORE
   likely, not less: each territory reads only its own memory. The owner found
   the first one, not the system.
0a. **Read `docs/territories/DECISIONS.md`.** Before you propose anything or
   call anything a bug, check whether the owner has already settled it. A
   suggestion they have already declined is not a fresh idea; a defect they
   have deliberately parked is not an open defect. Each entry carries a
   **Re-open when** condition — meet it, or leave it alone.
0. **Read `docs/territories/INTAKE.md`.** The input to this system is not a
   ticket — it is a sentence typed by the person who uses the product, or a
   screenshot with no words at all. That file is how to read one, and it is
   short. **Reproduce the sentence, not your hypothesis.**
1. **Read your memory.** `docs/territories/<you>.md` first, always. Then only the
   files it tells you matter for this job. Do not read `CONTEXT_ARCHIVE.md` unless
   your memory sends you to a specific section of it.
2. **Check your inbox.** Open `_contracts.md` and read any OPEN request addressed
   to you. Another territory may already be waiting on you.
3. **Do the work — inside your border.** If the job needs a change outside your
   paths, you do not make it. You open a request (below) and say so in your report.
4. **Raise what you could not do yourself.** Append to `_contracts.md`:

   ```
   ### C-0042 · surface → deep · OPEN · 2026-09-09
   **Asks for:** a `candidates.preferred_shift` column, nullable text.
   **Because:** the sourcing filter has a shift control with nothing behind it.
   **Blocked until answered:** yes — the control is hidden in the meantime.
   ```

   An id, a direction, a status, a date, what and why. Status is `OPEN`,
   `ANSWERED`, or `DECLINED` with a reason. Never delete an entry; close it.
4b. **Stop cleanly if you are cut off.** A rate limit, an API error or a
   cancelled run can end you mid-job. **Never leave a file half-written**:
   finish the edit you are inside, or undo it, before you stop. Then report
   what you actually completed and what you had not started. A clean stop with
   three of five things done is recoverable; a half-written file in a codebase
   with no build step is a silent breakage — `node --check` will pass on a file
   with a function missing from the middle of it. Two territory jobs died this
   way on 2026-09-09 and left nothing behind, which is the standard to hold.
5. **Write your memory, then stop.** Update `docs/territories/<you>.md`: what is
   now true, what you learned that would have saved you an hour, what is still
   open. Then report back in the format below and **end**. Your context dies here
   — the memory file is the only thing that survives, so anything not written
   down is lost.

## What a territory reports back

Six lines. Not a narrative.

```
TERRITORY: harbour
DID:       <what changed, in the owner's language, not the code's>
FILES:     <paths touched>
VERIFIED:  <the exact command run and its result — or "not verified", honestly>
RAISED:    <contract ids opened, or "none">
MEMORY:    updated
```

## Border rules

- **A territory never edits another territory's paths.** Not "just this once",
  not "it was a one-line fix". The silent divergence this prevents is the single
  most expensive class of bug in this codebase (see `CLAUDE.md` on the three lead-
  release paths, and the stage vocabulary living in six files).
- **A shared file has one owner.** `index.js` belongs to **gateway**. `CLAUDE.md`
  belongs to the orchestrator. When you need a change in someone else's file, that
  is a contract, not an edit.
- **Any territory may READ anything.** Borders restrict writing, never looking.
- **`foundry` and `rampart` have standing right of review** over every other
  territory's work — quality and security are not optional sign-offs.
- **No territory applies a database migration.** `deep` writes them; only the
  owner authorises applying one, freshly, each time.

## Who to ask for what

- **not sure, or it is just a sentence and a screenshot → `dispatch`** (the
  front door; it reads the sentence, reproduces it, and routes)
- something on screen → `surface`
- an endpoint, a route, the server → `gateway`
- a column, a table, a migration → `deep`
- anything that sends or receives mail → `harbour`
- a model, a prompt, a score, a budget → `observatory`
- stages, submissions, candidates, job orders → `guild`
- login, roles, org isolation, RLS → `rampart`
- a test, a release, the deploy → `foundry`
- plans, limits, opt-outs, anything a regulator would read → `ledger`
