# DDIA (Kleppmann) - Part II intro, Ch5 Replication, Ch6 Partitioning - notes

## PART II intro: Distributed Data
Core argument: Part I covered one machine; Part II asks what changes when several machines store data. Three reasons to distribute: scalability (load beyond one machine), fault tolerance/high availability (survive machine/network/datacenter loss), latency (serve users from nearby datacenters).
- Vertical scaling (scale up) / shared-memory: one bigger machine; cost grows faster than linearly, a 2x machine does not handle 2x load, limited fault tolerance, single location. NUMA footnote: even one big box needs partitioning of work for memory locality.
- Shared-disk: several machines, shared disk array (NAS/SAN); used for some data warehousing; locking overhead and contention limit scale.
- Shared-nothing (horizontal scaling / scale out): each node (machine/VM) has own CPU, RAM, disk; coordination in software over normal network; commodity hardware, multi-region possible, even small companies can do it on cloud. Focus of the book because it demands most care from the developer: the DB cannot hide the trade-offs. Costs: app complexity, sometimes limits data model. A single-threaded program can beat a 100+ core cluster (COST paper).
- Two mechanisms, often combined: Replication (copy of same data on several nodes: redundancy + performance) and Partitioning/sharding (split big DB into partitions on different nodes). Fig II-1: two partitions, two replicas each.
- Roadmap: transactions Ch7; fundamental limits Ch8-9; Part III integrates multiple stores.
Quote: "For a successful technology, reality must take precedence over public relations, for nature cannot be fooled." (Feynman epigraph)

## CHAPTER 5: Replication
### Core argument
Replication = same data on multiple machines, for geographic closeness (latency), availability, and read throughput. Static data is trivial; all difficulty is propagating changes. Three families: single-leader, multi-leader, leaderless. Key choices: sync vs async, handling failed replicas. Async replication gives eventual consistency, with unbounded lag; lag causes user-visible anomalies (stale own writes, time going backward, causality violations) that applications must either tolerate or be given guarantees against. Transactions exist so apps do not have to reason about this; many distributed DBs dropped them, which the author calls overly simplistic.
(Chapter assumes whole dataset fits on one machine; partitioning is Ch6.)

### Leaders and Followers
- Replica = node holding a copy. Leader-based (active/passive, master-slave): one leader takes all writes, writes locally, ships change (replication log/change stream) to followers (read replicas, secondaries, hot standbys), who apply in same order. Reads may go to leader or any follower; followers read-only to clients. Built into PostgreSQL (9.0+), MySQL, Oracle Data Guard, SQL Server AlwaysOn; MongoDB, RethinkDB, Espresso; Kafka, RabbitMQ queues; DRBD. Footnote: PostgreSQL "hot standby" = replica accepting reads; "warm" = processes changes but serves no queries.
- Sync vs async (Fig 5-2): sync follower: leader waits for its confirmation before reporting success and before making write visible. Pro: follower guaranteed up to date, data survives leader failure. Con: if sync follower is down/slow the write blocks; all-sync is impractical (any outage halts writes). Practice = semi-synchronous: one sync follower, rest async; if it lags, promote an async one to sync, so >=2 nodes always have latest data. Fully async: leader keeps writing even if all followers behind, but a confirmed write can be lost if leader dies unrecoverably (durability weakened). Async widely used anyway, especially with many or geo-distributed followers. Normal lag is under a second but no guarantee; can be minutes (recovering follower, near-capacity, network trouble).
- Research note: chain replication (variant of sync, used in Azure Storage) loses no data yet keeps performance. Replication consistency is tied to consensus (Ch9).
- Setting up new followers without downtime: (1) consistent snapshot of leader without locking whole DB (same feature as backups; innobackupex for MySQL); (2) copy to new node; (3) follower requests all changes since snapshot, needs snapshot tied to exact log position (Postgres: log sequence number; MySQL: binlog coordinates); (4) when backlog applied it has "caught up". Plain file copy is wrong because data is in flux. Automation varies by DB; some are arcane manual workflows.
- Node outages (also planned: kernel patch reboots; ability to reboot nodes without downtime is an ops win).
  - Follower failure: catch-up recovery: follower keeps log of received changes on disk; after crash/network blip it knows last processed transaction and requests everything after.
  - Leader failure: failover: promote a follower, reconfigure clients to write to new leader, other followers consume from new leader. Manual or automatic. Automatic steps: (1) detect failure, usually by timeout (e.g., 30 s of silence), no foolproof way; (2) choose new leader by election (majority of remaining replicas) or appointed by controller; best candidate = replica with most up-to-date data; it is a consensus problem (Ch9); (3) reconfigure system, ensure old leader, if it returns, steps down and becomes follower.
  - Failover pitfalls: (a) async: new leader may lack old leader's last writes; common fix is discarding them, violating durability; (b) discarding is dangerous when other systems depend on DB contents: GitHub incident, stale MySQL follower promoted, its auto-increment counter lagged and reused primary keys that were also used in Redis, so private data was shown to wrong users; (c) split brain: two nodes both think they are leader, both accept writes, data loss/corruption without conflict resolution; fencing/STONITH safety catch can shut down both nodes if badly designed; (d) timeout tuning: too long = slow recovery; too short = unnecessary failovers, which under load or network trouble make things worse. Hence some ops teams prefer manual failover.
- Implementation of replication logs:
  - Statement-based: ship each INSERT/UPDATE/DELETE statement. Breaks on nondeterministic functions (NOW(), RAND()), on autoincrement or dependent UPDATE ... WHERE needing identical order, and on side-effecting triggers/stored procs/UDFs. Workaround: leader substitutes fixed values; but many edge cases. MySQL used it before 5.1, now switches to row-based when nondeterministic; VoltDB uses it but requires deterministic transactions.
  - WAL shipping: the storage engine's append-only log (LSM log or B-tree WAL) sent to followers; used by PostgreSQL and Oracle. Con: very low level (which bytes in which disk blocks), coupled to storage engine/version; usually leader and follower must run same version, so upgrades need downtime. If followers could be newer, you could do zero-downtime upgrade: upgrade followers, then fail over.
  - Logical (row-based) log: separate format from storage engine. Insert: new values of all columns; delete: identifying info (primary key, or all old values if none); update: row identity plus new values; transaction ends with commit record. MySQL row-based binlog. Benefits: backward compatible across versions/engines, easy for external systems to parse = change data capture (Ch11) into warehouse, custom indexes, caches.
  - Trigger-based: app-level replication via triggers/stored procedures that log changes to a table an external process reads; tools: Oracle GoldenGate (reads log), Databus for Oracle, Bucardo for Postgres. Use when you need subset replication, cross-DB replication, or custom conflict resolution. Higher overhead and more bug-prone than built-in, but flexible.

### Problems with Replication Lag
- Read-scaling architecture: many followers serve reads (web is read-heavy); only realistic with async, because with sync-to-all, one failure blocks writes and more nodes means more likely a failure. Cost: followers can be stale: same query on leader and follower gives different answers. Temporary: "eventual consistency" (term deliberately vague; no bound on lag; footnote: coined by Terry et al., popularized by Vogels; asynchronously replicated relational DBs are eventually consistent too, not only NoSQL).
- Three anomalies:
  1. Reading your own writes (Fig 5-3): user submits (goes to leader), then views (goes to stale follower), data appears lost. Needs read-after-write (read-your-writes) consistency: user always sees their own updates; no promise about others' updates. Techniques: read user-modifiable things from leader (e.g., own profile from leader, others' from followers); if most things are editable, use heuristics: read from leader for 1 minute after last update, or block followers more than 1 minute behind; client remembers timestamp of latest write (logical like log sequence number, or system clock which needs sync) and serves reads only from replicas that have caught up to it (or wait/another replica); multi-datacenter: leader-needed requests routed to the leader's datacenter. Cross-device read-after-write (desktop + phone): the last-write timestamp metadata must be centralized; devices may route to different datacenters (home broadband vs cellular), so may need to route all of a user's devices to one datacenter.
  2. Monotonic reads (Fig 5-4): two reads to different replicas, first fresh, second stale: comment appears then vanishes; time goes backward. Guarantee: weaker than strong consistency, stronger than eventual: successive reads by one user never go to older data. Fix: each user always reads from same replica (e.g., chosen by hash of user ID, not random); if replica fails, reroute.
  3. Consistent prefix reads (Fig 5-5, Mr Poons / Mrs Cake dialog): observer sees answer before question because of different lag per partition. Guarantee: writes in a certain order are seen in that order. Mostly a problem in partitioned DBs where there is no global write order. Fixes: put causally related writes in same partition (not always feasible); algorithms tracking causal dependencies (happens-before, Ch5 later).
- Solutions: ask "what if lag becomes minutes/hours?" If bad UX, provide stronger guarantee. Pretending async is sync is a recipe for problems. App-level workarounds (reading from leader) are complex and error-prone; transactions exist so DB provides the guarantees. Distributed DBs abandoned transactions claiming cost/availability and that eventual consistency is inevitable; "some truth, overly simplistic". Returns Ch7, Ch9, Part III.

### Multi-Leader Replication
- Single-leader downside: one leader; if you cannot reach it, you cannot write. Multi-leader (master-master, active/active): more than one node accepts writes; each leader is also a follower of the others. Footnote: in partitioned DBs each partition has one leader, possibly on different nodes.
- Rarely worth it inside one datacenter (complexity > benefit). Use cases:
  1. Multi-datacenter (Fig 5-6): a leader per DC, leader-follower inside, leaders replicate asynchronously across DCs. Vs single-leader: performance (writes handled locally, inter-DC delay hidden), DC outage tolerance (each DC continues independently; single-leader needs failover), network-problem tolerance (single-leader writes cross the public internet synchronously; multi-leader async tolerates blips). Tools: Tungsten Replicator (MySQL), BDR (Postgres), GoldenGate (Oracle). Downsides: write conflicts; it is a retrofitted feature with pitfalls (autoincrement keys, triggers, integrity constraints); "dangerous territory that should be avoided if possible".
  2. Clients with offline operation: calendar apps on phone/laptop: each device's local DB is a leader; async sync with lag of hours/days; "each device is a datacenter" with an extremely unreliable link; history of broken calendar syncs shows it is hard. CouchDB designed for this.
  3. Collaborative editing (Etherpad, Google Docs): edits applied to local replica instantly and replicated async. Lock-per-document avoids conflicts = single-leader with transactions; for fast collaboration make unit of change tiny (keystroke), no locking, and you get multi-leader conflict resolution.
- Handling write conflicts (Fig 5-7: wiki title A->B at one leader, A->C at another). Single-leader: second writer blocks or aborts and retries. Multi-leader: both succeed, conflict found asynchronously, maybe too late to ask the user. Sync conflict detection defeats the purpose (just use single-leader).
  - Conflict avoidance: route all writes for a record through one leader (e.g., user's "home" datacenter). Breaks when you reroute (DC failure, user moves). Frequently recommended since tools handle conflicts poorly.
  - Converging: no defined order, so must resolve convergently (all replicas same final value). Options: unique ID per write (timestamp/random/UUID/hash) highest wins = last write wins (LWW), prone to data loss; unique replica ID, higher replica wins (data loss); merge values (e.g., concatenate sorted "B/C"); record conflict in explicit structure and resolve later in app code / prompt user.
  - Custom resolution code: on write (handler called when conflict detected in log; runs in background, cannot prompt user; e.g., Bucardo Perl) or on read (store all versions, return to app on next read, app/user resolves and writes back; CouchDB). Resolution is per row/document, not per transaction.
  - Automatic resolution: Amazon shopping cart anecdote (removed items reappeared). Research: CRDTs (sets, maps, ordered lists, counters; Riak 2.0), mergeable persistent data structures (Git-like three-way merge), operational transformation (Etherpad, Google Docs; ordered lists of characters). Young in DBs.
  - What is a conflict: obvious = same field set to different values; subtle = meeting-room double booking across two leaders even though each checked availability.
- Topologies (Fig 5-8): circular (MySQL default), star/tree, all-to-all. Circular/star: writes pass through nodes; each node has unique ID and writes are tagged with IDs of nodes passed, a node ignores changes tagged with its own ID (prevents infinite loops). One node failing breaks flow in circular/star (manual reconfig). All-to-all more fault-tolerant, but messages may overtake others (Fig 5-9: update reaches leader 2 before the insert it depends on) = causality problem; timestamps insufficient because of clock skew (Ch8); fix is version vectors (see Leaderless). Many systems poor: PostgreSQL BDR no causal ordering; Tungsten does not detect conflicts. Advice: read docs, test that guarantees really hold.

### Leaderless Replication
- Any replica accepts writes directly from clients (or via a coordinator that does NOT enforce ordering). Early systems; revived by Amazon's in-house Dynamo (not DynamoDB, which is single-leader, footnote). Open source Dynamo-style: Riak, Cassandra, Voldemort.
- Writing when a node is down (Fig 5-10): no failover. Client writes to all n replicas in parallel; succeeds when w acknowledge; the down node misses the write. Reads also go to several nodes in parallel; version numbers pick the newest.
- Catching up: read repair (client detects stale replica in a read, e.g., version 6 vs 7, writes newer value back; good for frequently read values) and anti-entropy process (background process comparing replicas and copying missing data, no particular order, may be slow). Voldemort lacks anti-entropy; without it, rarely read values may be on few replicas = reduced durability.
- Quorums: n replicas, write needs w acks, read queries r nodes; if w + r > n, at least one of r read nodes has the latest value (Fig 5-11). Common: n odd (3 or 5), w = r = ceil((n+1)/2). Read-heavy: w = n, r = 1 (fast reads, but one failed node blocks all writes). More than n nodes may exist in cluster (partitioning); a value is stored on n of them. Tolerance: n=3,w=2,r=2 tolerates 1 down; n=5,w=3,r=3 tolerates 2. Requests always go to all n; w and r are how many you wait for. Fewer than w/r available = error; cause of unavailability irrelevant.
- Limits of quorum consistency: quorums need not be majorities, only overlapping. Smaller w+r <= n: more stale reads but lower latency, higher availability. Even with w + r > n, stale reads possible: sloppy quorum (writes land on different nodes); concurrent writes (LWW loses data via clock skew); write concurrent with read (undetermined); write succeeded on some but fewer than w replicas, not rolled back, so a "failed" write may still be read; node with new value restored from an old replica drops below w; timing edge cases (see linearizability and quorums, Ch9). Dynamo-style DBs are for use cases tolerating eventual consistency; w and r tune the probability, not guarantees. No read-your-writes/monotonic/consistent-prefix guarantees; stronger needs transactions or consensus.
- Monitoring staleness: leader-based: lag = leader log position minus follower position, exposed as metrics. Leaderless: no fixed order, harder; read-repair-only means unbounded staleness. Research predicting stale-read % from n,w,r not mainstream; author wants staleness in standard DB metrics: "quantify eventual".
- Sloppy quorums and hinted handoff: when a client is cut off from the n home nodes, choose between errors or accepting writes on reachable non-home nodes (sloppy quorum; couch-at-neighbour's analogy). When network heals, hinted handoff sends the writes to home nodes. Increases write availability (any w nodes), but not a real quorum: only a durability assurance; reads may miss it until handoff. Optional: Riak default on; Cassandra, Voldemort default off.
- Multi-datacenter: leaderless suits it. Cassandra/Voldemort: n spans DCs, configurable replicas per DC, write sent to all but client waits for a quorum in local DC, remote async. Riak: n within one DC, cross-DC async replication like multi-leader.
- Detecting concurrent writes (Fig 5-12: clients A and B write key X; nodes get them in different orders; naive overwrite leaves permanent inconsistency; most implementations poor, developers must know internals).
  - LWW: attach timestamp, keep largest, discard others; Cassandra's only method, optional in Riak. Converges but sacrifices durability (silent loss of writes reported successful, may even drop non-concurrent writes); OK for caching; only safe if key written once and immutable (Cassandra advice: UUID as key).
  - Happens-before: A happens before B if B knows of, depends on, or builds on A; concurrent = neither happens before the other. Fig 5-9 not concurrent (causal dependency), Fig 5-12 concurrent. Exact physical time irrelevant (clocks unreliable, Ch8); analogy to special relativity: concurrent = unaware of each other; slow network can make distant-in-time ops concurrent.
  - Algorithm (Fig 5-13/5-14, shopping cart with milk, eggs, flour, ham, bacon; or air traffic controllers): server keeps a version number per key, incremented per write; read returns all non-overwritten values plus latest version; client must read before write, merges all values received, and sends write with the version from its read; server overwrites all values with version <= that, keeps higher-version (concurrent) values. Write without a version is concurrent with everything and overwrites nothing. Server decides concurrency from versions alone, value can be any structure.
  - Merging siblings (Riak's term for concurrent values): clients clean up. LWW loses data; union works for add-only carts; with removals the removed item reappears, so need tombstones (deletion markers with version). App-level merging is error-prone, hence CRDTs (e.g., Riak datatypes).
  - Version vectors (multi-replica leaderless): single version number is insufficient; use a version number per replica as well as per key; each replica increments its own counter on a write and tracks counters seen from others. The collection = version vector (Riak 2.0 uses dotted version vector; encoded as "causal context" string). Sent to client on read and returned on write; lets DB tell overwrite from concurrent write; safe to read from one replica and write to another (may create siblings, no data lost if merged properly). Version vectors != vector clocks (subtle; use version vectors for comparing replica state).

### Chapter 5 Summary (author's)
Replication serves: high availability, disconnected operation, latency, scalability (reads). Three approaches: single-leader (popular: easy to understand, no conflict resolution; reads from followers can be stale), multi-leader and leaderless (more robust to faulty nodes, network interruptions, latency spikes, but harder to reason about and only weak consistency). Sync vs async has profound effect on faults: promoting an async follower can lose recently committed data. Consistency models to decide app behaviour under lag: read-after-write, monotonic reads, consistent prefix reads. Multi-leader/leaderless: concurrency and conflicts; happens-before algorithm; merging.

### Ch5 failure modes / pitfalls (consolidated)
- Async failover loses committed writes; discarded writes + external systems = inconsistency (GitHub auto-increment key reuse leaked private data via Redis).
- Split brain; badly designed fencing shuts down both nodes; failover timeout too short/long.
- Statement-based replication with NOW()/RAND()/autoincrement/triggers; WAL shipping blocks mixed-version upgrades.
- Replication lag anomalies: own writes vanish, time goes backward, answers before questions; lag unbounded.
- Cross-device and cross-datacenter variants of read-your-writes.
- Multi-leader: conflicts found too late, LWW data loss, autoincrement/trigger/constraint surprises, messages overtaking, circular/star single-node breakage, Amazon cart resurrecting deleted items, meeting-room double bookings.
- Leaderless: quorum edge cases (sloppy quorum, failed-but-persisted writes, restore from stale replica, clock skew LWW), no anti-entropy = rare values under-replicated, union merge resurrects deletions without tombstones, hard to monitor staleness.

### Ch5 key terms
- Replica: node holding a copy. Leader/follower: write-accepting node / read-only copy applying leader's log. Replication lag: delay between write on leader and visibility on follower.
- Semi-synchronous: one sync follower, rest async. Failover: promoting a follower to leader. Split brain: two nodes believe they are leader. Fencing/STONITH: forcibly shutting down the other leader.
- Statement-based / WAL shipping / logical (row-based) log / trigger-based replication. Change data capture: exporting DB changes via logical log.
- Eventual consistency; read-after-write (read-your-writes); monotonic reads; consistent prefix reads.
- Multi-leader; replication topology (circular, star, all-to-all); LWW; CRDT; operational transformation; mergeable persistent data structure.
- Leaderless/Dynamo-style; quorum (n, w, r; w+r>n); read repair; anti-entropy; sloppy quorum; hinted handoff; happens-before; concurrent; siblings; tombstone; version vector (dotted); causal context.

### Ch5 relevance to PACE-type SaaS (Node/Express + single managed Postgres on Supabase, small host)
Applies directly:
- Single-leader is exactly what a managed Postgres gives; WAL (physical) streaming is what Postgres uses, so Supabase read replicas/standbys are async followers: anything routed to a replica has the lag anomalies. Rule: if you add a read replica, route "read what I just wrote" (saving a candidate, then reloading the list) to the primary, or use time-since-last-write / LSN tracking; keep a user on one replica for monotonic reads. Without replicas none of these apply: a single node gives strong consistency.
- Moving the DB to another region (latency): there is a single leader, so write latency is cross-region round trip between app host and DB; put app and DB in same region. Moving = snapshot + catch-up from log position (same as new-follower setup) or a promoted cross-region replica; async means a failover/cutover can lose the last writes unless you stop writes first. Multi-region multi-leader is not worth it (conflicts); at most per-tenant "home region" (conflict avoidance) later.
- Failover lessons: a managed provider does failover; understand it is async-promotion risk (lost writes, key reuse like GitHub incident: if IDs also live elsewhere e.g. caches/queues/storage, they can diverge). Backups/PITR are the safety net.
- Logical replication / CDC: Postgres logical replication can feed warehouse/search/audit later without app changes.
- Idempotency/ordering: external flows (email sends, webhooks) with at-least-once semantics are unrelated to DB replicas but "version number / tombstone" ideas apply to soft deletes and sync from outside systems (e.g., mailbox sweeps).
- Optimistic concurrency: a version column on rows (compare-and-set on update) is the single-node form of detecting concurrent edits (two recruiters editing the same candidate); LWW silently loses edits.
Only at much larger scale: multi-leader, leaderless/Dynamo quorums, sloppy quorums, version vectors, CRDTs/OT (relevant only if building real-time collaborative editing or offline-first clients), consensus-based failover.

## CHAPTER 6: Partitioning
### Core argument
When data or query throughput exceeds one machine, split the dataset into partitions (sharding) so each record lives in exactly one partition and partitions spread across nodes of a shared-nothing cluster. Goal: even spread of data and load; skew and hot spots defeat it. Two main schemes: key range (ordered, range scans, hot-spot risk) and hash (even, loses order), with compound keys as a hybrid. Secondary indexes complicate things: local (document-partitioned: cheap writes, scatter/gather reads) vs global (term-partitioned: cheap reads, costlier and often async writes). Adding/removing nodes requires rebalancing (do not use hash mod N; use many fixed partitions, dynamic splitting, or partitions per node), ideally with a human in the loop. Clients need request routing (service discovery), often via ZooKeeper or gossip. Cross-partition writes are the hard remaining problem (next chapters).
Terminology: partition = shard (MongoDB, Elasticsearch, SolrCloud), region (HBase), tablet (Bigtable), vnode (Cassandra, Riak), vBucket (Couchbase). Footnote: unrelated to network partitions (netsplits, Ch8).

### Intro
- Each partition is effectively a small DB of its own though cross-partition operations may be supported. Main reason: scalability: data across many disks, query load across many processors; single-partition queries run independently on their node, so throughput scales with nodes; big complex queries can be parallelized but it is much harder. Pioneered 1980s (Teradata, Tandem NonStop SQL), rediscovered by NoSQL and Hadoop warehouses; applies to OLTP and analytics.
- Partitioning and replication combined (Fig 6-1): copies of each partition on several nodes; a node may hold several partitions, be leader for some and follower for others. Everything from Ch5 applies; partitioning scheme mostly independent of replication scheme.

### Partitioning of Key-Value Data
- Goal: spread data and queries evenly; ideal 10 nodes = 10x capacity. Skewed = unfair; hot spot = partition with disproportionate load; worst case one busy node and nine idle.
- Random assignment avoids hot spots but you cannot know where an item lives, so must query all nodes.
- By key range (Fig 6-2, paper encyclopedia volumes): contiguous key ranges per partition; boundaries adapt to data (not evenly spaced; volume 1 = A-B, volume 12 = T-Z); chosen by admin or automatically. Used by Bigtable, HBase, RethinkDB, MongoDB < 2.4. Keys sorted within partition: easy range scans, concatenated-key fetches (e.g., sensor readings by month). Downside: access patterns create hot spots: timestamp key means all current writes hit today's partition. Fix: prefix key with something else (sensor name then time), spreading writes; but multi-sensor time-range queries now need one range query per sensor.
- By hash of key: good hash turns skewed/similar keys uniform (32-bit range). Need not be cryptographic (Cassandra and MongoDB MD5; Voldemort Fowler-Noll-Vo). Pitfall: language built-in hashes (Java Object.hashCode, Ruby Object#hash) may give different values per process, so unsuitable. Each partition gets a range of hashes (Fig 6-3); boundaries even or pseudorandom ("consistent hashing"). Consistent hashing (Karger et al.) = random boundaries for internet-wide caches/CDNs, avoiding central control/consensus; unrelated to replica or ACID consistency; works poorly for databases, so author recommends just saying "hash partitioning".
  - Loses range queries: keys scattered. MongoDB hash mode sends range queries to all partitions; Riak, Couchbase, Voldemort don't support primary-key range queries.
  - Cassandra compromise: compound primary key; first column hashed for partition, other columns sorted within (SSTable) as a concatenated index; cannot range-query the first column but can range-scan others given a fixed first. Elegant for one-to-many, e.g., (user_id, update_timestamp): all of a user's updates on one partition sorted by time.
- Skewed workloads/hot spots: hashing cannot help when all traffic is for one key (celebrity with millions of followers). Systems generally cannot auto-fix; application must reduce skew: add random number (e.g., 2-digit) to hot key to split writes over 100 keys; cost: reads must query all 100 and combine, and you must track which keys are split (only worth it for the few hot keys).

### Partitioning and Secondary Indexes
- Secondary index finds occurrences of a value (all actions by user 123; red cars), not unique records; bread and butter of relational DBs, common in document DBs; HBase/Voldemort avoided them for complexity, Riak added; Solr/Elasticsearch exist for them. Doesn't map neatly onto partitions. Footnote: hand-built secondary indexes in a key-value store risk going out of sync (races, partial write failures); see multi-object transactions (Ch7).
- Document-partitioned (local) index (Fig 6-4, used-car site, partition by document ID, index on color and make): each partition keeps its own index covering only its documents; writes touch one partition. Reads: red cars may be in every partition, so query all partitions and combine = scatter/gather: expensive, prone to tail latency amplification even if parallel. Used by MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud, VoltDB. Vendors advise designing partitioning so index queries hit one partition, not always possible (multiple filters).
- Term-partitioned (global) index (Fig 6-5): one index covering all partitions, itself partitioned (differently from data); the term (e.g., color:red) decides the index partition; colors a-r in partition 0, s-z in partition 1. Partition by term itself (good for range scans, e.g., asking price) or by hash of term (more even load). Pro: reads hit a single partition. Con: writes slower/more complex: one document write can touch several index partitions on different nodes; keeping it perfectly current needs a distributed transaction (not universally supported), so updates are usually asynchronous (DynamoDB GSIs usually update within a fraction of a second, longer on faults). Others: Riak search, Oracle data warehouse (local or global choice). Returns Ch12.

### Rebalancing Partitions
- Reasons: more throughput (CPUs), bigger dataset (disks/RAM), failed machine. Rebalancing = moving load between nodes. Requirements: fair load share afterwards; keep accepting reads/writes during; move no more data than necessary (less network/disk I/O).
- How not to: hash mod N: changing N moves most keys (123456 mod 10 = 6, mod 11 = 3, mod 12 = 0). Too expensive.
- Fixed number of partitions (Fig 6-6): create many more partitions than nodes (e.g., 1000 over 10 nodes = ~100 each). New node steals a few partitions from each existing node; removal reverses. Only whole partitions move; key-to-partition mapping never changes, only partition-to-node. Transfer takes time, old assignment serves meanwhile. More powerful nodes can be given more partitions. Used by Riak, Elasticsearch, Couchbase, Voldemort. Number fixed at setup = max number of nodes, so choose high enough but each partition has overhead. Hard if dataset size varies greatly: partitions too large make rebalancing/recovery expensive, too small waste overhead.
- Dynamic partitioning: key-range DBs (HBase, RethinkDB) split a partition when it exceeds a size (HBase default 10 GB) into two halves, merge when shrunk; like B-tree top-level. One half can move to another node (HBase via HDFS). Number of partitions adapts to data volume. Caveat: empty DB starts with one partition so all writes hit one node: pre-splitting (HBase, MongoDB) needs knowing key distribution. Works for hash partitioning too; MongoDB 2.4+ supports key-range and hash with dynamic splitting.
- Partitioning proportional to nodes (Cassandra, Ketama): fixed number of partitions per node (Cassandra default 256). New node randomly picks existing partitions to split and takes half of each; randomness can be unfair but evens out over many partitions; Cassandra 3.0 added an algorithm avoiding unfair splits. Requires hash partitioning; closest to original consistent hashing; newer hash functions achieve this with less metadata.
- Automatic vs manual: gradient; Couchbase, Riak, Voldemort suggest an assignment and admin commits it. Automatic is convenient but unpredictable: rebalancing is expensive (rerouting + big data moves) and can overload network/nodes and hurt other requests. Dangerous combined with automatic failure detection: an overloaded slow node is judged dead, load is shifted, making things worse and potentially cascading. Human in the loop recommended (slower, fewer surprises).

### Request Routing
- Question: how does a client know which node/IP/port serves key "foo" as assignments change? Instance of service discovery (general to any networked highly-available software; many in-house tools, some open source).
- Three approaches (Fig 6-7): (1) client contacts any node (e.g., round-robin LB), which forwards to the owner if needed; (2) a routing tier (partition-aware load balancer, handles no requests itself) forwards; (3) partition-aware client connects directly. Key problem in all: how the deciding component learns about assignment changes; participants must agree or requests go to wrong nodes; consensus protocols are hard to implement (Ch9).
- ZooKeeper (Fig 6-8): separate coordination service holding authoritative partition-to-node map; nodes register; routing tier/clients subscribe and are notified of changes. Users: LinkedIn Espresso (Helix on ZooKeeper, routing tier), HBase, SolrCloud, Kafka. MongoDB: own config servers + mongos routing daemons. Cassandra and Riak: gossip protocol between nodes spreads cluster state; requests to any node which forwards (approach 1): more complexity in DB nodes, no external dependency. Couchbase: no automatic rebalance (simpler), routing tier moxi learns changes from nodes. Finding IPs of nodes/routing tier changes slowly, so DNS usually suffices.
- Parallel query execution: NoSQL stores mostly do single-key and scatter/gather. MPP relational warehouses support joins, filters, grouping, aggregation; optimizer breaks query into stages and partitions run in parallel; scans of large data benefit. Detail in Ch10.

### Ch6 Summary (author's)
Partitioning needed when one machine cannot store/process the data; aim to avoid hot spots, choose scheme suited to data, rebalance when nodes change. Key range: sorted, range queries, hot-spot risk with adjacent keys, dynamic split rebalancing. Hash: even load, ranges inefficient, fixed number of partitions typical, whole partitions move; dynamic also possible. Hybrid: compound key (one part picks partition, another sorts). Secondary indexes: document-partitioned (local; one-partition write, scatter/gather read) vs term-partitioned (global; multi-partition write, single-partition read). Routing from partition-aware load balancing to parallel query engines. Partitions operate mostly independently, but multi-partition writes are hard to reason about (what if one succeeds and another fails?), addressed in later chapters.

### Ch6 failure modes / pitfalls

### Ch6 relevance to PACE-type SaaS (single managed Postgres, small host)
Applies directly (design choices cheap now, costly later):
- Tenant id (org_id) as the leading column of keys/indexes = compound-key hybrid: all of a tenant's rows are co-located and range-scannable, and it is the natural future partition key. Postgres has declarative partitioning (by list/hash of org_id, or range by time for event/log/email tables) on a single node: helps pruning, retention (drop old partitions instead of deleting), vacuum; no cluster needed. Time-ordered keys (timestamps, serial ids) concentrate recent writes on one partition/index end: the hot-spot lesson maps to hot index pages on append-only tables, usually harmless on one node.
- Partitioning by tenant later: sharding by org_id across databases is the likely path (large customers get own DB/schema, small ones share); keep every query tenant-scoped and avoid cross-tenant joins/foreign keys so the move stays possible; a routing table (org -> database) is the "request routing" piece (a lookup in a control table/cache, DNS-like). Use a lookup/directory (not hash mod N) so tenants can be moved individually: this is the "many fixed partitions" idea (tenants as partitions, assignment table maps tenant to node).
- Hot tenant = hot spot / celebrity key: one huge customer or a bulk import can swamp shared resources; per-tenant rate limits and the ability to move that tenant out are the application-level fixes the book prescribes.
- Secondary indexes: on a single Postgres, indexes are local and consistent with the data; global-index staleness only arises if you copy data into a separate search engine (Elasticsearch/Typesense) -> that index is async and may lag; design UIs (read-your-writes after saving) accordingly, same as replica lag.
- Scatter/gather cost warning applies if a search/filter would ever span many shards (e.g., cross-tenant admin reports).
Only at much larger scale: consistent hashing, vnodes, dynamic range splitting and pre-splitting, ZooKeeper/gossip routing, automatic rebalancing, MPP parallel query engines.
