# DDIA Ch.9 Consistency and Consensus — notes (PART 1: lines 1-1500; later parts appended below)

## Intro (L1-52)
Epigraph: "alive and wrong or right and dead" (Kreps). Simplest fault handling = let the service fail and show an error; otherwise build general-purpose abstractions with guarantees, implemented once (like transactions give atomicity/isolation/durability). Key abstraction = consensus (all nodes agree). Use: leader election (avoid split brain = two nodes both believe they lead -> data loss), atomic commit. Chapter assumes all Ch.8 faults (loss, reorder, duplication, delay, approximate clocks, pauses, crashes). Informal intuition only, no proofs.

## Consistency Guarantees (L53-108)
- Eventual consistency = if writes stop, replicas eventually converge (better name: convergence). Very weak: no bound on when; until then reads may return anything/nothing; even your own write may not be seen (read routed to another replica). Hard for developers because DB looks like a variable but is not; bugs are subtle, appear only under faults or high concurrency, rarely caught by testing.
- Stronger models cost performance and/or fault tolerance, but are easier to use correctly.
- Distributed consistency models resemble transaction isolation levels but are mostly independent: isolation = races between concurrent transactions; consistency = coordinating replica state under delay/faults.
- Chapter plan: linearizability; ordering/causality; distributed transactions and consensus.

## Linearizability (L110-492)
- Definition: make the system appear as if there is one copy of the data and all operations atomic. Aliases: atomic consistency, strong consistency, immediate consistency, external consistency. It is a RECENCY guarantee: once a write completes, every subsequent read (any client) sees it.
- Non-linearizable example (Fig 9-1): Alice sees World Cup final result, tells Bob; Bob reloads, hits lagging replica, still sees "ongoing". Violation because Bob's request began after Alice's finished. If simultaneous, no violation.
- What makes it linearizable (Figs 9-2..9-4): model a register x with read, write, and cas(x, old, new) (atomic compare-and-set). Each op is a bar (send -> response). Reads fully before write -> old; reads starting after write completed -> new; reads overlapping the write may return either, BUT (Fig 9-3) once ANY read returns the new value, all later reads (any client) must too, even if the write has not yet completed. There must be a single point in time where the value atomically flips. Visualize by placing a marker per op inside its bar; markers joined in order must always go forward in time and form a valid register history. Fig 9-4 details: concurrent requests may be processed in an order different from send order; a read may return a value before the writer gets its ok (response delayed); model assumes no transaction isolation (others may change value anytime; cas protects); the last read by B is non-linearizable because A had already read newer value 4. Testing linearizability is possible by recording all request/response timings and searching for a valid ordering, but computationally expensive.
- Linearizability vs serializability: serializability = isolation of multi-object transactions behaving as if run in some serial order (order may differ from actual); linearizability = recency on single objects, no grouping, doesn't prevent write skew. Both together = strict serializability / strong-1SR. 2PL and actual serial execution are typically linearizable; SSI (serializable snapshot isolation) is NOT linearizable by design (reads from a consistent snapshot, which excludes newer writes).
- Where linearizability is needed:
  * Locking and leader election: lock must be linearizable or useless; ZooKeeper/etcd (consensus-based) used; Apache Curator gives recipes; fencing issues still apply. Footnote: ZooKeeper/etcd give linearizable writes, but reads may be stale by default (etcd quorum read; ZooKeeper sync() before read). Oracle RAC uses per-disk-page linearizable locks (dedicated interconnect).
  * Constraints and uniqueness: usernames/emails, unique file path, balance never negative, stock not oversold, seat not double-booked -> need one up-to-date agreed value; like acquiring a lock / atomic CAS (set username to user ID if not taken). Sometimes constraints can be loose (overbook flights, compensate) - see Ch.12 "Timeliness and Integrity". A HARD uniqueness constraint needs linearizability; foreign key / attribute constraints do not.
  * Cross-channel timing dependencies: Alice's voice is a second channel; computer analogue (Fig 9-5): web server writes photo to file storage, then queues a resize message; the resizer may read stale/missing image if storage is non-linearizable and the queue is faster than storage replication -> permanently inconsistent full-size and thumbnail. Linearizability is the simplest fix; if you control the extra channel you can use read-your-writes-style techniques at added complexity.
- Implementing linearizable systems: single copy is simplest but not fault-tolerant; so use replication:
  * Single-leader: potentially linearizable if reads go to the leader or synchronously updated followers; but not guaranteed (snapshot isolation, bugs); a "delusional" leader that wrongly thinks it is leader breaks it; async failover can lose committed writes (breaks durability and linearizability). Sharding with a leader per partition doesn't affect it (single-object guarantee).
  * Consensus algorithms: linearizable, with split-brain/stale-replica protection (ZooKeeper, etcd).
  * Multi-leader: not linearizable (concurrent writes, conflict resolution).
  * Leaderless (Dynamo-style): probably not, even with w + r > n. LWW with time-of-day clocks almost certainly not (clock skew); sloppy quorums ruin it. Fig 9-6: strict quorum n=3,w=3,r=2 still non-linearizable because reader A sees new value from one node, later reader B (different quorum) sees only old values, due to variable network delay while the write is in flight. Can be made linearizable at a cost: synchronous read repair before returning, and writers read latest state from a quorum before writing (Riak doesn't do sync read repair; Cassandra does but loses linearizability with concurrent writes due to LWW). Linearizable CAS cannot be done this way; needs consensus. Safe assumption: Dynamo-style = not linearizable.
- Cost of linearizability: Fig 9-7 two datacenters, network link between them broken. Multi-leader: each DC keeps working, queues writes. Single-leader: clients in the follower DC cannot write or do linearizable reads (can read stale locally) -> unavailable.
- CAP theorem: applies to any linearizable DB, even within one DC. If you need linearizability and some replicas are disconnected, they must wait or error (unavailable); if you don't need it, each replica can serve independently (available but non-linearizable). Naming: CP vs AP, flawed classification. Brewer 2000; trade-off known since 1970s; credited with pushing the NoSQL / shared-nothing exploration.
  * "Unhelpful CAP": "pick 2 of 3" is misleading because partitions are faults, not a choice; better: "Consistent or Available when Partitioned". When the network works you can have both. CAP's "availability" definition is idiosyncratic (many 'highly available' systems don't meet it); formal CAP covers one consistency model (linearizability) and one fault (partitions); says nothing about delays, dead nodes; superseded by more precise results; "best avoided". Footnote: network partition (fault) vs data partitioning (sharding) naming clash.
  * Linearizability and network delay: even multi-core RAM is not linearizable (per-core caches / store buffers; needs memory fences); reason is performance, not fault tolerance. Many DBs drop linearizability for speed, not fault tolerance. Attiya-Welch: response time of linearizable reads/writes is at least proportional to network delay uncertainty -> inevitably slow on variable networks; no faster algorithm exists. Weaker models are much faster; Ch.12 discusses avoiding linearizability without losing correctness.

## Ordering Guarantees (L624-1151)
Ordering is a recurring theme: leader in single-leader replication orders writes in the log; serializability = as-if serial order; timestamps/clocks try to impose order. Deep connection between ordering, linearizability and consensus.
- Ordering and causality: causality = cause before effect (question before answer; row created before updated; "happened-before" relation; consistent snapshot = consistent with causality; read skew violates causality; write skew has causal dependency between observation and action - SSI tracks it; Alice/Bob and image resizer are causality violations). Chains of causally dependent operations define the causal order. System obeying it is causally consistent (snapshot isolation provides causal consistency).
- Causal order is a PARTIAL order, not total. Total order: any two elements comparable (natural numbers). Partial order: some incomparable (sets {a,b} vs {b,c}). Linearizability = total order (single timeline, no concurrency). Causality = partial order; concurrent ops are incomparable (timeline branches and merges, like Git history).
- Linearizability is stronger than causal consistency: linearizable implies causal, preserving causality across channels automatically. But it hurts performance/availability. Causal consistency is the strongest model that does NOT slow down due to network delays and stays available during network failures (CAP does not apply). Many systems that seem to need linearizability only need causal consistency; research DBs (recent at the time) aim for this; few in production.
- Capturing causal dependencies: need to know which op happened before which; a replica must have processed all causal predecessors before applying an op (otherwise wait). Need a notion of what a node "knew" when it wrote (like investigating whether the CEO knew X when deciding Y). Version vectors generalised across whole DB; DB must be told which version was read (cf. Fig 5-13 version numbers on write; SSI tracks reads per transaction).
- Sequence number ordering: tracking all causal dependencies is impractical (clients read lots before writing). Alternative: sequence numbers / logical clocks (counters incremented per op) - compact, totally ordered, and can be made consistent with causality (A before B causally => A's number lower; concurrent ops ordered arbitrarily - imposes more order than needed). Footnote: random UUID ordering is a valid total order but useless/inconsistent with causality.
  * Single-leader: replication log + leader counter gives a causality-consistent total order; followers applying in log order are causally consistent even if lagging.
  * Non-causal generators when no single leader (multi-leader, leaderless, partitioned): (1) per-node odd/even or node-ID bits; (2) time-of-day timestamps (LWW); (3) preallocated blocks (A:1-1000, B:1001-2000). All scalable and unique but NOT consistent with causality: nodes progress at different rates; clock skew (Fig 8-3); a causally later op may get a lower block. (Spanner can make physical timestamps consistent by waiting out clock uncertainty, but most clocks lack the uncertainty metric.)
  * Lamport timestamps (1978): pair (counter, node ID); order by counter then node ID; unique and total. Key rule: every node and client tracks the max counter seen and sends it on every request; a node receiving a higher max immediately advances its own counter (Fig 9-8: client A gets 5 from node 2, passes to node 1 whose counter was 1, node 1 jumps to 5 and next op is 6). Hence every causal dependency increases the timestamp. No relation to physical time. Differs from version vectors: those distinguish concurrent vs causally dependent; Lamport always gives a total order and cannot tell concurrency, but is more compact.
  * Timestamp ordering is NOT sufficient: e.g. unique username - lowest timestamp wins works only after the fact once all operations are collected; a node must decide NOW and cannot know if another node is concurrently claiming the same name with a lower timestamp; checking with every node would halt on any failure. You need to know WHEN the total order is finalized -> total order broadcast.
- Total order broadcast (a.k.a. atomic broadcast, total order multicast - term "atomic" is misleading, unrelated to ACID atomicity): protocol for exchanging messages with two safety properties: reliable delivery (no message lost: delivered to one => delivered to all) and totally ordered delivery (same order everywhere). Must hold even under faults; delivery may be delayed during network failure, but retries continue and ordering is still preserved. Scope footnote: partitioned DBs with one leader per partition usually order only per partition; global order across partitions needs extra coordination.
  * Uses: ZooKeeper and etcd implement it; database replication via state machine replication (every replica applies same writes in same order); serializable transactions via deterministic stored-procedure messages (actual serial execution style); it behaves like an append-only log (delivery = append, all nodes read same sequence); lock service with fencing tokens (log sequence number = token; ZooKeeper calls it zxid). Order is fixed at delivery: a node cannot retroactively insert earlier messages -> stronger than timestamp ordering.
  * Linearizable storage from total order broadcast: broadcast is asynchronous (no guarantee when delivered) while linearizability is recency; but you can build linearizable CAS on it: (1) append tentative claim message (e.g. username), (2) read log until your message is delivered back to you, (3) if the first claim for that name in the log is yours, commit and ack; else abort. All nodes agree on winner. Gives linearizable WRITES only; reads from an async-updated store may be stale (this is sequential/timeline consistency). Making reads linearizable: sequence reads through the log (etcd quorum reads); fetch latest log position linearizably and wait to catch up to it (ZooKeeper sync()); read from a synchronously updated replica (chain replication). Footnotes: linearizable read-write register is an easier problem than total order broadcast (= consensus, no deterministic solution in async crash-stop model, FLP), but adding atomic CAS or increment-and-get makes a register equivalent to consensus. Acknowledging a write on enqueue without waiting resembles x86 multicore memory model (neither linearizable nor sequentially consistent).
  * Total order broadcast from linearizable storage: keep a linearizable integer register with atomic increment-and-get (or CAS); each message gets the number as sequence number; send to all (resend lost); recipients deliver strictly consecutively. Unlike Lamport timestamps, the numbers have NO GAPS, so a node knows to wait for message 5 before delivering 6 - the key difference between total order broadcast and timestamp ordering. Making that integer fault-tolerant (network cuts to its node, restoring value after failure) leads inevitably to a consensus algorithm. Linearizable CAS/increment register, total order broadcast, and consensus are all equivalent.

## Distributed Transactions and Consensus (L1152-1500+)
- Consensus: get several nodes to agree; deceptively hard; many broken systems built assuming it's easy; understanding took decades. Uses: leader election (avoid split brain), atomic commit (all nodes commit or all abort).
- FLP impossibility: no algorithm always reaches consensus if a node may crash, in the asynchronous model (deterministic, no clocks/timeouts). Escapes: use timeouts / failure suspicion (even if sometimes wrong), or randomness. So practically achievable. Footnote: atomic commit (commit only if ALL vote yes) formalised differently from consensus (any proposed value), but reducible to each other; nonblocking atomic commit is harder.
- 2PC is the common atomic commit algorithm (in databases, messaging systems, app servers) - a kind of consensus, "not a very good one". Better ones: Zab (ZooKeeper), Raft (etcd).
- Atomic commit: atomicity avoids half-finished state; also keeps secondary indexes consistent with primary data. Single node: write data durably (WAL), then commit record; the moment the commit record hits disk is the commit point - one device decides. Multi-node (partitioned multi-object transactions, term-partitioned secondary indexes): can't just send commit to all - some may abort (constraint violation), some commit requests lost, some nodes crash before writing the commit record. A commit is irrevocable (others may have read the data; basis of read committed). Compensating transactions are a separate transaction and the app's problem.
- 2PC (also made available as XA, WS-AtomicTransaction): don't confuse with 2PL. New component: coordinator (transaction manager), often a library in the app process (Narayana, JOTM, BTM, MSDTC). Flow (Fig 9-9): app reads/writes on participants; phase 1 coordinator sends prepare to all; all say yes -> phase 2 commit; any no -> abort. Marriage analogy.
- "System of promises" in 6 steps: (1) get globally unique transaction ID from coordinator; (2) single-node transaction on each participant tagged with it (anyone may abort now); (3) coordinator sends prepare; any failure/timeout -> abort; (4) participant on prepare must guarantee it can definitely commit (write all data to disk, check conflicts/constraints; disk full or crash no longer acceptable excuse); replying yes surrenders the right to abort; (5) coordinator decides (commit only if all yes) and writes decision to its durable log = the COMMIT POINT; (6) sends commit/abort to all, retrying forever until success; a crashed participant commits on recovery. Two points of no return: participant yes vote, and coordinator decision.
- Coordinator failure: before prepare - participant can abort safely; after voting yes, participant is "in doubt/uncertain" and must wait (Fig 9-10: coordinator decided commit, db2 got it, coordinator crashed before db1; db1 can neither abort nor commit unilaterally; participants talking to each other is not part of 2PC). Only way out: coordinator recovers and reads its log; transactions with no commit record in the log are aborted. So the commit point is a plain single-node atomic commit on the coordinator.
- 2PC is a "blocking" atomic commit protocol. 3PC is nonblocking but assumes bounded network delay and response times, so it fails in practice; nonblocking atomic commit needs a perfect failure detector, which timeouts are not -> 2PC persists despite the problem.
- Distributed transactions in practice: mixed reputation - useful guarantee vs operational problems, performance (MySQL distributed transactions reported >10x slower; costs from extra fsync and round trips), "promising more than they can deliver"; many cloud services avoid them. Two kinds: database-internal (same software on all nodes, e.g. VoltDB, MySQL Cluster NDB; can optimise; often work well) vs heterogeneous (different technologies, e.g. two vendors' DBs or DB + message broker; much harder).
- Exactly-once message processing: ack of a queue message and the DB writes commit atomically in one distributed transaction; on failure both abort and the broker can safely redeliver, so processing is effectively exactly once. Requires every system touched by side effects to take part in the same atomic commit protocol: e.g. if processing sends an email and the email server has no 2PC, the email can go out twice on retry. Revisited in Ch.11.
- XA (X/Open eXtended Architecture, 1991) is the standard for 2PC across heterogeneous tech... (continues in part 2)

## XA transactions (L1499-1584) [continues Distributed Transactions in Practice]
- XA (X/Open eXtended Architecture, 1991): standard for 2PC across heterogeneous tech; supported by PostgreSQL, MySQL, DB2, SQL Server, Oracle and brokers ActiveMQ, HornetQ, MSMQ, IBM MQ. NOT a network protocol - a C API to a transaction coordinator; bindings elsewhere (Java: JTA, via JDBC drivers and JMS).
- Driver must support XA: it tells the DB whether an op is part of a distributed transaction and exposes callbacks for prepare/commit/abort. Coordinator is usually a library in the app process with a local-disk log of decisions. If the app process/machine dies, the coordinator dies with it; prepared participants are stuck in doubt until that server restarts and the library reads its log; the DB cannot contact the coordinator directly (all via client library).
- Holding locks while in doubt: row-level exclusive locks (and shared locks under 2PL serializable) cannot be released until commit/abort, so in-doubt time = lock time. Coordinator down 20 minutes = locks 20 min; log lost = locks forever (until manual fix). Others may be blocked even from reading; large parts of the app may become unavailable.
- Recovering from coordinator failure: orphaned in-doubt transactions do occur (lost/corrupted log, bugs); cannot resolve automatically; rebooting DB doesn't help (correct 2PC preserves in-doubt locks across restarts). Only fix: administrator manually inspects participants, finds whether any committed/aborted, applies the same outcome to all - under high stress during an outage. Escape hatch: "heuristic decisions" - participant unilaterally commits/aborts; euphemism for "probably breaking atomicity"; for catastrophes only.
- Limitations: the coordinator is itself a database (stores outcomes) and needs the same care: (1) unreplicated coordinator = single point of failure (many implementations not HA by default); (2) coordinator inside app server makes app servers stateful - logs become critical durable state, defeating the stateless-app model; (3) XA is a lowest common denominator: no cross-system deadlock detection, doesn't work with SSI; (4) even database-internal (non-XA) distributed transactions require ALL participants to respond, so any broken part fails the transaction: distributed transactions amplify failures, counter to fault-tolerance goals. Alternatives without heterogeneous distributed transactions are deferred to Ch.11 and Ch.12.

## Fault-Tolerant Consensus (L1626-1846)
- Consensus formalised: nodes propose values; algorithm decides one. Example: several customers racing for the last seat; each node proposes the customer ID it serves; decision says who wins. Four properties: Uniform agreement (no two nodes decide differently); Integrity (no node decides twice); Validity (decided value was proposed by some node - rules out "always decide null"); Termination (every non-crashed node eventually decides) = fault tolerance/liveness (others are safety). Without fault tolerance a hard-coded "dictator" node satisfies the first three - exactly 2PC's coordinator problem; 2PC fails termination. Crash model: a crashed node vanishes forever (datacenter buried in mud), so algorithms waiting for recovery fail termination.
- Any consensus algorithm needs a MAJORITY of nodes working for termination (fewer than half crashed/unreachable). Safety properties hold even if a majority fails or the network is bad: an outage stops service but cannot corrupt decisions. Most assume no Byzantine faults; Byzantine-tolerant versions need < 1/3 faulty nodes (not covered).
- Algorithms: Viewstamped Replication, Paxos, Raft, Zab (similar but not identical). Implementing one yourself is "probably not advisable - it's hard". They decide on a SEQUENCE of values, i.e. they are total order broadcast = repeated rounds of consensus (agreement -> same order, integrity -> no duplicates, validity -> nothing fabricated/corrupt, termination -> no loss). VR, Raft, Zab implement TOB directly; Paxos's optimisation = Multi-Paxos.
- Single-leader replication and consensus: manually chosen leader = dictatorial "consensus" with no termination (needs human to progress; can work well in practice). Automatic failover approaches consensus, but electing a leader seems to need a leader first (chicken-and-egg).
- Epoch numbering and quorums: protocols use an epoch number (Paxos ballot, VR view number, Raft term); guarantee a unique leader per epoch, not globally. When leader presumed dead, a vote with incremented epoch starts; higher epoch wins conflicts. Before deciding, a leader must verify no higher epoch exists by collecting votes from a quorum (usually majority); node votes yes only if unaware of a higher-epoch leader. Two votes: pick leader, then vote on each proposal; quorums must overlap, so a successful proposal vote includes someone who saw the latest election - leader can conclude it hasn't been ousted. Similar to 2PC but: coordinator is elected, only a majority (not everyone) must vote yes, and there's a recovery process for consistency after a new leader.
- Limitations: voting is a kind of synchronous replication (many DBs choose async and accept possible loss on failover for performance); needs strict majority: 3 nodes tolerate 1 failure, 5 tolerate 2; in a partition only the majority side progresses; fixed membership usually (dynamic membership less well understood); timeouts for failure detection -> in variable-delay (geo-distributed) networks false suspicion causes frequent elections and terrible performance (safety unaffected); sensitive to network problems - Raft edge case with one flaky link makes leadership bounce or leader be forced to resign, no progress; open research.

## Membership and Coordination Services (L1847-1980)
- ZooKeeper, etcd (and Consul) look like key-value stores but hold small, in-memory (disk-persisted) data replicated by fault-tolerant total order broadcast. Rarely used directly; used indirectly by HBase, Hadoop YARN, OpenStack Nova, Kafka. Modelled on Google Chubby. Features: (1) linearizable atomic ops (CAS -> locks, usually as leases with expiry); (2) total ordering with monotonically increasing zxid/cversion usable as fencing tokens; (3) failure detection via long-lived sessions with heartbeats; on session timeout, ephemeral nodes (e.g. locks) auto-release; (4) change notifications/watches (no polling; learn when clients join/fail). Only the atomic ops strictly need consensus; the combination is what's useful.
- Allocating work: choose leader/primary among instances (also for job schedulers and stateful systems); assign partitions to nodes and rebalance when nodes join/leave/fail; via atomic ops + ephemeral nodes + notifications; enables automatic recovery without humans; hard even with Curator but better than DIY consensus (poor track record).
- ZooKeeper runs on a fixed small number of nodes (3 or 5), outsources consensus, ordering and failure detection for many clients. Data is slow-changing (e.g. "node 10.1.1.23 leads partition 7"), not per-request runtime state (use e.g. Apache BookKeeper for replicating that).
- Service discovery (ZooKeeper, etcd, Consul): services register endpoints at startup. May not need consensus: DNS reads are not linearizable, stale is OK; availability matters more. Leader election does need consensus; so consensus systems may offer read-only caching replicas that receive the decision log asynchronously, don't vote, and serve non-linearizable reads.
- Membership services: determine which nodes are live cluster members (history back to 1980s, e.g. air traffic control). Failure detection + consensus gives agreement on membership; a node may be wrongly declared dead but agreement still valuable (e.g. leader = lowest-numbered current member only works if all agree on membership).

## Summary (L1982-2082)
Linearizability: easy to understand, but slow with large network delays. Causality: partial order, branching and merging history, less coordination, tolerant of network problems; but Lamport timestamps can't enforce uniqueness -> consensus. Problems equivalent to consensus: linearizable CAS registers; atomic transaction commit; total order broadcast; locks and leases; membership/coordination service (given a failure detector); uniqueness constraints. All trivial with a single decision-making node (single-leader DB: gives linearizability, uniqueness, ordered log). If the leader fails or is unreachable, three options: (1) wait for recovery (many XA/JTA coordinators; fails termination); (2) manual failover by humans ("consensus by act of God"; many relational DBs; slow); (3) automatic election via a proven consensus algorithm. A leader just "kicks the can down the road": consensus still needed for leadership changes, less often. Use ZooKeeper-like tools for outsourced consensus rather than writing your own. Not every system needs consensus: leaderless/multi-leader systems skip it and cope with branching version histories. Theory is valuable for knowing what can and cannot be done. End of Part II.

## 3. Failure modes / pitfalls
- Assuming eventual consistency means read-your-writes; bugs only at faults/high concurrency.
- Stale reads breaking cross-channel causality (file store + queue race, Alice/Bob).
- Believing quorums (w + r > n) give linearizability; LWW with wall clocks; sloppy quorums.
- Delusional leader / split brain; async failover losing committed writes.
- Using timestamps (even Lamport) to enforce uniqueness without knowing the order is final.
- Committing independently on each node (non-atomic commit); coordinator crash leaving participants in doubt, holding locks (possibly forever); orphaned in-doubt transactions; heuristic decisions breaking atomicity; unreplicated coordinator = SPOF; coordinator logs making app servers stateful; failure amplification (all participants must be up).
- Retrying side effects that are not part of the atomic commit (email sent twice).
- 3PC assumes bounded delays - unsafe in real networks.
- Consensus: false leader-failure suspicion -> election storms; flaky link breaks Raft progress; fixed membership; need >= 3 nodes; writing your own consensus.
- Calling CAP "pick 2 of 3"; using CAP to justify multi-core memory models.
- Confusing 2PC with 2PL; atomic broadcast with ACID atomicity; linearizability with serializability.

## 4. Key terms
Eventual consistency/convergence: replicas agree once writes stop, no time bound. Linearizability: single-copy illusion, recency guarantee, total order. Register: one object (key/row/document). CAS: atomic compare-and-set. Serializability: transaction isolation as-if serial. Strict serializability: both. CAP: when partitioned choose consistent or available. Causal consistency: respects happens-before; partial order; strongest model with no availability/latency penalty. Total vs partial order. Logical clock: counter-based sequence generator. Lamport timestamp: (counter, nodeID), max-counter propagation, total order consistent with causality. Version vector: tracks concurrency vs causality. Total order broadcast (atomic broadcast): reliable + same-order delivery, gap-free, fixed once delivered. State machine replication: all replicas apply same ordered writes. Fencing token: monotonic number guarding a lock. zxid: ZooKeeper transaction id. Sequential/timeline consistency: all see the same order but reads may lag. Consensus: uniform agreement, integrity, validity, termination. FLP: no deterministic async consensus with a crash. 2PC: prepare then commit with a coordinator. Coordinator/transaction manager. Participant. In doubt/uncertain. Commit point. Heuristic decision. XA. Epoch/ballot/view/term number. Quorum. Ephemeral node. Lease. Membership service. Multi-Paxos. Byzantine fault. Split brain. Compensating transaction.

## 6. Relevance to multi-tenant Node/Express + single Supabase Postgres + small host with scheduled jobs and email
DIRECT:
- You have ONE Postgres: writes go to a single leader, so within it you get serializable/linearizable-per-object semantics for free if you use transactions and constraints. Hard uniqueness (email per org, one active candidate application, one row per idempotency key) MUST be enforced by a UNIQUE constraint / INSERT ... ON CONFLICT in the DB, not by check-then-insert in Node (the chapter's username-registration example = CAS). This is the practical form of "uniqueness needs a single agreed value".
- Read replicas (Supabase read replicas, or any lagging cache/CDN) reintroduce non-linearizable reads: read-your-writes problems (Alice/Bob); after a write read from primary, or pin the user's session to primary briefly. Cross-channel race: if you write a row then enqueue/trigger a job or webhook that reads it, make sure the job reads from the primary / after commit (the photo-resizer example); enqueue after COMMIT, not before.
- Making sure only one process runs a scheduled job: you need a lock/lease (CAS + expiry). With one Postgres use a DB-level lock (pg advisory lock, or UPDATE ... SET locked_until WHERE locked_until < now() with a returning row, or SELECT ... FOR UPDATE SKIP LOCKED for queue rows). Leases expire, and a paused process (GC, host sleep on a free tier) can wake up believing it still holds the lock -> use a monotonically increasing fencing token (e.g. a job-run counter checked on each write). This is the "leader and the lock" problem. A lease via wall-clock is unsafe if clocks drift; compare using DB time (now() on the DB) rather than app clocks.
- Sending email exactly once: the DB and the email provider (Resend/Gmail/Graph) are heterogeneous systems with no shared 2PC, so you cannot atomically commit "row marked sent" + "email sent". The chapter's own example: side effect on non-2PC email server can happen twice on retry. Practical pattern: write an outbox row/idempotency key first (status 'sending') in a transaction, send, then record result; use provider idempotency keys where available; treat an uncertain outcome (timeout) as 'unknown' and not auto-retry (matches PACE's "uncertain send never retries"); on boot, reconcile rows left in 'sending'. Accept at-least-once with dedupe or at-most-once with manual retry; you can't get true exactly-once. Compensating action (apology/suppress follow-up) is the application's problem.
- Don't use XA/2PC across Supabase and a third party; don't build your own consensus; if you ever need cross-service coordination use an outbox/idempotent consumers (Ch.11/12).
- Multi-tenant: constraints scoped by org_id (UNIQUE (org_id, email)) are single-object uniqueness, fine in one Postgres. Per-partition (per-tenant) ordering is enough; no global order needed.
- Serializability vs linearizability: use SERIALIZABLE isolation or explicit locks/constraints for write-skew cases (e.g. "max N active submissions", "daily send limit not exceeded") - single-object linearizability doesn't prevent write skew; materialise the conflict (counter row with FOR UPDATE) or use a unique/atomic UPDATE ... WHERE count < limit.
- Sequence numbers: Postgres sequences give gap-possible increasing numbers; Lamport/causality only matters if you merge writes from multiple writers; timestamps from app servers (wall clock) are not trustworthy for ordering - use DB now()/serial ids for "who was first" decisions.
- Failure-detection by timeout can't distinguish slow from dead: jobs marked 'running' too long may still be running; reaping them needs fencing/idempotent jobs.
- Managed Postgres failover: Supabase/hosted failover is automated consensus-like but async replication can lose last committed writes on failover (durability trade-off) - know this when promising "never lose a send record".
