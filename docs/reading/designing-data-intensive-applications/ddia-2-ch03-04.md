# CHAPTER 3: STORAGE AND RETRIEVAL
---------------------------------------------------------------

## 1. Core argument
A database does two things: store data, and give it back. You will rarely write a storage engine, but you must choose one and tune it, so you need a rough mental model of what happens inside. The chapter contrasts two families of OLTP engines: log-structured (append-only, merge in the background: Bitcask, SSTables/LSM-trees, LevelDB, RocksDB, Cassandra, HBase, Lucene) and update-in-place page-oriented (B-trees, used by essentially all relational databases). Every index is extra structure derived from the primary data: it speeds reads and slows writes, so indexes are chosen deliberately by someone who knows the query patterns. The second half separates transactional (OLTP) access from analytic (OLAP) access: analytics scans huge numbers of rows but reads few columns, so warehouses use star schemas and column-oriented, compressed, sorted storage where indexes matter far less. The practical message: know which workload you have, then pick the structure (and tune it) accordingly; benchmark with your own workload because no rule settles B-tree vs LSM.

## 2. Concepts, techniques, trade-offs (by section)

### Intro / "Data Structures That Power Your Database"
- Simplest DB: two Bash functions, db_set appends "key,value" to a file; db_get greps and takes the last match (tail -n 1). Writes are very fast (append is the cheapest write); reads are O(n) full scans.
- A "log" here = any append-only sequence of records (not application text logs). Real DBs add concurrency control, disk reclamation, error/partial-record handling, but same principle.
- Index = extra metadata acting as a signpost, derived from primary data; adding/removing an index changes only query performance, not contents. Several access paths => several indexes.
- KEY TRADE-OFF: well-chosen indexes speed reads, but every index slows writes (must be updated on every write). Hence DBs do not index everything by default; developer/DBA picks indexes from knowledge of query patterns, avoiding unnecessary overhead.

### Hash Indexes
- In-memory hash map: key -> byte offset in the append-only data file. Write: append + update map. Read: lookup offset, seek, read. This is essentially Bitcask (Riak default engine): high-performance reads/writes provided ALL KEYS FIT IN RAM; values can exceed RAM (one disk seek, maybe served from filesystem cache).
- Good fit: few distinct keys, many updates per key (example: play counter per cat-video URL).
- Avoiding running out of disk: split log into fixed-size segments; compaction = discard duplicate keys keeping most recent value per key; merge several segments while compacting, writing to a new file in a background thread; reads/writes continue on old segments, then switch over and delete old ones. Segments are never modified after written. Each segment has its own hash map; lookup checks newest segment first, then older. Merging keeps segment count small.
- Real-implementation concerns: (a) File format: binary with length-prefixed strings beats CSV (no escaping). (b) Deletion: append a tombstone; merge discards earlier values. (c) Crash recovery: in-memory hash maps lost on restart; rebuilding by scanning all segments is slow; Bitcask snapshots hash maps to disk. (d) Partially written records: crash mid-append; checksums let corrupted tail be detected and ignored. (e) Concurrency: single writer thread; immutable segments can be read concurrently.
- Why append-only beats update-in-place: sequential writes much faster than random (especially spinning disks, somewhat on SSDs); concurrency/crash recovery simpler (no half-old/half-new values); merging avoids fragmentation.
- Limitations: hash table must fit in memory (on-disk hash maps perform badly: random I/O, expensive growth, collision logic); range queries inefficient (e.g., keys kitty00000..kitty99999 need individual lookups).

### SSTables and LSM-Trees
- SSTable (Sorted String Table): segment files whose key-value pairs are sorted by key, each key once per merged segment. Advantages over hash-indexed logs:
  1. Merging is simple/efficient even for files larger than RAM, like mergesort's merge step: read inputs side by side, copy the lowest key; when a key appears in several segments keep the value from the most recent segment.
  2. No need for an in-memory index of all keys: a SPARSE index (one key per few KB) suffices - e.g., to find "handiwork", jump to offset of "handbag" and scan to "handsome". (With fixed-size records you could binary-search, but real records are variable-length.)
  3. Because reads scan a range anyway, group records into blocks and compress; sparse index points at block starts; saves disk space and I/O bandwidth.
- Constructing SSTables: writes arrive in any order. Keep an in-memory balanced tree (red-black / AVL) = MEMTABLE. When memtable exceeds a threshold (few MB) write it out as a new SSTable (already sorted); new writes go to a fresh memtable meanwhile. Read: memtable, then newest segment, then older. Background merging/compaction discards overwritten/deleted values.
- Crash problem: memtable contents lost. Fix: separate unsorted append-only write log on disk, used only to rebuild the memtable after a crash; discard it once the memtable is flushed.
- LSM-tree = "Log-Structured Merge-Tree" (O'Neil et al.), the principle of merging and compacting sorted files; used by LevelDB, RocksDB (embeddable libs), Cassandra, HBase (inspired by Google Bigtable, which coined SSTable/memtable). LevelDB can replace Bitcask in Riak. Lucene (behind Elasticsearch and Solr) uses a similar SSTable-like structure for its term dictionary: key = term, value = postings list (document IDs).
- Performance optimisations: looking up a non-existent key is slow (must check memtable and every segment) -> use Bloom filters (memory-efficient approximate set; can say definitely-not-present, saves disk reads). Compaction strategies: size-tiered (newer smaller SSTables merged into older larger ones; HBase, Cassandra) vs leveled (key range split into small SSTables in levels; incremental, less disk space; LevelDB, RocksDB, Cassandra).
- Bottom line: cascade of SSTables merged in the background works even when data >> RAM; range queries efficient because sorted; very high write throughput because writes are sequential.

### B-Trees
- Most widely used index structure; introduced 1970; standard in almost all relational DBs and many non-relational ones. Keeps key-value pairs sorted (good for lookups and range scans) but a different philosophy: fixed-size PAGES/blocks (traditionally 4 KB) read/written one at a time, matching hardware blocks; update in place.
- Pages reference other pages by disk address (like on-disk pointers) forming a tree: root page -> child pages each covering a continuous key range -> leaf pages holding values inline or references. Branching factor = number of child references per page (typically several hundred). Example lookup key 251 follows reference between boundaries 200 and 300.
- Update existing key: find leaf, change value, write page back. Insert new key: find page covering the range; if no room, split into two half-full pages and update the parent. Tree stays balanced: depth O(log n); 3-4 levels suffice for most DBs (4 levels, 4 KB pages, branching 500 => up to ~256 TB). Deleting while keeping balance is more involved.
- Reliability: write = overwrite page in place (location unchanged). Multi-page operations (a split) are dangerous: crash midway leaves a corrupt index (e.g., an orphan page). Therefore a write-ahead log (WAL / redo log): append-only file where every modification is written BEFORE being applied to tree pages; replayed on recovery. Concurrency with in-place updates needs latches (lightweight locks); log-structured is simpler here since merges are background and swap segments atomically.
- Optimisations: copy-on-write instead of WAL (LMDB: write modified page to a new location, create new parent versions; also helps concurrency/snapshot isolation); abbreviate keys in interior pages for higher branching factor (B+ tree variant); lay out leaf pages sequentially (hard to maintain as tree grows; LSM easier since it rewrites big segments); sibling pointers on leaf pages to scan in order; variants like fractal trees borrow log-structured ideas.

### Comparing B-Trees and LSM-Trees
- Rule of thumb: LSM faster for writes, B-trees faster for reads (LSM reads check several structures at different compaction stages). But benchmarks are inconclusive and workload-sensitive: test with YOUR workload.
- Advantages of LSM: B-tree writes data at least twice (WAL + page, plus splits; whole page even for tiny change; some engines write a page twice to survive power loss). LSM also rewrites data via repeated compaction. "Write amplification" = one logical write causing multiple physical writes over time; matters on SSDs (limited erase cycles) and in write-heavy workloads where disk bandwidth is the bottleneck. LSM often sustains higher write throughput (sequential compact files, sometimes lower write amplification); compresses better and has less fragmentation (B-trees leave unused space in pages) especially with leveled compaction. Even on SSDs (whose firmware is itself log-structured) lower amplification and compactness help.
- Downsides of LSM: compaction can interfere with ongoing reads/writes - average impact small but high percentiles (tail latency) can be bad, B-trees more predictable. At high write rates disk bandwidth is shared between initial writes and compaction; if compaction cannot keep up, unmerged segments pile up, disk fills, reads slow; engines usually do NOT throttle incoming writes, so explicit monitoring is needed. B-tree advantage: each key lives in exactly one place, which suits transactional semantics (range locks attach directly to the tree; see Ch. 7). No quick rule: test empirically. B-trees are not going away; log-structured gaining popularity in new datastores.

### Other Indexing Structures
- Primary key index uniquely identifies a row/document/vertex; other records reference it. Secondary indexes (CREATE INDEX) are crucial for efficient joins (e.g., index on user_id columns). Built from a key-value index by making keys non-unique: either value = list of row IDs (like postings list) or append row ID to key to make it unique. Works with B-trees and LSM.
- Storing values in the index: index value is either the row itself or a reference into a heap file (rows stored unordered; avoids duplicating data across secondary indexes). Update in place works if the new value is not larger; otherwise the row moves and either all indexes are updated or a forwarding pointer is left. CLUSTERED INDEX stores the row in the index (MySQL InnoDB: primary key always clustered, secondary indexes refer to PK; SQL Server: one clustered index per table). COVERING INDEX / index with included columns stores some columns in the index so some queries are answered from the index alone. Trade-off: faster reads, more storage, write overhead, extra work to keep duplicates consistent.
- Multi-column indexes: concatenated index appends columns into one key (phone-book example (lastname, firstname)): useful for lastname or lastname+firstname, USELESS for firstname alone (column order matters). Multi-dimensional indexes for queries on several ranges at once (lat/long map-area query): ordinary B-tree/LSM cannot do a 2-D range efficiently; options are a space-filling curve + B-tree or specialised R-trees (PostGIS implements via PostgreSQL's Generalized Search Tree). Not just geography: (r,g,b) colour search, (date,temperature) weather observations (HyperDex).
- Full-text and fuzzy search: exact-match indexes can't find misspellings. Search engines expand synonyms, ignore grammatical variants, proximity search. Lucene finds words within an edit distance (1 = one letter added/removed/replaced) by using a finite state automaton (trie-like) over term characters as the in-memory index, transformable into a Levenshtein automaton. Other fuzzy techniques go toward document classification/ML (see IR textbooks).

### Keeping everything in memory
- Disk structures are awkward answers to disk limitations; disks win on durability and cost/GB, and RAM cost is falling, so in-memory databases are feasible, possibly distributed. Memcached: cache-only, loss on restart acceptable. Others are durable via battery-backed RAM, change log to disk, periodic snapshots, or replication. Still "in-memory" because disk is just an append-only log and reads come from memory; disk files are also easy to back up/inspect. Examples: VoltDB, MemSQL, Oracle TimesTen (relational); RAMCloud (durable key-value, log-structured); Redis and Couchbase (weak durability, async disk writes).
- Counterintuitive: speed advantage is NOT from avoiding disk reads (OS page cache already does that) but from avoiding the overhead of encoding in-memory structures into a disk-writable form. Also enables data models hard to do on disk (Redis priority queues and sets). Anti-caching: evict least-recently-used records (not whole pages) to disk and reload on access, like OS swap but record-granular; indexes must still fit in RAM. Non-volatile memory (NVM) may require further engine redesign - area to watch.

### Transaction Processing or Analytics?
- "Transaction" = a group of reads and writes forming a logical unit; need not be ACID; means low-latency interactive reads/writes (vs batch jobs).
- OLTP: look up a few records by key via an index; insert/update from user input; interactive. OLAP: scan huge numbers of records, read few columns, compute aggregates (count/sum/avg) for business intelligence (e.g., revenue per store in January; bananas sold during promotion; baby food bought with brand-X diapers).
- Table 3-1 (OLTP vs OLAP): read pattern small number of records by key vs aggregate over many; write pattern random-access low-latency user input vs bulk import (ETL) or event stream; users end customer via web app vs internal analyst; data = latest state vs history of events; size GB-TB vs TB-PB.
- Data warehouse: separate read-only database for analysts, because ad hoc analytic queries are expensive and would hurt OLTP performance/availability (DBAs guard OLTP DBs). ETL = Extract-Transform-Load from OLTP systems (periodic dump or continuous stream), cleaned into an analysis-friendly schema. Common in large enterprises, rare in small companies (few systems, small data - conventional SQL DB or even spreadsheet suffices). Warehouse can use access-pattern-specific optimisations; OLTP indexing algorithms are poor for analytics.
- Divergence: data model usually relational (SQL good for analytics; GUI tools generate SQL: drill-down, slicing and dicing). Vendors increasingly specialise in either OLTP or analytics; combined products (SQL Server, SAP HANA) are really two engines behind one SQL interface. Examples: Teradata, Vertica, ParAccel (Amazon Redshift hosted), SQL-on-Hadoop (Hive, Spark SQL, Impala, Presto, Tajo, Drill; some based on Google Dremel).

### Stars and Snowflakes: Schemas for Analytics
- Star schema (dimensional modelling): central FACT table where each row is an event (e.g., a purchase of a product, or a page view/click), usually captured as individual events for maximum later flexibility, so it gets huge (tens of PB at Apple/Walmart/eBay). Fact columns = attributes (price, cost -> margin) plus foreign keys to DIMENSION tables (who/what/where/when/how/why): product, store, date, promotion, customer. Even date is a dimension table so holidays etc. can be encoded. Name from the star shape.
- Snowflake schema: dimensions further normalised into sub-dimensions (brands, categories as separate tables). More normalised, but stars usually preferred because simpler for analysts.
- Tables are very wide: facts often 100+ columns, hundreds sometimes; dimension tables wide too (store details etc.).

### Column-Oriented Storage
- Problem: fact tables with trillions of rows; a typical query touches only 4-5 of 100+ columns (example 3-1: weekday x category sums of quantity for fruit/candy in 2013 needs only date_key, product_sk, quantity). Row-oriented storage + indexes still loads whole 100+ attribute rows from disk, parses and filters.
- Column-oriented: store each column's values together (one file per column); read only needed columns. Same row order in every column file, so row k is the kth entry of each file. Applies to non-relational too (Parquet, based on Dremel, supports document model).
- Column compression: columns repetitive. Bitmap encoding: for a column with n distinct values (small vs rows, e.g., 100,000 products vs billions of sales) make n bitmaps, one bit per row; if n small store bits directly; if sparse, run-length encode. Queries: IN (30,68,69) => bitwise OR of three bitmaps; product_sk=31 AND store_sk=3 => bitwise AND (works since rows are in the same order across columns). Other schemes exist.
- Misnomer: Cassandra/HBase "column families" (from Bigtable) are NOT column-oriented - they store all columns of a row together with a row key and no column compression.
- Memory bandwidth and vectorized processing: bottlenecks beyond disk-to-memory: memory-to-CPU-cache bandwidth, branch mispredictions, pipeline bubbles, SIMD usage. Column layout + compression lets chunks fit in L1 cache and be processed in tight loops without function calls; bitwise AND/OR operate directly on compressed chunks = vectorized processing.
- Sort order: can store in insertion order, or impose a sort as an indexing mechanism (like SSTables). Must sort whole ROWS (not columns independently, else row reconstruction breaks). Admin chooses sort keys from common queries (e.g., date_key first for last-month queries; product_sk second to group same product-day). Sorted first column compresses extremely well with run-length encoding (billions of rows -> kilobytes); effect weaker for 2nd/3rd keys.
- Several different sort orders: C-Store / Vertica store replicas sorted differently and pick the best for a query. Similar to multiple secondary indexes in row stores but without pointers - column stores just hold values.
- Writing to column stores: compression and sorting make in-place updates impractical (inserting mid-table could rewrite all column files). Solution: LSM-tree style - writes go to an in-memory sorted store (row- or column-oriented), then are merged with column files in bulk (Vertica). Queries combine disk data and recent in-memory writes transparently, so analysts see updates immediately.
- Aggregation: materialized views vs virtual views. Virtual view = shortcut expanded into its query on read; materialized view = real copy of query results on disk, a denormalised copy that must be updated when underlying data change (makes writes more expensive, so rarely used in OLTP; may make sense in read-heavy warehouses; benefit not guaranteed). Data cube / OLAP cube = materialised grid of aggregates (e.g., SUM of net_price) grouped by dimensions (date x product, plus roll-ups along each axis; 5 dims in the example schema). Pro: precomputed => very fast (total sales per store yesterday). Con: inflexible - cannot answer questions on non-dimension attributes (e.g., share of sales from items over $100). Warehouses keep raw data and use cubes only as a performance boost.

## Summary points of the chapter (from author)
- Two broad categories: OLTP (user-facing, huge volume of small key-based requests, seek time often the bottleneck) vs analytics (fewer but heavy queries scanning millions of records; disk bandwidth the bottleneck; column storage increasingly popular).
- OLTP engine schools: log-structured (append only, never updates a file: Bitcask, SSTables, LSM, LevelDB, Cassandra, HBase, Lucene) turning random writes into sequential; update-in-place (B-trees) in all major relational DBs.
- With analytic scans, indexes matter less; compact encoding to minimise bytes read is what matters.
- Application developers should understand internals to choose tools, interpret tuning parameters, and read DB documentation.

## 3. Failure modes / pitfalls
- Hash-indexed log: key set outgrowing RAM; slow restart without hash snapshots; torn writes at crash tail (need checksums); range scans impossible.
- LSM: reads of non-existent keys slow without Bloom filters; compaction can't keep up with writes -> segment pile-up, disk exhaustion, slower reads, and no automatic throttling - must be monitored; tail latency spikes from compaction; write amplification wears SSDs.
- B-tree: multi-page splits corrupt index on crash without WAL; concurrency needs latches; fragmentation/unused page space; scanning leaf pages non-sequentially causes seeks.
- Concatenated index misuse: wrong column order makes index useless for queries on the trailing column only.
- Clustered/covering/materialised copies add write cost and consistency burden.
- Running analytics on the OLTP database harms transactional performance.
- Data cubes lose flexibility; do not delete raw data.
- Benchmarks are workload-sensitive; do not trust rules of thumb blindly.

## 4. Key terms
- Log: append-only sequence of records. Index: derived structure to find data faster; costs writes.
- Hash index: in-memory map key->file offset. Segment: fixed-size piece of a log. Compaction: dropping superseded keys. Tombstone: deletion marker.
- SSTable: segment sorted by key, unique keys. Memtable: in-memory sorted tree buffering writes. LSM-tree: engines merging/compacting sorted files. Bloom filter: probabilistic set that proves absence. Size-tiered / leveled compaction: two merge strategies.
- B-tree: tree of fixed-size pages updated in place. Page, branching factor, leaf page, page split. WAL/redo log: pre-write log for crash recovery. Latch: lightweight lock. Copy-on-write B-tree (LMDB).
- Write amplification: one logical write -> many physical writes. 
- Secondary index, heap file, clustered index, covering index (included columns), concatenated index, multi-dimensional index, R-tree, space-filling curve, edit distance, Levenshtein automaton.
- In-memory database, anti-caching, NVM.
- OLTP / OLAP, data warehouse, ETL, star schema, snowflake schema, fact table, dimension table, column-oriented storage, bitmap encoding, run-length encoding, vectorized processing (SIMD), column family (misnomer), materialized view, data cube.

## 6. Relevance to multi-tenant SaaS on Node/Express + single managed Postgres (Supabase), small host
DIRECTLY APPLICABLE
- Postgres is a B-tree (update-in-place + WAL) system; default CREATE INDEX is a B-tree. Slow list queries => add the right index; every extra index taxes inserts/updates, so index to real query patterns, not everything. Review/drop unused indexes.
- Multi-tenant lists: an index like (org_id, created_at) or (org_id, status, ...) as a CONCATENATED index - column order matters; leading column must match the equality filter (org_id) and the next the sort/range. An index on created_at alone, or with org_id last, will not serve "tenant X's newest 50".
- Covering index (INCLUDE columns in Postgres) can make hot list endpoints index-only; partial indexes follow the same cost logic. Secondary index on foreign keys (user_id, candidate_id, job_id) is needed for joins and cascade deletes.
- Postgres tables are heap files with indexes referencing heap locations; updates leave dead tuples (VACUUM) - the book's heap-file/forwarding-pointer discussion is the conceptual basis. (Book does not name VACUUM; this is my inference.)
- Fuzzy/full-text candidate search: use Postgres full-text search (tsvector/GIN) or trigram indexes (pg_trgm) rather than LIKE '%x%' scans; conceptually the postings list + edit-distance material. Geospatial radius search: PostGIS/GiST (R-tree idea).
- OLTP vs OLAP: reporting dashboards that aggregate over many rows will compete with interactive traffic on one small database. At small scale: precompute with materialized views or summary tables refreshed on a schedule, run heavy reports off-peak or on a read replica; avoid SELECT *. Book says small companies need no warehouse - one SQL DB or spreadsheet is enough. Materialized views: read speed vs refresh cost; fine for read-heavy dashboards, not for hot write tables.
- Keep raw event history (facts) and treat aggregates as caches (data-cube lesson): don't throw away raw events like submissions/stage changes that analytics may want later.
- Write amplification / WAL: heavy per-row updates (e.g., counters, status flips) cost more than appends; prefer append-only event tables for high-churn logs.
- Caching: Memcached/Redis-style cache loses data on restart - fine for cache, not source of truth.
ONLY AT MUCH LARGER SCALE
- Choosing between LSM and B-tree engines, tuning compaction, Bloom filters, SSTable internals, column stores (Redshift/ClickHouse/Parquet), star-schema warehouse + ETL, vectorized processing, in-memory DBs, NVM. Revisit only when analytics on Postgres becomes too slow or too intrusive.

# CHAPTER 4: ENCODING AND EVOLUTION
---------------------------------------------------------------

## 1. Core argument
Applications change, so stored and transmitted data formats change too, but code and data cannot all change at the same instant: rolling (staged) upgrades deploy new code to a few nodes at a time, client apps update when users choose, and old data persists in storage. So old and new code and old and new data formats coexist, and the system needs backward compatibility (new code reads old data) and forward compatibility (old code reads data written by new code - the harder one, since old code must ignore what it doesn't understand). The chapter surveys encodings (language-specific, JSON/XML/CSV, binary JSON variants, Thrift, Protocol Buffers, Avro) and how each supports schema evolution, then walks the three dataflow paths where encoding matters: through databases, through services (REST/RPC), and through asynchronous message passing. Takeaway: with a bit of care - optional/default-valued new fields, never reusing tags, preserving unknown fields - compatibility and rolling upgrades are quite achievable, and they enable frequent small, low-risk releases.

## 2. Concepts, techniques, trade-offs (by section)

### Intro
- Relational DBs: one schema in force at any time (schema migrations = ALTER). Schema-on-read DBs hold a mixture of old and new formats. Code changes often need data changes (new field, new record type).
- Rolling upgrade: benefits - no downtime, check new version on a few nodes first, encourages frequent releases (evolvability). Client-side apps: user decides when to update. Hence coexistence and need for both compatibilities. Backward compat is easy (you know the old format); forward compat requires older code to ignore additions.

### Formats for Encoding Data
- Two representations: in-memory (objects, structs, pointers, optimised for CPU) vs byte sequences for files/network (self-contained; pointers meaningless to others). Translation = encoding (serialization, marshalling) and decoding (parsing, deserialization, unmarshalling). Author uses "encoding" because "serialization" clashes with transaction serialization (Ch.7). Encoding is not encryption.
- Language-specific formats (Java Serializable, Ruby Marshal, Python pickle, Kryo): convenient but: tied to one language (commits you long-term, blocks integration with other organisations); decoding must instantiate arbitrary classes => security risk (attacker-controlled bytes can lead to remote code execution); versioning/forward-backward compatibility is an afterthought; efficiency is an afterthought (Java serialization slow and bloated). Verdict: avoid except for very transient purposes.
- JSON, XML, CSV (textual): widely supported, "almost as widely disliked"; XML verbose and complicated; JSON popular due to browser built-in support (JS subset) and simplicity; CSV language-independent but less powerful. Subtle problems:
  - Number ambiguity: XML/CSV can't distinguish number from digit-string without a schema; JSON distinguishes string/number but not integer/float, and gives no precision. Integers > 2^53 lose precision as IEEE 754 doubles (JavaScript). Example: Twitter 64-bit tweet IDs - API returns each ID twice, as a JSON number and a decimal string, to work around JS parsing.
  - No binary strings: people Base64-encode (hacky, +33% size; schema must say it's Base64).
  - Optional schemas exist (XML Schema, JSON Schema) but are complicated; many JSON tools skip them, so apps hard-code interpretation logic.
  - CSV has no schema; app defines meaning; adding a column/row needs manual handling; vague about commas/newlines in values; RFC 4180 escaping formally specified but not all parsers follow it.
  - Still good enough, especially for data interchange between organisations, where getting parties to agree outweighs elegance or efficiency.
- Binary encoding of JSON/XML (MessagePack, BSON, BJSON, UBJSON, BISON, Smile; WBXML, Fast Infoset): used internally when you can pick a compact/fast format; gains matter at terabyte scale, negligible for small datasets. They keep the schemaless model so field names are embedded in every record. Worked example (Example 4-1: {"userName":"Martin","favoriteNumber":1337,"interests":["daydreaming","hacking"]}): MessagePack = 66 bytes vs 81 bytes JSON text (minified); type/length bytes like 0x83 (object with 3 fields), 0xa8 (8-byte string). Author doubts that small gain is worth losing readability.

### Thrift and Protocol Buffers
- Both: require a schema (Thrift IDL / protobuf definitions), generate code in many languages from it, binary-encode. Protobuf from Google, Thrift from Facebook; both open-sourced 2007-08.
- Thrift schema: struct Person {1: required string userName, 2: optional i64 favoriteNumber, 3: optional list<string> interests}. Protobuf equivalent uses message Person with `= 1; = 2; = 3` tags and a `repeated` marker for lists.
- Thrift has multiple encodings: BinaryProtocol (59 bytes for the example; each field has type annotation + length, but FIELD TAGS (numbers 1,2,3) instead of names) and CompactProtocol (34 bytes: packs type and tag into one byte, variable-length integers - 1337 in 2 bytes, top bit signals continuation; -64..63 in one byte, -8192..8191 in two). (Also DenseProtocol C++ only and JSON-based ones.) Protocol Buffers has one binary encoding, 33 bytes, similar bit-packing.
- required vs optional makes no difference to the bytes; required only adds a runtime check that fails if unset (useful for catching bugs).
- Field tags and schema evolution: encoded record = concatenation of tagged, typed fields; unset fields are omitted. You can RENAME a field (names never encoded) but never CHANGE a tag (invalidates existing data). Add new fields with NEW tag numbers: old code ignores unknown tags (datatype annotation tells how many bytes to skip) => forward compatible; new code reads old data fine as tags unchanged => backward compatible, but any field added after initial deployment must be optional or have a default (a required new field would fail on old data). Removing a field: only optional fields, and never reuse the tag number (old data may contain it).
- Datatype changes: possible but risk loss of precision/truncation (32-bit -> 64-bit: new code reads old fine; old code reading new values truncates). Protobuf has no list type, only `repeated`: lets you change optional (single) to repeated (multi) - new code sees list of 0/1 elements for old data; old code reading new data sees only the last element. Thrift has a true list<T> type: no single-to-multi evolution, but supports nested lists.

### Avro
- Started 2009 as Hadoop subproject (Thrift a poor fit). Two schema languages: Avro IDL (human) and JSON (machine). Example: record Person {string userName; union{null,long} favoriteNumber = null; array<string> interests;}. NO tag numbers. Encoding is 32 bytes - the most compact: just values concatenated (length-prefixed strings, variable-length ints), no field identifiers or types in the data. To decode you walk the schema in order, so you need exactly the schema that wrote the data.
- Writer's schema vs reader's schema: they need only be COMPATIBLE, not identical. The Avro library resolves differences, matching fields by NAME: field order may differ; field in writer's but not reader's schema is ignored; field in reader's but not writer's gets the reader's declared default.
- Evolution rules: forward compat = new schema as writer, old as reader; backward compat = new reader, old writer. Only add or remove fields that have a default value (adding a field without default breaks backward compat; removing one without default breaks forward compat). null isn't a default for everything: nullable fields require a union type (e.g., union{null,long,string}); null default only valid if null is a union branch (and default must match the first branch type) - more verbose but prevents null bugs. No required/optional markers (unions and defaults instead). Type changes allowed if Avro can convert. Renaming a field via aliases in the reader's schema: backward compatible but not forward compatible; adding a union branch: backward but not forward compatible.
- How does the reader get the writer's schema? Depends on context: (1) large file of millions of records, same schema: put schema once at file start (object container files); (2) database with individually written records: put a version number at the start of each record, keep a table/list of schema versions (Espresso does this), reader fetches the writer's schema by version; (3) network connection: negotiate schema version at connection setup (Avro RPC). A schema-version database is useful anyway as documentation and for checking compatibility; version can be an incrementing integer or a hash of the schema.
- Dynamically generated schemas: advantage over protobuf/Thrift. Dumping a relational DB to a file: generate an Avro record schema per table, column -> field by name; when the DB schema changes just regenerate the schema; readers match by name. With Thrift/protobuf, tags would have to be assigned by hand (and never reuse old tags) each time; not a design goal there.
- Code generation and dynamic languages: Thrift/protobuf rely on code generation - helpful in statically typed languages (efficient in-memory structs, compile-time checks, IDE autocomplete); little point in dynamically typed languages (JavaScript, Ruby, Python) with no compile-time checker, and generated code is an obstacle for dynamic schemas. Avro: code generation is optional; self-describing container files can be opened and read like JSON (handy with Apache Pig).

### The Merits of Schemas
- Protobuf/Thrift/Avro schema languages are far simpler than XML Schema/JSON Schema (no regex or range validation), hence easier to implement, wider language support. Not new: ASN.1 (1984) has tag-number evolution and DER encoding (X.509 SSL certs) but is complex and badly documented - not recommended for new applications. Many databases use proprietary binary network protocols via drivers (ODBC/JDBC).
- Benefits of schema-based binary encodings: more compact than binary JSON (omit field names); schema = documentation guaranteed up to date (required for decoding); a schema registry lets you check forward/backward compatibility BEFORE deploy; codegen gives compile-time type checking. Schema evolution gives schemaless-like flexibility plus stronger guarantees and tooling. Downside (in summary): data must be decoded before humans can read it.

### Modes of Dataflow
Compatibility is a relationship between the process that encodes and the one that decodes. Three paths: databases, service calls, async messages.

#### Dataflow Through Databases
- Writer encodes, reader decodes. Single-process case: storing = sending a message to your future self => backward compatibility essential. Usually many processes/instances access the DB, and during a rolling upgrade some run old code, so old code may read data written by new code => forward compatibility also needed.
- Snag (Fig 4-7): new code writes a new field; old code reads the record, updates it, writes it back - it should preserve the unknown field, but if it decodes into model objects and re-encodes, the field is silently lost. Formats support preservation; application-level mapping layers (ORMs/model objects) may drop it. "Not a hard problem; just be aware."
- Different values written at different times: DB rows may be 5 ms or 5 years old. "Data outlives code": code is replaced in minutes, but old data stays in its old encoding unless rewritten. Migrating all data is expensive on large datasets, so DBs avoid it where possible; most relational DBs allow simple changes like adding a column with a NULL default without rewriting existing rows (old rows read as null for missing columns). Exception: MySQL often rewrites the whole table unnecessarily. LinkedIn's Espresso stores Avro, using its evolution rules. Schema evolution lets the DB look like it has a single schema even if storage holds many historic versions.
- Archival storage / snapshots (backup, warehouse load): encode the dump consistently in the latest schema; immutable, one-shot writes suit Avro object container files, or analytics-friendly columnar Parquet.

#### Dataflow Through Services: REST and RPC
- Client/server roles; the server's API is a "service". The web is the model (HTTP GET/POST, URLs, TLS, HTML). Other clients: native apps, in-browser JavaScript via XMLHttpRequest/Ajax (typically gets JSON, not HTML, and client/server must agree on app-specific API details). A server can itself be a client (web app server -> database or other services). Decomposing an app into services = service-oriented architecture (SOA), rebranded microservices. Services differ from databases: they expose an application-specific API with predetermined inputs/outputs, giving encapsulation and fine-grained restrictions. Goal: independently deployable and evolvable services, one owning team releasing frequently without coordination; so old and new servers and clients coexist and API encoding must be compatible across versions.
- Web services (HTTP as the protocol): three contexts - (1) client devices to a service over the internet, (2) service-to-service inside one organisation (often same datacentre; middleware), (3) service-to-service across organisations (public APIs, payment processors, OAuth).
- REST vs SOAP: REST is a design philosophy built on HTTP principles - simple data formats, URLs identify resources, uses HTTP features for caching, authentication, content negotiation; "RESTful" APIs; gaining over SOAP in cross-org integration, associated with microservices. SOAP: XML-based protocol, tries to be HTTP-independent, with a sprawl of WS-* standards; described by WSDL (not human-readable, enables code generation, depends on heavy tooling/IDEs, hard for languages unsupported by vendors; interoperability problems); still in large enterprises, out of favour in smaller companies. REST favours less codegen/tooling; OpenAPI (Swagger) describes RESTful APIs and generates documentation. SOAP is not required for SOA.
- Problems with RPC: older tech (EJB, RMI Java-only; DCOM Microsoft-only; CORBA complex and no compatibility). RPC tries to make a remote call look like a local function (location transparency) - fundamentally flawed because: network requests are unpredictable (loss, slowness, unavailability; must anticipate and retry); a request can return with no result due to timeout - you don't know whether it got through; retries can execute an action multiple times unless the protocol has deduplication/idempotence; latency is much higher and wildly variable (sub-ms to many seconds); parameters must be encoded to bytes (fine for primitives, awkward for large objects) rather than passing pointers; cross-language type translation is ugly (e.g., JS numbers > 2^53). So don't hide that it is a network protocol - part of REST's appeal.
- Current directions: Thrift/Avro RPC, gRPC (protobuf), Finagle (Thrift), Rest.li (JSON over HTTP). Newer frameworks are explicit about remote failure: futures/promises for async failing calls and parallel requests, gRPC streams, service discovery. Custom binary RPC is faster than generic JSON/REST, but REST is great for experimentation/debugging (curl, browser, no codegen), supported in all mainstream languages, and has a vast tooling ecosystem (caches, load balancers, proxies, firewalls, monitoring, testing). REST dominates public APIs; RPC frameworks mainly for intra-organisation, same-datacentre calls.
- Data encoding and evolution for RPC: can assume servers update first and clients second => need backward compatibility on requests and forward compatibility on responses. Compatibility inherited from encoding: Thrift/gRPC/Avro RPC follow their format's rules; SOAP via XML schemas with subtle pitfalls; REST typically JSON responses (no formal schema) and JSON/URI/form-encoded requests - adding optional request params and adding new response fields are generally considered compatible. Cross-organisation APIs: provider can't force clients to upgrade, so compatibility must be kept long (maybe indefinitely); breaking change => maintain multiple API versions side by side. No consensus on API versioning: common REST approaches = version in the URL or in the HTTP Accept header; with API keys, store the client's requested version server-side and let it be changed via an admin interface (Stripe-style).

#### Message-Passing Dataflow
- Between RPC and databases: low-latency delivery like RPC, but via a message broker (message queue / message-oriented middleware) that stores messages temporarily. Advantages over direct RPC: buffer when recipient unavailable/overloaded (reliability); redelivery to crashed processes (no lost messages); sender need not know recipient address (useful in cloud where VMs come and go); one message to many recipients; decouples sender from recipient. Differences: usually one-way/asynchronous (fire and forget); replies, if any, go on a separate channel/reply queue.
- Brokers: historically commercial (TIBCO, IBM WebSphere, webMethods); now RabbitMQ, ActiveMQ, HornetQ, NATS, Apache Kafka. Usage: producer sends to a named queue or topic; broker delivers to one or more consumers/subscribers; many producers and consumers per topic. A consumer may republish to another topic (chaining) - if so, preserve unknown fields (Fig 4-7 problem). Brokers impose no data model: message = bytes + metadata, any encoding; with a backward/forward-compatible encoding you can change and deploy publishers and consumers independently in any order.
- Distributed actor frameworks: actor model = single-process concurrency model without threads/locks; each actor has private state, communicates via async messages, processes one message at a time, delivery not guaranteed. Distributed version spreads actors across nodes using same message passing (transparent encode/send/decode); location transparency works better than RPC since the model already assumes message loss. It is effectively a message broker plus actor model; rolling upgrades still require compatible message encodings. Akka: Java serialization by default (no compat) - swap in Protocol Buffers for rolling upgrades. Orleans: custom format without rolling upgrade support (spin up new cluster, shift traffic, shut down old). Erlang OTP: record-schema changes surprisingly hard; rolling upgrades need careful planning; maps type (R17) may help.

## Summary (author's)
Rolling upgrades enable frequent small releases, less risky deployments, quick rollback of faulty releases before they reach many users. Therefore assume mixed versions and use encodings that give backward compatibility (new code reads old data) and forward compatibility (old code reads new data). Language-specific encodings: single-language, usually poor compatibility. Textual JSON/XML/CSV: compatibility depends on your usage; vague about numbers and binary strings. Binary schema-driven formats (Thrift, protobuf, Avro): compact, well-defined compatibility, docs/codegen, but not human-readable. Dataflow modes: databases, RPC/REST, async messaging.

## 3. Failure modes / pitfalls
- Using pickle/Java serialization for persisted or network data: language lock-in, deserialization RCE, no versioning.
- JSON numbers above 2^53 silently corrupted in JavaScript (tweet-ID case); no integer/float distinction; binary data needs Base64 (+33%); CSV edge cases (commas, newlines), no schema.
- Making a newly added field required (protobuf/Thrift) or giving no default (Avro) => breaks backward compatibility; removing required fields; REUSING a removed tag number; CHANGING a tag; widening types then reading with narrow old code (truncation).
- Old code read-modify-write dropping unknown fields written by newer code (model-object round trip).
- Assuming a rolling deploy is instantaneous; data outlives code; assuming all rows share the latest schema.
- Treating RPC as a local call: timeouts with unknown outcome, duplicate execution on retry without idempotence, variable latency, cross-language type mismatch.
- Public API: cannot force clients to upgrade; breaking changes require parallel versions; no versioning consensus.
- Avro decode with the wrong (mismatched) schema yields garbage; must know writer's schema (version number/registry).
- Message brokers with republishing consumers: unknown-field loss; some actor frameworks have no rolling-upgrade story.

## 6. Relevance to multi-tenant SaaS on Node/Express + single Postgres (Supabase), small host
DIRECTLY APPLICABLE
- Rolling deploys / migrations: during any deploy (and especially Render/auto-deploy with overlapping old+new instances, or a frontend loaded in a browser tab with old JS) OLD CODE AND NEW SCHEMA COEXIST and the reverse. Use expand/contract migrations: add columns as nullable or with defaults (cheap; Postgres adds nullable/constant-default columns without rewriting the table - my addition, book says "most relational DBs" and singles out MySQL as the exception); deploy code that writes/reads the new column; only later drop old columns, after no running code references them. Never add NOT NULL without default in one step with code that doesn't yet write it; never rename/drop a column in the same release that stops using it. Apply migration before the code that uses it (backward-compatible migration first), as in book's "new fields must be optional/defaulted" rule.
- Backward vs forward compatibility maps to: new code vs old rows (backward - always needed, data outlives code) and old instances/browser tabs/cached frontend vs new data/API responses (forward). Frontend JS cached in browsers = the "client-side apps update when the user chooses" case.
- JSON API evolution: adding optional request params and adding fields to responses is safe; removing/renaming fields or changing types is breaking. Clients must ignore unknown fields. Public/customer-facing API (Growth bet) will need versioning (URL or Accept header; per-API-key pinned version à la Stripe) and long compatibility windows because you can't force customers to upgrade.
- JSON columns (jsonb) in Postgres = schema-on-read: need tolerant readers, defaults for missing keys, and read-modify-write must not drop unknown keys (Fig 4-7) - relevant to any code that loads a row into an object, edits, and writes back the whole object (or ORM update of full JSON blob) while another version of the app is live.
- JSON number pitfall: bigint IDs (Postgres bigint/int8, 64-bit) exceed JS safe integer range; node-postgres returns bigint as strings by default - keep as strings or use UUIDs; avoid Number() on large ids. Also Base64 for binary (resumes/attachments) costs +33%; prefer storage bucket + signed URL over inline Base64 in JSON.
- CSV import/export: no schema, escaping vagaries (commas, newlines in resume text/notes) - use a proper parser; define column meanings explicitly and version templates.
- Webhooks / outbound HTTP and RPC lessons: network calls can time out with unknown outcome; retries can duplicate effects, so use idempotency keys/dedup for non-idempotent actions (e.g., sending email, charging payments, webhook handlers: Stripe-style event IDs); latency variable so set timeouts. Treat third-party APIs as unreliable RPC, not local functions.
- REST over JSON with curl-debuggability is the right style for this stack; OpenAPI can document the API.
- Message queues: decouple slow/unreliable work (email sends, resume parsing) from request handling; a DB-backed job table (or a small queue) provides buffering, redelivery after crash, and decoupling at small scale without Kafka. Make consumers idempotent.
- Backups/exports: dump consistently in the latest schema; for analytics, an export to a columnar format is optional later.
- Avoid pickle-style/eval-style deserialization of untrusted input (in Node: don't use unsafe deserializers/eval for user-supplied data; JSON.parse is safe).
ONLY AT MUCH LARGER SCALE
- Choosing Thrift/Protobuf/Avro, schema registries, gRPC, service meshes/microservices with independent team deployment, message brokers like Kafka/RabbitMQ, distributed actor frameworks, Avro object container files for data lakes. A single Express app + Postgres normally needs only: disciplined backward-compatible migrations, tolerant JSON handling, API versioning when external customers appear, idempotency for retries.
