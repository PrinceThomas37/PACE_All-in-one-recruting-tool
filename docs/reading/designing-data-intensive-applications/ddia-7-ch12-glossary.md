# DDIA Ch.12 "The Future of Data Systems" + Glossary — notes (Part A: file lines 1-1000)

## Core argument (Chapter 12)
No single data tool fits every use, so real applications compose several; the author argues they should be joined by an ordered, durable event log (CDC/event sourcing) from which every other store (index, cache, view, model) is deterministically derived, asynchronously and loosely coupled, rather than by dual writes or distributed transactions. This "unbundled database / dataflow" view lets you rerun derivations to evolve schemas or recover from bugs, and can extend all the way to client devices. Correctness is then pursued end to end: client-generated operation IDs make retries idempotent, constraints can be checked asynchronously (or loosely, with apologies), and the key distinction is integrity (never lose or corrupt data; essential) versus timeliness (freshness; often negotiable), which lets systems avoid coordination. Because components and people err, systems should audit themselves ("trust, but verify"). The chapter closes by arguing engineers are ethically responsible for how data about people is used: predictive analytics can encode bias and trap people, tracking amounts to surveillance without meaningful consent, and data is a hazardous asset to be minimised and purged.

### Intro (opening, pp.489)
- Chapter shifts from "how things are" to "how they should be" (author's opinion, first person). Ties together the book's three themes (reliable, scalable, maintainable) and aims at apps that are robust, correct, evolvable and "beneficial to humanity". ### Data Integration
- No single tool fits all access patterns; every piece of software, even a "general-purpose" DB, is built for a usage pattern. Complex apps use the same data in several ways, so you inevitably cobble together several tools. Distrust claims like "99% of people only need X" — they reflect the speaker's experience; integration needs show up when you zoom out to org-wide dataflow.
- **Combining specialised tools by deriving data.** Example: OLTP DB + full-text search index. Postgres has built-in full-text search (enough for simple apps); sophisticated search needs specialist IR tools; search indexes are poor systems of record. More representations (warehouse, caches, denormalised copies, ML/ranking, notifications) = harder integration.
- **Reasoning about dataflows.** Be explicit: where is data written first, which representations derive from which? Recommended: write to a system of record, capture changes (CDC) and apply to the index in the same order. If CDC is the ONLY path into the index, the index is fully derived and consistent (barring bugs). Letting the app dual-write to DB and index risks the Fig 11-4 problem: two clients' conflicting writes arrive in different order at each store -> permanent inconsistency because neither is "in charge" of ordering. Funnel all input through one system that decides a total order (state-machine replication / total order broadcast). CDC vs event sourcing matters less than the principle of deciding on a total order. Derived-data updates from a log can be deterministic and idempotent -> easy fault recovery.
- **Derived data vs distributed transactions.** Same goal, different means: transactions order via locks (2PL) and get exactly-once via atomic commit; log-based systems order via the log and get effect-once via deterministic retry + idempotence. Transactions usually give linearizability (read-your-writes); derived systems are async so don't by default. Author: XA has poor fault tolerance/performance; a better protocol is possible but adoption unlikely soon; so log-based derived data is the most promising integration route — but don't just tell people "eventual consistency is inevitable, suck it up"; later (Aiming for Correctness) he builds a middle ground.
- **Limits of total ordering.** Works at small scale (single-leader DB logs). Breaks down when: (1) throughput exceeds one node -> partitioned log, order across partitions undefined; (2) multi-datacenter with a leader per DC -> cross-DC order undefined; (3) microservices each with own durable state -> no order across services; (4) offline-capable clients with local state updated instantly -> client and server see different orders. Total order broadcast == consensus; most consensus algorithms assume one node can handle the whole stream; scaling consensus beyond one node and geo-distributed is open research.
- **Ordering events to capture causality.** Without a causal link, no total order is needed; updates to the same object can be totally ordered by routing by object ID to one partition. Subtle cases: example — user unfriends ex, then posts a rude message meant to be hidden from ex; if friend list and messages live in different places, the notification service may process message-send before unfriend and wrongly notify the ex (a join between messages and friend list -> time-dependence of joins). No simple answer. Starting points: (a) logical timestamps (total order without coordination, but receivers must still handle out-of-order delivery and metadata is carried); (b) log an event recording the state the user saw before deciding, give it a unique ID, and have later events reference it (causal dependency; returns in "Reads are events too"); (c) conflict-resolution algorithms (fix state but cannot undo external side effects like sent notifications). Hope: patterns will emerge that capture causality without total-order bottleneck.
- **Batch and stream processing.** Goal of integration = data ends up in the right form in all the right places (consume, transform, join, filter, aggregate, train models, write outputs). Outputs are derived datasets (search indexes, materialised views, recommendations, aggregate metrics). Main difference: stream = unbounded input, batch = finite; distinctions blur (Spark = streaming on microbatches; Flink = batch on a stream engine); microbatching performs poorly on hopping/sliding windows.
- **Maintaining derived state.** Batch has a functional flavour: deterministic pure functions, immutable inputs, append-only outputs; stream adds managed fault-tolerant state. Deterministic functions with explicit inputs/outputs aid fault tolerance and reasoning about org dataflows. Think "pipelines that derive one thing from another" whether the target is index, model or cache. Derived data could be sync (like DB secondary indexes in same txn), but async is what makes log-based systems robust: a fault stays local, whereas distributed transactions abort when any participant fails and amplify failures. Secondary indexes crossing partitions (term- or document-partitioned) are most reliable/scalable when maintained async.
- **Reprocessing data for application evolution.** Stream = low-delay reflection of changes; batch = reprocess large historical data into new views. Without reprocessing, schema evolution is limited to adding optional fields/record types (true for schema-on-write and schema-on-read). With reprocessing you can restructure a dataset into a different model. Railway analogy: converting track gauge by adding a third rail (dual gauge), letting old and new trains coexist until the old gauge is removed. Likewise keep old and new schema as two derived views; shift a small share of users to the new view, ramp up, eventually drop the old. Every stage is reversible -> less risk -> faster progress.
- **Lambda architecture.** Record immutable events in an append-only dataset; run a batch system (e.g., MapReduce) and a stream system (e.g., Storm) in parallel: stream gives a fast approximate view, batch later produces a corrected view (batch is thought simpler/less buggy; stream faster/approximate). Influential (popularised deriving views from immutable event streams and reprocessing). Problems: same logic maintained in two frameworks (operational complexity even with abstractions like Summingbird); merging the two outputs is easy for tumbling-window aggregates but hard for joins/sessionisation/non-time-series; full reprocessing is expensive so batch is made incremental, bringing back stragglers/window-boundary issues and making batch as complex as stream.
- **Unifying batch and stream** in one system needs: replay of historical events through the same engine as live events (replayable log brokers, or reading from HDFS); exactly-once semantics (discard partial output of failed tasks); windowing by event time not processing time (Apache Beam API, run on Flink or Google Cloud Dataflow).

### Unbundling Databases
- DBs, Hadoop and OSes all store and process data. Unix = thin low-level hardware abstraction (files/pipes as bytes); relational DB = high-level abstraction (SQL, transactions) hiding disk/concurrency/crash recovery. Both "simple" in different ways; the tension has lasted since the early 1970s; NoSQL read as applying Unix-style low-level abstraction to distributed OLTP storage. The section tries to combine the best of both.
- **Composing data storage technologies.** Databases offer secondary indexes, materialised views (precomputed cache of query results), replication logs, full-text indexes; batch/stream systems rebuild these same things outside the DB.
- **Creating an index.** CREATE INDEX = scan consistent snapshot, extract/sort values, write index, then process the backlog of writes since the snapshot, then keep updating. Same pattern as setting up a new follower replica and as bootstrapping CDC (initial snapshot + log). I.e. the DB reprocesses existing data and derives a new view.
- **The meta-database of everything.** Org-wide dataflow looks like one huge database; batch/stream/ETL jobs are like triggers, stored procedures and materialised-view maintenance; derived stores are like different index types (B-tree, hash, spatial) but run by different software on different machines/teams.
- Two avenues to compose tools: **Federated databases (unify reads)** — one query interface over many engines (polystore); e.g., PostgreSQL foreign data wrappers; apps can still use engines directly. Follows relational tradition: single system, high-level language, complicated implementation. **Unbundled databases (unify writes)** — make it easy to plug storage systems together so changes reach all the right places despite faults (CDC, event logs), like unbundling index maintenance; follows the Unix tradition (small tools, uniform low-level API = pipes, composed by a higher-level language = shell).
- **Making unbundling work.** Federation and unbundling are two sides of one coin. Read federation = data-model mapping (manageable); keeping writes in sync is the harder problem. Traditional answer (distributed transactions across heterogeneous stores) is judged wrong; within one system (e.g., stream processors' internal exactly-once) transactions are fine, but across systems built by different groups the lack of a standard protocol hurts. Use an async ordered event log with idempotent consumers: simpler abstraction, feasible across heterogeneous systems. Benefits = loose coupling: (1) system level — a slow/failed consumer just lags, the log buffers, producer and other consumers unaffected, consumer catches up later with no data loss (contrast: sync transactions escalate local faults); (2) human level — teams can develop/maintain components independently behind well-defined interfaces; logs are strong enough (durable, ordered) yet general.
- **Unbundled vs integrated.** Unbundling will not replace databases (still needed for stream-processor state and to serve query output; MPP warehouses stay best for exploratory analytics). Cost: each extra piece has learning curve/config/quirks; a single integrated product may be faster and more predictable for its workload; building for scale you don't need is premature optimisation. Unbundling is about breadth not depth. RULE: if one product does everything you need, use it; compose only when no single product satisfies your requirements.
- **What's missing.** No declarative "shell" for composing stores — wish: `mysql | elasticsearch` as the unbundled CREATE INDEX (index all docs, then continuously apply changes, no custom code). Similarly declarative precomputed caches (materialised views incl. recursive/graph queries and app logic); research such as differential dataflow.

### Designing Applications Around Dataflow
- The "database inside-out" approach (author's 2014 talk) — a design pattern, not a grand new architecture; draws on dataflow languages (Oz, Juttle), FRP (Elm), logic programming (Bloom); "unbundling" term credited to Jay Kreps. Spreadsheet analogy (VisiCalc 1979): change an input, dependent formulas recompute automatically; data systems should do the same for indexes/caches/aggregates but be fault-tolerant, scalable, durable, and integrate disparate tech/languages.
- **Application code as a derivation function.** Derived datasets come from transformation functions: secondary index (extract + sort), full-text index (NLP: language detection, stemming, synonyms, then inverted index), ML model (derived from training data via feature extraction; model outputs derived from input + model), cache (aggregation shaped like the UI; UI changes may need cache rebuild). Standard functions (CREATE INDEX) are built in; custom ones need application code — where DBs struggle: triggers/stored procs/UDFs exist but are an afterthought.
- **Separation of application code and state.** DBs make poor deployment environments for app code (dependency/package management, version control, rolling upgrades, monitoring, metrics, network calls, external integration); orchestration tools (Mesos, YARN, Docker, Kubernetes) do this better. Typical web apps are stateless services with state in the DB ("separation of Church and state"); the DB acts as a mutable shared variable accessed synchronously. Weakness: you can't subscribe to changes of that variable, only poll; DBs inherited the passive approach; change subscription is only starting to emerge.
- **Dataflow: interplay between state changes and application code.** Treat the DB's change log as an event stream; application code reacts to state changes in one place by causing changes elsewhere (similar to actors, tuple spaces, DB triggers/index updates). Maintaining derived data != generic async job execution: (1) ORDER of state changes often matters (all views must process events in the same order; many brokers lose order on redelivery; dual writes ruled out); (2) fault tolerance is key — losing one message leaves the derived set permanently out of sync; delivery and state updates must both be reliable (many actor systems keep state/messages in memory and lose them on crash). Stable ordering + fault-tolerant processing are stringent but cheaper and more robust than distributed transactions; modern stream processors provide them at scale and can run app code as operators, composed like Unix pipes.
- **Stream processors and services.** Microservices (sync REST) give organisational scalability via loose coupling; dataflow is similar but uses one-way async streams. Currency-conversion example: microservice approach queries an exchange-rate service per purchase; dataflow approach subscribes to the rate stream, keeps the current rate in a local DB and queries locally — faster and robust to the other service being down ("the fastest and most reliable network request is no network request"). It is a stream-table join, and time-dependent: reprocessing later needs the historical rate at purchase time. Footnote: a microservice could cache rates locally but must then poll/subscribe to keep fresh — which is the dataflow approach.

### Observing Derived State
- **Write path** = precomputed, eager work done as data arrives (through batch/stream stages until derived datasets are updated); **read path** = work done lazily only when someone asks. The derived dataset is where they meet; it trades write-time work against read-time work (analogy: eager vs lazy evaluation).
- **Materialized views and caching.** Search index: writes update index entries for each term; reads look up each query word and combine with AND/OR (synonyms). No index = cheap writes, expensive reads (grep-style scan). Precomputing all possible queries = cheap reads, infinite write cost. Middle: cache/materialise only common queries, serve the rest from the index (the cache must be updated when new documents affect those results). Role of caches/indexes/materialised views = shift the read/write boundary (echo of the Twitter timeline example, where celebrities are treated differently).
- **Stateful, offline-capable clients.** Question the stateless-client/authoritative-server assumption. Single-page JS apps and mobile apps hold lots of state; renewed interest in offline-first apps using a local DB and background sync (good on slow/unreliable mobile networks). Treat on-device state as a cache of server state; screen pixels = materialised view of client model objects; model objects = local replica of remote state.
- **Pushing state changes to clients.** A loaded web page is a stale cache unless polled (RSS = polling). Server-sent events (EventSource) and WebSockets let the server push; this extends the write path all the way to the end user. Initial load still uses a read path; afterwards a stream of changes. Offline devices handled like log consumers using offsets: reconnect and resume without missing messages — each device is a small subscriber to a small stream.
- **End-to-end event streams.** Elm, React/Flux/Redux already manage client state as event streams (event-sourcing-like); natural to let the server push state-change events into that pipeline, giving low-delay (~<1s) propagation from one device's interaction through logs and derived systems to another user's screen. Chat and games already do this. Why not everywhere? Request/response and stateless-client assumptions are baked into DBs, libraries, protocols; few datastores offer subscribe-to-changes. Author hopes designers keep "subscribe to changes, not just query current state" in mind.
- **Reads are events too.** A store is the boundary between write and read paths; stream processors' own state can sometimes be queried externally (stream processor as a simple DB). Further idea: represent read requests as events too, send reads and writes through the same stream operator, which emits read results to an output stream — i.e. a stream-table join between the query stream and the DB (read events must be routed to the partition holding the data, like co-partitioned join inputs).

- (Reads are events too, cont.) Serving a request == performing a join: a one-off read passes through the join and is forgotten; a subscribe request is a persistent join over past and future events. Logging read events (what the user saw) helps track causal dependencies and data provenance; example: online shop — displayed shipping date and inventory status influence a purchase, so to analyse the decision you must record what the query returned. Cost = extra storage/IO; optimising is open research; if you already log reads for ops, making the log the source of requests is a small step.
- **Multi-partition data processing.** For single-partition queries, streaming the query is overkill; for queries combining many partitions it reuses stream infrastructure (routing, partitioning, joining). Examples: Storm distributed RPC computing the number of people who saw a URL on Twitter (union of followers of all who tweeted it, across partitions); fraud scoring a purchase by joining reputation databases for IP, email, billing and shipping address (each partitioned differently). MPP DBs do the same internally; prefer a database offering this feature rather than hand-building on a stream processor, but the stream approach is an option at the limits of off-the-shelf tools.

### Aiming for Correctness
- Stateless read-only services are easy to fix (patch and restart); stateful systems remember for ever, so errors last. Four decades of ACID transactions as the tool of choice, but weaker than they look (weak isolation level confusion); some areas abandon transactions for messier models (leaderless replication); "consistency" is poorly defined; "embrace weak consistency" is said without clarity. Hard to know whether an app is safe at a given isolation/replication config; naive solutions look right under low concurrency/no faults and hide subtle bugs. Jepsen tests show gaps between claimed and actual guarantees; even if the DB is right, app code must use features correctly (hard with weak isolation, quorums). If you can tolerate occasional unpredictable corruption/loss, life is simpler; otherwise serializability + atomic commit work but usually only within one datacenter and cap scale/fault tolerance. Traditional transactions are not the last word.

#### The End-to-End Argument for Databases
- A strong data system (serializable txns) does not protect you from app bugs that write wrong data or delete data; hence the argument for immutable, append-only data (easier recovery). Immutability is not a cure-all.
- **Exactly-once execution.** On failure you drop (data loss) or retry (risk of double processing). Double processing is corruption (double charge, double-counted metric). "Exactly-once" = final effect as if no fault. Best tool: make the operation **idempotent** (same effect once or many times); making a non-idempotent op idempotent needs metadata (e.g., set of operation IDs that have updated a value) and fencing on failover.
- **Duplicate suppression.** TCP dedups via sequence numbers but only within one connection. Example 12-1 (non-idempotent money transfer: +11 to account 1234, -11 from 4321, COMMIT): if the connection drops after COMMIT is sent, the client doesn't know whether it committed; a retry on a new connection could transfer $22. Real banks do not work like this. 2PC breaks the 1:1 connection/transaction mapping but still doesn't cover the end-user hop: a browser POST on weak cellular signal that times out; user resubmits ("Are you sure you want to submit this form again?" — the Post/Redirect/Get pattern does not help if the POST itself times out); server and DB see a separate request/transaction, so usual dedup fails.
- **Operation identifiers.** Make it idempotent across all hops with an end-to-end ID: generate a UUID as a hidden form field (or hash of the relevant form fields) and carry it all the way to the DB; Example 12-2: `ALTER TABLE requests ADD UNIQUE (request_id)`, insert the request row in the same transaction as the balance updates; a duplicate ID makes the INSERT fail and aborts the txn. Uniqueness constraints are maintained correctly even at weak isolation, unlike app-level check-then-insert (write skew / phantoms). The requests table doubles as an event log -> hints at event sourcing; the balance updates could be derived downstream, if processed exactly once, again enforced by request ID.
- **The end-to-end argument (Saltzer, Reed, Clark 1984).** A function can be completely and correctly implemented only with the knowledge and help of the application at the endpoints; communication-layer versions are at best performance enhancements. Applies to duplicate suppression (TCP, DB txns, stream-processor exactly-once each insufficient alone), to integrity checks (Ethernet/TCP/TLS checksums miss bugs in sender/receiver software and disk corruption; need end-to-end checksums) and to encryption (home Wi-Fi password blocks local snoopers only; TLS blocks network attackers but not server compromise; only end-to-end encryption/authentication covers all). Low-level features still help because they lower the probability of higher-level problems.
- **Applying end-to-end thinking in data systems.** The app must take end-to-end measures (dedup) even atop strong stores. Transactions collapse many failure kinds into commit/abort — a big simplification, but expensive (especially heterogeneous), so when we refuse distributed transactions we reimplement fault tolerance in app code, and the author suspects most such mechanisms are incorrect -> lost/corrupted data. Calls for fault-tolerance abstractions that make application-specific end-to-end correctness easy while keeping performance and operability.

#### Enforcing Constraints
- Uniqueness-style constraints: unique usernames/emails, unique filenames, no double-booked seat, non-negative balance, no overselling stock, no overlapping room bookings; techniques for uniqueness extend to these.
- **Uniqueness requires consensus** in a distributed setting (decide which concurrent conflicting op wins). Usual way: single leader decides (funnel all requests, a failure brings you back to consensus). Scale out by partitioning on the value that must be unique (request ID; hash of username). Async multi-master replication is ruled out (conflicting writes accepted concurrently); if you want to reject violating writes immediately, synchronous coordination is unavoidable.
- **Uniqueness in log-based messaging.** Log gives total order == consensus. A stream processor consumes each log partition sequentially on one thread. Username claim: (1) request appended as message to partition chosen by hash of username; (2) processor reads sequentially, keeps a local DB of taken names, emits success or rejection to an output stream; (3) client watches the output stream for its result. Scales with partition count; general principle: route all potentially conflicting writes to the same partition and process sequentially; the processor can apply arbitrary validation logic. Similar to Bayou (1990s).
- **Multi-partition request processing.** Transfer touches request-ID, payer and payee partitions. Traditional = atomic commit across three partitions (forces a total order, hurts throughput). Alternative without atomic commit: (1) client gives the transfer a unique request ID and appends it as one message to a log partition by request ID; (2) a stream processor reads it and emits a debit instruction (partitioned by payer A) and a credit instruction (partitioned by payee B), each carrying the request ID; (3) further processors consume debit/credit streams, dedupe by request ID, apply to balances. Single-object (single message) writes are atomic nearly everywhere, so no multi-partition commit needed. Processor crash -> resumes from checkpoint, may re-emit duplicates, but deterministic so same output, deduped downstream by request ID. Overdraft protection: a processor partitioned by payer account keeps balances and validates; only valid requests enter the request log. Result: each request applied exactly once to both accounts despite faults, no atomic commit.

#### Timeliness and Integrity
- Transactions are typically linearizable (writer waits for commit, then visible). Unbundled multi-stage stream pipelines are asynchronous; a client can still wait for a message on an output stream (as in the username example) — and correctness doesn't depend on that waiting, it only informs the sender.
- "Consistency" conflates two things: **Timeliness** (users see up-to-date state; staleness is temporary and resolved by waiting/retrying; linearizability is the strong form, read-after-write a weaker useful one) and **Integrity** (no corruption: no data loss, no contradictory or false data; derived views must be correctly derived; violations are permanent and need explicit checking and repair; ACID "C" is app-specific integrity, supported by atomicity and durability). Slogan: timeliness violations = "eventual consistency"; integrity violations = "perpetual inconsistency". Integrity matters much more than timeliness in most apps (credit-card statement lag is normal; wrong sums or money charged but not paid to the merchant is catastrophic).
- **Correctness of dataflow systems.** ACID gives both; event-based dataflow decouples them: no timeliness guarantee unless you build waiting consumers, but integrity is central. Exactly/effectively-once and duplicate suppression preserve integrity. Reliable stream processing preserves integrity without distributed transactions via: (a) write content as a single atomic message (event sourcing); (b) derive all other state updates from it with deterministic functions (like stored procedures); (c) pass a client-generated request ID through all levels for end-to-end dedup/idempotence; (d) immutable messages with periodic reprocessing of derived data to recover from bugs. "Very promising direction for fault-tolerant applications".
- **Loosely interpreted constraints.** Uniqueness needs consensus and funnelling via one node — unavoidable for the traditional form. But many businesses accept weaker uniqueness plus apology: duplicate username/seat -> apologise and ask to choose again (**compensating transaction**); oversold stock -> reorder, apologise, discount (same workflow as forklift damage); airlines/hotels deliberately overbook with refund/upgrade processes (needed anyway for cancellations/strikes); bank overdraft fees with a daily withdrawal limit to bound risk. Often cheap to apologise (can't unsend an email but can send a correction; double charge -> refund). Whether an apology's cost is acceptable is a business decision; if so, writing optimistically and checking after the fact is fine — but validate before things expensive to recover from. These apps still need integrity (no lost reservations, no vanishing money) but not timeliness of constraint enforcement.
- **Coordination-avoiding data systems.** Two observations: dataflow can keep integrity on derived data without atomic commit, linearizability or cross-partition sync coordination; and many apps tolerate loose constraints fixed up later if integrity holds. So many apps can be served without coordination, with strong integrity: better performance and fault tolerance, e.g. multi-leader across datacenters with async replication; each DC works alone; weak timeliness, strong integrity. Serializable transactions remain useful at small scope for derived state; heterogeneous XA not needed; add synchronous coordination only where unrecoverable actions demand it. Trade-off view: constraints reduce apologies from inconsistency but may raise apologies from outages; find the sweet spot.

#### Trust, but Verify
- Our system model assumes some faults can happen (crashes, power loss, network delays) and others (fsync'd data lost, memory corruption, CPU arithmetic wrong) can't; in reality it's probabilistic. Disk data can corrupt while idle; network corruption can evade TCP checksums. Author's crash-report example: some reports only explained by random bit flips; rowhammer shows pathological access patterns can flip bits (and break OS security). Still rare on modern hardware, but not impossible.
- **Maintaining integrity despite software bugs.** Even MySQL (failing to maintain a uniqueness constraint) and PostgreSQL (serializable isolation showing write skew) have had bugs; less mature software is worse; app code is reviewed/tested far less and often fails to use integrity features (foreign keys, unique constraints) properly. ACID consistency assumes bug-free transactions; misuse (e.g., unsafe weak isolation) voids it.
- **Don't blindly trust what they promise.** Assume corruption will eventually happen; need to detect it, fix it, find the source: **auditing**. Important in finance because mistakes are expected, but auditing is not only for finance. HDFS and S3 don't fully trust disks: background processes read files back, compare replicas, move files. To know data is there, read and check it; test restoring backups periodically, else you find a broken backup too late.
- **A culture of verification.** Few systems continuously self-audit; many treat guarantees as absolute. ACID culture bred blind trust and neglect of auditability; when NoSQL/weaker guarantees and immature stores arrived, no audit mechanisms existed, making blind trust more dangerous. Hope for self-validating/self-auditing systems.
- **Designing for auditability.** Multi-object transaction logs/CDC don't explain why mutations happened; the app logic invocation is transient. Event sourcing: user input = one immutable event, state updates derived deterministically and repeatably (same log + same code version = same state). Explicit dataflow clarifies provenance, making integrity checks feasible: hash the event store to detect corruption; rerun batch/stream derivations to check results match, or run a redundant derivation in parallel. Deterministic dataflow also enables debugging/tracing and "time-travel debugging" to reproduce the exact circumstances.
- **End-to-end argument again.** Check integrity end to end: the more systems inside the check, the fewer places corruption can hide; verifying a whole derived pipeline implicitly covers disks, networks, services and algorithms. Continuous end-to-end checks give confidence to move faster, like automated tests; fear of change is reduced.
- **Tools for auditable data systems.** Few systems make audit top-level; some apps write all changes to a separate audit table, but guaranteeing audit-log vs DB-state integrity is hard; signing a transaction log with an HSM prevents tampering but not wrong entries going in. Cryptocurrencies/blockchains/distributed ledgers (Bitcoin, Ethereum, Ripple, Stellar) are distributed DBs whose replicas, hosted by mutually untrusting organisations, check each other and use consensus. Author is skeptical of Byzantine tolerance and finds proof-of-work wasteful, Bitcoin throughput low (for political/economic reasons) — but integrity-checking ideas interesting. **Merkle trees** (trees of hashes) efficiently prove a record is in a dataset; certificate transparency uses them to check TLS certificates. Expect such auditing algorithms to spread to general data systems once scalable and low overhead.

### Doing the Right Thing
- Frame: every system has a purpose and unintended consequences; engineers carry responsibility to decide what world they build. Datasets are about people: treat with humanity and respect; "users are humans too". ACM Software Engineering Code of Ethics exists but is rarely discussed/applied/enforced; engineers and PMs are often cavalier about privacy. Technology is not good or bad itself (search engine like a gun): consequences are ours to bear.
- **Predictive analytics.** Weather/disease prediction is one thing; predicting reoffending, loan default, insurance claims, or whether to hire affects individual lives. Organisations are risk-averse (cost of missed opportunity low vs cost of a bad loan/employee high), so "if in doubt, say no". Someone labelled risky (accurately or not) may suffer many "no"s — jobs, travel, insurance, rental, finance — "algorithmic prison"; unlike criminal justice (presumption of innocence), automated systems can exclude someone without proof of guilt or real appeal.
- **Bias and discrimination.** Algorithms are not inherently better or worse than humans; hope that data could be fairer to the overlooked. But rules are inferred from data and opaque; systematic bias in input is learned and amplified. Protected traits (ethnicity, age, gender, sexuality, disability, belief) are protected by law; correlated features (postal code, IP address as race proxy) leak them. Belief that biased data yields fair output is delusional ("machine learning is like money laundering for bias"). Predictive systems extrapolate the past and codify its discrimination; improving the future needs human moral imagination: "data and models should be our tools, not our masters".
- **Responsibility and accountability.** Who is accountable when an algorithm errs (self-driving crash; discriminatory credit scoring)? Can you explain a model's decision to a judge? Credit scores summarise "how did you behave"; ML scoring asks "who is similar to you and how did they behave" -> stereotyping (e.g., by where you live), wrong-bucket problems, almost no recourse for bad data. Statistical outputs can be right on average and wrong for an individual (life-expectancy 80 doesn't mean you die at 80). Need accountability, transparency, bias avoidance, and fixes; also prevent predatory use (targeting vulnerable people for high-cost loans, worthless degrees) vs using insight to direct aid.
- **Feedback loops.** Recommenders create echo chambers (stereotypes, misinformation, polarisation, election impact). Self-reinforcing loops: employers screen on credit score -> a misfortune hurts your score -> harder to get work -> poverty -> worse score. Can't always predict, but "systems thinking" (include humans in the system) helps: does it amplify existing differences or combat injustice? Beware unintended consequences.
- **Privacy and tracking.** If a system stores only what the user entered for a purpose, the user is the customer. When activity is tracked as a side effect, the service acquires interests of its own that may conflict with the user's. Some tracking benefits users (search ranking from clicks, "people who liked X", A/B tests, flow analysis). With ad funding, advertisers are the customers; tracking gets more detailed, data kept long to build profiles; the user is coaxed to engage; author calls this **surveillance**.
- **Surveillance.** Thought experiment: replace "data" with "surveillance" ("surveillance warehouse", "surveillance scientists"). We have built the biggest mass-surveillance infrastructure ever (phones, smart TVs, voice assistants, baby monitors, toys; IoT with poor security) — a microphone in every room that repressive regimes could only dream of; difference is that corporations collect it. Why accept it? "Nothing to hide" is a privilege of those aligned with power structures; benign purpose (recommendations) blurs when linked to predictive analytics; car insurance via trackers, health cover via fitness devices; analysis can be surprisingly intrusive (smartwatch motion sensors can infer what you type, e.g., passwords); algorithms will improve.
- **Consent and freedom of choice.** "They agreed to terms" is weak: users don't know what data is fed in, retained, processed; privacy policies obscure; no meaningful consent without understanding; data about one user also reveals non-users who never agreed; derived datasets mixing the whole user base, tracking and external sources are exactly what users cannot understand. Relationship is one-way extraction, asymmetric, no negotiation; opting out is not free when a service is regarded as essential for social participation (network effects); real choice only for the privileged with time/knowledge — for others surveillance is inescapable.
- **Privacy and use of data.** "Privacy is dead" misunderstands: privacy = freedom to choose what to reveal to whom (a decision right), not secrecy of everything. Surveillance transfers that right to the collector ("trust us"). Firms keep outcomes secret (would seem creepy), revealing intimate info only indirectly (ad-targeting to e.g. people with an illness); even without re-identification, users lose agency over disclosure. Companies manage perceptions of creepiness rather than intrusiveness; correct data can still be unwelcome (painful memories). Expect data to be wrong/undesirable/inappropriate and build mechanisms to handle those failures; algorithms don't understand "inappropriate" unless programmed — be humble. Privacy settings controlling what other users see are a start but the service itself has unfettered access, bounded only by its policy (usually broad internal processing, even if it promises not to sell). Historical difference: surveillance used to be costly and manual; trust relationships (doctor, attorney) were governed by ethical/legal/regulatory limits — internet services amass sensitive data without meaningful consent and use it at massive scale.
- **Data as assets and power.** "Data exhaust" framing is wrong: for ad-funded services behavioural data IS the core asset and the app is bait to feed more data. Evidence: data brokers (secretive industry buying, aggregating, inferring, reselling); startups valued on "eyeballs". Governments want it too (deals, coercion, legal compulsion, theft); bankrupt companies sell their data; breaches are frequent. Hence "toxic asset" (Schneier) or "hazardous material" (balance need vs want). When collecting, consider benefit vs risk of it falling into the wrong hands: criminals, hostile intelligence, insider leaks, unscrupulous new management, a future regime that compels handover. Consider all possible future governments: "poor civic hygiene to install technologies that could someday facilitate a police state". Knowledge is power; scrutinising others while avoiding scrutiny is power; tech firms' accumulated knowledge gives surreptitious power outside oversight.
- **Remembering the Industrial Revolution.** Information age ~ industrial revolution: big long-term gains but pollution, exploitation, child labour; safeguards (environmental rules, workplace safety, child labour bans, food inspection) came late and raised costs yet benefited society. Schneier: data is the pollution problem of the information age; privacy protection is the environmental challenge; how we contain and dispose of data is central; future generations will judge us.
- **Legislation and self-regulation.** 1995 EU Data Protection Directive: personal data must be collected for specified, explicit, legitimate purposes, not processed incompatibly, and be adequate, relevant, not excessive (data minimisation/purpose limitation). Doubtful effectiveness: runs against Big Data's maximise-collect-and-explore ethos (unforeseen purposes vs specified purposes; meaningful consent doubtful); updated regulations in development. Companies resist regulation as hindering innovation — partly fair (e.g., medical data sharing could save lives; overregulation could block it; hard balance). Author's call for a culture shift: stop treating users as metrics to optimise; respect, dignity, agency; self-regulate collection/processing to earn trust; educate end users about use of their data; the individual right to control data is like a national park — unprotected, it will be destroyed (tragedy of the commons); surveillance is not inevitable. Concrete directions: **do not retain data forever — purge as soon as no longer needed** (conflicts with immutability, but solvable); enforce access control through **cryptographic protocols rather than only policy**; cultural change needed overall.

### Summary (chapter)
- No single tool serves all uses -> compose tools; solve integration with batch + event streams; designate systems of record and derive everything else (indexes, materialised views, ML models, summaries); asynchronous, loosely coupled derivation contains faults; rerun new transformation code on the whole input to evolve or to recover from bugs; this is unbundling a database; derived state can itself be observed downstream, all the way to end-user devices (UI updating live, working offline). Correctness: strong integrity achievable scalably with async event processing, end-to-end operation IDs for idempotence and async constraint checks; clients can wait for the check or proceed and risk apologising; more scalable and robust than distributed transactions and matches real business processes; avoid most coordination, even across datacenters; audits verify integrity and detect corruption. Ethics: data can do good or serious harm (hard-to-appeal decisions, discrimination, exploitation, normalised surveillance, intimate-info exposure, breaches, unintended consequences); engineers must work toward a world that treats people with humanity and respect.

## Failure modes / pitfalls (consolidated)
- Dual writes to DB + search index/cache: conflicting writes land in different order in each -> permanent divergence.
- Losing a single event/message in derived-data pipelines -> derived data out of sync forever; brokers that reorder on redelivery; in-memory actor state lost on crash.
- Treating async job-queue semantics as sufficient for derived data (order and durability matter).
- Distributed (XA) transactions: poor fault tolerance/performance; failures amplify.
- Missing causal dependencies across stores (unfriend then message -> wrong notification); conflict resolution can't undo external side effects (emails/notifications).
- Lambda architecture: two codebases, hard output merge, incremental batch complexity.
- Non-idempotent retries (double charge, double increment); relying on TCP/DB/stream-processor dedup only at their own layer; check-then-insert uniqueness under weak isolation.
- Believing strong isolation (serializable) protects from app bugs or from client-visible duplicates.
- Enforcing uniqueness with async multi-master replication.
- Blind trust in hardware/software/backups; never testing restores; no audit trail; audit table whose integrity vs data is unverifiable; signing a log doesn't guarantee correct entries.
- Predictive systems encoding historic bias; proxy features (postal code/IP) for protected traits; no recourse/explainability; feedback loops; statistical-average-vs-individual errors.
- Surveillance by default, meaningless consent, unbounded retention, data as toxic asset (breach, bankruptcy sale, future-regime access); treating "privacy is dead".

## Key terms (one line each)
- System of record / source of truth: authoritative store where writes first land; others derive from it.
- Derived data: dataset rebuilt from other data by a repeatable function (index, cache, view, model).
- Total order broadcast: delivering all messages to all nodes in the same order; equivalent to consensus.
- CDC / event sourcing: two ways to produce an ordered log of changes from which derived data is built.
- Unbundling / "database inside-out": splitting a DB's internals (index maintenance, views) into separate loosely coupled systems joined by logs.
- Federated database (polystore): one read interface over many stores.
- Write path / read path: eager precomputation at write time vs lazy work at query time; caches/indexes/views move the boundary.
- Lambda architecture: parallel batch (exact, late) + stream (approximate, fast) pipelines over immutable events.
- End-to-end argument: some guarantees (dedup, integrity, encryption) can only be fully provided by the endpoint application.
- Operation / request ID: client-generated unique ID passed through every hop to make retries idempotent.
- Idempotence / exactly-once (effectively-once): same final effect no matter how many times an operation is executed.
- Compensating transaction / apology: after-the-fact correction of a violated constraint.
- Timeliness vs integrity: freshness of what is seen (temporary staleness) vs absence of corruption (permanent if broken).
- Coordination-avoiding data system: keeps integrity without synchronous cross-node coordination; accepts weak timeliness.
- Auditing / self-validating system: continually re-checking that stored data and derivations are intact.
- Merkle tree: tree of hashes for efficient proof of record membership/integrity (used in certificate transparency).
- Algorithmic prison: systematic exclusion by automated risk labels.
- Data exhaust / toxic asset: behavioural by-product reframed as core, hazardous asset.
- Privacy (decision right): freedom to choose what to reveal to whom.

## Relevance to a multi-tenant SaaS on Node/Express + single managed Postgres (Supabase) that sends recruiting/sales email and stores personal data of candidates/contacts

### Correctness: request IDs, idempotence, auditing
- Biggest lever: the end-to-end argument maps directly onto email sending. A browser click -> Express -> Postgres -> email provider (Outlook/Gmail) is exactly the multi-hop chain where a timeout leaves "did it send?" unknown. Pattern from Example 12-2: client (or send-loop) generates a stable operation/idempotency key per intended send (e.g., per org + candidate/contact + template/campaign step), insert it into a table with a UNIQUE constraint in the same transaction that claims the send, and let the unique violation be the dedup. This is the single-Postgres version of "request_id UNIQUE"; no consensus problem because one DB. Cheap now, painful to retrofit. It supports PACE's existing double-send guard and the 'sending' -> "Didn't send" boot recovery: a claim row with a state machine (pending -> sending -> sent/failed/uncertain) is the event-log analogue.
- Uncertain outcomes: the chapter says a timed-out call has unknown result and retrying a non-idempotent op duplicates it. Outbound email provider APIs (e.g., Graph sendMail) are not idempotent, so the only safe policy is the one PACE already holds: never auto-retry an uncertain send; retry only provably temporary failures; surface "uncertain" to the user. A provider-side idempotency token (if offered) or a provider-id lookup (check Sent folder / message-id) is the "verify before retry" step.
- Use the chapter's "single atomic record, derive the rest" idea: write one durable row/event for the user's intent (send requested) and derive follow-ups, counters, tracking and UI state from it deterministically; this makes recomputation/repair of derived tables (email history merge views, counts like submissions per stage, conversation-intel queues) possible and auditable. Derived views (search index, counters, caches) should be rebuildable from the system of record; avoid dual writes (e.g., writing to the DB and to a cache/search/analytics/CRM at the same time from request handlers) — write to Postgres, then derive via a job/queue or LISTEN/NOTIFY/outbox table so there is one ordering authority.
- Outbox pattern fits Supabase: transactional "outbox" rows written with the business change, processed by a worker with idempotent consumers (dedup by id). This is the practical single-DB form of log-based integration and avoids 2PC.
- Webhooks/inbound events (billing webhook, mail-scanner link fetches, replies): treat as at-least-once; dedupe by provider event id; make handlers idempotent; order not guaranteed -> store event timestamps and tolerate out-of-order.
- Timeliness vs integrity: for this product integrity (no lost candidate, no double email, no mislabelled stage, no cross-tenant leak, counts add up) outranks timeliness (a dashboard count a minute stale is fine). That justifies async derived counters/briefings and strict DB constraints (UNIQUE, FK, CHECK, NOT NULL, RLS) as the integrity backbone — the chapter notes apps often fail to use DB constraints; push uniqueness (org_id + email, org + request key) into the schema rather than check-then-insert in Node (race under concurrency at default Read Committed).
- Loosely interpreted constraints/apologies: mailbox daily limits, seat/plan limits, duplicate-contact detection can be soft (enforce and reconcile, with an apology/"merge" flow) except for irreversible actions (sending an email can't be unsent -> validate BEFORE sending; follow-up correction email is the "apology"). Matches "validate before things expensive to recover from."
- Auditing: keep an append-only audit/event table (who/what/when/before-after, request id, org_id) written in the same transaction as the change; make it insert-only (revoke UPDATE/DELETE, RLS) and consider hash-chaining rows for tamper evidence; propagate a request/correlation id from the browser through Express logs, DB rows and outbound provider calls (and Sentry) so any outcome can be traced end to end. "Trust but verify": periodic reconciliation jobs (sent rows vs provider sent items; counts vs source rows; orphan checks; per-tenant row-count/RLS checks), plus real restore drills of Supabase backups. Free-tier note: schedule these sparingly (hard instance-hours budget).
- Time-dependent joins: store the template/version, merge-field values and mailbox identity used at send time (PACE already keeps stored bodies with {{sender}} resolved at send), and snapshot facts (stage, owner, exchange rate-like data) used for decisions, so history can be reconstructed; "reads are events too" argues for logging what an AI/rule showed a recruiter before an action (explainability for scoring/ranking).
- Schema/data evolution: run old and new schema/view side by side (expand/contract migrations, dual-read views) and shift gradually, with reversibility — consistent with 'apply migration before code that uses it'.
- Keep it simple: the chapter itself says use one integrated product if it does what you need; a single Postgres plus an outbox covers the realistic needs; do not adopt Kafka/event-streaming infra now.

### Ethics / privacy (candidates and contacts — high relevance)
- Recruiting is a textbook "predictive analytics affecting people's lives" domain: candidate match scores, applicant scores, ranking, auto-rejection and AI drafts can create an "algorithmic prison" and encode bias (proxy features such as postal code, names, school, employment gaps, age cues). Implications: keep a human decision-maker for stage moves and rejections; show score reasons (explainability) and allow correction; never use protected traits or obvious proxies; log inputs/versions behind each score (audit); give a candidate-facing path to correct/contest data; keep "—" rather than a fake 0 for unknown (already PACE policy); test for disparate impact periodically; make rules-first scoring inspectable (an advantage over opaque ML).
- Consent and purpose limitation: candidate data collected for one job/application should not be silently reused for unrelated marketing or cold outreach; record the lawful basis/consent and source per person (applied via link, imported, sourced from a vendor, scraped) and honour it; sourced contacts who never agreed to anything are exactly the "non-user whose data is in the system" problem. Provide clear, plain-language notices on public apply pages; opt-out must be one click and permanent (suppression list, honour across tenants/campaigns for that address and across all three email pipelines); the chapter's point that "opting out isn't free" applies to candidates who need a job: do not make applying conditional on marketing consent.
- Data minimisation: collect only fields the recruiting purpose needs; avoid storing sensitive categories (health, ethnicity, religion, etc.) unless legally required; avoid tracking beyond what the feature needs (email open tracking pixels and link tracking are surveillance-adjacent — be transparent, prefer click-on-explicit-action; PACE already avoids recording scanner fetches); don't enrich/profile contacts beyond need.
- Retention and purge: chapter says don't keep data forever; define per-tenant retention (e.g., inactive candidates auto-expire or are reviewed after N months; rejected applicants shorter), scheduled purge/anonymisation jobs, deletion on request (erasure) that cascades to derived copies (search indexes, caches, analytics, resume files in the storage bucket `candidate-docs`, email bodies, backups' eventual expiry), and a documented tension with immutable audit logs (keep audit entries but redact/crypto-erase the personal payload). Remember GDPR/DPDP-type rights (access, rectification, erasure, portability, objection to automated decisions) since customers span US + India; the platform is a processor and the customer is the controller — need DPA, sub-processor list (Supabase, Render, email providers, AI providers, Apollo/JSearch), data-region awareness, and ability to export/delete a tenant on offboarding.
- Security as ethics: personal data is a "toxic asset"; breaches, insider access and acquisition risk are real. Controls: RLS everywhere (already), least-privilege roles (already "who sees what"), encryption of secrets/keys per customer, encrypt or minimise highly sensitive fields, access logging for views/exports of candidate records, short-lived signed URLs for resumes, rate limits on export, tenant isolation tests, breach-response plan. Cryptographic access control (chapter's suggestion) maps to per-tenant keys / column encryption for the most sensitive items.
- AI use: sending candidate data to third-party model APIs is a disclosure; minimise/redact what is sent, keep it per-tenant opt-in (already rules-first and admin-controlled), record that a draft was AI-assisted, and check outputs (already). Avoid fully automated adverse decisions.
- Feedback loops: ranking by past recruiter behaviour can entrench bias (who got submitted before); recency/engagement-based prioritisation can bury under-served candidates; periodically audit outcomes by cohort.
- Commercial framing: since the product is sold to other companies, ship privacy and audit as features (retention settings, consent log, suppression, export/delete, audit trail view, subprocessor page) — both an ethical stance and a competitive/enterprise-sales requirement.

# GLOSSARY (paraphrased, one line each; book says its definitions are deliberately short)
- asynchronous: not waiting for something (e.g., a network send) to finish and assuming nothing about how long it takes.
- atomic: (1) concurrent sense — an operation appears to take effect at one instant, never seen half-done; (2) transaction sense — a group of writes all commit or all roll back, even through faults.
- backpressure (= flow control): making a sender slow down because the receiver cannot keep up.
- batch process: computation over a fixed, usually large input producing output without modifying the input.
- bounded: having a known upper limit (of delay or dataset size).
- Byzantine fault: a node that misbehaves arbitrarily, e.g., sends contradictory or malicious messages.
- cache: component holding recently used data to speed up repeat reads; usually incomplete, so misses go to slower complete storage.
- CAP theorem: widely misunderstood theoretical result the author considers not useful in practice.
- causality: dependency between events where one "happens before" another (a response to, built on, or to be understood in light of an earlier one).
- consensus: getting several nodes to agree on something (e.g., who is leader); much harder than it looks.
- data warehouse: database combining data from several OLTP systems prepared for analytics.
- declarative: describing the properties wanted, not the steps; a query optimiser decides execution.
- denormalize: add redundancy (cache/index) to a normalised dataset to speed reads; a precomputed query result, like a materialised view.
- derived data: data produced from other data by a repeatable process that could be rerun; indexes, caches, materialised views.
- deterministic: always the same output for the same input — no dependence on randomness, clock, network, etc.
- distributed: running on several networked nodes, marked by partial failures where it is often unclear what is broken.
- durable: stored so that it is believed to survive faults.
- ETL (Extract-Transform-Load): pull data from a source DB, reshape for analytics, load into a warehouse or batch system.
- failover: in single-leader systems, moving the leader role to another node.
- fault-tolerant: able to recover automatically from things like machine crashes or link failures.
- flow control: see backpressure.
- follower: replica that takes no client writes, only applies changes from the leader (secondary, slave, read replica, hot standby).
- full-text search: keyword search over text, often with fuzzy/synonym matching; a full-text index is a kind of secondary index.
- graph: data structure of vertices (nodes/entities) and edges (relationships/arcs).
- hash: function mapping input to a random-looking number, deterministic, with rare collisions.
- idempotent: safe to retry; executing more than once has the same effect as once.
- index: structure for efficiently finding all records with a given field value.
- isolation: how far concurrently running transactions can interfere; serializable is strongest, weaker levels common.
- join: bringing together records with something in common, typically following a reference (foreign key, document reference, graph edge).
- leader: the designated replica allowed to make changes (primary/master), elected or chosen by an admin.
- linearizable: behaving as if there were a single copy of the data updated by atomic operations.
- locality: performance technique of storing data together when it is often needed together.
- lock: ensures only one thread/node/transaction accesses something while others wait.
- log: append-only file — write-ahead log (crash safety), log-structured storage, replication log, or event log for streams.
- materialize: compute eagerly and store the result rather than computing on demand.
- node: an instance of software on a computer that talks to others over a network.
- normalized: structured without redundancy, so a change is made in one place only.
- OLAP: online analytic processing — aggregating over many records.
- OLTP: online transaction processing — fast queries reading/writing few records, usually by key.
- partitioning (sharding): splitting a dataset or computation across machines.
- percentile: threshold such that a given percent of values fall below it (e.g., p95 response time).
- primary key: unique record identifier, usually system-generated.
- quorum: minimum number of nodes that must vote for an operation to count as successful.
- rebalance: moving data or services between nodes to even out load.
- replication: keeping copies of the same data on several nodes for availability.
- schema: description of data structure (fields, types), checkable at various times and evolvable (Chapter 4).
- secondary index: extra structure kept alongside primary storage to find records matching other conditions.
- serializable: concurrent transactions behave as if executed one at a time in some serial order.
- shared-nothing: architecture of independent nodes with own CPU/memory/disk joined by an ordinary network.
- skew: (1) uneven load across partitions (hot spots); (2) timing anomaly making events appear out of order (read skew, write skew, clock skew).
- split brain: two nodes simultaneously believe they are leader, risking violated guarantees.
- stored procedure: transaction logic encoded to run entirely on the DB server without client round trips.
- stream process: continuously running computation consuming an endless event stream to derive output.
- synchronous: opposite of asynchronous.
- system of record (source of truth): holds the authoritative version; changes written here first, other datasets derived.
- timeout: simplest fault detector — no response within a time; cannot tell node failure from network problem.
- total order: comparison where any two items can be ranked; if some are incomparable it is a partial order.
- transaction: grouping reads and writes into one logical unit to simplify error handling and concurrency.
- two-phase commit (2PC): algorithm making several DB nodes all commit or all abort a transaction.
- two-phase locking (2PL): serializable-isolation algorithm: lock everything read/written and hold until transaction end.
- unbounded: no known upper limit; opposite of bounded.
