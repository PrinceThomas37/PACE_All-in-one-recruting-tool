# CHAPTER 7 — Transactions

## Core argument
Many things go wrong in data systems: the database or app crashes mid-write, the network cuts off, many clients write at once, readers see half-finished updates. Handling all of these by hand is huge work. A transaction groups several reads/writes into one logical unit that either fully commits or aborts (rolls back), so the app can ignore partial failure and simply retry. Transactions are not a law of nature, and not every app needs them; the NoSQL wave wrongly claimed they are the enemy of scalability, while vendors wrongly claim they are mandatory for "serious" data. Both are hyperbole. The meat of the chapter is isolation: most databases use weak isolation levels (read committed, snapshot isolation) that stop some race conditions but not others (lost updates, write skew, phantoms), and these bugs are nondeterministic and hard to test. Only serializable isolation prevents all of them, and there are three ways to get it: literal serial execution, two-phase locking (2PL), and serializable snapshot isolation (SSI), each with different costs.

## The Slippery Concept of a Transaction
- Almost all relational DBs follow the style of IBM System R (1975); MySQL, PostgreSQL, Oracle, SQL Server are uncannily similar. NoSQL databases in the late 2000s often dropped transactions or redefined the word to mean much weaker guarantees.
- Trade-off view: transactions have advantages and limits like any design choice; neither "abandon them to scale" nor "essential for valuable data" is the truth.

### The meaning of ACID
- Coined 1983 (Haerder and Reuter). In practice one DB's "ACID" is not another's; ACID is "mostly a marketing term". BASE (Basically Available, Soft state, Eventual consistency) is vaguer still, effectively "not ACID".
- **Atomicity**: NOT about concurrency (that is isolation). It means if a fault (crash, network break, disk full, constraint violation) happens partway through several writes, the transaction aborts and all its writes are discarded. Without it you cannot tell which changes took effect, and retry risks duplicating changes. With it, an aborted transaction changed nothing, so retry is safe. "Abortability" would be a better name.
- **Consistency**: overloaded word (replica consistency, consistent hashing, CAP's linearizability, and ACID's). ACID consistency = application-specific invariants always true (e.g. credits and debits balance). It is the application's responsibility; the DB can only enforce some (foreign key, uniqueness). A, I, D are DB properties; C is an app property, "tossed in to make the acronym work" (Hellerstein).
- **Isolation**: concurrently running transactions cannot step on each other. Textbook formalisation is serializability: each transaction can pretend it is the only one; result equals some serial order. Example: two clients incrementing counter 42 both read 42 and write 43 (Figure 7-1). In practice serializable is rarely used because of performance cost; Oracle 11g's "serializable" is really snapshot isolation.
- **Durability**: once committed, data is not forgotten even after crash. Single node: written to nonvolatile storage plus write-ahead log. Replicated: copied to some number of nodes before reporting commit. Perfect durability does not exist. Sidebar "Replication and Durability": disk-only means data inaccessible if machine dies; correlated faults can kill all replicas; async replication loses recent writes on leader failure; SSDs can violate fsync guarantees on power loss; firmware/filesystem bugs; silent corruption (may also reach replicas/recent backups, so keep historical backups); 30-80% of SSDs develop a bad block in 4 years; SSD unpowered can lose data in weeks. Conclusion: use risk-reduction techniques together (disk, replication, backups) and take guarantees with a grain of salt.

### Single-object and multi-object operations
- Multi-object transactions are needed when several pieces of data must stay in sync. Example (Figures 7-2, 7-3): email app with denormalized unread counter. Without isolation, user sees new email but counter still 0 (dirty read). Without atomicity, if counter update fails, mailbox and counter diverge; atomic transaction rolls the inserted email back.
- Relational DBs group operations by TCP connection: everything between BEGIN and COMMIT on a connection is one transaction. Footnote: flaw — if connection drops after commit requested but before ack, the client does not know the outcome; a transaction manager with an ID not tied to a connection would fix this (revisited in end-to-end argument chapter).
- Many non-relational DBs lack grouping; a multi-put may succeed for some keys and fail for others (partial update).
- **Single-object writes**: storage engines almost universally give atomicity (via a crash-recovery log) and isolation (lock per object) for one object on one node. Question posed: 20 KB JSON write interrupted at 10 KB, spliced old/new on power fail, reader sees partial write. Also atomic increment (removes read-modify-write) and compare-and-set. These are sometimes marketed as "lightweight transactions" or "ACID" but are not transactions (which means multi-operation, multi-object). Footnote: "atomic increment" uses atomic in the multithreading sense; in ACID terms it is isolated/serializable increment.
- **Need for multi-object transactions**: (1) foreign keys / graph edges stay valid; (2) denormalized document data across several documents (document DBs without joins encourage denormalization); (3) secondary indexes are separate objects — without isolation a record could appear in one index but not another. Apps can work without transactions but error handling becomes far more complex and lack of isolation causes concurrency problems.
- **Handling errors and aborts**: the philosophy is abort rather than leave half-finished. Leaderless-replication stores work "best effort" and do not undo. ORMs (Rails ActiveRecord, Django) do not retry aborted transactions; the error bubbles up and user input is thrown away — a shame. Retry is not perfect: (a) commit succeeded but ack was lost, so retry runs it twice unless app-level deduplication; (b) if the error is overload, retries worsen it — cap retries, use exponential backoff, treat overload errors differently; (c) only retry transient errors (deadlock, isolation violation, temporary network, failover), not permanent ones (constraint violation); (d) side effects outside the DB (e.g. sending an email) still happen even if the transaction aborts — 2PC can coordinate multiple systems; (e) if the client dies while retrying, the data it was writing is lost.

## Weak Isolation Levels
- Concurrency bugs only occur when transactions touch the same data and timing is unlucky: rare, hard to reproduce, hard to find by testing, hard to reason about in a big app. Serializable isolation would hide this but costs performance, so weak levels are common and have caused real money loss (exchange thefts cited), financial-auditor investigations and corrupted customer data. "Use an ACID database for financial data" misses the point because many "ACID" relational DBs use weak isolation by default.

### Read committed (the most basic level)
Two guarantees: no dirty reads, no dirty writes.
- **No dirty reads**: you only see committed data; a transaction's writes become visible all at once at commit (Figure 7-4: x=3 uncommitted, other user still reads 2). Why: avoid seeing partial multi-object updates; avoid seeing data later rolled back.
- **No dirty writes**: a later write must not overwrite an uncommitted earlier write; the second write is delayed until the first transaction commits/aborts. Example (Figure 7-5): Alice and Bob buy the same used car; listing goes to Bob, invoice to Alice because the two writes interleave. Read committed prevents this. It does NOT prevent the counter lost-update of Figure 7-1 (second write comes after the first commit).
- **Implementation**: row-level locks for dirty writes, held until commit/abort (automatic). For dirty reads, read locks work badly (one long writer blocks all readers), so most DBs keep the old committed value plus the new uncommitted one and give readers the old value until commit. Default in Oracle 11g, PostgreSQL, SQL Server 2012, MemSQL and many others. Footnote: only DB2 and SQL Server (read_committed_snapshot=off) use locks for read committed. Footnote: "read uncommitted" is weaker — prevents dirty writes but not dirty reads.

### Snapshot isolation and repeatable read
- Problem with read committed: **read skew / nonrepeatable read** (Figure 7-6): Alice has $500+$500 across two accounts; during a $100 transfer she reads one account before the credit and the other after the debit and sees $900. Each value was committed when read, so read committed allows it. Usually transient (refresh fixes it) but intolerable for: **backups** (hours-long copy mixes old and new data; inconsistency becomes permanent on restore) and **analytic queries / integrity checks** (scan large parts of DB; nonsense results if parts are from different times).
- (The word "skew" here means timing anomaly, not unbalanced workload.)
- **Snapshot isolation**: each transaction reads from a consistent snapshot — everything committed at the transaction start; later changes by others are invisible. Great for long read-only queries. Supported by PostgreSQL, MySQL/InnoDB, Oracle, SQL Server.
- **Implementation**: write locks as before (writers can block writers) but reads take no locks: "readers never block writers, writers never block readers". Uses **multi-version concurrency control (MVCC)** — keep several committed versions of each object. Read committed under MVCC uses a new snapshot per query; snapshot isolation uses one snapshot for the whole transaction.
- PostgreSQL's scheme (Figure 7-7): each transaction gets an always-increasing txid (32-bit, wraparound handled by vacuum). Each row has created_by and deleted_by (initially empty). Delete just sets deleted_by; update = delete + create (so account 2 has the $500 row marked deleted by tx 13 and a $400 row created by tx 13). A garbage-collection process later removes rows no transaction can see.
- **Visibility rules**: at transaction start, list all in-progress transactions; ignore their writes (even if they later commit); ignore writes of aborted transactions; ignore writes from later txids; everything else is visible. Equivalent: an object is visible if its creator had committed at reader start and it is not deleted, or the deleter had not committed at reader start. Long transactions keep reading old values; since values are never updated in place, overhead is small.
- **Indexes**: either index points to all versions and the query filters invisible ones (cleaned up with GC; PostgreSQL optimises to avoid index updates when versions fit the same page), or the append-only / copy-on-write B-tree variant (CouchDB, Datomic, LMDB): each write creates a new root, each root is a snapshot, needs background compaction/GC.
- **Naming confusion**: Oracle calls snapshot isolation "serializable"; PostgreSQL and MySQL call it "repeatable read" (the SQL standard, based on 1975 System R, has no snapshot isolation concept); DB2 uses "repeatable read" for serializability. The standard's definitions are ambiguous. "Nobody really knows what repeatable read means."

### Preventing lost updates
- Lost update = two concurrent read-modify-write cycles; the later write clobbers the earlier. Scenarios: counter/balance increment; editing a complex value such as adding to a list inside a JSON document; two users editing a wiki page and each saving the whole page.
- **Atomic write operations**: e.g. `UPDATE counters SET value = value + 1 WHERE key = 'foo'`; MongoDB local doc modifications; Redis data-structure ops. Usually the best solution when expressible. Implemented by exclusive lock on the object during read-update ("cursor stability") or by running all atomic ops on one thread. Warning: ORMs make it easy to accidentally write unsafe read-modify-write code instead of using atomic ops; hard to catch by testing.
- **Explicit locking**: when logic cannot be expressed as a DB operation (example: multiplayer game must check move validity), use `SELECT ... FOR UPDATE` inside a transaction, then update (Example 7-1). Easy to forget a lock somewhere and introduce a race.
- **Automatically detecting lost updates**: let read-modify-write cycles run in parallel and have the transaction manager abort the offender, which retries. Efficient with snapshot isolation. PostgreSQL repeatable read, Oracle serializable and SQL Server snapshot isolation detect it automatically; **MySQL/InnoDB repeatable read does NOT** (so arguably is not true snapshot isolation). Advantage: no special app code, so less error-prone.
- **Compare-and-set**: for DBs without transactions, update only if the value is unchanged since read: `UPDATE wiki_pages SET content='new' WHERE id=1234 AND content='old'`; check rows affected and retry if 0. Caveat: if the WHERE clause reads from an old snapshot, it may not prevent lost updates — verify your DB.
- **Conflict resolution and replication**: with multi-leader/leaderless replication, locks and CAS do not apply (no single up-to-date copy). Approach: allow concurrent writes to create sibling versions and merge afterwards in app code or with commutative data structures (counters, sets; Riak 2.0 datatypes). Last-write-wins (the default in many replicated DBs) loses updates.

### Write skew and phantoms
- **Write skew** example (Figure 7-8): hospital must have at least one on-call doctor. Alice and Bob each check "two on call" (both see 2 under snapshot isolation), each takes themselves off call, both commit; zero on call. Neither a dirty write nor a lost update since different rows are updated; it is a race condition because a serial order would have blocked the second. Generalisation of lost update: two transactions read the same objects and update some (possibly different) ones.
- Options are limited: atomic single-object ops don't help; automatic lost-update detection doesn't catch it (not in PG repeatable read, InnoDB, Oracle serializable, SQL Server snapshot); true serializable isolation does; multi-object constraints are not natively supported (maybe triggers or materialized views); second best is explicit `SELECT ... FOR UPDATE` on the rows the transaction depends on.
- **More examples**: meeting room double-booking (check overlap, insert; Example 7-2; PostgreSQL range types more elegant); multiplayer game moving two figures to one square (unique constraint may help); **claiming a username** (unique constraint is the simple fix); **double-spending** of money or points (insert tentative spending item, sum, check positive — two concurrent inserts break it).
- **Phantoms**: common pattern — SELECT to check a condition, app decides, write that changes the condition's result. In the doctors case the written row was among the rows read, so FOR UPDATE can lock them. In the other four cases the check is for the ABSENCE of rows, so there is nothing to lock. A write in one transaction changing the result of another's search is a **phantom**.
- **Materializing conflicts**: create concrete lock rows (e.g. a table of room x 15-minute slots for the next six months) and `SELECT FOR UPDATE` them before checking and inserting. Hard, error-prone, leaks concurrency control into the data model — last resort; serializable preferred.

## Serializability
- Weak isolation is hard to understand, inconsistently implemented, hard to judge from app code, and there are no good tools to detect races; testing is nondeterministic. Researchers' answer since the 1970s: use serializable isolation (strongest; result same as serial execution; prevents all race conditions). Three techniques in use: actual serial execution, 2PL, optimistic (SSI).

### Actual serial execution
- Run one transaction at a time on a single thread, so isolation is serializable by definition. Became feasible around 2007 because (1) RAM got cheap enough to hold the active dataset, (2) OLTP transactions are short with few reads/writes; long analytics are read-only and can run on a snapshot outside the serial loop. Used by VoltDB/H-Store, Redis, Datomic. Avoids locking overhead but limited to one CPU core's throughput.
- **Stored procedures**: interactive multi-statement transactions waste time on network round trips, so serial systems require the entire transaction code to be submitted ahead as a stored procedure (Figure 7-9). Original dream of one transaction spanning a whole user flow (airline booking) fails because humans are slow; on the web a transaction must not span HTTP requests.
- **Pros and cons of stored procedures**: bad reputation — vendor-specific archaic languages (PL/SQL, T-SQL, PL/pgSQL), hard to debug/version/deploy/test/monitor, DB is shared and performance-sensitive so a bad procedure hurts more. Modern ones use general languages (VoltDB Java/Groovy, Datomic Java/Clojure, Redis Lua). VoltDB replicates by running the same procedure on each replica, so procedures must be deterministic (time via special APIs).
- **Partitioning**: to scale beyond one core, partition so each transaction touches a single partition, giving near-linear scaling; cross-partition transactions need lock-step coordination and are vastly slower (VoltDB ~1,000 cross-partition writes/s, cannot be raised by adding machines). Key-value data partitions easily; data with many secondary indexes needs cross-partition coordination.
- **Constraints**: transactions small and fast (one slow transaction stalls everything); active dataset fits in RAM (anti-caching: abort, fetch async, restart); write throughput fits one core or is partitionable; cross-partition use is limited.

### Two-phase locking (2PL)
- For ~30 years the only widely used serializability algorithm. NOT the same as two-phase commit (2PC). Variant called strong strict 2PL (SS2PL).
- Stronger than dirty-write locks: many readers may share an object, but any writer needs exclusive access. Writers block readers and readers block writers (opposite of snapshot isolation's mantra). It protects against lost updates and write skew.
- Used by MySQL/InnoDB and SQL Server serializable, and DB2 repeatable read.
- Implementation: lock per object, shared mode (reads, many holders) or exclusive mode (writes); read-then-write upgrades shared to exclusive; locks held until commit/abort (acquire phase during execution, release phase at the end). Deadlocks are easy to hit; the DB detects them and aborts one transaction, which the app must retry.
- **Performance**: significantly worse throughput and response time than weak isolation — lock overhead and, mainly, reduced concurrency. No limit on how long a transaction waits; queues form; unstable latencies and bad high percentiles under contention; one slow transaction can stall everything. Deadlocks far more frequent than under lock-based read committed, wasting retry effort.
- **Predicate locks**: to stop phantoms, a lock belongs to all objects matching a search condition (including not-yet-existing rows). Reader takes shared predicate lock on its WHERE condition; writer (insert/update/delete) checks whether old or new value matches any existing predicate lock and waits. Prevents write skew and makes 2PL serializable. Slow when many locks.
- **Index-range locks (next-key locking)**: practical approximation — widen the predicate to a superset (e.g. all of room 123 at any time, or all rooms for noon-1pm) and attach a shared lock to the index entry or range. Less precise but cheap. If no suitable index, fall back to a shared lock on the whole table (safe but blocks all writers).

### Serializable Snapshot Isolation (SSI)
- Question: are serializability and performance fundamentally at odds? SSI says maybe not — full serializability with only small penalty over snapshot isolation. First described 2008 (Cahill); used in PostgreSQL serializable since 9.1; FoundationDB uses a similar algorithm. Still young.
- **Pessimistic vs optimistic**: 2PL is pessimistic (wait if anything could go wrong); serial execution is pessimism to the extreme (exclusive lock on whole DB/partition, made OK by speed). SSI is optimistic: proceed anyway, check at commit, abort and retry if isolation was violated. Optimistic does badly under high contention (many aborts, retries add load near max throughput) but better with spare capacity and low contention. Commutative atomic operations (counter increments) reduce contention. SSI sits on snapshot isolation and adds an algorithm to detect serialization conflicts.
- **Decisions based on an outdated premise**: the write-skew pattern is acting on a premise (e.g. "two doctors on call") that may no longer be true at commit. The DB doesn't know how the app uses a query result, so it assumes any change in a query result may invalidate that transaction's writes (causal dependency) and aborts. Two cases:
  1. **Detecting stale MVCC reads** (Figure 7-10): tx 43 read Alice on_call=true while tx 42's write was uncommitted and ignored; by 43's commit, 42 has committed. DB tracks ignored writes and at commit aborts if any of them has since committed. Why wait until commit rather than abort immediately: 43 may be read-only (no risk), 42 may still abort, so avoids needless aborts and keeps long read-only snapshot reads.
  2. **Detecting writes that affect prior reads** (Figure 7-11): record on index entries (e.g. shift_id=1234) or at table level which transactions read that data (keep only until all concurrent transactions finish). A writer checks for recent readers and acts as a tripwire (not a blocking lock), notifying them their read may be stale. Tx 42 commits first (OK), tx 43 on commit finds the conflicting write already committed and aborts.
- **Performance**: tracking granularity trade-off (precise = more bookkeeping; coarse = more unnecessary aborts); PostgreSQL uses theory proving some stale reads still serializable to reduce aborts. Advantages: no blocking on locks, readers and writers don't block each other, predictable latency, read-only queries run lock-free; unlike serial execution it isn't bound to one core (FoundationDB distributes conflict detection). Abort rate matters: long read-write transactions are likely to conflict, so read-write transactions must be fairly short (long read-only fine). Less sensitive to slow transactions than 2PL or serial.

## Summary (chapter)
Transactions let an app pretend certain faults and concurrency problems don't exist; many errors become "abort and retry". Simple single-record access patterns may manage without. Anomalies and what prevents them:
- Dirty reads — prevented by read committed and stronger.
- Dirty writes — prevented by almost all implementations.
- Read skew — snapshot isolation (MVCC).
- Lost updates — some snapshot-isolation implementations detect automatically; else manual lock (SELECT FOR UPDATE).
- Write skew — only serializable.
- Phantom reads — snapshot isolation prevents plain phantoms; phantoms in write skew need index-range locks / serializable.
Serializable options: serial execution (fast short transactions, one core), 2PL (decades-standard, performance issues), SSI (optimistic, newer).

## Failure modes / pitfalls (Chapter 7 checklist)
- Counter race (read 42, both write 43) — lost update.
- Unread counter out of sync with mailbox — dirty read (isolation) / partial failure (atomicity).
- Used-car sale: listing to Bob, invoice to Alice — dirty write.
- Alice's $900 — read skew; permanent when it hits a backup.
- Wiki/JSON read-modify-write — lost update; ORMs hide unsafe cycles.
- Doctors on call = 0 — write skew; room double-booking, same-square game moves, duplicate usernames, double-spend — phantom-driven write skew.
- Retry pitfalls: ack lost so duplicate; overload amplification; retrying permanent errors; external side effects (emails) repeated; client dies mid-retry.
- ORMs not retrying aborted transactions.
- "Atomic"/"ACID"/"repeatable read"/"serializable" meaning different things per DB.
- Compare-and-set whose WHERE reads an old snapshot.
- 2PL: deadlocks and latency instability; serial execution: one slow transaction stalls all; SSI: high abort rates with long read-write transactions or high contention.

## Key terms (Ch 7)
- Transaction: group of reads/writes executed as one unit, commit or abort.
- Atomicity (ACID): all-or-nothing on fault; abortability.
- Consistency (ACID): app-defined invariants stay true.
- Isolation: concurrent transactions don't interfere; ideally serializable.
- Durability: committed data survives crashes.
- Dirty read / dirty write: reading / overwriting uncommitted data.
- Read committed: no dirty reads or writes.
- Read skew (nonrepeatable read): seeing different points in time within one transaction.
- Snapshot isolation: each transaction reads a consistent snapshot from its start.
- MVCC: keeping multiple versions of each object to serve snapshots.
- Lost update: concurrent read-modify-write where one write is clobbered.
- Compare-and-set: write only if value unchanged since read.
- Write skew: decisions on a stale premise lead to writes to different objects violating an invariant.
- Phantom: a write changes the result of another transaction's search query.
- Materializing conflicts: add lock rows to give phantoms something to lock.
- Serializability: outcome equals some serial order.
- Stored procedure: transaction code shipped to and run inside the DB.
- 2PL: shared/exclusive locks held to end of transaction.
- Predicate lock / index-range (next-key) lock: lock on a search condition / approximation via index.
- SSI: optimistic snapshot-based serializability with conflict detection at commit.
- Pessimistic vs optimistic concurrency control: wait vs proceed-and-check.

## Relevance to a multi-tenant Node/Express + single managed Postgres (Supabase) SaaS with an email send queue (Ch 7)
- **Postgres default isolation is READ COMMITTED** (book states it: default in PostgreSQL). Its "repeatable read" is snapshot isolation (detects lost updates, does NOT catch write skew); "serializable" is SSI (since 9.1) and aborts with serialization failures that the app must retry. Supabase/PostgREST calls (supabase-js) are each one statement/own transaction, so multi-step logic in Node is NOT one transaction unless done in an RPC/SQL function or a direct pg connection.
- **Claim-before-send (email queue)**: a read-then-update in app code (SELECT pending, then UPDATE to 'sending') is a lost-update/read-modify-write race under read committed; two workers can both claim the row and send twice. Fix: a single atomic statement (`UPDATE ... SET status='sending' WHERE id=... AND status='pending' RETURNING *` — a compare-and-set on status; under read committed the second updater waits on the row lock then re-evaluates the WHERE, so it matches 0 rows) or `SELECT ... FOR UPDATE SKIP LOCKED` (not in this chapter but follows from explicit locking). Check rows affected, only send if you won the claim.
- **Row stuck in "sending" after a crash**: atomicity covers DB writes only. The external side effect (sending email) is outside the transaction, so a transaction cannot make "mark sending + send + mark sent" atomic; book warns retries can duplicate external effects and acks can be lost. Needs application-level dedupe (idempotency key / unique constraint on a send id), a claim timestamp/lease with sweep for stale 'sending' rows, and treating uncertain outcomes as "don't retry blindly".
- **Read-modify-write races**: counters (daily send quota, usage/plan limits, unread/pipeline counts) should use atomic `SET n = n + 1` or conditional updates, not read-in-Node-then-write. ORM/Node code makes unsafe cycles easy.
- **Write skew / phantoms in business rules**: "limit N per day/plan seats" checks, "only one active X per Y", duplicate candidate/submission detection, double-booking interviews. Use unique constraints (best for username/email/duplicate checks), locking a parent row (`SELECT ... FOR UPDATE` on the org/mailbox row) to serialize, or SERIALIZABLE with retry. Remember multi-tenant: scope locks per org/mailbox to avoid cross-tenant contention.
- **Retry rules**: retry only transient errors (deadlock, serialization failure, connection), with backoff and a cap; never retry permanent constraint errors; beware lost commit acks.
- **Keep transactions short**; don't hold a transaction across an HTTP call to a third party or across HTTP requests (book: a transaction should not span requests). Long read transactions are fine under MVCC but can bloat vacuum.
- **Backups/analytics**: snapshot isolation gives consistent reports/exports on a live DB (use REPEATABLE READ for multi-query reports/CSV exports).
- Multi-object consistency: denormalized counters/indexes and status+history rows should change in one transaction (SQL function / RPC), as the unread-counter example.
- Only matters at larger scale: serial-execution/VoltDB/partitioning, cross-partition throughput, predicate vs index-range lock internals, append-only B-trees, leaderless/LWW conflict resolution, FoundationDB.

# CHAPTER 8 — The Trouble with Distributed Systems

## Core argument
A program on one computer is deterministic and either works or crashes totally; computers are deliberately designed to hide physical messiness. Once software spans machines connected by a network, you must confront partial failure: some parts break unpredictably while others work, and the outcome of any multi-node operation is nondeterministic and often unknowable (you may not know whether something succeeded). The chapter is deliberately pessimistic: it catalogues unreliable networks (loss, unbounded delay, no way to tell why a reply is missing), unreliable clocks (drift, NTP error, jumps, leap seconds, no confidence interval), and process pauses (GC, VM suspend, swapping) that make a node unaware time passed. Consequence: a node cannot trust its own view of the world; truth is decided by a quorum, and safety must be protected by mechanisms such as fencing tokens. To reason about this, you state a system model (timing assumptions plus failure assumptions) and prove algorithms correct under it using safety and liveness properties. Practical conclusion: build reliability on unreliable parts, assume faults, test them, and keep things on a single machine if you can.

## Faults and Partial Failures
- Single computer: deterministic; hardware faults usually mean total failure (kernel panic) — a design choice, since wrong results are worse than crashing.
- Distributed: partial failure is nondeterministic and is "what makes distributed systems hard". Coda Hale anecdote: partitions, PDU and switch failures, rack power cycles, a driver hitting the DC's HVAC.
- **Cloud vs supercomputing**: HPC jobs checkpoint and, on any node failure, stop everything and restart from the last checkpoint (partial failure escalated to total failure, like a single machine). Internet services differ: must be online with low latency (can't stop to repair); commodity hardware has higher failure rates; IP/Ethernet Clos networks; in a big system something is always broken, so "give up" error handling wastes time; tolerating node failure enables rolling upgrades and killing a slow VM; geographically distributed deployments run over the slow, unreliable internet.
- Therefore build fault tolerance into software, even for small systems. Don't assume faults are rare; consider unlikely faults and deliberately create them in testing. "Suspicion, pessimism, and paranoia pay off."
- **Building reliable systems from unreliable components**: not limited by the weakest link — error-correcting codes over noisy channels; TCP over unreliable IP (retransmits, dedupes, reorders). There is always a limit (TCP cannot remove delay), but the higher layer makes remaining faults easier to reason about (end-to-end argument returns later).

## Unreliable Networks
- Focus is shared-nothing systems communicating only via network; dominant because cheap, commodity, redundant across DCs. The internet and DC Ethernet are **asynchronous packet networks**: no guarantee of arrival or timing.
- Six things that can go wrong with a request/response (Figure 8-1): request lost; request queued; remote node failed; remote node paused (GC) but will resume; request processed but response lost; request processed but response delayed. The sender cannot distinguish them; the usual remedy is a **timeout**, but after a timeout you still don't know if the remote got the request (it may still be delivered).
- **Network faults in practice**: one medium DC study ~12 network faults/month (half disconnect a machine, half a rack); redundant gear helps less than hoped because human error (misconfigured switches) is a major cause; public clouds (EC2) have frequent transient glitches; a switch software upgrade caused >1 minute packet delays; sharks bite undersea cables; a NIC that drops all inbound but sends outbound (asymmetric). "Network partition / netsplit" = part of the network cut off (book prefers "network fault" to avoid confusion with sharding).
- Untested network-fault handling can deadlock a cluster forever or delete data. Handling does not always mean tolerating (showing an error may be fine) but you must know and test the behavior (Chaos Monkey idea).
- **Detecting faults**: needed for load balancers (remove dead node) and leader failover. Possible explicit signals: TCP RST/FIN if the process died but machine is up (but unknown how much was processed if it crashed mid-request); scripts notifying others of a crashed process (HBase); querying switch management interfaces (not over internet/shared DC); ICMP Destination Unreachable. None are reliable: TCP ack doesn't mean the app handled it — you need a positive application-level response. In general assume no response; retry, wait for timeout, declare dead.
- **Timeouts and unbounded delays**: long timeout = slow detection; short timeout = risk of falsely declaring a slow node dead. A falsely-dead node mid-action (e.g. sending an email) can lead to the action being performed twice by the node that takes over. Moving load to other nodes while overloaded can cascade (all nodes declare each other dead). If networks had a max delay d and servers a max handling time r, a timeout of 2d + r would be right — but real networks have unbounded delays and servers can't guarantee max handling time.
- **Network congestion and queueing**: delay variability mostly from queueing: switch queues when many senders target one port (packets dropped if the queue fills); OS queueing when CPU cores are busy; VM pauses of tens of ms buffered by the hypervisor; TCP flow control/backpressure queueing at the sender; TCP retransmission after a lost-packet timeout (app sees only delay). **TCP vs UDP**: UDP (VoIP, video calls) avoids retransmission/flow control delay — good where delayed data is worthless. Queueing delay grows sharply near capacity. In public clouds/multi-tenant DCs "noisy neighbors" (e.g. MapReduce batch jobs saturating links) make delays highly variable. Choose timeouts experimentally (measure RTT distributions) or, better, adapt continuously via a **Phi Accrual failure detector** (Akka, Cassandra); TCP retransmission timeouts work similarly.
- **Synchronous vs asynchronous networks**: the fixed telephone network uses circuits (reserved bandwidth end-to-end, e.g. ISDN 16 bits per 250 microsecond frame), so no queueing and bounded delay. Datacenter/internet are packet-switched because they're optimised for bursty traffic; circuits would waste capacity or force guessing bandwidth. Hybrids (ATM, InfiniBand link-layer flow control, QoS plus admission control) can emulate bounded delay.
- **Latency and resource utilization**: variable delay is the result of dynamic resource sharing (same trade as CPU time-sharing between threads and VMs). Static partitioning gives latency guarantees but lower utilization, i.e. more expensive. "Variable delays are not a law of nature, but simply the result of a cost/benefit trade-off." Current public clouds offer no such QoS: assume congestion and unbounded delays; there is no "correct" timeout value, determine it experimentally.

## Unreliable Clocks
- Clock questions: durations (timeouts, p99 response time, QPS, time on site) vs points in time (article published, when to send a reminder email, cache expiry, log timestamps). Each machine has its own quartz clock that drifts; sync via NTP against servers that get time from GPS etc. Message latency is variable so event ordering across machines is hard.
- **Monotonic vs time-of-day clocks**:
  - Time-of-day (wall-clock): `clock_gettime(CLOCK_REALTIME)`, Java `System.currentTimeMillis()`; seconds since Unix epoch (1970 UTC), ignores leap seconds; NTP-synced so comparable across machines; but can be forcibly reset and jump backward, so unsuitable for measuring elapsed time. Historically coarse resolution (10 ms on old Windows).
  - Monotonic: `CLOCK_MONOTONIC`, Java `System.nanoTime()`; always moves forward; only differences within one machine are meaningful (absolute value arbitrary, e.g. since boot); never compare across machines. NTP may slew the rate by up to 0.05% but can't jump it. Fine for timeouts/response times in distributed systems. Multi-socket per-CPU timers: take monotonicity with a pinch of salt.
- **Clock synchronization and accuracy pitfalls**: quartz drift (Google assumes 200 ppm = 6 ms per 30 s resync, 17 s per day); NTP-forced resets or refusal to sync if too far off; node firewalled from NTP unnoticed; NTP accuracy bounded by network delay (≥35 ms over internet, spikes to ~1 s); wrong NTP servers off by hours (clients mitigate by querying several and ignoring outliers); leap seconds (59/61-second minutes) have crashed many large systems (best handled by smearing); VM clocks virtualised, pauses appear as clock jumps; untrusted devices (mobile) may have deliberately wrong clocks. High accuracy is possible (MiFID II requires 100 microseconds for high-frequency traders via GPS and PTP) but needs significant effort.
- **Relying on synchronized clocks**: incorrect clocks go unnoticed (unlike a dead CPU), so failure is silent, subtle data loss rather than crash. If you depend on synced clocks, monitor offsets between machines and eject any node that drifts too far.
- **Timestamps for ordering events**: Figure 8-3: multi-leader replication; client A writes x=1 on node 1 (timestamp 42.004), client B then increments on node 3 giving x=2 (timestamp 42.003, because of <3 ms skew); node 2 applies last-write-wins and keeps x=1, silently dropping B's increment. LWW problems: writes silently vanish (a node with a lagging clock can't overwrite values from a fast clock until the skew elapses); cannot distinguish sequential from truly concurrent writes (need version vectors); equal timestamps need a tiebreaker which can break causality. NTP can't be accurate enough because its accuracy is bounded by network RTT. Safer alternative: **logical clocks** (incrementing counters; relative order only). Time-of-day and monotonic clocks are "physical clocks".
- **Clock readings have a confidence interval**: a reading is a range, not a point (e.g. tens of ms over public NTP; >100 ms under congestion); microsecond digits are meaningless. Most APIs (`clock_gettime`) don't expose the uncertainty. Exception: Google Spanner's **TrueTime** returns [earliest, latest].
- **Synchronized clocks for global snapshots**: snapshot isolation needs monotonically increasing transaction IDs, which are a coordination bottleneck across many machines/DCs (Snowflake-style generators aren't causally consistent). Spanner uses clock timestamps as transaction IDs: if two TrueTime intervals don't overlap, the order is certain; it **waits for the length of the confidence interval before committing** a read-write transaction so later readers' intervals don't overlap. Google puts GPS/atomic clocks in each DC (~7 ms uncertainty). Not in mainstream databases outside Google (CockroachDB mention in refs).
- **Process pauses**: example — leader holds a lease (lock with timeout) and loops: renew if <10 s left, then process requests if lease valid. Bugs: (1) compares an expiry set by another machine against the local clock (needs synced clocks); (2) even with a monotonic clock, assumes negligible time passes between the check and processing; a 15-second pause makes the lease expire so it processes a request as a stale leader. Causes of pauses: stop-the-world GC (up to minutes), VM suspend/live migration, laptop lid close, context switches and hypervisor steal time, synchronous disk I/O (including lazy class loading, network filesystems like EBS), swapping/page faults/thrashing (disable paging on servers), SIGSTOP/Ctrl-Z. A node must assume it can be paused at any point; the world moves on and may declare it dead. Single-machine thread-safety tools (mutexes, semaphores, atomics, queues) don't directly translate because there's no shared memory.
- **Response time guarantees**: hard real-time systems (airbags, aircraft) need RTOS, worst-case execution time documentation, restricted dynamic allocation, huge testing; expensive, lower throughput, restricted tooling; "real-time" on the web is just a vague marketing term. Not economical for most server-side systems.
- **Limiting the impact of GC**: treat GC pauses as brief planned outages — warn the app, drain requests from the node, collect, rejoin (used in some trading systems); or use GC only for short-lived objects and restart processes periodically with traffic shifted (rolling restart).

## Knowledge, Truth, and Lies
- A node can't know anything for sure; it only guesses from messages (or silence). We instead state assumptions (a system model) and design to meet them.
- **The truth is defined by the majority**: asymmetric fault node dropped as "dead" though healthy; a node after a one-minute GC pause comes back unaware it was declared dead. A node can't trust its own judgment; decisions use a **quorum** (usually an absolute majority >50%; 3 nodes tolerate 1 failure, 5 tolerate 2); only one majority can exist, so no conflicting decisions. A node declared dead by quorum must step down.
- **The leader and the lock**: need exactly one leader per partition (avoid split brain), one lock holder, one claimant of a username. A node that believes it is the chosen one may be wrong. Figure 8-4: a client holds a lease for a file, pauses, lease expires, client 2 gets the lease and writes, client 1 resumes believing its lease is valid and writes — corrupted file (HBase had this bug).
- **Fencing tokens** (Figure 8-5): the lock service returns a monotonically increasing token with each grant; the client sends it on every write; the storage service remembers the highest token seen and rejects lower ones (client 1 with token 33 is rejected after client 2 with 34 has written). With ZooKeeper, zxid or cversion work as tokens. The resource itself must check tokens — client self-checking is insufficient; if the resource lacks support, workaround e.g. put the token in the filename. Server-side checking is good because clients can't be trusted to behave ("clients are jerks").
- **Byzantine faults**: fencing tokens stop an inadvertent mistaken node, not a lying one. The book assumes nodes are unreliable but honest. Byzantine fault = node sends arbitrary/false messages; Byzantine Generals Problem (generalisation of Two Generals): n generals, some traitors. Byzantine-fault-tolerant (BFT) systems need >2/3 of nodes working correctly. Relevant in aerospace (radiation-corrupted memory) and multi-organisation/blockchain systems; not in a single-organisation datacenter, where the cost is impractical. Web apps must distrust clients (input validation, sanitization, output escaping against SQL injection and XSS) but solve it by making the server the authority rather than BFT protocols. BFT can't help against software bugs deployed identically on all nodes or against attackers who compromise one node (then all); use authentication, access control, encryption, firewalls.
- **Weak forms of lying** worth guarding against: application-level checksums for corrupted packets that evade TCP/UDP checksums; sanitize inputs (range checks, string size limits to avoid DoS), even for internal services; configure NTP with multiple servers and discard outliers.

## System Model and Reality
- A **system model** abstracts the assumptions an algorithm may make. Timing models: **synchronous** (bounded delay, pauses, clock error; unrealistic), **partially synchronous** (behaves synchronously most of the time but occasionally exceeds bounds; the realistic one), **asynchronous** (no timing assumptions or clocks at all; very restrictive). Node failure models: **crash-stop** (node crashes and is gone forever), **crash-recovery** (can come back; nonvolatile storage survives, memory lost), **Byzantine** (arbitrary behavior). Most useful: partially synchronous + crash-recovery.
- **Correctness of an algorithm**: defined by properties. Fencing-token example: uniqueness (no two requests return the same token), monotonic sequence (if x completed before y began, tx < ty), availability (a non-crashing requester eventually gets a response).
- **Safety vs liveness**: uniqueness and monotonic sequence are safety (nothing bad happens; if violated you can point to the moment and the damage can't be undone); availability is liveness (something good eventually happens; "eventually" is the giveaway; may not hold now but can still be satisfied later; eventual consistency is a liveness property). Safety must hold in all situations of the model (even if all nodes crash); liveness may carry caveats (e.g. only if a majority is up and the network eventually recovers).
- **Mapping to the real world**: models are simplifications. Real systems have disk corruption, amnesiac nodes that lose stored data (breaks quorum algorithms), firmware that fails to see drives. Implementations may need code for "impossible" cases, even if just halting for a human operator ("computer science vs software engineering"). Theory and empirical testing are equally important; proofs find problems that otherwise hide until timing assumptions break.

## Summary (chapter)
Packets can be lost or arbitrarily delayed, as can replies, so no reply = no knowledge. Clocks can be out of sync, jump, and have unknown error. Processes can pause for long periods and come back unaware. Partial failure is the defining characteristic of distributed systems. Fault detection mostly relies on timeouts, which can't distinguish network from node failure, and nodes can be "limping" (e.g. gigabit NIC dropping to 1 Kb/s) which is harder than a clean failure. There's no shared state/global variable, so major decisions need a quorum. If you can keep things on one machine, do so; but fault tolerance and low latency need distribution. Reliable networks/real-time are possible but expensive and underutilize hardware; most systems choose cheap and unreliable. Bad config rolled to all nodes still kills a distributed system.

## Failure modes / pitfalls (Chapter 8 checklist)
- Request sent, no response: lost request vs dead node vs lost response — indistinguishable (retry may duplicate).
- Timeout too short: false death, work taken over and done twice (e.g. email sent twice), cascading failure; too long: slow detection.
- Using wall-clock time for elapsed time (jumps back/forward, leap seconds, NTP resets, VM pauses).
- LWW with timestamps: silently lost writes (Figure 8-3), sub-ms ties, lagging clocks.
- Clock confidence interval ignored; ordering by timestamps across machines.
- Lease/lock held by a paused process (GC, VM suspend, swapping, SIGSTOP) and used after expiry (Figure 8-4); lease expiry compared to the local clock set by another machine.
- Node isolated by asymmetric network fault declared dead by others.
- Leader believing it is still leader (split brain).
- NTP misconfigured/firewalled unnoticed; wrong NTP servers; leap seconds.
- Assuming partitions/faults are rare or untested; correlated human-error outages.
- Silent corruption of packets beyond checksum coverage; unsanitized inputs.
- Assuming stable storage never loses data in crash-recovery model.

## Key terms (Ch 8)
- Partial failure: some parts of a system fail while others work, nondeterministically.
- Shared-nothing: machines communicate only via the network.
- Asynchronous packet network: no guarantee of delivery or timing.
- Timeout: giving up on a reply after a set time; the only practical failure detector.
- Network fault / partition (netsplit): part of the network cut off.
- Phi Accrual failure detector: adaptive timeout from observed response-time distribution.
- Circuit-switched vs packet-switched: reserved bandwidth with bounded delay vs shared bursty transport with queueing.
- Time-of-day clock / monotonic clock / logical clock / physical clock.
- NTP: Network Time Protocol; slewing: NTP adjusting clock rate; smearing: spreading a leap second over a day.
- Clock drift: quartz clock running fast/slow.
- Confidence interval (TrueTime [earliest, latest]).
- Last write wins (LWW): keep highest timestamp, discard others.
- Process pause / stop-the-world GC / steal time.
- Hard real-time system: guaranteed deadlines, RTOS.
- Lease: lock with a timeout.
- Quorum: minimum votes (usually majority) needed for a decision.
- Split brain: two nodes both believing they are leader.
- Fencing token: monotonically increasing number checked by the resource to reject stale lock holders.
- Byzantine fault / BFT: nodes may lie arbitrarily; tolerance needs >2/3 honest.
- System model: synchronous / partially synchronous / asynchronous; crash-stop / crash-recovery / Byzantine.
- Safety property: nothing bad ever happens (irreversible when broken); liveness property: something good eventually happens.
- Limping node / degraded state: alive but extremely slow.

## Relevance to a multi-tenant Node/Express + single managed Postgres (Supabase) on a small host, sending email from a queue (Ch 8)
Directly applicable even though the app is not a multi-node database:
- **The app/DB/email-provider boundary IS a network**: every call to Supabase, Gmail/Outlook/Graph, Apollo, JSearch, OpenRouter, Resend etc. has the six failure cases. A timeout on "send email" does NOT mean it wasn't sent. So: do not blindly retry a send after a timeout (duplicate email to a candidate/client); record "uncertain" state, use provider idempotency keys where offered, and reconcile (check Sent folder / provider status) rather than retry. Retries only for operations known safe (GET, idempotent).
- **Timeouts on every third-party call** (no unbounded waits; Node http without timeout can hang); choose by measuring latencies; pair with backoff and caps; don't let retries pile on an overloaded provider (cascade). A slow-but-alive service is worse than a dead one (limping).
- **Row stuck in "sending" after a crash**: this is the process-pause/crash-recovery problem. A worker that claimed a row may die or be paused (Render free tier sleeps/restarts, deploy restarts, GC, event-loop stalls) — the claim must be a lease with a timestamp, and boot/sweeper logic must reclaim stale 'sending' rows; treat the outcome as uncertain (maybe sent, maybe not) rather than automatically resending; the paused-then-resumed worker must re-validate (fencing): e.g. make the final status update conditional (`WHERE id=... AND claim_token=...`/attempt counter) so a stale worker cannot overwrite a newer attempt — the fencing-token idea applied to a single Postgres row (an attempt/version counter monotonically increasing).
- **Don't use in-process locks or in-memory flags as the single source of truth** if the host can run two instances (rolling deploy overlap on Render): use DB-level atomic claims or advisory locks; lease expiries need expiry computed by one clock (the DB `now()`), not compared with the app server's clock.
- **Clocks/timezones**: use the DB clock (`now()`) as the single time authority for ordering, claim leases, and daily send caps; store UTC (timestamptz); use monotonic timers (`process.hrtime`/`performance.now()`) for measuring durations/timeouts in Node, not `Date.now()`; don't order events across app instances by app-server timestamps (LWW pitfall); watch scheduled sends in the recipient's timezone and DST (days aren't always 24h) — leap seconds/NTP are the host's concern. Clock readings are ranges: don't rely on sub-second ordering of "who clicked first".
- **Last-write-wins in the UI/API**: two recruiters editing the same record save whole objects, the later save silently overwrites (same as Ch 7 lost update); use version/updated_at checks (optimistic concurrency) rather than trusting timestamps blindly.
- **Webhooks/inbound events** (mail replies, Stripe-like billing): may arrive late, duplicated or out of order; handle idempotently and don't assume order by arrival time.
- **Quorum, fencing, Byzantine, system models, TrueTime, circuit vs packet networks**: matter only at much larger scale or with multi-node databases; for a single managed Postgres, Supabase handles replication/failover. Byzantine: only relevant as "treat every client/browser/webhook payload as hostile" — validate input, authorize on the server, verify webhook signatures; the book's own point (server is the authority).
- **Operational**: test failure paths deliberately (kill the process mid-send, drop DB connection, slow provider) — "chaos"-style tests; monitor clock/uptime; detect failures via explicit app-level positive responses, not just TCP success; log with timestamps in UTC.
- **Keep it on one machine/DB if you can** — the book's own advice; the single-Postgres design lets Ch 7's transactions provide the consistency that a distributed design would need consensus for.
