## PART III intro: Derived Data
- Real applications combine several stores (DBs, indexes, caches, analytics systems) and must move data between them; no single DB satisfies every access pattern. Integrating disparate systems is one of the most important, often-overlooked jobs.
- **System of record (source of truth):** authoritative version; new data written here first; each fact represented once (normalised); in a discrepancy, it is by definition right.
- **Derived data system:** result of transforming other data; can be recreated if lost. Caches, denormalised values, indexes, materialised views, recommendation summaries. Redundant by nature but essential for read performance; can derive many datasets ("points of view") from one source.
- The distinction is about how a tool is USED, not the tool itself. Being explicit about which data derives from which clarifies architecture (running theme).
- Roadmap: Ch10 batch (MapReduce), Ch11 same ideas on streams with lower delay, Ch12 future of reliable apps.

# CHAPTER 10 — Batch Processing

## Core argument
Three kinds of systems: services (request/response, judged by response time and availability), batch jobs (big bounded input, produce output, run periodically, judged by throughput), stream processors (in between; act on events shortly after they happen). The chapter uses Unix pipelines as the model for good batch design: small single-purpose tools, a uniform interface (bytes/files), wiring separated from logic, immutable inputs, output replaced wholesale. MapReduce is "Unix distributed over thousands of machines": mappers extract key/value, the framework sorts/shuffles by key, reducers process adjacent groups. The big wins are not scale per se but the discipline: inputs immutable, no side effects except output, so you can re-run freely, tolerate faults by retrying, and treat output as derived data. Joins and grouping all reduce to "bring related records to the same place" via key partitioning. (Later sections - see below - cover why dataflow engines replaced MapReduce.)

## Intro (lines 60-132)
- Services: wait for request, answer fast. Batch (offline): large input, job runs minutes to days, scheduled periodically (e.g. daily), nobody waiting, metric = throughput. Stream (near-real-time/nearline): consumes events soon after they happen rather than a fixed dataset; lower latency than batch; builds on batch.
- MapReduce published 2004 (Google); implemented in Hadoop, CouchDB, MongoDB; importance declining but explains why batch is useful. Batch is very old (Hollerith punch-card machines, 1890 US census; IBM card sorters resemble MapReduce).

## Batch Processing with Unix Tools (133-391)
**Simple log analysis.** Top-5 pages from an nginx access log: `cat | awk '{print $7}' | sort | uniq -c | sort -r -n | head -n 5`. Processes gigabytes in seconds; easy to tweak (filter CSS, count IPs instead). Many analyses can be done in minutes with awk/sed/grep/sort/uniq/xargs, and perform well.
**Chain of commands vs custom program.** Ruby equivalent uses an in-memory hash table of URL->counter. Differences show on large data:
- *Sorting vs in-memory aggregation:* hash table working set depends on number of DISTINCT keys (a million hits to one URL still costs one entry). If it fits in memory (say 1 GB for small/mid sites) fine; if not, the sort approach wins because it spills to disk using mergesort (sorted chunks written as segments, then merged — same principle as SSTables/LSM-trees; sequential I/O). GNU sort spills to disk and parallelises across cores automatically, so the pipeline scales without running out of memory; bottleneck becomes disk read rate.
**Unix philosophy (1978):** (1) one program does one thing well, build afresh rather than add features; (2) output of every program becomes input to another, unknown program — no clutter, avoid columnar/binary input, don't insist on interactivity; (3) design to be tried early (weeks), throw away clumsy parts; (4) prefer tools to unskilled help, even detouring to build tools. Author: sounds like Agile/DevOps — automation, prototyping, incremental iteration, experimentation-friendly, break big projects into chunks. `sort` is excellent at one thing but only powerful in combination.
- *Uniform interface:* in Unix it's the file/file descriptor = ordered byte sequence (files, pipes, sockets, devices). By convention ASCII text with newline as record separator (arbitrary choice; ASCII record separator 0x1E would have been better). Parsing of fields is vaguer (whitespace, tabs, CSV, pipes; xargs has half a dozen parse options). Not beautiful (`$7` instead of a named field) but remarkably composable; most software today does NOT interoperate this well (can't pipe your email + shopping history through an analysis tool into a spreadsheet then to a wiki). Lack of integration -> "Balkanization" of data. Analogy: URLs/HTTP as uniform interface of the web (vs BBSs each with own phone number).
- *Separation of logic and wiring:* programs use stdin/stdout; shell wires them (pipes use a small in-memory buffer, no full intermediate dump). Loose coupling / late binding / inversion of control. You can write your own program (e.g. IP->country) and plug it in. Limits: multiple inputs/outputs awkward; can't pipe into a network connection; if a program opens files/network/subprocess itself, wiring is no longer the shell's.
- *Transparency and experimentation:* inputs are immutable so you can re-run with different options; can end the pipeline at any stage and inspect with `less`; can write a stage's output to a file and restart later stages without rerunning everything. Blunt tools compared with a DB query optimiser, but great for experimentation.
- Biggest limit: single machine -> Hadoop.

## MapReduce and Distributed Filesystems (392-1000)
- A MapReduce job ~ one Unix process: reads inputs, writes outputs, normally no side effects, doesn't modify input; output files written once, sequentially.
- **HDFS:** open-source GFS clone; shared-nothing (commodity machines + ordinary network) in contrast to shared-disk NAS/SAN (central appliance, custom hardware, Fibre Channel). A daemon per machine serves its files; a central NameNode tracks block locations. Blocks replicated (copies, or erasure coding such as Reed-Solomon for lower overhead; like RAID but over a network). Scales to tens of thousands of machines, hundreds of PB, cheaper than storage appliances. Alternatives: GlusterFS, QFS; object stores (S3, Azure Blob, Swift) similar, but they separate storage from compute, whereas HDFS can schedule compute where the data is (locality lost with erasure coding).
**Job execution (4 steps):** (1) read input files, break into records (input format parser); (2) call mapper per record to emit key-value pairs (any number, incl. none; stateless between records); (3) sort all pairs by key (implicit); (4) call reducer with key + iterator over all values for that key. In the log example: mapper = awk, sort = sort, reducer = `uniq -c`. A second sort stage (ranking) = second MapReduce job. Role of mapper: put data into a form suitable for sorting; reducer: process sorted data.
**Distributed execution:** parallelism by partitioning; each input file/block = one map task; scheduler runs mapper on a machine holding a replica ("put computation near the data", saves network); code (JAR) is copied to the machine. Number of reducers is set by the job author; hash of key chooses the reducer so equal keys meet. Mapper writes sorted per-reducer partition files to local disk (SSTable-like); when a mapper finishes, reducers fetch their partitions from every mapper = the **shuffle** (no randomness despite the name); reducer merges the sorted files keeping order; output written to the distributed FS (one local copy + replicas). Fig 10-1: three mappers, three reducers (figure not present in text; described by caption/prose).
**Workflows:** a single job is limited (can count views per URL but not rank them). Jobs are chained implicitly by directory names (job 2 reads job 1's output dir); framework sees independent jobs. More like temp files between commands than Unix pipes. Output only valid when the job completes; partial output of failed jobs discarded; so downstream waits for upstream success. Workflow schedulers: Oozie, Azkaban, Luigi, Airflow, Pinball. Workflows of 50-100 jobs common for recommendation systems; many teams read each other's outputs -> tool support essential. Higher-level tools (Pig, Hive, Cascading, Crunch, FlumeJava) wire multi-stage workflows automatically.

### Reduce-side joins and grouping
- Joins are needed wherever code touches both sides of an association (foreign key, document reference, graph edge); denormalising reduces but doesn't remove them. MapReduce has no indexes: it reads whole inputs (full table scan) — outrageous for a few records, reasonable for analytics aggregating many. In batch, "join" means resolving ALL occurrences of an association (all users at once), not one user.
- **Example (Fig 10-2):** activity-events log (fact table) joined to user database (dimension) to correlate pages with age groups. Naive: query remote user DB per event -> throughput bounded by round-trip time, cache effectiveness depends on data distribution, parallel queries can overwhelm the DB, and the job becomes non-deterministic because the remote DB changes. Better: copy the user DB (ETL/backup) into the same distributed FS and join locally. Principle: computation should be local to one machine; no random-access network requests per record.
- **Sort-merge join (Fig 10-3):** one set of mappers emits (userID, event), another emits (userID, dateOfBirth). Partition+sort puts the user record and that user's events adjacent in the same reducer. **Secondary sort** makes the user record arrive first, then events in timestamp order. Reducer keeps one user record in memory, outputs (url, viewer-age) pairs; no network requests.
- **Bringing related data together:** mappers "send messages" to reducers; the key is the destination address. MapReduce separates the physical network communication (getting data to the right place) from application logic, and also shields app code from partial failures (it transparently retries failed tasks). Contrast with DB access buried deep in app code.
- **GROUP BY:** same pattern — mappers key records by the grouping key; reducers aggregate (COUNT, SUM, top-k). **Sessionization:** group all of a user's activity events (scattered across web servers' logs) by session cookie/user id to reconstruct the action sequence, e.g. A/B testing, marketing effect.
- **Skew / hot keys / linchpin objects (celebrities with millions of followers):** one reducer gets disproportionate work and the whole job (and downstream jobs) waits for the slowest reducer. Remedies: Pig *skewed join* — sampling job finds hot keys; records for a hot key are sent to a random one of several reducers, and the other join input's records for that key are replicated to all of them. Crunch *sharded join* — same but hot keys named explicitly. Hive *skewed join* — hot keys declared in table metadata, stored in separate files, joined map-side. For grouping/aggregating a hot key: two stages — first spread to random reducers for partial aggregates, second combines them.

### Map-side joins
- Reduce-side joins need no assumptions about the input but sorting/copying/merging is expensive (data may hit disk several times). Map-side joins: no reducers, no sorting; each mapper reads one input block and writes one output file — requires assumptions.
- **Broadcast hash join:** small dataset fits in memory; every mapper loads it into a hash table and scans its block of the large input. Called replicated join (Pig), MapJoin (Hive), also Cascading, Crunch, Impala. Variation: store the small input as a read-only index on local disk; OS page cache keeps hot parts, nearly as fast without needing it all in RAM.
- **Partitioned hash join (Hive: bucketed map join):** if both inputs are partitioned identically (same key, same hash function, same partition count; e.g. last digit of user ID), each mapper loads only its matching partition into its hash table.
- **Map-side merge join:** if inputs are partitioned AND sorted by the same key, the mapper does the reducer's merge incrementally; no memory limit. Typically means a prior job produced that layout.
- **Workflows with map-side joins:** reduce-side output is partitioned and sorted by join key; map-side output is partitioned/sorted like the large input. Physical layout metadata (number of partitions, keys) matters; kept in HCatalog / Hive metastore.

### The output of batch workflows
- Batch is neither OLTP nor pure analytics; output is often not a report but another structure.
- **Building search indexes:** Google's original use (5-10 jobs). Mappers partition documents; each reducer builds the index for its partition (document-partitioned index) and writes immutable index files. On document change: either rebuild everything and swap wholesale (expensive but "documents in, indexes out" easy to reason about) or build incrementally (Lucene writes new segments and merges in the background; see Ch 11).
- **Key-value stores as batch output:** ML classifiers (spam, anomaly), recommendations (people you may know, related products) produce a DB queried by the web app. Writing record-by-record from mappers/reducers into the production DB is a bad idea: (a) a network request per record is orders of magnitude slower; (b) many parallel tasks can overwhelm the production DB and hurt query performance elsewhere; (c) MapReduce's all-or-nothing guarantee (output = each task run exactly once, retries hidden; failure = no output) is broken by external side effects — partial results visible, task-attempt and speculative-execution duplicates. Better: build a brand-new DB as immutable files in the job output dir and bulk-load into read-only servers (Voldemort, Terrapin, ElephantDB, HBase bulk load). Voldemort keeps serving old files while copying new ones, switches atomically, can switch back since old files remain. Read-only stores need no WAL.
- **Philosophy of batch outputs:** (line 989 on) Unix-like: inputs immutable, previous output fully replaced, no other side effects -> can re-run, tweak, debug freely; easier to maintain (continues below).

### Philosophy of batch outputs (continued, lines 1001-1037)
- **Human fault tolerance:** buggy code writing bad data is fixed by rolling back code and re-running the job, or keeping the old output directory and switching back. Read-write databases lack this (rolling back code does not repair data already written). Minimising irreversibility speeds feature development (Agile).
- Failed tasks are retried automatically on the same input; bug -> fails after a few attempts; transient fault -> tolerated. Safe ONLY because inputs are immutable and failed-task output is discarded.
- Same input files can feed monitoring jobs that check output sanity (e.g. compare to previous run, measure discrepancy).
- Logic separated from wiring (input/output dirs) -> separation of concerns, reuse across teams.
- Difference from Unix: Hadoop uses structured, schema'd formats (Avro, Parquet) instead of untyped text, removing low-value parsing; schemas can evolve.

### Comparing Hadoop to Distributed Databases (1038-1205)
- MapReduce wasn't new: MPP databases (Gamma, Teradata, Tandem NonStop SQL) had the same parallel join algorithms a decade earlier. Difference: MPP = parallel analytic SQL; Hadoop = general-purpose "operating system" that runs arbitrary programs.
- **Diversity of storage:** DB needs a data model up front; files are bytes (text, images, video, sensor data, matrices, genomes). Hadoop allows dumping data first, deciding later; MPP needs careful modelling before import. Argument: making data available quickly, even raw, usually beats deciding the ideal model up front. "Data lake / enterprise data hub"; **schema-on-read** shifts interpretation to the consumer (good when producer and consumers are different teams; there may be no single ideal model). **Sushi principle: "raw data is better".** Hadoop commonly used for ETL: dump raw data, jobs clean/transform to relational form, load into an MPP warehouse; modelling happens, but decoupled from collection.
- **Diversity of processing models:** MPP = monolithic, tightly tuned, SQL accessible to BI tools (Tableau), but ML, recommendations, full-text ranking, image analysis, feature engineering, fraud scoring need code, not queries. MapReduce lets engineers run own code; you can build SQL on top (Hive) but also other processes. Later models built on Hadoop because MapReduce was limiting/slow; all run on one shared cluster over the same files — no copying data between specialised systems. HBase (OLTP) and Impala (MPP analytic) coexist on HDFS without MapReduce.
- **Designing for frequent faults:** batch is less sensitive to faults (no user waiting, re-runnable). MPP aborts the whole query on node crash and retries (queries are seconds/minutes; keeps data in memory). MapReduce retries per task and writes to disk eagerly (fault tolerance + assumes data bigger than RAM); worthwhile for big, long jobs likely to see at least one task failure. But machine failures are rare — why the overhead? Because at Google, batch ran at low priority on mixed-use machines with containers/priorities/pricing and could be PREEMPTED. An hour-long task has ~5% chance of being killed for a higher-priority process (more than an order of magnitude more than hardware failures); 100 tasks of 10 min -> >50% chance at least one is killed. So task-level retry exists to enable overcommitment/better utilisation, not because hardware is flaky. Open-source schedulers rarely preempt (YARN CapacityScheduler some; Mesos/Kubernetes/YARN no general priority preemption), so MapReduce's design makes less sense there.

## Beyond MapReduce (1210-1410)
- MapReduce is a good learning tool (simple to understand, hard to use: e.g. implement joins from scratch). Pig/Hive/Cascading/Crunch lighten it. But the execution model itself is slow for some work; it is very robust (arbitrarily large data on unreliable multi-tenant systems), yet other tools can be orders of magnitude faster.
### Materialization of intermediate state
- MapReduce jobs only touch the world via input/output directories; external scheduler must start job 2 after job 1. Good when output is a published dataset reused by many teams (loose coupling via well-known location). But when output only feeds one job of the same team it's just intermediate state (50-100 job recommendation workflows have lots). Writing it out = **materialization** (eager compute and write, as with materialized views). Unix pipes stream instead with a small buffer.
- Downsides of full materialization: (1) next job waits for all prior tasks including **stragglers** (pipes start concurrently); (2) mappers often redundant — they just reread what a reducer wrote; could chain reducers if partitioning/sorting already matches; (3) replicating temp files across HDFS nodes is overkill.
### Dataflow engines (Spark, Tez, Flink; based on research Dryad, Nephele)
- Treat the whole workflow as ONE job. User-defined functions = **operators**, not forced alternation of map/reduce; options to connect operators: repartition+sort by key (shuffle; sort-merge joins, grouping); partition the same way without sorting (partitioned hash joins); broadcast one output to all partitions (broadcast hash join).
- Advantages: sort only where needed; no redundant mappers; scheduler sees all dependencies so can optimise locality (shared-memory buffer); intermediate state kept in memory or local disk, not replicated HDFS; operators start as soon as input ready; JVM processes reused (MapReduce starts a new JVM per task). Same Pig/Hive/Cascading code can switch from MapReduce to Tez/Spark by configuration. Tez is a thin library over YARN shuffle service; Spark and Flink are big frameworks with own network layer, scheduler, APIs.
### Fault tolerance in dataflow engines
- MapReduce: materialised on HDFS = durable, just rerun task. Spark/Flink/Tez: lost intermediate state is RECOMPUTED from earlier stage or original input; framework tracks lineage — Spark **RDD** tracks ancestry; Flink **checkpoints operator state**.
- Need **determinism** when recomputing: if a recomputed operator emits different data than what was already sent downstream, downstream must be killed and rerun (cascading faults). Nondeterminism sneaks in via hash-table iteration order, randomness (use fixed seeds), system clock, external data sources. When intermediate data is much smaller than source data or computation is very CPU-heavy, materialising is cheaper than recomputing.
### Discussion of materialization
- MapReduce ~ temp files; dataflow ~ pipes. Flink is built around pipelined execution. Sorting must consume all input before output (the last record could be the smallest) so sort operators accumulate state. Final outputs and inputs still durable on HDFS; inputs immutable, output replaced entirely.

## Graphs and Iterative Processing (1413-...)
- Batch graph analysis over a whole graph (PageRank, recommendations, ranking). Dataflow-engine DAGs are NOT graph processing (naming confusion: the operators form a graph; data are tuples).
- Graph algorithms traverse an edge at a time, propagating info until a condition (no edges left / metric converges), e.g. transitive closure (the NA locations example from Ch2). Plain MapReduce does a single pass, so iteration is driven by an external scheduler: run a step, check completion, repeat. Very inefficient on MapReduce: reads whole input and writes whole new output each round even if little changed.
- **Pregel / bulk synchronous parallel (BSP):** (Giraph, Spark GraphX, Flink Gelly). Vertices "send messages" along edges; each iteration calls a function per vertex with its incoming messages (like reducer); BUT the vertex keeps state in memory between iterations, so only new messages need processing; no messages = no work. Like actor model but state + messages are fault-tolerant/durable and delivery is in fixed rounds.
- **Fault tolerance:** vertices only communicate by messages (so batched, less waiting; waits only between iterations). Despite networks dropping/duplicating/delaying messages, Pregel guarantees each message processed exactly once at its destination vertex in the next iteration. Done by checkpointing all vertex state at the end of an iteration; on node failure roll the whole graph back to the last checkpoint, or (if deterministic and messages logged) recover only the lost partition.
- **Parallel execution (graphs):** a vertex doesn't know its machine; sends messages to vertex IDs; framework partitions the graph (usually by arbitrary vertex ID, because optimal colocation is hard). Result: lots of cross-machine traffic; the message state is often bigger than the graph itself. If the graph fits in one machine's memory, a single-machine (even single-threaded) algorithm likely beats the distributed one; if it fits on one machine's disk, GraphChi-style processing is viable; only if too big use Pregel-like distributed processing.

## High-Level APIs and Languages (1524-1628)
- Infrastructure now robust at PB scale / 10,000+ machines; focus has moved to programming model and efficiency. Hive/Pig/Cascading/Crunch exist because hand-written MapReduce is laborious; they could move to Tez without rewrites. Spark and Flink have own high-level dataflow APIs (inspired by FlumeJava) using relational building blocks: join, group, filter, aggregate. Benefits: less code, interactive use in a shell (incremental exploration, Unix-like), and machine-level efficiency.
- **Move toward declarative:** stating the join lets a cost-based optimiser (Hive, Spark, Flink) choose the join algorithm and even reorder joins to minimise intermediate state. But MapReduce heritage is function callbacks, which allow arbitrary code and reuse of library ecosystems (parsing, NLP, image analysis, stats) — what distinguishes it from MPP databases, whose UDFs are cumbersome and poorly integrated with package managers (Maven, npm, Rubygems). Yet declarative pieces help even for simple filters/projections: avoids per-record function-call CPU overhead, allows column-oriented reads (only required columns) and **vectorized execution** (tight inner loops, cache-friendly; Spark generates JVM bytecode, Impala uses LLVM). Result: batch frameworks approach MPP DB performance while keeping flexibility.
- **Specialisation for domains:** reusable building blocks: ML (Mahout on MapReduce/Spark/Flink; MADlib inside an MPP DB), spatial algorithms (k-nearest neighbours / similarity search), approximate string search for genomics. Batch engines and MPP databases converge: "they are all just systems for storing and processing data."

## Summary of Ch10 (1629-1707)
- Design principles carried from Unix: immutable inputs, outputs become input to unknown programs, compose small tools. Uniform interface: files/pipes in Unix, distributed FS in MapReduce; dataflow engines add pipe-like transport but job inputs/outputs usually still HDFS.
- Two problems frameworks solve: **Partitioning** (mappers by input block; repartition+sort+merge into reducer partitions to bring related data — same key — together; dataflow engines avoid sorting unless required) and **Fault tolerance** (MapReduce writes to disk often -> easy per-task recovery but slower; dataflow engines keep more in memory -> recompute more on failure; deterministic operators reduce recomputation).
- Join recap: sort-merge, broadcast hash, partitioned hash.
- **Restricted programming model on purpose:** callbacks are stateless and have no externally visible side effects besides their designated output; so tasks can be retried safely, failed task output discarded, and if several attempts succeed only one's output becomes visible. Framework guarantees the final output equals a fault-free run — far stronger than typical online services that write to DBs as a side effect of requests.
- Defining feature: input is **bounded** (known fixed size, e.g. a snapshot or set of log files) so the job knows it's finished. Stream processing = unbounded input, job never completes.

## Ch10 — Failure modes / pitfalls
- Per-record network requests to a remote DB from a batch job: slow, nondeterministic (DB changes during run), can overwhelm the DB.
- Writing batch output straight into a production DB: slow, overloads it, exposes partial results from failed/retried/speculative tasks; side effects defeat all-or-nothing.
- Hot keys/skew: one reducer holds up the entire job and downstream stages (stragglers).
- Nondeterministic operators (hash iteration order, random numbers, clock, external data) break recomputation -> cascading reruns.
- Full materialisation: stragglers block next stage; redundant mappers; over-replication of temp data.
- Distributed graph processing with arbitrary partitioning: huge message overhead; a single machine often wins.
- Preemption: low-priority batch jobs get killed often; design for retries.
- Full-scan joins are awful for a few records (no index).
- Schema-on-read / data lake: interpretation pushed to the consumer; risk of "indiscriminate dumping".

## Ch10 — Key terms
- *System of record* — authoritative copy. *Derived data* — recreatable result (cache, index, view).
- *Batch job* — bounded input -> output, throughput-oriented. *Bounded/unbounded* — finite/never-ending input.
- *Mapper / reducer* — key-value extraction callback / group-processing callback. *Shuffle* — partition+sort+copy mapper output to reducers. *Secondary sort* — control ordering of values within a key group.
- *Sort-merge join* (reduce-side), *broadcast hash join*, *partitioned (bucketed) hash join*, *map-side merge join*.
- *Sessionization* — group a user's events into a session. *Hot key / linchpin object / skew* — disproportionately busy key.
- *Materialization* — eagerly writing intermediate results to storage. *Dataflow engine* — runs a whole multi-stage workflow as one job (Spark, Tez, Flink). *Operator* — generalised map/reduce function.
- *RDD* — Spark's lineage-tracking dataset. *Pregel/BSP* — vertex-message-in-rounds graph model. *Straggler* — slow task holding up a stage.
- *HDFS/NameNode, erasure coding, shared-nothing vs shared-disk (NAS/SAN)*. *MPP database* — parallel analytic SQL DB. *Data lake, schema-on-read, sushi principle.* *Human fault tolerance* — recovering from buggy code by re-deriving data.
- *Declarative query / cost-based optimiser; vectorized execution.*

## Ch10 — Relevance to PACE (multi-tenant Node/Express + Supabase Postgres, small host, daily batch jobs, send queue)
Applies directly:
- **Re-runnable jobs.** The core batch lesson: treat the job's input as immutable/read-only, write results to a distinct place, keep job logic free of hidden side effects, so a crashed run can simply be run again. For daily follow-up and mailbox-sweep jobs: derive "what to send/sweep" from a snapshot of state, record outcomes idempotently (a unique key per intended send, status column), and make a second run of the same job a no-op for work already done. The text's key sentence: automatic retry is only safe because inputs are immutable and failed-task output is discarded. Email is an external side effect that CAN'T be rolled back, so the all-or-nothing guarantee MapReduce gives does not carry over; need explicit dedupe/claim (the book's warning about writing to external systems from inside a job).
- **Human fault tolerance:** keep derived tables (follow-up schedule, sweep summaries, search/score caches) re-derivable from the system of record so a code bug is fixed by deploying the fix and re-deriving, not by hand-repairing data. Distinguish system of record (submissions, candidates, emails sent) from derived data (counts, queues, caches, conversation-intel summaries).
- **Don't hit the DB once per record from a batch** — read in sets (one SQL query / join in Postgres) rather than N+1 round trips; do the join in SQL (the DB already does hash/merge joins) not in app code per row. Postgres is the "MPP-lite" here.
- **Bulk-write instead of record-at-a-time; don't overwhelm the production DB** with a batch burst while users are active; throttle/batch the daily jobs and run off-peak (free-tier host).
- **Swap-in outputs:** build new derived data separately and switch atomically (like Voldemort's atomic switch) — e.g. rebuild a derived table then swap, or write a new version id and flip a pointer, rather than half-updating live rows.
- **Monitoring job output:** compare each run to the previous run and flag anomalies (e.g. today's sweep processed 0 messages while yesterday processed hundreds) — the text suggests monitoring jobs that evaluate whether output has expected characteristics. Directly addresses "a job that silently does nothing".
- **Skew:** a single tenant/mailbox with huge volume can hold up a per-tenant loop — process tenants independently with per-tenant limits so one hot tenant doesn't block others.
- **Unix mindset:** small single-purpose jobs, clear input/output, inspectable intermediate results (write stage output to a table you can query/restart from).
- **Bounded vs unbounded:** a daily job sees a bounded slice; choosing the slice boundary (by a stable watermark/high-water mark column, not "now") makes re-runs deterministic. Avoid nondeterminism (current time, random ordering) inside the unit of work, or capture it once as an input.
Only matters at much larger scale: HDFS, shuffle, skewed-join variants, broadcast vs partitioned joins, dataflow engines, Spark/Flink/Tez, preemption economics, Pregel/graph partitioning, vectorized execution, erasure coding, MPP vs Hadoop. If a data-lake/analytics need arises later, a Postgres replica/warehouse export (ETL) is the first step, not Hadoop.

# CHAPTER 11 — Stream Processing (part 1: source lines 1927-2500)

## Core argument
Batch assumes bounded input, but real data arrives forever; batch jobs chop it into fixed windows (daily/hourly), so results lag. Stream processing removes the slicing by processing each event as it happens. This chapter covers: how event streams are transmitted (messaging systems, brokers, partitioned logs), how streams relate to databases (change data capture, event sourcing, immutability, state vs. changelog), and how streams are processed (use cases, time reasoning, joins, fault tolerance). A recurring thread: a durable, ordered, replayable log (as in database replication) is the unifying primitive that keeps derived systems consistent with a system of record and gives streaming the same repeatability and fault tolerance that batch gets from immutable inputs.

## Intro (1927-1969)
- Unbounded data: users generate data today, yesterday and tomorrow; dataset never "complete". Batch artificially splits into fixed durations. Daily batch delays results by a day; shrink the window (per second) or go continuous = stream processing. "Stream" = data incrementally available over time (stdin/stdout, lazy lists, file streams, TCP, audio/video).

## Transmitting Event Streams (1970-2379)
- **Event** = small, self-contained, immutable record of something that happened at a time (usually with a time-of-day timestamp): user action, sensor reading, metric, web log line, DB write. Encoded as text/JSON/binary; can be appended to a file, inserted in a table, or sent over the network. Generated once by a **producer** (publisher/sender), processed by possibly many **consumers** (subscribers/recipients); related events grouped into a **topic/stream**.
- Plain file/DB could connect producers and consumers (consumers poll for new events) but **polling gets expensive at low latency**: the more often you poll, the lower the fraction of polls returning anything. Better to notify consumers. DB triggers exist but are limited and an afterthought, so specialised tools were built.

### Messaging systems
- Pub/sub with many producers and many consumers per topic (unlike pipe/TCP = one-to-one). Two questions to differentiate systems: (1) **Producers faster than consumers?** options: drop messages, buffer in a queue (what if queue outgrows memory? spill to disk? performance effect?), or **backpressure/flow control** (block the producer; Unix pipes and TCP). (2) **What if nodes crash/go offline — are messages lost?** Durability costs (disk writes/replication); if loss is acceptable you get higher throughput/lower latency. Loss tolerance depends on app: periodic sensor readings can lose a point (but beware, large silent loss makes metrics wrong); event COUNTERS need reliable delivery.
- Contrast: batch gives retry + discard-partial-output semantics so output equals a fault-free run; later in chapter shows equivalents for streams.
- **Direct messaging (no broker):** UDP multicast (finance market feeds; app-level retransmission, producer must remember sent packets), brokerless libs (ZeroMQ, nanomsg), StatsD/Brubeck (UDP metrics; counters only approximate), and direct HTTP/RPC calls = **webhooks** (callback URL registered with another service). Fine for what they're designed for, but app code must handle message loss; they assume producers and consumers are always online; an offline consumer misses messages; a producer retry buffer is lost if the producer crashes.
- **Message brokers (message queues):** a server/database optimised for message streams; producers write, consumers read. Centralising data tolerates clients that come/go/crash; durability becomes the broker's job (memory-only or disk). Generally allow unbounded queueing for slow consumers. Consumers are **asynchronous**: producer waits only for the broker's confirmation of buffering, delivery occurs later (usually sub-second; longer with backlog).
- **Brokers vs databases:** some brokers join 2PC (XA/JTA). Differences: DBs keep data until explicitly deleted; brokers auto-delete after successful delivery (not for long-term storage). Brokers assume short queues (long backlogs hurt throughput). DBs have secondary indexes/search; brokers offer subscription to topic patterns. DB query = point-in-time snapshot (client isn't told later changes unless it re-queries/polls); brokers don't support arbitrary queries but notify when data changes. Standards/software: JMS, AMQP; RabbitMQ, ActiveMQ, HornetQ, Qpid, TIBCO EMS, IBM MQ, Azure Service Bus, Google Cloud Pub/Sub.
- **Multiple consumers (Fig 11-1):** *Load balancing* (each message to ONE consumer; share work; for expensive-to-process messages; AMQP: multiple clients on one queue; JMS: shared subscription) and *fan-out* (each message to ALL consumers; independent consumers like multiple batch jobs reading the same file; JMS topic subscriptions, AMQP exchange bindings). Can combine: groups of consumers, each group gets all messages, one node per message within a group.
- **Acknowledgments and redelivery:** consumers can crash mid-process, so the client must explicitly ack when done; no ack (connection closed/timeout) -> broker redelivers to another consumer. The message might actually have been fully processed with only the ack lost; handling that needs atomic commit. **Load balancing + redelivery reorders messages** (Fig 11-2: consumer 2 crashes on m3, m3 redelivered to consumer 1 after m4, ordering m4, m3, m5). Even JMS/AMQP can't prevent this; use a separate queue per consumer to avoid it. Matters only when messages have causal dependencies.

### Partitioned logs
- Conventional brokers: transient mindset, receiving/acking is destructive, a new consumer sees only messages sent after it registers, you can't re-run a consumer for the same result. Databases/files: permanent. Hybrid = **log-based message broker**: durable storage + low-latency notification.
- **Using logs for message storage:** a log = append-only sequence on disk. Producer appends; consumer reads sequentially, waits for notification at the end (like `tail -f`). To scale, **partition** the log across machines; a **topic** = group of partitions carrying the same type of message. Within a partition each message gets a monotonically increasing **offset**, total order inside a partition; NO ordering guarantee across partitions (Fig 11-3). Implementations: Apache Kafka, Amazon Kinesis Streams, Twitter DistributedLog; Google Cloud Pub/Sub is architecturally similar with a JMS-style API. Millions of messages/second via partitioning, fault tolerance via replication.
- **Logs vs traditional messaging:** fan-out is trivial (reading doesn't delete). Load balancing is by assigning whole PARTITIONS to consumer-group nodes; each consumer reads its partition sequentially, single-threaded. Downsides: max consumers = number of partitions; one slow message blocks later messages in that partition (head-of-line blocking). So: expensive-per-message processing with parallelism per message and little ordering need -> JMS/AMQP style; high throughput, fast messages, ordering important -> log-based. (Footnote: parallelism is best raised by adding partitions rather than thread pools, which complicate offset tracking.)
- **Consumer offsets:** everything below the offset is processed, above is not; broker records only periodic offsets, not per-message acks -> less bookkeeping, batching/pipelining, higher throughput. Offset ≈ replication log sequence number (broker = leader, consumer = follower). If a consumer fails, another takes its partitions starting at the last recorded offset; messages processed after the last recorded offset are processed AGAIN (to be handled later in the chapter).
- **Disk space usage:** log divided into segments; old segments deleted or archived. A slow consumer whose offset points to a deleted segment misses messages: the log is a bounded **circular/ring buffer** on disk. Back-of-envelope: a 6 TB drive writing at 150 MB/s fills in ~11 hours at full rate; in practice days or weeks of retention. Throughput stays roughly constant regardless of retention (everything is written to disk anyway), unlike in-memory brokers that slow down when spilling to disk.
- **Consumers can't keep up:** the log-based approach is buffering with a large fixed-size buffer; monitor consumer lag vs the head of the log and alert; big buffer gives humans time to fix before messages are lost. Only that consumer is affected, so you can experimentally consume a production log without disrupting others; a stopped consumer leaves only its offset (unlike traditional brokers where orphaned queues keep accumulating messages and eating memory).
- **Replaying old messages:** consuming is read-only; the only side effect is the offset moving, which the consumer controls. Start a copy with yesterday's offset and write output elsewhere to reprocess; repeat with changed code. Makes streams like batch: derived data is cleanly separated from input via a repeatable transformation; easier error recovery; good for integrating dataflows across an organisation.

## Databases and Streams (2380-...)
- A write to a database is itself an event. A replication log is a stream of DB write events. **State machine replication:** if every replica processes the same deterministic events in the same order, they end in the same state.
### Keeping systems in sync
- Most apps combine OLTP DB + cache + search index + warehouse; each holds its own representation and must be kept in sync. Warehouse sync usually = ETL (full copy, transform, bulk load: a batch process). If full dumps are too slow: **dual writes** (app writes DB, then search index, then invalidates cache). Problems: (1) **race condition (Fig 11-4)** — two clients' writes reach the DB in order A,B but reach the search index in order B,A; final values differ permanently and no error occurs; unnoticed unless version vectors/concurrency detection; (2) **partial failure** — one write succeeds and the other fails -> inconsistency; making both atomic = atomic commit/2PC, expensive. Root cause: no single leader across the systems (like multi-leader replication conflicts). Better: one leader (the DB) and make the others followers.
### Change data capture (CDC)
- Replication logs were historically internal implementation details, not public APIs; many DBs had no documented way to get the change log. CDC = observing all writes to a DB and extracting them for replication to other systems, ideally as a stream immediately. Apply the changes to a search index in the same order -> index matches the DB (Fig 11-5). Derived systems (search index, warehouse, cache) are consumers of the change stream; i.e. one database is the leader, others followers. A log-based broker is a good transport because it preserves ordering (avoids the Fig 11-2 reordering).

### Change data capture (continued, source 2501-2583)
- **Implementation options:** DB triggers writing into a changelog table (fragile, performance overhead) vs parsing the replication log (more robust, but schema changes are hard). Tools: LinkedIn Databus, Facebook Wormhole, Yahoo Sherpa; Bottled Water (PostgreSQL WAL decoding), Maxwell and Debezium (MySQL binlog), Mongoriver (MongoDB oplog), GoldenGate (Oracle). CDC is usually asynchronous: the source doesn't wait for consumers (a slow consumer doesn't hurt the source) but all replication-lag problems apply.
- **Initial snapshot:** the full log lets you rebuild state, but keeping every change forever is costly; log gets truncated. Building a new index needs the whole dataset, not just recent changes, so start from a consistent snapshot that corresponds to a known log position/offset, then apply changes after it. Some CDC tools integrate this, others leave it manual.
- **Log compaction:** keep only the latest record per key (older duplicates discarded in the background; a null "tombstone" marks deletion). Disk size depends on current DB contents, not on write count. Works for CDC if each change carries a primary key and replaces the previous value. Then a new derived system starts at offset 0 of the compacted topic and scans to get a full copy without a new snapshot. Kafka supports it; lets a broker be durable storage not just transient messaging.
- **API support for change streams:** databases increasingly make change streams first-class: RethinkDB (subscribe to query result changes), Firebase and CouchDB (change feed sync), Meteor (MongoDB oplog drives UI), VoltDB (a special output-stream table that transactions insert into, cannot be queried, consumed asynchronously in commit order). Kafka Connect integrates CDC tools for many databases into Kafka.

### Event Sourcing (2584-2683)
- From domain-driven design (DDD). Like CDC, stores all changes as a log of events; differs in abstraction level. **CDC:** app uses the DB mutably (update/delete); changes extracted at low level (replication log), preserving true write order (avoids the Fig 11-4 race); app is unaware. **Event sourcing:** app logic is built on immutable events in an append-only event store; updates/deletes discouraged/prohibited; events reflect application-level things that happened.
- Benefits: more meaningful data modelling (record the user's action, not its effect on mutable tables), easier evolution, easier debugging/understanding why something happened, guards against bugs. Example: "student cancelled enrollment" (intent, neutral) vs side effects (deleted row, added feedback row) that embed assumptions; a new feature (offer place to next person on waiting list) can chain off the existing event. Similar to chronicle data model and fact tables in star schemas. Specialised DB: Event Store; but can be built on a normal DB or a log-based broker.
- **Deriving current state:** users want current state (cart contents), so transform the event log into application state with deterministic logic (re-runnable). Log compaction differs: a CDC event holds the full new record, so only the latest per key matters and compaction works; event-sourced events express intent so later events don't override earlier ones — full history required, compaction not possible the same way. Apps use snapshots of derived state as a performance optimisation only; the intention is to keep all raw events and reprocess when needed.
- **Commands vs events:** a request is first a command, which can still fail (validate integrity: username free? seat free?). Once accepted it becomes an event: durable, immutable, a fact. Later change/cancel is a new event. A consumer cannot reject an event. So validation must be synchronous before the event is written (e.g. serializable transaction that validates and publishes atomically) or split into tentative reservation event + later confirmation event, letting validation run asynchronously.

### State, Streams, and Immutability (2684-2864)
- Immutability is what makes batch re-runs safe and what makes event sourcing/CDC powerful. Mutable state and an append-only log are two sides of the same coin: state = integral of the event stream over time; change stream = derivative of state (Fig 11-6; analogy has limits). Store the changelog durably -> state is reproducible. If you treat the log as system of record, state is derived. Quote from Pat Helland: the truth is the log; the database is a cache of a subset of the log (the latest values). Log compaction bridges log and state.
- **Advantages of immutable events:** accountants' append-only ledger — mistakes are corrected by adding a compensating transaction, never erasing; incorrect entry stays for audit; published wrong figures corrected in the next period. Auditability useful beyond finance; with append-only events it's easier to diagnose and recover from buggy code than if code destructively overwrote data. Events keep more information than state (e.g. cart add then remove: useful analytics signal lost if the row was deleted).
- **Deriving several views from the same log:** read-optimised views (Druid ingests directly from Kafka; Pistachio KV store uses Kafka as commit log; Kafka Connect sinks to various DBs/indexes). Build a new view for a new feature and run old and new side by side instead of a complex schema migration; shut the old one down later. Separating write form from read form = **CQRS** (command query responsibility segregation). The "fallacy" that data must be written in the form it'll be queried; normalisation/denormalisation debates matter less if views are derived (denormalise freely in views because translation keeps them consistent). Example: Twitter home timelines are denormalised read state kept in sync by the fan-out service.
- **Concurrency control:** downside — consumers are usually async, so a user may write and then read a stale view (read-your-writes problem). Fixes: update the read view synchronously with the log append via a transaction (same storage system or distributed transaction) or use total-order-broadcast based linearizable storage. Upside — multi-object transactions are often needed because one user action changes several places; with event sourcing an event can be a self-contained description of the action = single append, easy to make atomic. If log and state are partitioned the same way, a single-threaded consumer per partition needs no concurrency control (serial order; removes nondeterminism). Events touching several partitions need more work (Ch12).
- **Limitations of immutability:** many systems rely on immutability internally (MVCC snapshots, Git/Mercurial/Fossil). Feasibility depends on churn: append-mostly workloads are easy; high update/delete rate on a small dataset makes history grow big, fragmentation, compaction/GC performance matter. Also legal/administrative deletion needs (privacy regulations after account closure, data protection corrections, leaked sensitive info): appending a "deleted" event isn't enough — you must rewrite history (Datomic "excision", Fossil "shunning"). Truly deleting is hard: SSDs/filesystems write elsewhere, backups are deliberately immutable. Deletion is more "making it harder to retrieve" than impossible.

## Processing Streams (2865-...)
- Three things to do with a stream: (1) write events to a DB/cache/search index (keeping a store in sync; stream-side analogue of batch output); (2) push to humans (email alerts, push notifications, live dashboards); (3) process input streams into output streams (a pipeline) — the rest of the chapter. A stream processing piece of code = **operator or job**, like a Unix process/MapReduce job: reads inputs read-only, writes append-only output. Partitioning/parallelism/map/filter are like Ch10.
- Crucial difference: stream never ends -> sorting doesn't make sense so sort-merge joins don't apply; fault tolerance changes: a batch job running minutes can restart from the start, a stream job running for years cannot.

### Uses of stream processing
- Monitoring/alerting: fraud detection (card usage pattern changes), trading systems, factory machine monitoring, military/intelligence. Need sophisticated pattern matching.
- **Complex event processing (CEP):** 1990s; search for patterns of events in a stream like regex over characters. Declarative query language (SQL-like) or GUI; engine keeps a state machine; on match emits a complex event. Roles reversed vs DB: queries stored long-term, events flow past them. Implementations: Esper, IBM InfoSphere Streams, Apama, TIBCO StreamBase, SQLstream; Samza gaining SQL.
- **Stream analytics:** aggregations and statistics over many events: rate of an event type, rolling average, compare to previous intervals (same time last week). Over fixed-length **windows** (e.g. last 5 minutes: queries/sec, p99 latency; smooths fluctuation yet stays timely). May use probabilistic algorithms (Bloom filters for set membership, HyperLogLog for cardinality, percentile estimators) — approximate but much less memory; but stream processing is NOT inherently approximate. Frameworks: Storm, Spark Streaming, Flink, Concord, Samza, Kafka Streams; hosted: Google Cloud Dataflow, Azure Stream Analytics.
- **Maintaining materialized views:** CDC-driven caches/indexes/warehouses are materialised-view maintenance. In event sourcing, app state is a materialised view needing a window back to the beginning of time (minus compacted events); runs against assumptions of window-oriented analytics frameworks; Samza and Kafka Streams support it on Kafka's compaction support (continues).

### Materialized views, continued; Search on streams; Message passing and RPC (3001-3047)
- Samza and Kafka Streams support unbounded-history materialised views on Kafka log compaction.
- **Search on streams:** search individual events by complex criteria (full-text). Media monitoring subscribes to news feeds and matches stored queries; real-estate sites notify on new matching listings; Elasticsearch **percolator**. Inverts search: queries stored, documents run past them (like CEP). Simple: test every document against every query (slow with many queries); optimise by indexing the queries too.
- **Message passing/actors vs stream processing:** actors manage concurrency and distributed execution; communication ephemeral, one-to-one, arbitrary (even cyclic request/response); stream processors are a data management technique with durable multi-subscriber logs and acyclic pipelines where each stream derives from defined inputs. Crossover: Storm's distributed RPC. Actor frameworks often don't guarantee delivery on crash -> not fault tolerant without extra retry logic.

### Reasoning About Time (3048-3203)
- Batch uses the timestamps embedded in events (not the system clock of the run), which also makes processing deterministic. Many stream frameworks window by local **processing time** — simple and fine if lag is negligible, wrong with significant lag.
- **Event time vs processing time:** delay causes: queueing, network faults, contention/performance, consumer restart, reprocessing old events after a bug fix or fault. Delays also reorder messages (A then B requests, but B's event reaches the broker first). Star Wars release-order analogy: processing order (release/viewing) differs from event order (episode number). Confusing them yields bad data: after a one-minute redeploy, measuring request rate by processing time shows a false spike when the backlog is processed (Fig 11-7: windowing by processing time creates artifacts).
- **Knowing when you're ready:** with event-time windows you never know whether all events for a window have arrived (the 37th-minute window). Timeout-based close still leaves **straggler** events (e.g. buffered on another machine). Options: (1) ignore stragglers, track dropped count as a metric and alert if significant; (2) publish a **correction** (updated value, possibly retracting the previous output). Alternatively a special message "no more messages earlier than t" lets consumers trigger windows, but with multiple producers the consumer must track each producer's threshold individually, making adding/removing producers harder.
- **Whose clock?** Events buffered at several points (mobile app offline for hours/days) look like extreme stragglers. Device clock is the meaningful one but untrustworthy (can be wrong deliberately/accidentally); server receive time is trustworthy but less meaningful. Remedy: log three timestamps — event time (device clock), send time (device clock), receive time (server clock); (receive − send) estimates the clock offset (if network delay is negligible), apply it to the event time. Batch has the same problem; just more visible in streams.
- **Types of windows:** *Tumbling* (fixed length, each event in exactly one; round timestamp down). *Hopping* (fixed length, overlapping, e.g. 5 min with 1-min hop; compute from 1-min tumbling windows). *Sliding* (all events within some interval of each other; keep a time-sorted buffer and evict expired events). *Session* (no fixed duration; group a user's events close in time; ends after inactivity, e.g. 30 min).

### Stream Joins (3204-3350)
- Same need as batch joins but harder because new events can arrive any time. Three types:
- **Stream-stream (window) join:** e.g. click-through rate: join search events and click events on session ID. A click may never come, may take seconds to weeks, may arrive before the search event; choose a window (e.g. one hour). Embedding search details in the click event is NOT equivalent (you'd miss searches without clicks, so CTR would be wrong). Needs state: last hour's events indexed by session ID; emit "clicked result" on match; if a search event expires with no click, emit "not clicked".
- **Stream-table join (enrichment):** enrich activity events with user profile data. Querying a remote DB per event is slow and risks overload; instead load a local copy (in-memory hash table or local-disk index; like a map-side hash join). Unlike batch (point-in-time snapshot), the stream processor is long-running so the local copy must be updated: subscribe to the profile DB's changelog via CDC = a join between two streams. Differs from stream-stream in that the changelog side uses a window reaching back to the beginning of time (newer versions overwrite older), and the stream side might keep no window.
- **Table-table join (materialized view maintenance):** Twitter timeline cache: on tweet, add to followers' timelines; on delete, remove; on follow, add the followee's recent tweets; on unfollow, remove. The processor consumes tweet and follow event streams and maintains the followers set. Equivalent to maintaining the materialised view of a SQL join (tweets JOIN follows ... GROUP BY follower). Footnote: product rule — (u·v)' = u'v + uv'; every change of tweets joins with current followers, and every change of followers joins with current tweets.
- **Time-dependence of joins:** all three need state based on one input queried by the other; the order of state-maintaining events matters (follow then unfollow vs the reverse). Ordering is preserved within a partition but not across streams/partitions. Which profile version applies to an activity event processed near an update? Example: tax rate at time of sale vs today's rate when reprocessing history. Unordered cross-stream events -> nondeterministic join; rerunning may give different output. Data warehouse name: **slowly changing dimension (SCD)**; fix: give each version of the joined record a unique identifier (new tax-rate id when it changes; invoice stores the id), which makes the join deterministic but prevents log compaction (all versions kept).

### Fault Tolerance (3351-3472)
- Batch tolerates faults easily: immutable inputs, per-task output files, output visible only on success; result "as if each record was processed exactly once" = **exactly-once semantics** (better named "effectively-once"). In streaming, you can't wait for a task to finish before exposing output (infinite).
- **Microbatching and checkpointing:** *Microbatching* (Spark Streaming): treat small blocks (~1 s) as mini batch jobs; size is a compromise (smaller = more scheduling overhead, larger = more delay); implicit tumbling window equal to batch size by processing time; larger windows need explicit state carried over. *Checkpointing* (Flink): rolling state checkpoints to durable storage, triggered by barriers in the stream; on crash restart from last checkpoint and discard output after it. Both give exactly-once WITHIN the framework; once output leaves (database write, external broker, **emails**), the framework can't discard it, so a restart repeats the external side effect.
- **Atomic commit revisited:** to appear exactly-once, all outputs and side effects of processing an event must take effect iff processing succeeds: messages to downstream operators/external systems (including email and push notifications), DB writes, operator state changes, and input acknowledgement (consumer offset advance). Needs atomic commit as in Ch 9, but efficient in restricted environments (Google Cloud Dataflow, VoltDB, planned for Kafka): no heterogeneous cross-tech transactions like XA; state and messaging managed internally by the framework; overhead amortised by handling several input messages per transaction.
- **Idempotence:** alternative to distributed transactions. Idempotent operation: doing it many times = once (setting a key to a value is idempotent; incrementing a counter is not). Make non-idempotent ops idempotent with extra metadata: store the Kafka offset of the message that caused the last write alongside the value, so a repeat is detected and skipped (Storm Trident similar). Assumptions: replay the same messages in the same order (log-based broker), deterministic processing, no other node concurrently updates the same value. On failover, **fencing** may be needed to stop a node thought dead but still alive. Effective with small overhead.
- **Rebuilding state after failure:** windowed aggregates, join tables/indexes need recoverable state. Options: remote replicated datastore (slow per-message queries); local state replicated periodically — Flink snapshots operator state to HDFS; Samza/Kafka Streams send state changes to a log-compacted Kafka topic (CDC-like); VoltDB processes each input redundantly on several nodes. Or rebuild from input: replay a short window, or rebuild a CDC-maintained local DB replica from the compacted change stream. No universal trade-off; depends on network vs disk latency/bandwidth.

## Summary of Ch11 (3473-3549)
- Stream processing = batch ideas on unbounded input; brokers and logs = streaming's filesystem.
- **Two broker types:** AMQP/JMS style (broker assigns individual messages to consumers, per-message ack, deleted after ack; good as asynchronous RPC / task queue where order doesn't matter and no replay) vs log-based (all messages of a partition to one consumer in order, parallelism by partitioning, consumers checkpoint offsets, retained on disk so replay is possible; fits stream processing that creates derived state/streams).
- Sources of streams: user events, sensors, data feeds, and database writes (changelog via CDC or event sourcing); log compaction keeps a full copy. Treating DBs as streams lets you keep indexes/caches/analytics continuously in sync and build fresh views by replaying from the beginning.
- Purposes: CEP, windowed analytics, materialised views. Time pitfalls: processing time vs event time, stragglers. Joins: stream-stream (events within a window; may be a self-join), stream-table (activity stream + DB changelog -> enriched events), table-table (two changelogs -> stream of changes to the materialised join).
- Fault tolerance: long-running + continuous output means you can't discard all output, so use finer-grained recovery: microbatching, checkpointing, transactions, or idempotent writes.

## Ch11 — Failure modes / pitfalls
- Polling at low latency: overhead rises as fewer polls return anything.
- Dropping vs unbounded buffering vs backpressure: silent loss makes metrics wrong without anyone noticing; unbounded queues eat memory/disk and slow throughput.
- Direct messaging/webhooks: offline consumer misses messages; crashed producer loses its retry buffer.
- Redelivery after missing ack: duplicates (ack lost although processing finished); load balancing + redelivery reorders messages.
- Traditional brokers: destructive consume, new consumers can't see history; forgotten queues of dead consumers accumulate and starve memory.
- Partitioned logs: head-of-line blocking; max parallelism = partition count; slow consumer falls off the retained log and loses messages; consumer reprocesses messages after crash (offset recorded late).
- Dual writes: interleaving race leaves systems permanently inconsistent without any error; one-side failure inconsistency; need atomic commit.
- CDC via triggers fragile/slow; log-parsing breaks on schema changes; async -> replication lag; need consistent snapshot tied to a log position.
- Event sourcing: stale reads from async views; log compaction not possible for intent-level events; history growth/fragmentation for high-churn data; legal deletion conflicts with immutability (need excision/shunning; true deletion hard because of SSD/FS/backups).
- Consumer cannot reject an event — validation must precede writing the event.
- Time: processing-time windows produce artifacts after outage/backlog; late stragglers; untrustworthy device clocks; cross-stream ordering undefined -> nondeterministic joins; slowly changing dimensions.
- Fault tolerance: external side effects (DB writes, emails) done twice on task restart; idempotence needs same-order replay, determinism, no concurrent writers, and fencing on failover.

## Ch11 — Key terms
- *Event* — small immutable timestamped record. *Producer/consumer, topic.* *Backpressure* — block the sender when the receiver can't keep up. *Message broker/queue* — server optimised for message streams. *Webhook* — callback URL called when an event occurs.
- *Ack/redelivery* — consumer confirms processing; unacked messages are redelivered. *Fan-out* vs *load balancing*. *Log-based broker* — append-only partitioned log with offsets (Kafka, Kinesis). *Offset* — position in a partition; consumer offset = progress. *Segment / ring buffer* — log retention unit / bounded disk buffer.
- *System of record / derived data* (Part III). *Dual writes* — app writes to several systems itself (race-prone). *CDC (change data capture)* — extract DB changes as a stream. *Log compaction* — keep latest record per key; *tombstone* — null value marks deletion. *Event sourcing* — immutable application-level events as source of truth. *Command vs event.* *CQRS* — separate write model from read models. *Changelog.*
- *CEP* — pattern matching over event streams; *stream analytics*, *window* (tumbling, hopping, sliding, session). *Processing time vs event time; straggler.* *Stream-stream / stream-table / table-table join.* *SCD (slowly changing dimension).*
- *Microbatching, checkpointing/barriers, exactly-once (effectively-once), idempotence, fencing.* *Percolator* — stored-query matching in Elasticsearch.

## Ch11 — Relevance to PACE (multi-tenant Node/Express + one managed Postgres, small host, daily batch jobs, send queue)
Applies directly:
- **Send queue as a queue table vs a broker.** PACE's send queue (`emails` pending rows with ORDER BY, retries, "sending" -> "Didn't send" recovery) is the traditional-broker pattern implemented in a database table. The chapter's comparison: brokers delete on ack and assume short queues; DBs keep data. For PACE scale a Postgres queue table (claim rows with `FOR UPDATE SKIP LOCKED` or a status/lease column) beats adding Kafka/RabbitMQ: durable, queryable, transactional with the business data. Keep processed rows (don't delete) so the table doubles as an audit log; this matches the "log-based" benefit of replay/inspection without a broker. Load-balancing + redelivery = reordering: if send order matters (it does, per `send-queue-order`), run a single consumer per mailbox/partition key (partition by mailbox/tenant, as logs do) rather than parallel workers.
- **Acks, redelivery and the exactly-once problem for email.** An email send is an external side effect that can't be rolled back; "ack lost although processed" is exactly the "uncertain send" case. Chapter's answer: use idempotence with metadata — a unique send key (dedupe key / outreach row id) stored with the intended action and checked before sending; a lost ack must not cause a second send. Mark intent first (status 'sending' with lease), send, then record result; on recovery, treat 'sending' with unknown outcome as uncertain and do NOT blind-retry (consistent with "an uncertain one never retries"). Retry only temporary failures. Idempotence assumptions: deterministic processing, ordered replay, no concurrent writers for the same row (-> claims/locks, fencing via lease expiry tokens when a worker is thought dead).
- **Idempotent daily jobs that can re-run.** Fault tolerance section: restart safely by recording the "last processed position" with the output (the Kafka-offset-with-value trick) — e.g. high-water-mark per mailbox sweep (message id / delta token / timestamp), written in the same transaction as the derived rows. Mailbox sweeps then resume without missing or double-processing. Prefer UPSERT / unique constraints (set-to-value) over increments (counters) so a re-run converges.
- **A job that silently does nothing.** Chapter's recurring advice: monitor consumer lag (how far behind the head of the log), count and alert on dropped/late events, and compare each run to the previous run. For PACE: record per-run counters (rows considered, sent, skipped with reason, errors), alert when a scheduled job did not run, ran with zero input unexpectedly, or lag (oldest pending age) grows. Also "if large numbers of messages are dropped it may not be obvious metrics are wrong".
- **Event log / audit trail.** Event sourcing and ledger analogy: keep immutable, append-only records of things that happened (email sent, stage changed, reply received, opt-out) alongside current-state rows; fix mistakes with compensating events rather than overwriting; the log doubles as audit trail, enables debugging "why did this happen", and lets new derived views (conversation intelligence, "needs you today" queue, reporting) be rebuilt by replay. This matches `conversation_messages` and submission stage history. Mutable state tables are then derived data (a cache of the log) and can be re-derived after a bug (human fault tolerance).
- **Command vs event / validation first.** Validate (permissions, plan limits, double-send guard, merge fields) BEFORE writing the fact; consumers can't reject an event. Fits PACE rule "a rule that decides whether an action is allowed lives where the action is OFFERED".
- **Dual writes.** Avoid writing the same fact to two places (e.g. DB + external provider + cache) from app code without a single source of truth; make Postgres the system of record and derive everything else (including webhooks/sync to other systems) from it — via a changes/outbox table (transactional outbox: write the business row and an outbox row in one transaction, a worker publishes) rather than two independent writes. Directly relevant to Supabase/Gmail/Outlook sync.
- **CDC at small scale.** Supabase offers logical replication / Realtime (WAL-based); triggers writing to a changelog/audit table are the book's "fragile, overhead" option, acceptable at low volume. Use a `updated_at` + monotonic cursor for incremental processing; consumers poll cheaply (polling at low frequency is fine for daily jobs; the book's polling cost warning matters only for low-latency needs).
- **Time handling.** Use event time (when the email was sent/received per provider timestamp) not processing time for follow-up windows, "days since" rules and windows (e.g. 90-day horizon); record stored timestamps in UTC and keep the candidate's timezone for send windows; be robust to late/out-of-order provider events (webhooks delivered late or out of order) — idempotent handlers that compare event timestamps/ids. Late events (straggler) -> correction rather than ignore for state like replies/opt-outs.
- **Webhooks** (billing, mail providers) are direct messaging without a broker: the sender may retry, the receiver may be offline, deliveries can duplicate or reorder -> receivers must be idempotent (dedupe by event id), verify signatures, and a reconciliation sweep should catch missed ones.
- **Stream-table join/enrichment** analog: avoid per-row remote lookups in loops; load needed reference data once per run (or join in SQL).
- **Immutability limits / deletion:** candidate-privacy/opt-out deletion (GDPR-style) conflicts with append-only logs; plan the ability to actually delete or redact personal data in event/audit tables (excision), and remember backups.
- **Log compaction analog:** for state like "current stage", store the latest row (compacted) plus a separate history table.
Only matters at much larger scale: Kafka-style partitioned logs, consumer groups, partition-count limits, ring-buffer sizing, CEP, probabilistic algorithms (HyperLogLog), hopping/sliding windows, microbatching/checkpoint barriers, distributed transactions inside stream frameworks, state replication via compacted topics, CQRS with many derived read stores. At PACE's size a single Postgres with queue tables, an outbox/audit table, idempotency keys and run-level monitoring covers the same ideas.
