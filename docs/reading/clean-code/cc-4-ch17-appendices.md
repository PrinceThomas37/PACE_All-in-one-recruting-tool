# Clean Code slice cc-4: Ch.17, Appendix A, Appendix C, Epilogue

Legend: [J] Java-specific, [JS] transfers to JavaScript/Node, [Both] principle transfers, syntax is Java.

## Chapter 17: Smells and Heuristics
Intro: The list builds on Fowler's "Refactoring" smells plus the author's own. He made it by refactoring several programs and writing down why he made each change. Read top to bottom, then use as a reference. Appendix C cross-references each code to the pages that use it. The list "implies a value system" and is not claimed complete.

### Comments
- C1 Inappropriate Information: Comments must not hold what belongs in other systems (source control, issue tracker): change history, author, last-modified date, ticket numbers. Reserve comments for technical notes about code and design. [JS]
- C2 Obsolete Comment: Comments age fast and drift away from the code they described, becoming misleading "floating islands". Update or delete at once; better not to write ones likely to rot. [JS]
- C3 Redundant Comment: A comment that restates what the code already says (e.g. "increment i", or a doc-comment that adds nothing beyond the signature). Comments should say what code cannot. [JS]
- C4 Poorly Written Comment: If worth writing, write it well: careful words, correct grammar, brief, no rambling, no stating the obvious. [JS]
- C5 Commented-Out Code: Nobody dares delete it, so it rots, refers to things that no longer exist, and distracts readers. Delete it; version control remembers. He calls it an "abomination". [JS]

### Environment
- E1 Build Requires More Than One Step: A build should be one trivial command after one checkout; no hunting for extra jars/XML/artifacts or arcane script sequences. [JS] (npm install/build fits)
- E2 Tests Require More Than One Step: All unit tests should run with one command (ideally one IDE button); being able to run them all must be quick, easy, obvious. [JS]

### Functions
- F1 Too Many Arguments: Zero is best, then one, two, three; more than three is very questionable and to be avoided "with prejudice". [JS] (options-object is the JS workaround, but only if the object is a coherent concept)
- F2 Output Arguments: Readers expect arguments to be inputs. If a function must change state, change the object it is called on. [JS] (mutating a passed-in object is the JS version)
- F3 Flag Arguments: A boolean argument announces the function does two things; eliminate (split the function). [JS]
- F4 Dead Function: Methods never called should be deleted; source control remembers. [JS]

### General
- G1 Multiple Languages in One Source File: A file may mix Java, XML, HTML, JS, English comments etc. Ideal: one language per file; at least minimise number and extent of extras. [Both] (JS: HTML-in-JS strings, inline SQL, CSS-in-JS)
- G2 Obvious Behavior Is Unimplemented: By the Principle of Least Surprise, a function should do what a reasonable reader expects (a day-name parser should accept "Monday", common abbreviations, any case). Otherwise readers lose trust and must read the details. [JS]
- G3 Incorrect Behavior at the Boundaries: Developers trust intuition instead of proving corner and boundary cases. No substitute for due diligence: hunt every boundary and write a test for each. [JS]
- G4 Overridden Safeties: Turning off safeguards (compiler warnings, failing tests "to fix later", manual serialVersionUID) is as dangerous as how Chernobyl was caused by overriding safety systems; compared to treating credit cards as free money. [Both] (JS: disabled lint rules, skipped tests, ts-ignore)
- G5 Duplication: One of the most important rules (DRY; "once and only once"; Ron Jeffries ranks it second only to passing tests). Duplication is a missed abstraction. Forms: copy-paste blocks (make a function), repeated switch/if chains (use polymorphism), similar algorithms with different lines (Template Method or Strategy). Many design patterns, database normal forms, OO and structured programming are all duplication-removal strategies. [JS]
- G6 Code at Wrong Level of Abstraction: Keep high-level concepts in the base/container and low-level detail in derivatives/other modules, and the separation must be complete. Example: a Stack interface exposing percentFull belongs in a BoundedStack; faking it by returning 0 is a lie. Wrong abstractions have no quick fix. [Both]
- G7 Base Classes Depending on Their Derivatives: A base class that names its subclasses is suspect; bases should know nothing of derivatives so they deploy independently. Exception: a fixed set of derivatives (state machines), which then deploy together. [Both] (JS: a module importing its own plugins/implementations)
- G8 Too Much Information: Good modules have small interfaces that do a lot; wide interfaces mean high coupling. Hide data, helpers, constants, temporaries; few methods, few instance variables, few protected members. [JS] (export little from a module)
- G9 Dead Code: Code that never executes (impossible-condition branches, catch blocks that never fire, uncalled helpers, impossible cases). It rots because it is not updated when design changes. Give it a decent burial: delete. [JS]
- G10 Vertical Separation: Declare variables just above first use with small vertical scope; put private functions just below their first caller. [JS]
- G11 Inconsistency: Do similar things the same way (same variable name for the same kind of object, parallel method names like processVerificationRequest / processDeletionRequest). Follows least surprise. [JS]
- G12 Clutter: Empty default constructors, unused variables, uncalled functions, comments adding nothing: remove. [JS]
- G13 Artificial Coupling: Things that do not depend on each other should not be tied together by convenient-but-wrong placement (a general enum inside a specific class, general static helper in a specific class). Take time to decide where things belong. [Both]
- G14 Feature Envy: A method more interested in another class's data (calling its getters to compute) than its own should live there. Caveat: sometimes necessary, e.g. a report formatter should not be moved into the data class, since that would couple the data class to report format. [Both]
- G15 Selector Arguments: The dangling `false` at the end of a call; each selector (boolean, enum, int) merges several functions into one. Prefer several well-named functions. [JS]
- G16 Obscured Intent: Run-on expressions, Hungarian notation, magic numbers hide intent; make it expressive, not merely dense/small. [JS]
- G17 Misplaced Responsibility: Put code where a reader would naturally look (PI near trig functions; OVERTIME_RATE in the pay calculator). Test by function names: which of `getTotalHours` (report) vs `saveTimeCard` implies totalling? If performance forces computing it elsewhere, name it to say so (computeRunningTotalOfHours). [JS]
- G18 Inappropriate Static: Static is fine for something like Math.max (all data from arguments, never polymorphic). But if you might want different behaviours (different pay algorithms), make it an instance method. When in doubt, nonstatic. [J] mostly; in JS the analogue is module-level functions versus methods you may want to swap/inject.
- G19 Use Explanatory Variables: Break calculations into intermediate, well-named values (regex group 1 = key, group 2 = value). "Hard to overdo"; more is generally better. [JS]
- G20 Function Names Should Say What They Do: `date.add(5)` leaves unit and mutate-vs-return-new unknown; name it addDaysTo vs daysLater. If you must read the implementation to know what it does, rename or restructure. [JS]
- G21 Understand the Algorithm: Code often "works" because enough ifs and flags were poked in until the tests passed. Before calling it done you must KNOW it is correct; often refactor until it is obviously so. Footnote: unsure whether an algorithm suits the requirement is normal; unsure what your code does is laziness. [JS]
- G22 Make Logical Dependencies Physical: A module should not assume things about another (a reporter hard-coding page size 55 for its formatter); it should ask the other module (formatter.getMaxPageSize()). Ties to G17. [JS]
- G23 Prefer Polymorphism to If/Else or Switch/Case: Chapter 6 says switches suit areas where new functions are likelier than new types, but most switches are brute-force habit and function-volatile cases are rare, so be suspicious. "ONE SWITCH" rule: at most one switch per type of selection, and its cases create polymorphic objects that replace the other switches. [Both] (JS: dispatch tables/objects of strategies)
- G24 Follow Standard Conventions: Teams follow a coding standard based on industry norms (declarations, naming, braces) where the code itself demonstrates it; it does not matter where braces go as long as all agree. [JS] (linters/formatters)
- G25 Replace Magic Numbers with Named Constants: Old rule (86,400 -> SECONDS_PER_DAY, 55 -> LINES_PER_PAGE). Exceptions: obvious well-known values in self-explanatory formulas (5280 feet/mile, 8 hours a day, `*2` for circumference). Long constants like pi should be named to avoid single-digit typos and variants (3.14, 3.142). "Magic number" includes any token whose meaning is not self-describing, e.g. test values like 7777 and "John Doe". [JS]
- G26 Be Precise: Do not assume first match is only match; floating point for currency is "almost criminal" (use integers or a Money class); skipping locks/transactions because concurrency "is unlikely" is lazy; over-constraining (ArrayList for List) or under-constraining (everything protected); check for null if the function may return it. Imprecision comes from disagreement or laziness. [JS] (JS: integer cents, null/undefined checks, rows.length checks)
- G27 Structure over Convention: Enforce design decisions with structure (abstract methods force implementation) rather than naming conventions or switches on enums that nobody is forced to keep in sync. [Both]
- G28 Encapsulate Conditionals: Extract boolean logic into well-named functions (shouldBeDeleted(timer)). [JS]
- G29 Avoid Negative Conditionals: Positives are easier than negatives (`shouldCompact()` over `!shouldNotCompact()`). [JS]
- G30 Functions Should Do One Thing: Split functions with several sections (loop, check, act) into small functions each doing one thing (pay -> payIfNecessary -> calculateAndDeliverPay). [JS]
- G31 Hidden Temporal Couplings: When call order matters, make it unavoidable via a "bucket brigade": each step returns what the next needs (gradient -> splines -> dive), so out-of-order calls cannot compile/run. Extra syntactic complexity exposes true temporal complexity. [JS] (async pipelines passing results)
- G32 Don't Be Arbitrary: Have a reason for structure and let structure show it; arbitrary structure invites others to change it, consistent structure gets preserved. Example: a committer nested a public class inside an unrelated class for convenience; public non-utility classes belong at top level of their package. [Both]
- G33 Encapsulate Boundary Conditions: Keep +1/-1 fiddling in one place (a `nextLevel` variable) rather than scattered. [JS]
- G34 Functions Should Descend Only One Level of Abstraction: All statements in a function should sit one level below the function's name. Hardest heuristic to follow because people mix levels seamlessly. Example: HR-tag render function mixed "a rule has a size" with raw HTML syntax; extracting an HtmlTag object separated them and even uncovered a bug (missing closing slash). Splitting along one abstraction line often reveals new hidden lines. [JS]
- G35 Keep Configurable Data at High Levels: Defaults/config known at a high level belong at the top (e.g. argument defaults beside the command-line parsing) and are passed down, not buried in low-level functions. [JS] (central config module; relevant to settings, not hard-coded caps)
- G36 Avoid Transitive Navigation (Law of Demeter, "shy code"): a.getB().getC().doSomething() makes every user know the object graph so inserting Q between B and C requires finding every chain. Modules should know only immediate collaborators; ask them to do the work. [JS]

### Java
- J1 Avoid Long Import Lists by Using Wildcards: Import whole packages; specific imports are hard dependencies, wildcards are not, and long lists clutter the top. Caveats: name clashes (rare) and a very rare legacy use for finding classes to stub; IDEs can expand wildcards anyway. [J] Java-specific; in JS the nearest analogue is not applicable (and wildcard imports hurt tree-shaking), so DO NOT transfer. Also widely disputed today.
- J2 Don't Inherit Constants: Putting constants in an interface and implementing it to access them hides where constants come from. Use a static import instead. Don't use inheritance to cheat scoping. [J] (JS: import named constants from a module)
- J3 Constants versus Enums: Use enums (Java 5) instead of public static final ints; meaning of ints gets lost, enums belong to a named type and can carry methods and fields (each pay grade has its own rate). [J] syntax; the principle (named, self-describing values, behaviour attached) transfers to JS via frozen objects/const maps/TypeScript unions.

### Names
- N1 Choose Descriptive Names: Names are "90 percent of what make software readable"; meanings drift as software evolves so reevaluate. Example: an opaque bowling-score function x() vs score() with isStrike/isSpare; good names "overload the structure with description" so remaining functions are "pretty much what you expected". [JS]
- N2 Choose Names at the Appropriate Level of Abstraction: Do not name after implementation. Modem.dial(phoneNumber) commits to phones; connect(connectionLocator) fits hard-wired or USB connections too. Revisit each pass. [JS]
- N3 Use Standard Nomenclature Where Possible: Use pattern names (Decorator), language conventions (toString), and the project's ubiquitous language (Eric Evans, DDD). [JS]
- N4 Unambiguous Names: A name must disambiguate. doRename contains renamePage and tells you nothing; renamePageAndOptionallyAllReferences is long but called from one place, so clarity wins. [JS]
- N5 Use Long Names for Long Scopes: Short names (i, j) are fine for a five-line scope; names with wide scope need to be longer and more precise. [JS]
- N6 Avoid Encodings: No type/scope prefixes (m_, f) or subsystem prefixes (vis_); "Hungarian pollution". Modern environments supply this info. [JS]
- N7 Names Should Describe Side-Effects: Do not hide extra behaviour; getOos() that also creates the stream should be createOrReturnOos. [JS]

### Tests
- T1 Insufficient Tests: A suite should test everything that could break; "that seems like enough" is not a metric. Insufficient while any condition is unexplored or calculation unvalidated. [JS]
- T2 Use a Coverage Tool: Shows gaps (green/red lines), quickly finding untested ifs and catches. [JS] (c8/nyc/jest coverage)
- T3 Don't Skip Trivial Tests: Cheap to write; documentary value exceeds cost. [JS]
- T4 An Ignored Test Is a Question about an Ambiguity: Express unclear requirements as a commented-out or @Ignore'd test (choice depends on whether the ambiguity would compile). [Both] (JS: test.skip/todo)
- T5 Test Boundary Conditions: We often get the middle of an algorithm right and misjudge boundaries. [JS]
- T6 Exhaustively Test Near Bugs: Bugs congregate; when one is found in a function, test that function exhaustively. [JS]
- T7 Patterns of Failure Are Revealing: Complete, sensibly ordered test cases expose patterns (all inputs longer than five characters fail; negative second argument fails), sparking the diagnosis. [JS]
- T8 Test Coverage Patterns Can Be Revealing: Which code passing tests do or do not execute hints why failing tests fail. [JS]
- T9 Tests Should Be Fast: A slow test won't get run and will be dropped when time is tight. [JS]

### Chapter 17 Conclusion
The list is not complete and cannot be; it exists to convey a value system. Quote: "Clean code is not written by following a set of rules." Professionalism and craftsmanship come from values that drive disciplines, not from learning a list of heuristics.

## Appendix A: Concurrency II (by Brett L. Schuchert) -- in progress (notes below added as read)

### Client/Server Example
Core argument: a simple socket server (accept, process, loop) and a client; a test asserts throughput (all client requests complete within 10 s). If it fails, first find where time goes: I/O-bound (sockets, DB, swapping) or processor-bound (maths, regex, GC). Threads help I/O-bound work (overlap waiting) but not CPU-bound work (only more hardware does). [Both] -- Node's event loop gives the I/O overlap without threads; CPU-bound work blocks the single thread.
- Naive fix: start a new thread per client in process(). Test passes (about 1 s) but: no limit on thread count (can hit JVM limits / grind to a halt with many public users), and the single function now carries four responsibilities (connection management, client processing, threading policy, shutdown policy) at mixed abstraction levels.
- Rule: keep thread management in a few well-controlled places, and code that manages threads should do nothing else (concurrency bugs are hard enough alone). Split into connection manager, request processor and a ClientScheduler interface; ThreadPerRequestScheduler and later an Executor-backed scheduler plug in without touching the rest. Also makes everything else testable without threading. This is SRP applied to concurrency.
- Conclusion: concurrency can raise throughput and be validated by a throughput test; confine concurrency code to a few classes (SRP).

### Possible Paths of Execution
- A one-line `return ++lastIdUsed` is not one step: it compiles to eight bytecode instructions, and two threads can interleave them like shuffling cards. With two threads and lastIdUsed=93 outcomes: (94,95), (95,94), or both get 94 with a final value of 94 (a lost update). [J] bytecode; the lost-update idea transfers to JS only across await points or shared external stores (DB read-modify-write), not within synchronous code.
- Count of paths for T threads and N steps: (N*T)! / (N!)^T. Uncle Bob's email derives it (strings of thread digits, remove duplicate swaps): N=2,T=2 -> 6; N=2,T=3 -> 90; N=3,T=3 -> 1680. For 8 instructions and 2 threads: 12,870 paths; if the field is a long (two ops per read/write) 2,704,156. Making the method synchronized reduces possible paths to two for two threads (N! generally).
- Atomic operation = uninterruptible. Assigning a 32-bit value is atomic per the Java memory model; a 64-bit (long) assignment is not guaranteed atomic by the JVM spec (two 32-bit writes). Assigning a constant from ten threads has astronomical orderings but a single outcome, so it is harmless. Pre-increment ++ is NOT atomic (load, dup, getfield, add, store...): thread 1 can read 42, be preempted, thread 2 increments to 43, thread 1 then also writes 43 -> one increment lost. synchronized fixes it.
- Definitions: frame (per call: return address, params, locals), local variable (nonstatic methods always have `this`), operand stack (LIFO holding instruction params).
- Conclusion: you need not know bytecode, but must know the memory model well enough to know what is safe. Common misconception: ++ is atomic. Know (1) where shared objects/values are, (2) code that can cause concurrent read/update issues, (3) how to guard against it.

### Knowing Your Library
- Executor framework (Java 5, java.util.concurrent): thread pools that resize and recreate threads; works with Runnable and Callable (returns a result); supports futures (submit independent work, continue, call get() which blocks until done). If you hand-roll threads or pools, consider the Executor: cleaner, smaller. [J] -- JS analogue: Promise.all / async functions / worker_threads pools.
- Nonblocking solutions: Atomic classes (AtomicInteger, AtomicBoolean, AtomicReference) use hardware Compare-And-Swap: assume little contention, detect conflict and retry; analogous to optimistic locking in DBs, whereas synchronized is pessimistic and always takes a lock. Nearly always at least as fast, even under moderate to high contention. [J] -- the DB optimistic-locking analogy (version column, compare-and-set UPDATE) transfers directly to Node + Postgres.
- Non-thread-safe classes: SimpleDateFormat, DB connections, java.util containers, servlets. Individual thread-safe methods do not make compound operations safe (containsKey then put on a Hashtable can interleave). Three fixes: client-based locking (synchronize on the map), server-based locking via an Adapter (putIfAbsent method), or thread-safe collections (ConcurrentHashMap.putIfAbsent). [J] -- JS lesson: check-then-act across an await is the same bug (e.g. SELECT then INSERT); use atomic DB upserts/unique constraints.

### Dependencies Between Methods Can Break Concurrent Code
Example: an IntegerIterator with synchronized hasNext/next. Two threads: T1 sees hasNext true, is preempted, T2 consumes the last value, T1 calls next and overruns, throwing; occurs only on the final iteration, so it surfaces long after production. Three options: tolerate the failure (sloppy, "like cleaning up memory leaks by rebooting at midnight"), client-based locking, server-based locking.
- Client-based locking: every client wraps hasNext+next in synchronized(iterator). Duplicates locking (violates DRY), risky because every user must remember. Author's war story (1971, Local 705 trucker union accounting system): terminals randomly locked up due to a ring buffer counter out of sync with its pointer from one single unprotected use among hundreds; they built hacks (a front-panel-switch trap, then scheduler reset of buffers both empty and full) before finding it by reading listings. Moral quote: "Client-based locking really blows."
- Server-based locking (preferred): change the API so one synchronized method does check+act (getNextOrNull; client null-checks). Reasons: reduces repeated code; better performance (can swap in a non-thread-safe server for single-thread deployment); fewer errors; one policy in one place; smaller scope of shared variables. If you do not own the server: wrap in an Adapter that adds locking, or better use thread-safe collections with extended interfaces.
- [J] mechanics; the principle "make the check-and-act a single atomic operation owned by the server/DB" transfers.

### Increasing Throughput
Example: read a list of URLs, parse each, print a summary. A PageIterator hands out next page under a very small synchronized block ("always better to synchronize as little as possible"). Calculation: 1 s I/O (0% CPU) + 0.5 s parse (100% CPU) per page; single thread = 1.5 s x N (13 pages ~19.5 s). Three threads overlap I/O with parsing: in the ideal case two pages per second, three times the throughput. [Both] -- in Node, async I/O gives this overlap on one thread (Promise.all with a concurrency limit); the parse (CPU) part still blocks the loop.

### Deadlock
Scenario: a web app with two finite pools (DB connections, MQ connections); "create" takes DB then MQ, "update" takes MQ then DB. Pool size ten; ten creators hold all DB connections and ten updaters hold all MQ connections, each waiting for the other: permanent freeze, hard to reproduce, and adding debug output changes timing so the bug "disappears" (and the debug code stays as a "fix").
Four conditions, all required: mutual exclusion, lock and wait, no preemption, circular wait. Break any one:
- Break mutual exclusion: use resources allowing simultaneous use (AtomicInteger), have at least as many resources as threads, check all are free before seizing any. Limits: most resources are limited and exclusive; the second resource's identity may depend on the first.
- Break lock and wait: refuse to wait (check each resource, release all and start over if busy). Risks: starvation (a thread with a rare resource combination never gets them: low CPU use) and livelock (threads in lockstep acquiring/releasing forever: high useless CPU). Inefficient but almost always implementable as a last resort.
- Break no-preemption: a thread asks the owner to release; owners waiting on something else release everything and restart. Fewer restarts than the previous, but managing requests is tricky.
- Break circular wait: most common; all threads agree on a global order of acquiring resources. Costs: acquisition order may not equal use order (holds locks longer), and sometimes ordering is infeasible (second resource id comes from operating on the first).
TANSTAAFL (no free lunch). Isolate thread-related code so you can tune and experiment. [Both] -- JS: deadlocks appear as awaiting promises that depend on each other, exhausted connection pools (e.g. holding a pool connection while requesting another), or DB row-lock cycles; lock-ordering convention transfers to DB transactions.

### Testing Multithreaded Code
Goal: prove `return nextId++` is broken. The test remembers the id, starts two threads that each call takeNextId once, checks the id rose by two, and repeats (50,000 iterations) until it rose by only one; if it never fails, the test fails with "should have exposed a threading issue". Note the inverted logic: this test "passes" when it proves the production code broken; a failure means it could not prove anything (code fine, or too few iterations). The loop count is a balancing act (too many = slow test).
- Problem: the race is so rare that the test almost never catches it. It needs over a million iterations; at 1,000,000 iterations only 1 run in 10 exposed it, so reliable failure needs well over 100 million. Tuning is machine-, OS- and JVM-specific. If a trivial bug is this hard to demonstrate, complex ones are far harder, and you may not know where to look.
- Ideas: (1) Monte Carlo testing: make tests tunable, run repeatedly on a test/CI server with randomly varied tuning values, log the conditions of any failure, start writing such tests early. (2) Run on every target deployment platform, repeatedly and continuously (long failure-free runs mean either correct code or inadequate tests). (3) Run on machines under varying load, simulating production load. Even so, bugs with a cross-section of one in a billion remain "the terror of complex systems".
- Tool support: IBM ConTest instruments classes to make non-thread-safe code fail more readily (authors have no relationship with IBM). Usage: write tests simulating multiple users under varying load, instrument test and production code, run. In their trial failure rate went from about 1 in 10 million iterations to about 1 in 30 (observed runs failed after 13, 23, 0, 54, 16, 14, 6, 69, 107, 49, 2 iterations). [J] tool; in Node the equivalent worry is interleavings at await points, tested by injecting delays/ordering controls into async fakes (a transferable idea: perturb timing deliberately rather than waiting for luck).

## Epilogue
Core argument: a personal story. At the 2005 Agile conference in Denver, Elisabeth Hendrickson handed the author a green "Test Obsessed" wristband (like Lance Armstrong's). Having learned TDD from Kent Beck in 1999, he was already obsessed with test-driven development. He then found he could not take it off, "morally stuck": it was a visible statement of his professional ethics and his commitment to writing the best code he could, so removing it would feel like a betrayal. He still wears it; seen in peripheral vision while coding, it reminds him of the promise to write clean code. Rule/recommendation: none explicit; the point is that clean code is a matter of personal commitment and professional ethics, echoing the chapter 17 conclusion (values over rules). Key term: "Test Obsessed" (TDD as a moral discipline). Transfers fully (not language-specific).

## Java vs JavaScript/Node summary
- Fully transferable (language-independent): all C, E, F, N and T items; G1-G17, G19-G36 principles; Appendix A's SRP-for-concurrency, server-based locking idea (make check-and-act one atomic step owned by the owner of the state), synchronize/lock as little as possible, the four deadlock conditions and lock ordering, optimistic vs pessimistic locking, I/O-bound vs CPU-bound reasoning, "tests of concurrency are hard; perturb timing".
- Java-specific: J1 (wildcard imports; the advice is contested and does not apply to JS), J2 (interface constants), J3 (enums syntax), G18 (static vs instance), G7 jar deployment details, bytecode/JVM memory model, synchronized, Executor/Callable/Future, Atomic classes, ConcurrentHashMap, ConTest, thread-per-request servers.
- Node caveat: JS code between awaits runs to completion on one thread, so `++x` on a plain variable is already atomic; concurrency bugs live at await boundaries (read-then-write across an await, DB read-modify-write, double-submit, reentrant handlers), and worker_threads/cluster processes. Deadlock analogues: exhausted connection pools, DB row-lock cycles, mutually awaiting promises. Throughput reasoning (I/O overlap vs CPU blocking the event loop) transfers directly.
