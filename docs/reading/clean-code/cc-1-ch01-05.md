# Clean Code (Martin, 2008) - notes, front matter and Chapters 1-5

## Front matter (Foreword by Coplien, Introduction)

1. **Core argument.** Small details matter: quality comes from a million small acts of care (naming, tidiness, consistent indentation), not only from grand architecture. Coplien frames clean code through the Japanese 5S/TPM maintenance discipline, noting that about 80% of software work is maintenance. The Introduction says craftsmanship needs knowledge plus hard practice (the bicycle analogy), so the book is deliberately work: principles chapters, then long refactoring case studies, then a heuristics catalogue whose value lies in its links back to the case studies.
2. **Rules / recommendations.**
   1. Treat small things as serious (Danish saw: honesty in small things is not small). Reason: sloppy detail (a crooked tile, messy desk) spoils the whole. Example: Mies van der Rohe choosing every doorknob.
   2. Apply 5S to code: Seiri (organization; good naming), Seiton (tidiness; code is where you expect it), Seiso (cleaning; remove noise comments and commented-out code), Seiketsu (standardization; team-wide consistent style), Shutsuke (self-discipline; reflect and change).
   3. Refactor mercilessly and make code readable, not just executable; prevention beats breakdown maintenance. Example: TPM inspections and oil changes.
   4. "The code is the design"; rework in design leads to value. Be honest about the state of your code; refactoring belongs inside the definition of "Done".
   5. Learning is two-part: knowledge and practice. Read the case studies step by step; the heuristics are only valuable with the context where they were applied (forward references like [H22]).
3. **Caveats.** Coplien still endorses architecture and up-front thinking; clean code does not demand perfection, only honesty and best effort. His Bell Labs finding (consistent indentation as a strong predictor of low bug density) is described as back-of-envelope. Introduction warns the book is not a light read.
4. **Key terms.** 5S - five Japanese workplace disciplines used as a metaphor. TPM - Total Productive Maintenance, focus on maintenance over production. Heuristic/smell - a recorded reason for a cleanup decision.
5. **Quotes.** "Quality is the result of a million selfless acts of care" (Foreword, close paraphrase of: quality is the result of a million selfless acts of care - not just of any great method that descends from the heavens). "Making your code readable is as important as making it executable."
6. **Language-specific vs universal.** All universal; the metaphors (5S, craftsmanship) transfer fully to JS/Node.

## Chapter 1: Clean Code

1. **Core argument.** Code will never go away because code is the precise statement of requirements. Bad code, written in a rush, slows teams toward zero productivity and can sink companies; adding staff or planning a "grand redesign" does not rescue it. The fault is the programmer's professionalism, not managers: you are responsible for defending code quality as a doctor defends hand-washing. The only way to go fast is to keep code clean always. Clean code is hard to define, so Martin collects definitions from respected programmers and concludes it is code that someone cared for; since code is read over ten times more than written, readability is what makes writing fast too.
2. **Rules / heuristics.**
   1. Code will always exist; higher-level or domain languages are still code. Reason: precision cannot be removed from requirements. Example: failed dream of business people generating programs.
   2. Bad code kills: do not trade quality for speed. Reason: "later equals never" (LeBlanc's law). Example: the late-80s killer app company that went out of business from a rushed, messy code base.
   3. Total cost of a mess: every change breaks other things, productivity falls toward zero, adding staff makes it worse, a redesign tiger-team race can last a decade and repeats the mess. Example: Figure 1-1 productivity vs time.
   4. Take professional responsibility; do not blame managers or schedules; defend the code as passionately as they defend the schedule. Example: patient demanding the surgeon skip hand-washing (Semmelweis).
   5. The primal conundrum: you cannot make deadlines by making messes; the mess slows you immediately.
   6. Develop "code-sense": recognising clean code is not the same as being able to write it; a skilled programmer sees options and plots behaviour-preserving transformations. Example: painting analogy.
   7. Definitions gathered: Stroustrup (elegant, efficient, minimal dependencies, complete error handling, does one thing well; bad code tempts the mess to grow, link to the broken-windows theory); Booch (reads like prose, crisp abstractions, never obscures intent); Big Dave Thomas (readable and changeable by others, has tests, one way not many, minimal, literate); Feathers (looks like written by someone who cares); Jeffries (Beck's rules in priority order: runs all tests, no duplication, expresses design ideas, minimal entities; duplication signals a missing idea; wrap collection lookups in small abstractions); Cunningham (each routine is pretty much what you expected; beautiful when the language looks made for the problem - so the programmer must make the language look simple).
   8. We are authors: reading to writing ratio exceeds 10:1, so make reading easy even if writing is harder. Example: replaying editor sessions shows mostly scrolling and navigating.
   9. Boy Scout Rule: leave the code cleaner than you found it, in small increments (rename one variable, split one function, remove one duplicate). Reason: stops rot; continuous improvement is professionalism.
3. **Caveats.** Martin says the book is the "Object Mentor school" of clean code, presented as absolutes but not absolutely right; many recommendations are controversial and other schools have equal claim. The book cannot give code-sense, only thought processes; practice is up to you.
4. **Key terms.** Wading - slogging through bad code. LeBlanc's law - later equals never. Grand redesign in the sky - rewrite by a tiger team racing the old system. Code-sense - trained feel for cleanliness and the transformation steps. Broken windows - one neglected flaw invites more decay. Boy Scout Rule - leave it cleaner.
5. **Quotes.** "Later equals never." / "Clean code always looks like it was written by someone who cares." / "The ratio of time spent reading vs. writing is well over 10:1."
6. **Language-specific vs universal.** Entirely universal (people, process, professionalism); Eclipse rename tooling mention is dated but modern editors do the same for JS.

## Chapter 2: Meaningful Names (by Tim Ottinger)

1. **Core argument.** Names are everywhere in code, so doing them well is the cheapest big readability win. A name should answer why it exists, what it does and how it is used; if it needs a comment, it fails. Most of the chapter is a list of small rules that make names honest, distinguishable, pronounceable, searchable and consistent. Renaming is cheap and should be done freely.
2. **Rules.**
   1. Use intention-revealing names. Reason: the problem is "implicity" - context that lives in the reader's head. Example: a function returning cells where element 0 equals 4 becomes getFlaggedCells with named constants, then a Cell class with isFlagged; same logic, far clearer.
   2. Avoid disinformation: no names that hint at something false (hp/aix as variable names; accountList when it is not a List; near-identical long names; lowercase L and uppercase O that look like 1 and 0). Spelling similar concepts similarly is information; inconsistent spelling is disinformation (autocomplete sorting helps).
   3. Make meaningful distinctions: do not misspell or number-series names (a1, a2) just to satisfy the compiler; do not add noise words (Info, Data, the, a, Object, variable, table). Example: getActiveAccount / getActiveAccounts / getActiveAccountInfo cannot be told apart; copyChars(a1, a2) is better with source and destination.
   4. Use pronounceable names. Reason: programming is social; you must be able to discuss it aloud. Example: genymdhms vs generationTimestamp.
   5. Use searchable names. Single letters and magic numbers cannot be grepped; name length should match scope size (single-letter names only for locals in short methods). Example: the digit 5 vs WORK_DAYS_PER_WEEK.
   6. Avoid encodings: no Hungarian notation, no m_ member prefixes, no I-prefix on interfaces (if you must encode, mark the implementation, e.g. ShapeFactoryImp). Reason: modern type systems/IDEs make them clutter, they go stale (a phoneString that is not a string), and readers learn to ignore them.
   7. Avoid mental mapping: readers should not translate your names into others; loop counters i, j, k are the accepted exception. Clarity is king; showing off memory is not professional.
   8. Class names are nouns/noun phrases (Customer, AddressParser); avoid Manager, Processor, Data, Info. Method names are verbs; accessors/mutators/predicates use get/set/is. Prefer static factory methods with descriptive names over overloaded constructors (Complex.FromRealNumber(23.0)) and consider making constructors private.
   9. Don't be cute: no jokes or slang (HolyHandGrenade, whack, eatMyShorts). Say what you mean.
   10. Pick one word per concept (fetch/retrieve/get; controller/manager/driver) - a consistent lexicon.
   11. Don't pun: do not reuse a word for a different idea (an add that appends to a collection should be insert/append when other adds sum values).
   12. Use solution domain names (pattern, CS terms: AccountVisitor, JobQueue) because readers are programmers; when none exist use problem domain names so a domain expert can be asked.
   13. Add meaningful context: group related variables into a class/function/namespace (firstName, state ... into Address); prefix only as a last resort. Example: the guess-statistics message split into a GuessStatisticsMessage class with small methods.
   14. Don't add gratuitous context: no app-wide prefixes (GSD) that wreck autocomplete; add no more context than necessary.
   15. Final words: good naming needs descriptive skill and shared culture; do not fear renaming; use refactoring tools.
3. **Caveats.** Single-letter loop counters allowed; prefix conventions fine if they carry a real distinction (Martin himself abandoned the a/the prefix convention); noise-word rule is conditional on there being no real distinction; the interface-prefix preference is explicitly personal ("I prefer"). The author notes that solution-domain names can be mixed with problem-domain ones, and that a sentence is not always the best display (tables/data structures).
4. **Key terms.** Intention-revealing name; disinformation; noise words; number-series naming; Hungarian Notation; mental mapping; solution domain vs problem domain; pun (one word, two meanings); gratuitous context.
5. **Quotes.** "If a name requires a comment, then the name does not reveal its intent." / "Clarity is king." / "Say what you mean. Mean what you say."
6. **Language-specific vs universal.** Java/C++-specific: I-prefix on interfaces, m_ prefixes, Hungarian notation history, JavaBean get/set/is, static factory vs constructors, IDE autocomplete examples. Universal (transfer to JS/Node): intention-revealing, no disinformation, meaningful distinctions, pronounceable, searchable, no gratuitous context, one word per concept, no puns, no cuteness, class=noun/method=verb. Note JS has no static types so type-in-name is slightly more tempting, but the principle (do not encode) still holds in spirit; boolean-returning functions named is/has are common JS practice.

## Chapter 3: Functions

1. **Core argument.** Functions are the first line of organisation. They should be very small, do one thing at one level of abstraction, read top-down like a narrative, take as few arguments as possible, and have no hidden side effects. Martin shows an unreadable long FitNesse function and refactors it into tiny, well-named functions. He admits he writes long messy functions first and refines them under a unit-test safety net; the final structure is reached by editing. Ultimately the functions form a domain-specific language that tells the system's story.
2. **Rules.**
   1. Small. First rule: functions are small; second: smaller than that. Reason: pure experience (no research cited); from 3,000-line monsters to 2-4 line functions in Kent Beck's Sparkle program. Rule of thumb: rarely over 20 lines, lines under ~150 characters/less, blocks in if/else/while one line (a call), indent level at most one or two.
   2. Do one thing, do it well, do it only. Test: the function's steps are all one level below its name; if you can extract another function whose name is not a restatement of the implementation, it does more than one thing; sections inside a function (declarations, initialisation, sieve) are a symptom.
   3. One level of abstraction per function; mixing high-level concepts with low-level details is confusing and attracts more details (broken-windows effect).
   4. Stepdown Rule: read code top to bottom as a series of "TO" paragraphs, each followed by functions at the next lower level.
   5. Switch statements: hard to make small, always do N things, violate SRP and OCP, and the same switch gets repeated in many functions. Tolerate only once, to create polymorphic objects, buried behind an inheritance relationship (abstract factory). Example: calculatePay / isPayday / deliverPay on Employee types.
   6. Use descriptive names; a long descriptive name beats a short enigmatic one and beats a long comment; spend time, try several, be consistent in phrasing (includeSetupPages, includeTeardownPages...). Hunting for a name often improves the structure.
   7. Function arguments: ideal zero, then one, two; three should be avoided; more needs special justification. Reasons: conceptual burden, level-of-abstraction mismatch, hard to test combinations, output arguments are unexpected.
   8. Common monadic forms: ask a question about the argument, transform it and return it, or an event (no return); don't use other forms; a transformation should return its result, not mutate an output parameter.
   9. Flag arguments (booleans) are ugly: the function does one thing if true and another if false; split into two functions (renderForSuite / renderForSingleTest).
   10. Dyadic functions are harder (ordering, pausing, ignoring a parameter; assertEquals(expected, actual) order is only convention). Acceptable when the arguments are natural parts of one value (Point(x,y)). Convert to monads by making it a method of the object, a field, or extracting a class (FieldWriter).
   11. Triads are significantly harder; think very carefully (assertEquals(message, expected, actual) trips readers).
   12. Argument objects: wrap related args into a class (Point center instead of x, y). Argument lists (varargs) are treated as a single List argument so same limits apply.
   13. Verbs and keywords: monad as verb/noun (writeField(name)); keyword form encodes argument names in the function name (assertExpectedEqualsActual).
   14. Have no side effects: side effects are lies and create temporal couplings. Example: checkPassword that also initialises the session (could wipe a live session); if unavoidable put it in the name.
   15. Avoid output arguments; if state must change, change the owning object (report.appendFooter()).
   16. Command Query Separation: either change state or answer a question, not both. Example: set(attribute, value) returning boolean makes "if (set(...))" ambiguous; split into attributeExists and setAttribute.
   17. Prefer exceptions to returned error codes: codes force immediate nested handling and violate CQS; exceptions separate the happy path from error processing.
   18. Extract try/catch bodies into their own functions; error handling is one thing, so a function with try should start with it and have nothing after catch/finally.
   19. Error-code enums are dependency magnets (changing them forces rebuilds, so people reuse old codes); exceptions as derived classes avoid this (an OCP example).
   20. Don't repeat yourself: duplication (the same algorithm four times in the example) bloats code and multiplies change and omission errors; "may be the root of all evil in software"; much of software engineering history is about removing it.
   21. Structured programming (single entry/exit): helps only in large functions; in tiny functions multiple returns, break and continue are fine; goto still avoided.
   22. How to write such functions: draft first, then refine under a full unit-test suite (split, rename, dedupe, reorder, extract classes); nobody writes them this clean initially.
3. **Caveats.** Size advice is explicitly unsupported by research ("I can't provide any references"); "every circumstance is unique" and he sometimes violates the switch rule; he kept a flag argument in his refactor only to limit scope; Dijkstra's rules are conceded to be useful for large functions; "one thing" is admitted to be hard to define (hence the abstraction-level test).
4. **Key terms.** Niladic/monadic/dyadic/triadic/polyadic; flag argument; output argument; side effect; temporal coupling; Command Query Separation; Stepdown Rule; TO paragraph (LOGO-style description of a function); SRP; OCP; abstract factory; DRY; dependency magnet; structured programming.
5. **Quotes.** "Functions should do one thing. They should do it well. They should do it only." / "Side effects are lies." / "The art of programming is, and has always been, the art of language design."
6. **Language-specific vs universal.** Java-specific: checked exceptions/throws, StringBuffer, abstract factory/interfaces, polymorphic dispatch via class hierarchies, compile/redeploy cost of the Error enum, output args through objects. Transfers to JS/Node: small single-purpose functions, one abstraction level, stepdown ordering, few args (use an options object in JS as the "argument object"), no boolean flags, no hidden side effects, CQS, DRY, refine-under-tests. In Node, errors are also commonly handled via exceptions/promises rejection, or Result-style returns; the "don't return error codes" rule applies mostly to sync code and async handlers need a consistent single error-path (my gloss, not the book's). Switch-to-polymorphism may be a lookup table/strategy map in JS (my gloss).

## Chapter 4: Comments

1. **Core argument.** Comments are at best a necessary evil: each one compensates for a failure to express intent in code. They rot because code moves and changes while comments are not maintained, so inaccurate comments are worse than none; only the code tells the truth. The right first move is to make the code expressive (a well-named function) instead of commenting a mess. A short list of comment types is worth writing; most others are noise, lies, clutter or history that version control already holds.
2. **Rules.**
   1. Comments do not make up for bad code: clean the code instead of explaining the mess.
   2. Explain yourself in code: replace a comment with a named function/variable. Example: a flag-and-age comment replaced by employee.isEligibleForFullBenefits().
   3. Good comments (the only truly good comment is the one you found a way not to write):
      - Legal comments (copyright/licence header; keep short, point to a standard licence, let the IDE fold it).
      - Informative comments (e.g. what a regex matches) - but a rename or small class often removes the need.
      - Explanation of intent (why a decision was made, e.g. why an object sorts higher, or why a test spawns 25,000 threads to provoke a race).
      - Clarification of obscure arguments or return values in code you cannot alter - risky since the comment may be wrong.
      - Warning of consequences (a test that takes long; a non-thread-safe date formatter that must not be shared).
      - TODO comments (jobs that cannot be done now): not an excuse to leave bad code; scan and remove regularly.
      - Amplification (stress that an apparently trivial call matters, e.g. a trim).
      - Javadocs in public APIs (but they can mislead just like any comment).
   4. Bad comments:
      - Mumbling (comment written because process requires it; reader must go to other modules to decode it).
      - Redundant comments (restate the code; take longer to read; can be subtly wrong - the waitForClose comment says it returns when closed becomes true, but it actually waits a blind timeout).
      - Misleading comments.
      - Mandated comments (rule that every function has a javadoc yields clutter and lies).
      - Journal comments (change logs at the top of files - use source control).
      - Noise comments (restate the obvious: "default constructor"); readers learn to skip them and they later lie; venting comments ("Give me a break!") signal code that needs restructuring; "scary noise" - copy-paste errors inside noise javadocs.
      - Don't use a comment when you can use a function or a variable (introduce explanatory variables).
      - Position markers/banners (use very rarely).
      - Closing brace comments (shorten the function instead).
      - Attributions and bylines (source control knows).
      - Commented-out code (others fear deleting it, it piles up; just delete - version control remembers).
      - HTML in comments (the doc tool, not the programmer, should add markup).
      - Nonlocal information (a comment about a far-away default port that nothing here controls).
      - Too much information (historical essays, RFC text).
      - Inobvious connection (comment that needs its own explanation, e.g. the "+200" header bytes).
      - Function headers on short functions (a good name is better).
      - Javadocs in nonpublic code.
   5. Worked example: a "well-documented" prime generator (with author tag, history, section comments, line comments) refactored into small named functions with only two comments left - one introducing the algorithm and one explaining why the loop stops at the square root.
3. **Caveats.** Martin concedes comments are sometimes necessary and disciplined programmers should keep them accurate, but prefers to spend the energy on clearer code. He admits the leftover intro comment in the refactored example is arguably redundant, and doubts whether the square-root optimisation is worth the reader effort at all ("might be a conceit"). Banners are acceptable if rare; closing-brace comments make some sense in long, deeply nested functions (but he prefers short functions).
4. **Key terms.** Necessary evil; explanation of intent; amplification; TODO; noise comment; journal comment; mandated comment; position marker; nonlocal information.
5. **Quotes.** "The only truly good comment is the comment you found a way not to write." / "Inaccurate comments are far worse than no comments at all." / "Truth can only be found in one place: the code."
6. **Language-specific vs universal.** Java-specific: javadoc rules (public API docs, @param noise, HTML in javadoc, @Ignore example). Universal/transfers to JS/Node: comments as failure to express, rot, why-not-what, delete commented-out code, no bylines/journals (git), TODO hygiene, legal header, intent/warning comments. JSDoc for a published library API corresponds to "javadocs in public APIs" (my gloss); dynamic typing may make JSDoc types more tempting, but the "mandated/redundant comment" warning still applies.

## Chapter 5: Formatting

1. **Core argument.** Formatting is communication, the developer's first order of business, and signals professionalism; style and readability outlive the code itself. A file should read like a newspaper article: a simple name, high-level concepts at the top, detail increasing downward. Use vertical openness to separate concepts, density to group related lines, and distance to reflect relatedness; keep lines short and indentation consistent. The team agrees on one style (and automates it); personal preference yields to the team.
2. **Rules.**
   1. Choose simple rules, apply them consistently, have the team agree to one set; use an automated formatter. Example: FitNesse team agreed a style in ten minutes and encoded it in the IDE formatter.
   2. Vertical size: small files, typically ~200 lines with an upper limit ~500 (measured across seven Java projects; FitNesse is ~50,000 lines of files averaging ~65). Reason: small files are easier to understand. Not a hard rule.
   3. Newspaper metaphor: file name tells you whether you're in the right place; top = high-level, bottom = detail.
   4. Vertical openness: separate distinct concepts (package, imports, each function) with blank lines; removing them obscures grouping.
   5. Vertical density: closely related lines stay together; useless comments between two instance variables break their association.
   6. Vertical distance: keep related concepts close; avoid protected variables partly for this reason.
      - Declare local variables as close to use as possible (at top of short functions; loop variables in the loop statement; rare mid-block exceptions in long functions).
      - Instance variables at the top of the class in one well-known place (C++ "scissors rule" put them at the bottom; Java convention is top).
      - Dependent functions: caller above callee, vertically close, so flow reads downward.
      - Conceptual affinity: functions that share naming or perform variations of one task (assertTrue/assertFalse overloads) stay together even without calling each other.
   7. Vertical ordering: dependencies point downward; high level first, low-level details last (opposite of Pascal/C/C++ which require declaration before use). Also keep constants at the appropriate (high) level - pass a default down rather than bury it.
   8. Horizontal: lines short; data shows most lines under 80, nothing wrong with 100-120 but beyond is careless; author's limit is 120; do not shrink fonts to cram 200 columns.
   9. Horizontal openness/density: spaces around assignment (two distinct sides), none between function name and its parenthesis, spaces after commas between arguments, and spacing that shows operator precedence (tight for multiplication, loose for addition). Caveat: most auto-formatters ignore precedence and flatten this.
   10. Horizontal alignment (lining up declarations/rvalues): not useful - draws the eye to the wrong column, formatters undo it, and a long list that needs aligning means the class is too big.
   11. Indentation shows the scope hierarchy; do not collapse short if/while/functions onto one line; give any dummy loop body its own indented line with braces so a stray semicolon is visible.
   12. Team rules: the team's style beats personal preference; consistency lets readers trust that a formatting gesture means the same thing everywhere; code itself is the best coding-standard document (his sample listing).
3. **Caveats.** Formatting is "too important to ignore and too important to treat religiously"; file-size numbers are "a feel" not hard rules, and his chart's statistics are explicitly imprecise (non-normal distribution); his 120-column limit is personal; he admits his own earlier habits (alignment, one-line scope collapses) were wrong. Instance-variable location is convention-dependent by language.
4. **Key terms.** Newspaper metaphor; vertical openness/density/distance/ordering; conceptual affinity; scissors rule; dummy scope; team rules.
5. **Quotes.** "Code formatting is about communication, and communication is the professional developer's first order of business." / "Your style and discipline survives, even though your code does not." / "If he works in a team, then the team rules."
6. **Language-specific vs universal.** Java-specific: file/class equivalence for size, Java instance-variable-at-top convention, brace layout, function ordering contrast with C/C++/Pascal, long-line stats from Java projects. Transfers to JS/Node: newspaper ordering, openness/density, caller-above-callee (JS function declarations hoist so the stepdown order works; note arrow-function consts do not hoist - my gloss), line length ~100-120, no alignment, consistent indentation, one team style enforced by a tool (Prettier/ESLint in practice - my gloss, not the book's).
