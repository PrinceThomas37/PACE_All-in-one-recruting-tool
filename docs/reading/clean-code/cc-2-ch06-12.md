# Clean Code, Chapters 6-12 - notes

## Chapter 6: Objects and Data Structures

**1. Core argument.** Variables are made private so nobody depends on them, yet programmers reflexively add getters and setters that give the same exposure back. Real hiding comes from abstraction: an interface lets users manipulate the essence of the data without knowing how it is stored. Objects hide data and expose behaviour; data structures expose data and have no meaningful behaviour. These are opposites, and each makes a different kind of change easy or hard. A mature designer picks per part of the system rather than treating everything as an object.

**2. Rules / heuristics**
1. Hide implementation through abstraction, not through a layer of getters/setters. Reason: single-variable accessors still reveal the representation. Example: a Point interface with Cartesian and polar access that enforces setting coordinates together, versus public x/y fields.
2. Express data in abstract terms (percent fuel remaining) rather than raw storage terms (gallons, capacity). Reason: users learn nothing about how it is stored. The worst option is blithely adding getters and setters.
3. Data/object anti-symmetry: procedural code (data structures plus functions) makes adding functions easy but adding data types hard; OO code makes adding types easy but adding functions hard. Choose according to which kind of change you expect. Example: a Geometry class with instanceof branches over Square/Rectangle/Circle versus polymorphic area() on each shape.
4. "Everything is an object" is a myth; sometimes plain data plus procedures is right.
5. Law of Demeter: a method should call only methods of its own class, objects it created, objects passed in, and objects held in its fields; not on objects returned by those. "Talk to friends, not strangers." Reason: otherwise a module knows the innards of objects it uses.
6. Avoid train wrecks (chained calls a.b().c().d()); but splitting them into locals does not fix the underlying knowledge. Whether it violates Demeter depends on whether the things are objects (violation) or data structures (Demeter does not apply). Example: ctxt.getOptions().getScratchDir().getAbsolutePath().
7. Avoid hybrids: half object, half data structure (significant behaviour plus public accessors). They make it hard to add functions and hard to add types; they signal muddled design. Also called Feature Envy.
8. Tell objects to do things rather than asking for their internals. Find out why the caller wanted the data and move that job into the object. Example: ask the context to create a scratch file stream instead of fetching the scratch directory path.
9. DTOs (public fields, no behaviour) are fine and useful at boundaries (database rows, socket messages). "Beans" with private fields and getters/setters give only quasi-encapsulation and little benefit.
10. Active Records are DTOs with save/find; treat them as data structures. Do not put business rules in them; put rules in separate objects that hide the record.

**3. Caveats.** The Visitor/dual-dispatch footnote admits there are ways around the OO function-adding problem but they cost and return the structure to procedural. Admits frameworks (beans) force accessors on data structures, which confuses the Demeter question. Hiding-structure options (one big method on ctxt, or returning a data structure) "neither feel good" until the real intent is found.

**4. Key terms.** Data structure: exposes data, no meaningful behaviour. Object: hides data, exposes behaviour. Law of Demeter: only talk to immediate friends. Train wreck: chain of calls. Hybrid: half object/half data. DTO: public-field class. Bean: private fields with accessors. Active Record: DTO with persistence navigation methods.

**5. Quotes.**
- "Objects hide their data behind abstractions and expose functions that operate on that data."
- "Mature programmers know that the idea that everything is an object is a myth."
- "Hiding implementation is not just a matter of putting a layer of functions between the variables."

**6. Language.** Java-specific: beans, instanceof/casts, interfaces syntax, NoSuchShapeException. Universal and transfers to JS/Node: the object-versus-data-structure trade-off (a JS plain object or JSON row is a data structure; a class or closure with methods is an object), Demeter and chain-of-calls coupling (e.g. a.b.c.d optional chains), hybrids and rules-in-record smells (relevant to row objects from a database), tell-don't-ask.

## Chapter 7: Error Handling (by Michael Feathers)

**1. Core argument.** Error handling matters, but if it obscures the logic it is wrong. Treat error handling as a separate concern from the main algorithm so each can be read independently. Do this by using exceptions rather than return codes, defining the try scope first, giving exceptions context, shaping exception types around how callers handle them, and avoiding the invitation to errors that null creates. Robust and clean are not conflicting goals.

**2. Rules**
1. Use exceptions, not return codes or flags. Reason: codes clutter the caller, who must check immediately and may forget; exceptions separate the algorithm from error handling. Example: a device shutdown routine with nested status checks refactored into a try method that just does the steps.
2. Write the try-catch-finally first. A try block defines a transaction-like scope; the catch must leave the program consistent whatever happens. Write tests that force exceptions, then add behaviour. Example: a file-section retrieval built from a failing test, then catching a narrow exception type and rethrowing a domain one.
3. Use unchecked exceptions. Checked exceptions violate Open/Closed: a low-level change forces signature changes up the whole call chain and breaks encapsulation. Other languages (C#, Python, Ruby) manage fine without them.
4. Provide context with exceptions: say the operation that failed and the type of failure; a stack trace does not convey intent. Pass enough to log in the catch.
5. Define exception classes in terms of the caller's needs (how they are caught), not by source or type. Wrap third-party APIs so many vendor exceptions become one of yours, removing duplicated catch blocks. Example: LocalPort wrapping ACMEPort and translating three exceptions into one. A single class with details inside is often enough; use separate classes only when a caller wants to catch one and let the other pass.
6. Wrapping third-party APIs is a best practice: minimizes dependency, eases swapping vendors, eases mocking, and lets you define an API you like.
7. Define the normal flow using the Special Case pattern: return an object that carries the special-case behaviour so the client needs no exception handling. Example: a per-diem meal-expenses object returned when no meals are expensed.
8. Don't return null. It creates work for callers; one missed check breaks the app; too many checks are the real problem. Throw an exception or return a special-case object; wrap null-returning third-party methods. Example: return an empty list instead of null.
9. Don't pass null. It is worse than returning it. Throwing an invalid-argument exception or using assertions still leaves a runtime error. Rational approach: forbid passing null by default so a null in an argument list signals a bug.

**3. Caveats.** Checked exceptions can be useful in a critical library where callers must catch; in application work costs outweigh benefits. Admits "there are some times when you may not want to abort." Admits no good way in most languages to handle an accidentally passed null, hence the policy. Assertions are good documentation but do not solve it.

**4. Key terms.** Special Case pattern: an object that encapsulates exceptional behaviour. Checked exception: compiler-enforced declared exception. Wrapper/translation of exceptions. Normal flow: the main path uncluttered by error handling.

**5. Quotes.**
- "Error handling is important, but if it obscures logic, it's wrong."
- "Try blocks are like transactions."
- "If you are tempted to return null from a method, consider throwing an exception or returning a SPECIAL CASE object instead."

**6. Language.** Java-specific: checked versus unchecked, Collections.emptyList, assert statements, NullPointerException specifics. Universal/JS-Node: separate error handling from logic, wrap third-party APIs and normalise their errors, context-rich error messages (Error with cause), special case objects and empty arrays instead of null/undefined, do not swallow errors, treat try as a consistent-state scope (important with async code and promises), and policy against passing null/undefined.

## Chapter 8: Boundaries (by James Grenning)

**1. Core argument.** We rarely control all code in a system: third-party libraries, open source, other teams' components. A provider's broad interface and a user's narrow needs are in tension, and that tension causes trouble at the boundary. Keep boundary interfaces from spreading through your code: wrap or adapt them so few places know about them, test them, and prefer depending on something you control.

**2. Rules**
1. Do not pass a boundary type (such as a general Map) around the system or return it from public APIs; keep it inside the class or close family that uses it. Reason: a broad interface offers unwanted powers (clear, put of wrong types), forces casts at every call site, and changes ripple everywhere (e.g. when generics arrived). Example: a Sensors class with getById that hides the Map and can enforce business rules. Not every use of Map must be wrapped.
2. Write learning tests: controlled experiments that call the third-party API as you intend to use it, to learn it outside production code. Reason: learning and integrating at once is doubly hard. Example: a series of small tests discovering how to configure a console logger in log4j, ending in a reusable test file.
3. Learning tests are better than free: you must learn the API anyway, and the tests later detect behavioural differences when a new release arrives. Keep boundary tests exercising the interface the way production does, so migration is easy and you do not stay on an old version out of fear.
4. For code that does not exist yet, define the interface you wish you had, written in your own terms, and code against it; later write an adapter to the real API when it is defined. Example: a Transmitter interface with a transmit method, later bridged by a TransmitterAdapter. Benefits: client code stays clean, a seam for testing with a fake, single place to change.
5. Few places should refer to third-party particulars; wrap or adapt. "Better to depend on something you control than something you don't."

**3. Caveats.** Not our job to test third-party code, but worthwhile in our interest. Does not say to wrap every Map. The log4j example admits the library behaviour looked like a bug or inconsistency.

**4. Key terms.** Boundary: edge between your code and code you do not control (or do not yet know). Learning test: a test written to understand a third-party API. Adapter: class bridging your preferred interface to the provided one. Seam: a place to substitute behaviour for testing.

**5. Quotes.**
- "It's better to depend on something you control than on something you don't control, lest it end up controlling you."
- "Learning the third-party code is hard. Integrating the third-party code is hard too. Doing both at the same time is doubly hard."
- "This was the interface we wished we had."

**6. Language.** Java-specific: Map generics/casting detail, log4j, Java 5 history. Universal/JS-Node: wrap third-party SDKs/HTTP clients/DB clients behind your own module, learning tests for npm packages, writing your own interface before a vendor API exists, adapters, fakes at seams. Do not pass raw vendor response objects through the app.

## Chapter 9: Unit Tests

**1. Core argument.** Automated unit tests have become standard, but many teams miss subtler points. Test code is as important as production code and must be kept as clean; dirty tests are as bad as or worse than no tests because they become a liability, get discarded, and then the production code rots from fear of change. Tests are what let code stay flexible, maintainable and reusable ("-ilities"). A clean test is above all readable.

**2. Rules**
1. Three laws of TDD: no production code without a failing test; write no more of a test than is enough to fail (not compiling counts); write no more production code than needed to pass the failing test. Result: a cycle of about thirty seconds, tests and code growing together, tests covering virtually all production code.
2. Keep tests clean: same standards of quality as production code. Reason/story: a team allowed "quick and dirty" tests, costs rose, they discarded the suite, defects rose, fear grew and code rotted.
3. Tests enable the -ilities: coverage removes the fear of change, so you can improve architecture and design. Dirty tests hamper change.
4. Readability is the key quality of a test: clarity, simplicity, density of expression. Remove irrelevant detail. Example: three FitNesse tests full of path parsing and response-casting noise refactored into short tests with intent-revealing helpers.
5. Build-Operate-Check structure: each test has three parts: build test data, operate on it, check results.
6. Build a domain-specific testing language: helper functions on top of the production API that evolve through refactoring test code, not designed up front.
7. Dual standard: test code must be simple and expressive but need not be as efficient (memory/CPU) as production; never trade away cleanliness. Example: a state string like "HBchL" (upper case on, lower off) built by string concatenation, acceptable in tests though not in an embedded system; admitted as close to violating the mental-mapping rule but justified.
8. One assert per test is a good guideline: single conclusions are quick to understand; use given-when-then naming. But he is not afraid of more than one assert, and says minimizing asserts is the best statement. Splitting causes duplication, solvable with template method or @Before but "too much mechanism".
9. Single concept per test: avoid miscellaneous long test functions. Example: a date addMonths test mixing three concepts; splitting exposed a missing test (incrementing on February 28th).
10. F.I.R.S.T.: Fast (slow tests don't get run), Independent (no ordering; failures do not cascade), Repeatable (any environment, no network needed), Self-validating (boolean pass/fail, no log reading), Timely (written just before the production code, else code may be hard to test).

**3. Caveats.** Admits preferring the multi-assert version in his example. Says an entire book could be written about clean tests. Dual standard applies to efficiency, never cleanliness. Admits his own mental-mapping nearness.

**4. Key terms.** TDD; Build-Operate-Check; domain-specific testing language; given-when-then; F.I.R.S.T.; single concept per test; test double/mock; template method (used to dedupe tests).

**5. Quotes.**
- "Test code is just as important as production code."
- "Tests enable all the -ilities, because tests enable change."
- "The dirtier your tests, the dirtier your code becomes."

**6. Language.** Java-specific: JUnit annotations, StringBuffer remark, @Test(expected). Universal/JS-Node: all of it: three laws, readable helper-based tests, F.I.R.S.T., single concept per test, independence (no shared mutable fixtures between test files), repeatability without network, boolean exit codes (matches CI exit-code practice), writing tests in a timely way.

## Chapter 10: Classes (with Jeff Langr)

**1. Core argument.** Clean code needs clean organization at the class level, not just clean functions. The first rule is that classes should be small, measured by responsibilities rather than lines. The Single Responsibility Principle (one reason to change) gives both the definition and the size guideline; cohesion shows when a class should be split; and structuring classes to be open for extension, closed for modification, with dependence on abstractions, isolates the system from change.

**2. Rules**
1. Class organization: constants first, then private statics, then private instance variables, then public functions, with private helpers right after the public function that calls them (stepdown rule, reads like a newspaper).
2. Encapsulation: keep variables and utilities private, but "tests rule": loosen to protected/package scope if a test needs it; first look for a way to keep privacy; loosening is a last resort.
3. Classes should be small, then smaller; count responsibilities. Example: a SuperDashboard with ~70 public methods (God class), and even a five-method version has too many responsibilities.
4. Name test: if you cannot derive a concise name, the class is too large; weasel words (Processor, Manager, Super) hint at mixed responsibilities. Describe the class in about 25 words without "if", "and", "or", "but".
5. SRP: one reason to change. Example: version number methods extracted from the dashboard into a reusable Version class.
6. SRP is often abused because people stop when the code works; getting it to work and making it clean are two different activities, and you must go back and do the second. Fear that many small classes hide the big picture is unfounded: the same moving parts exist either way; prefer many small drawers, well labelled, over a few drawers where everything is tossed.
7. Cohesion: few instance variables; each method should use one or more; more variables used by a method means more cohesion. Example: a Stack. When a subset of methods uses a subset of variables, a class is trying to get out; split.
8. Maintaining cohesion yields many small classes: extracting from a big function tempts you to promote locals to fields, which lowers cohesion; resolve by splitting into new classes. Example: Knuth's prime printer turned from one long function into three classes (executable entry, page formatter, prime generator), each with one reason to change. Done not by rewrite but by tiny steps with a test suite proving behaviour after each change.
9. Organize for change (OCP): classes open for extension, closed for modification. Example: an Sql class with every statement type, rewritten as an abstract base with a subclass per statement, so adding update means adding a class. Primary trigger for splitting is actual change: if the class is logically complete, leave it; when you find yourself opening it, fix the design. Private methods used by only a subset of the class is a useful smell.
10. Isolate from change: depend on abstractions (Dependency Inversion Principle). Example: a Portfolio depending on a StockExchange interface so tests can use a fixed-price stub instead of a volatile live API.

**3. Caveats.** Not fanatic about private. Longer total code after refactoring is expected (longer names, declarations as commentary, whitespace). Leave a complete class alone. Admits people fear navigation across many classes (and answers it).

**4. Key terms.** SRP; cohesion; God class; OCP (Open-Closed); DIP (Dependency Inversion); stepdown rule; weasel words; stub/test double.

**5. Quotes.**
- "The first rule of classes is that they should be small. The second rule of classes is that they should be smaller than that."
- "When classes lose cohesion, split them!"
- "The SRP states that a class or module should have one, and only one, reason to change."

**6. Language.** Java-specific: access modifiers (protected/package), inheritance-based OCP solution, Swing. Universal/JS-Node: SRP, cohesion, naming and 25-word test, DIP via passing a dependency in (function parameter or module injection), refactor in small steps under tests, extend by adding modules rather than editing existing ones (e.g. strategy maps), splitting big route files/modules by reason to change.

## Chapter 11: Systems (by Dr. Kevin Dean Wampler)

**1. Core argument.** Systems, like cities, work because of modularity, levels of abstraction and decentralised management. Cleanliness must carry up to the system level. Separate constructing and wiring the system from using it, keep domain logic free of infrastructure (POJOs), handle cross-cutting concerns with aspect-like mechanisms, and let architecture grow incrementally instead of designing everything first. Defer decisions, use standards only when they add value, and use domain-specific languages. Simplest thing that can work.

**2. Rules**
1. Separate construction from use: startup (building and wiring objects) is a different concern from runtime logic. Lazy-initialization idiom hard-codes a concrete dependency, breaks testing, mixes two responsibilities, and scatters setup strategy through the code. Keep a global consistent strategy for resolving major dependencies.
2. Separation of main: do all construction in main (or modules it calls); the application assumes objects are built and wired; dependencies point away from main.
3. Factories (Abstract Factory) when the application must decide when to create an object but not how. Example: order processing creating line items through a factory implemented on the main side.
4. Dependency injection: an object does not instantiate its dependencies; it is passive and receives them via constructor arguments or setters, from main or a container configured by file or code. Lookup via a directory service is only partial DI. Lazy initialization is still allowed with DI (containers build on demand), but is merely an optimization and perhaps premature.
5. Scale up incrementally: it is a myth we can get systems right the first time; implement today's stories and refactor and expand. Software architecture can grow if concerns are separated. Counterexample: EJB2 entity beans coupled business logic to the container with required interfaces, lifecycle methods, XML descriptors, making unit tests, reuse and inheritance hard and spawning redundant DTOs.
6. Cross-cutting concerns (persistence, transactions, security) cut across object boundaries; handle with aspect-oriented programming: modular aspects that say where behaviour is changed noninvasively. Three mechanisms: Java dynamic proxies (simple but verbose, interface only, no system-wide specification); pure-Java AOP frameworks like Spring where POJOs hold domain logic and declarative configuration wraps them in nested decorators (the "Russian doll"); AspectJ (most powerful but needs new tools and idioms; Spring AOP/JBoss suffice for 80-90 percent of cases). EJB3 later adopted the Spring-like approach with annotations, far cleaner.
7. Test drive the system architecture: with POJOs decoupled from architecture at code level you can evolve simple to sophisticated, no Big Design Up Front (BDUF), which is harmful because of resistance to discarding effort and because choices bias later thinking. Start with a "naively simple but nicely decoupled" architecture. Not rudderless: have expectations about scope, goals, schedule.
8. Optimize decision making: modularity enables decentralised decisions; postpone decisions to the last responsible moment because a premature decision is made with suboptimal knowledge.
9. Use standards wisely, only when they add demonstrable value; teams adopted EJB2 as a standard even when lighter designs sufficed. Standards help reuse, hiring, wiring, but may be slow or lose touch.
10. Use domain-specific languages to cut the communication gap between domain experts and code; express all levels as POJOs.

**3. Caveats.** Lazy initialization has real merits (faster startup, never returns null). XML config can be verbose (can use convention and annotations). Building architects must do BDUF but software differs. Up-front design in general is fine; BDUF is the problem. A good API should disappear from view. AOP should not be confused with proxies as technique.

**4. Key terms.** Dependency Injection / Inversion of Control; Abstract Factory; cross-cutting concern; aspect/AOP; POJO; decorator; BDUF; DSL; lazy initialization; test double; separation of main.

**5. Quotes.**
- "It is a myth that we can get systems 'right the first time.'"
- "A premature decision is a decision made with suboptimal knowledge."
- "Whether you are designing systems or individual modules, never forget to use the simplest thing that can possibly work."

**6. Language.** Java-specific: EJB, Spring XML, JDK proxies, AspectJ, annotations, JNDI. Universal/JS-Node: composition root (build and wire dependencies at startup, e.g. in a single bootstrap/index, pass collaborators in), dependency injection by parameters, factories, middleware as the aspect-like mechanism for auth/logging/transactions in Express, keep domain logic free of framework imports, incremental architecture, defer decisions, adopt standards only for demonstrable value, small DSLs (query builders, test helpers).

## Chapter 12: Emergence (by Jeff Langr)

**1. Core argument.** Kent Beck's four rules of Simple Design, applied in order of importance, let good design emerge and help apply SRP and DIP almost automatically: run all the tests, contain no duplication, express the programmer's intent, minimise classes and methods. Having tests pushes design toward low coupling and high cohesion; once tests exist, constant small refactoring applies the remaining three rules.

**2. Rules**
1. Rule 1, runs all the tests: a system must be verifiable; an unverifiable system should arguably never be deployed. Testability pushes toward small single-purpose classes, and tight coupling makes tests hard, so writing tests drives DIP, interfaces, injection and abstraction.
2. Rules 2-4 are done in a refactoring step: after each few lines, reflect on the design, clean up, rerun tests; tests remove the fear.
3. Rule 2, no duplication: the primary enemy of good design (extra work, risk, complexity). Duplication appears as identical lines, similar lines (massage to look alike), and duplicated implementation (e.g. isEmpty defined via size). Examples: extracting a replaceImage helper shared by scale and rotate. Extracting small commonality exposes SRP violations and "reuse in the small" leads to reuse in the large. Template Method removes higher-level duplication (example: US vs EU vacation accrual sharing an algorithm skeleton with one overridable step).
4. Rule 3, expressive: most of the cost of software is maintenance, so make intent clear. Ways: good names (no surprises about responsibilities); small functions and classes; standard nomenclature (pattern names like Command, Visitor); well-written tests as documentation by example; and above all try: "care is a precious resource", the next reader is likely you.
5. Rule 4, minimal classes and methods: keep counts low; do not take SRP and duplication removal to dogmatic extremes (e.g. an interface for every class, or forced split between data classes and behaviour classes). This is the lowest priority.

**3. Caveats.** Admits no simple set of practices replaces experience; the rules crystallise decades of experience. The rules are explicitly ordered, and minimality yields to the first three.

**4. Key terms.** Simple Design (four rules); emergent design; refactoring; reuse in the small; Template Method pattern; expressiveness.

**5. Quotes.**
- "Duplication is the primary enemy of a well-designed system."
- "Writing tests leads to better designs."
- "Care is a precious resource."

**6. Language.** Java-specific: Template Method via abstract class inheritance; pattern names reference. Universal/JS-Node: all four rules; in JS dedupe via small shared functions or higher-order functions rather than inheritance; the priority order (tests, then no duplication, then clarity, then fewer pieces) transfers directly.
