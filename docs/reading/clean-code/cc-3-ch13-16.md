# Clean Code, Chapters 13-16 - notes

## Chapter 13: Concurrency (Brett Schuchert)

### 1. Core argument
Concurrency is a way of decoupling WHAT gets done from WHEN it gets done; it can improve structure (many small collaborating pieces) and throughput/response time (waiting on I/O, many users, big data sets). But it is very hard: code can look fine and fail only under stress, and bugs are rarely repeatable so people dismiss them as "one-offs". The chapter's answer is discipline: keep concurrency code separate and small, share as little data as possible, know the library and the classic models, and test hard with many configurations and deliberate perturbation.

### 2. Rules / heuristics
1. Myths to drop: concurrency does NOT always improve performance (only when there is wait time to share); design DOES change; you must understand concurrency even inside a container (web/EJB). Reasoning: containers only partly hide it. Balanced facts: it has overhead, is complex even for simple problems, bugs are non-repeatable, and often needs a design change.
2. Demonstration of the problem: two threads calling a trivial "next id" counter can both get the same number (lost update); there are thousands of possible interleavings of one line (12,870 for int, 2.7 million for long), and only a few are wrong - which is why failures are rare.
3. Single Responsibility: keep concurrency code separate from other code. Reasoning: it has its own life cycle, own challenges, and enough failure modes of its own.
4. Limit the scope of data: encapsulate shared data and keep the number of critical sections small. Reasoning: more places = more chances to forget a guard, duplicated effort (DRY), harder diagnosis.
5. Use copies of data: copy objects, treat as read-only, or let threads work on copies and merge results in one thread. Reasoning: avoiding locks usually pays for the extra object creation; measure to be sure.
6. Threads should be as independent as possible: each handles one request using only local data (the servlet model), or partition data into independent subsets. Caveat: shared resources like DB connections eventually appear.
7. Know your library: use thread-safe collections, the executor framework for unrelated tasks, non-blocking solutions where possible; know that some library classes are not thread-safe. Example: ConcurrentHashMap beats HashMap in nearly all situations; ReentrantLock, Semaphore, CountDownLatch exist for advanced designs.
8. Know the execution models and vocabulary, and study/implement them yourself: Producer-Consumer (bounded queue, signal each other), Readers-Writers (balance throughput vs starvation vs stale data), Dining Philosophers (competition for resources causes deadlock/livelock). Most real problems are variations of these three.
9. Beware dependencies between synchronized methods: prefer only one method on a shared object; when you must use several, use client-based locking, server-based locking (a new server method that does the locking), or an adapted server (intermediary when you cannot change the original).
10. Keep synchronized sections small: locks cost; but over-large critical sections increase contention. Minimal critical section, no more.
11. Shut-down code is hard: think about it early, get it working early; it takes longer than expected. Example: a parent waiting forever on a deadlocked child, or a consumer blocked waiting for a producer that already exited.
12. Testing: you cannot prove correctness, but good tests lower risk; run them often, with different configurations, systems and loads; never ignore a failure because the next run passed.
13. Treat spurious failures as candidate threading issues; assume "one-offs" do not exist (ignoring them lets more code build on a faulty approach).
14. Get non-threaded code working first: put logic in plain thread-ignorant objects (POJOs) that threads call; do not chase threading bugs and logic bugs together.
15. Make threaded code pluggable: runnable with one/many/varying threads, real or test-double collaborators, fast/slow/variable doubles, configurable iteration counts.
16. Make threaded code tunable: time performance under different thread counts early; allow the count to be changed (even at runtime, or self-tuning).
17. Run with more threads than processors, to force task switching and expose missing locks and deadlocks.
18. Run on different platforms: the author's own course demos failed more often on OS X than on Windows XP; the JVM does not even guarantee preemption. Test every target environment.
19. Instrument to force failures ("jiggling"): insert wait/sleep/yield/priority calls at risky spots, by hand (shotgun, slows production, hard to choose spots) or automated (a no-op "jiggle point" in production, randomised in test; tools such as aspect frameworks or IBM ConTest). If the code breaks, the code was already broken - jiggling just exposed it.

### 3. Caveats / admitted limits
- Chapter is only an overview; a deeper tutorial is in Appendix A. Tests do not guarantee correctness. Jiggling with random calls is "a bit simplistic" but at least due diligence. Servlet/container isolation is "far less than perfect". Copy cost should be measured, not assumed.

### 4. Key terms
- Bound resource: fixed-size/number resource (DB connections, buffers).
- Mutual exclusion: only one thread touches shared data at a time.
- Starvation: some threads are blocked for a very long time or forever.
- Deadlock: threads each hold what the other needs and wait forever.
- Livelock: threads keep trying but keep getting in each other's way.
- Critical section: code that must not run simultaneously for correctness.
- Producer-Consumer, Readers-Writers, Dining Philosophers: the three classic models.
- POJO (thread-ignorant object): plain object with no threading knowledge.
- Jiggling: perturbing execution order to expose races.

### 5. Quotes
- "Objects are abstractions of processing. Threads are abstractions of schedule." (Coplien, epigraph)
- "Concurrency is a decoupling strategy."
- "It is best to assume that one-offs do not exist."

### 6. Language-specific vs universal
- Java-specific: synchronized, ConcurrentHashMap, executors, ReentrantLock/Semaphore/CountDownLatch, Thread.yield, JVM preemption, servlet containers.
- Universal/transfers to Node: separate concurrency code from business logic; limit shared mutable state; copy/immutability; independent units of work per request; know your library; the three classic models (queues = producer-consumer; connection pools = bound resources); shutdown is hard (graceful drain of in-flight work); never dismiss non-repeatable failures; make concurrency limits configurable/tunable; test on target environment under load. Node's single thread removes data races inside one process but NOT the interleaving of async steps: a read-await-write sequence (check then update) can interleave with another request exactly like the counter example, and multiple server instances or database rows are truly concurrent. Worker threads and DB-level concurrency are the real equivalents.


## Chapter 14: Successive Refinement (case study: command-line argument parser "Args")

### 1. Core argument
Clean code is not written clean in one pass; it is written dirty and then cleaned, like successive drafts of an essay. The chapter shows a small argument-parsing class that started tidy (booleans only), got messy as string and integer types were bolted on, and was then restructured in many tiny, always-green steps into a small core plus one class per argument type and a separate exception class. The author's point: stopping to refactor the moment the mess starts to grow (before adding more features) is cheap, while leaving "it works" code behind is unprofessional and eventually crushes a project.

### 2. Rules / heuristics (and the sequence of transformations)
1. Working is not enough. Programmers who stop at "it works" are behaving unprofessionally; bad code is the most durable drag on a project (schedules, requirements and team dynamics can be repaired; rotten code cannot easily). Cleaning a mess five minutes old is easy; later it is very expensive because modules tangle together.
2. Write the rough draft, then refine. Do not expect to write elegant code in one pass.
3. Stop and restructure at the right moment. The author saw that adding the String and Integer types had caused the mess and that two more types were coming; he stopped adding features. His diagnosis: every new argument type needed code in three places (parse its schema marker, parse its value from the command line, return it typed to the caller) - "many types with similar methods sounds like a class", so the marshaler abstraction was born.
4. Incrementalism / TDD discipline: never make a change that breaks the system; keep the system working at every step. This needs a suite of automated tests (unit plus acceptance) that you can run at will. Massive "improvements" are one of the best ways to ruin a program.
5. Transformation sequence for the first refactoring (each step run against tests):
   a. Append an empty skeleton of the base marshaler class and three empty subclasses at the end of the old class - cannot break anything.
   b. Change the boolean map to hold marshaler objects; fix the null-handling that broke (the old null guard was no longer relevant because the thing that can be null is now the marshaler). Reason: smallest change that moves toward the goal; a failing test shows exactly what the change broke.
   c. Do the same for strings, then integers, putting all behaviour first in the BASE class (so everything still works), with the goal of pushing it down later.
   d. Push behaviour down into the subclasses one piece at a time: add an abstract "set", implement for boolean, switch the caller, delete the now-unused base method and move the private field into the subclass; add abstract "get" (returns generic Object, which is ugly but necessary); repeat for string and integer. Integer parsing errors become hidden inside the integer marshaler, which is a better place.
   e. Replace the three type-specific maps with one generic map: add the new map alongside, migrate methods one by one, then delete the old maps. Replace "is it a boolean arg" checks with type checks on the marshaler, remove duplicate lookups, inline the now-trivial helper methods.
   f. Result is judged "a bit disappointing": structure better, but still many fields, a type-switch (if/else on type) in the set method, ugly set functions and tangled error handling.
6. Remove the type switch by polymorphism: replace three type-specific set functions with a single call on the marshaler. Obstacle: the type-specific functions used two shared fields (the argument array and current index), and passing both is "dirty"; fix: convert the array to a list and pass an iterator (about ten tiny steps). Then add a second, iterator-taking "set" to the abstract class, implement per subclass, call it from the switch for all three types, and finally delete the switch and the old string-based set. The base class then becomes a pure interface. Reason: a type switch is a code smell (G23, prefer polymorphism to if/else); every new type would otherwise touch it.
7. Prove the new structure is extensible: adding a double type took a new test, one schema marker, one new marshaler class, one error code, one getter - changes small and isolated. Write the test first, including error cases (invalid and missing values), even "for completeness".
8. Pull the exception and error code out: merge the scattered exception types into one dedicated exception class in its own module; move error-message formatting there (about 30 tiny steps). Args then mostly shrinks (changes were mostly deletions) and each marshaler lives in its own file. Principle: "Much of good software design is simply about partitioning - creating appropriate places to put different kinds of code."
9. Stage-by-stage clean-up of the ARGS class itself is left as an exercise (final form shown at chapter start: error state carried in the exception, no valid flag, the iterator held, marshaler interface with one set method and typed static getters).
10. Names and small details: the author shortens a redundant long variable name to a short one during the refactor and cites numbered smells/heuristics from ch. 17 (G23 polymorphism over switches, F1 too many function arguments, N5 name length scoped to use).

### 3. Caveats / admitted limits
- Putting message formatting inside the exception class is called a "compromise" (it breaks single responsibility slightly but gives users canned messages; they can write their own).
- The author admits Java is wordy for this; he rewrote it later in Ruby at about one seventh the size with slightly better structure.
- Refactoring is "like solving a Rubik's cube": things put in (such as exception handling) are taken out again a few steps later; this is normal.
- A gap found mid-refactor: the unit tests did not cover behaviour that the separate acceptance suite did (calling a boolean getter on a non-boolean argument returns false); he had only run unit tests, so he added a unit test that invokes the acceptance suite. Lesson: run all the tests.
- The first-draft listing is deliberately a bad example; the final version is offered as "worth emulating" while allowing that experienced readers may quibble with style.

### 4. Key terms
- Successive refinement: improving code through repeated small drafts.
- Marshaler (ArgumentMarshaler): object that knows how to read and hold one argument type's value.
- Schema string: the format string describing which arguments exist and their types.
- Festering pile: the author's term for code that has crossed the line from untidy to unmaintainable.
- Incrementalism: making only tiny changes, each leaving the system working.
- Type-case: a chain of if/else or switch on an object's type.

### 5. Quotes
- "To write clean code, you must first write dirty code and then clean it."
- "It is not enough for code to work."
- "Never let the rot get started."

### 6. Language-specific vs universal
- Java-specific: static typing verbosity, instanceof/ClassCastException details, checked exceptions, the specific iterator API. 
- Universal/transfers to JavaScript: draft-then-refine; stop and restructure when each new case needs edits in the same N places; replace type switches with a per-type object/map of handlers (in JS a lookup table of parser functions); tiny always-green steps backed by tests; run the acceptance AND unit suites; keep errors in a dedicated error type; partition by concern. In JS the dynamic typing makes the class version far smaller (a handler table), as the author himself noted about Ruby.


## Chapter 15: JUnit Internals

### 1. Core argument
The author takes a small, already-good piece of the JUnit framework (a class that turns two differing strings into a short "expected vs actual" message with the difference in brackets) and applies the Boy Scout Rule: leave the code a little cleaner than you found it. The original is well tested (100 percent coverage) and well partitioned, yet a series of small improvements to naming, structure and hidden assumptions still makes it clearer and even reveals a redundant piece of logic. The lesson is that no module is immune from improvement, and that refactoring is trial and error, including reversing your own earlier decisions.

### 2. Rules / heuristics (sequence of transformations, with reasons)
1. Start from tests: the supplied tests are read first as the specification, and coverage (100 percent) is cited as the basis for confidence. The reader is invited to critique the tests too.
2. Remove the "f" prefix on member variables (N6): modern tools make scope-encoding prefixes redundant.
3. Encapsulate the conditional at the top of the main method into a named method (G28): the name states intent.
4. Remove names that clash between locals and members (N4): rename locals so they are unambiguous (compactExpected, compactActual).
5. Prefer positive conditionals (G29): invert the sense so the condition reads as "can be compacted".
6. Rename a method whose name hides what it does (N7): the method may not compact at all and returns a formatted message, so it is renamed to say it formats a compacted comparison.
7. Split responsibilities (G30): the "compact" part does only compacting; formatting stays in the public method; this promotes intermediate results to fields.
8. Use consistent conventions (G11): make the two "find" helpers return values the same way.
9. Name variables accurately (N1): "index" vs "length".
10. Expose hidden temporal coupling (G31): the suffix finder silently relied on the prefix finder having run first. First attempt: pass the prefix as a parameter - rejected as arbitrary (G32) because it enforces order without explaining why, and a later maintainer might undo it. Better: merge into one method that calls the prefix finder first, which makes the ordering dramatic and visible.
11. Clean the ugly suffix loop by extracting small helpers (a character-from-end helper and an overlap test).
12. Remove off-by-one noise (G33, boundary conditions): the "+1"s scattered through the suffix code came from the suffix being a 1-based "index" rather than a true length. Switching to a real length moves the correction into one place (the character-from-end helper, and two less-or-equal comparisons) where it makes sense.
13. A discovery: after the change, one "if suffix greater than zero" check suddenly made sense where before it had been non-functional (the old value could never be below one), so it was dead code. Both conditionals in the string-composing method were commented out; tests still passed; they were deleted and the method simplified (G9, dead code).
14. Final form: split into a group of analysis functions (find prefix and suffix) and a group of synthesis functions (compose the result from small named pieces: leading ellipsis, leading context, delta, trailing context, trailing ellipsis), ordered so each function appears just after it is used (top-down reading).
15. Reversals are normal: several earlier decisions (extracted methods, a flipped conditional) were undone in the final version.

### 3. Caveats / admitted limits
- The original is "pretty good"; the author shows a deliberately defactored (cryptic names) version to prove how much the authors already did right.
- Not every cleanup is shown; he skips to the result. A different "fix" (passing a parameter) is shown and rejected, to show trial and error.
- Refactoring "inevitably converging on something that we feel is worthy of a professional" - a judgment call, not a proof.

### 4. Key terms
- Boy Scout Rule: leave the campsite (code) cleaner than you found it.
- Temporal coupling: a hidden requirement that functions be called in a certain order.
- Defactored: a version of code with good structure and names deliberately stripped.
- Analysis vs synthesis functions: functions that work out facts vs functions that assemble the output.
- Code coverage: share of lines/branches executed by tests.

### 5. Quotes
- "No module is immune from improvement, and each of us has the responsibility to leave the code a little better than we found it."
- "Often one refactoring leads to another that leads to the undoing of the first."
- "Refactoring is an iterative process full of trial and error, inevitably converging on something that we feel is worthy of a professional."

### 6. Language-specific vs universal
- Java-specific: field prefix conventions, StringBuilder chaining, the testing framework itself.
- Universal: Boy Scout Rule; tests first as specification and safety net; intent-revealing names; positive conditionals; hidden ordering made explicit; replace magic +1/-1 with a correctly defined quantity; delete dead branches proven dead by tests; analysis-then-synthesis structure; top-down ordering. All transfer directly to JavaScript.


## Chapter 16: Refactoring SerialDate

### 1. Core argument
The author critiques a respected open-source date class (competent, public, "good code") as a professional code review, arguing that such review is normal and welcome, as in medicine or aviation. His method has two phases: first make it work (raise test coverage from about half to over 90 percent with his own independent tests, fix the bugs those tests expose), then make it right (walk top to bottom, improving names, placement of responsibility, abstractions and dead code, running all tests after every change). The result is smaller, clearer, better tested and with bugs fixed; the lesson is the Boy Scout Rule again, plus a large catalogue of specific smells, each tagged to a heuristic code (C = comments, G = general, N = names, J = Java, T = tests, F = functions) from Chapter 17.

### 2. Rules / heuristics and the sequence of changes

Phase 1: make it work
1. Do not trust "tests pass": check what the tests cover (T1 insufficient tests). A coverage tool showed only about half of executable statements ran (T2: use a coverage tool). A method no-one calls (F4 dead function) is also untested.
2. Write your own independent test suite for behaviour you think the class should have; leave failing tests commented out as a to-do list of behaviour to achieve. Trivial tests are cheap (T3). Obvious behaviour should be implemented (G2): e.g. weekday-name parsing should ignore case.
3. Tests exposed bugs: a "following weekday" function returned the same day instead of the next week (boundary condition error, G3/T5); the "nearest weekday" function failed whenever the nearest day was in the future. Clues the author used: a function that had been fixed repeatedly is suspect (T6 test near bugs), the pattern of failing cases is revealing (T7), and the coverage pattern is revealing (T8): a branch that never executes meant the algorithm was simply wrong. Fix: correct comparison operator; replace the nearest-day algorithm with a modular arithmetic one; return an error (throw an illegal-argument exception) instead of an error string.

Phase 2: make it right (in the order the author hit them)
4. Delete the change-history comment block: source control does that now (C1 inappropriate information). Keep legal licence text.
5. Shorten the import list with wildcards (J1) - the author's preference.
6. Avoid mixing languages in one place (G1): HTML in the doc comment is a fourth language in the file.
7. Rename the class away from a misleading, implementation-leaking name (N1 descriptive names; N2 names at the right level of abstraction): "Serial" is wrong (the value is an offset/ordinal, not a serial number) and reveals an implementation in what is an abstract class. Result: DayDate, the best compromise given that Date and Day are taken.
8. Do not inherit from a constants interface (J2); replace the constants with an enum (Month). Costs an hour of changes but removes the validity-check function and error-checking everywhere (G5 duplication; the type now makes invalid values impossible). Same for days of the week (J3 prefer enums to constants), week-in-month, an interval-type flag (renamed with mathematical terms: open/closed intervals, N3 unambiguous standard nomenclature), and the "last/next/nearest" selector.
9. Serialisation version id: he deletes it so the compiler regenerates it each build (G4 do not override safeties; he prefers a loud failure over a silent one). Admitted debatable: reviewers disagreed, saying open-source libraries should control it manually; he concedes the point and says the real moral is not to expect to deserialize across versions.
10. Delete redundant comments (C2 obsolete comments, C3 redundant comments): they become places to collect lies. Delete comments describing tables whose names suffice.
11. Move things to where they belong (G6 code at the wrong level of abstraction): earliest/latest ordinal constants and year bounds used only by the one concrete subclass go down into that subclass. Dilemma: another class needs the year bounds from the abstract class. Resolution: a base class should not know its derivatives (G7), but creation happened in the base; introduce an Abstract Factory (a date factory that creates dates and answers questions about the implementation, defaulting to the spreadsheet one but replaceable). Method names improved: "createInstance" becomes "makeDate".
12. Make internals private where an accessor function already exists (G8 too much information), delete unused tables and fields (G9 dead code), move a table next to its only user (G10 vertical separation: keep things close to where used; easily moved back later if needed), keep treatment consistent (G11).
13. Delete the degenerate default constructor and the many `final` keywords on arguments and locals as clutter (G12 clutter). He openly disagrees with the book that recommends `final` everywhere: unit tests already catch what it would.
14. Merge duplicate if-statements into one using or (G5). Move a string-parsing method to the enum it belongs to (G14 feature envy: a method that mostly uses another class's data belongs there), then move the enum out into its own file when it grows, since the concept does not depend on the container (G13 artificial coupling).
15. Collapse two functions where one only exists to be called by the other, and rename (G9, G12, F4). Replace twin functions that differ by a boolean flag with two clearly named methods (G15 selector arguments).
16. Make code more expressive with explanatory booleans (G16 obscured intent, e.g. leap-year rule split into named parts); move data to the class it describes (G17 misplaced responsibility).
17. Static versus instance (G18 inappropriate static): a "static" function that operates on a date's own data should be an instance method. Use explaining temporary variables (G19) for tricky algorithms (month arithmetic).
18. Names should reveal that an operation returns a new value (G20 function names should say what they do; N4 unambiguous names): after turning add methods into instance methods, "date.addDays(5)" could be misread as mutating the date, so rename to "plusDays" (returns a new date). 
19. Understand the algorithm before cleaning it (G21): simplified the previous/following weekday logic to a short offset computation with a sign adjustment, and made the nearest-weekday version consistent with them (G11).
20. A method that takes an instance of its own class as an argument envies itself: make it a true instance method (G14).
21. A clever refactoring chain can end in "delete it": moving a to-string method into an enum, renaming it, making it an instance method, then deleting it (enum values already print their names) - only to find the only callers were tests he had just edited. He deleted those too. "Fool me once..." (do not be too clever; check who actually uses something before polishing it). Same for another test-only function.
22. Push or pull methods to the right level in the hierarchy: abstract methods that do not depend on the implementation are pulled up (G6). A subtle one (day-of-week): no physical dependency but a LOGICAL dependency on the origin of the ordinal count (G22 make logical dependencies physical): introduce an abstract method that supplies the missing fact ("day of week for ordinal zero") and move the algorithm up.
23. Rename for what it returns (N1): "compare" becomes "days since"; write tests for any untested method touched.
24. Replace switch statements with polymorphism (G23): the range-inclusion switch moves into the interval enum, one case per enumerator.
25. Final pass over the whole class: shorten the out-of-date opening comment (C2); move enums to their own files (G12); move static helpers (month names, leap year, last day of month) to a utility class (G6); put abstract methods at the top (G24 coding standard / ordering); rename factory-style methods consistently ("fromInt"), make enum index private with a getter; extract a shared helper for duplicated end-of-month clamping in plusYears/plusMonths (G5); replace magic number 1 with named constants (G25).
26. Coverage went DOWN to about 85 percent after refactoring because the class shrank and a few trivial uncovered lines weigh more - not because less is tested.

### 3. Caveats / admitted limits
- Reviewers disagreed with deleting the serialization id; the author concedes the point is fair.
- Disagrees with common advice to put `final` everywhere (acknowledges it is against conventional wisdom).
- Name choices (DayDate, WeekdayRange, DateInterval) are personal and "may not make sense to you"; the point is they are now easy to change because they are symbols, not integers.
- The author admits being "a bit too clever" with one refactoring chain.
- The review is explicitly not malice: he says his own code would draw plenty of complaints, and praises the original author for publishing it.
- Some reasoning is a judgment call (where to put a table; whether a Date-like name is acceptable); he states the arguments on both sides.

### 4. Key terms
- Boy Scout Rule: leave the code cleaner than found.
- Abstract Factory: an interface/class that creates families of related objects so callers need not name concrete classes.
- Feature envy: a method more interested in another class's data than its own.
- Explaining temporary variable: a well-named local that makes a sub-expression self-documenting.
- Selector argument (flag argument): a boolean or enum parameter that picks which of two behaviours to run.
- Logical vs physical dependency: a hidden assumption about another part vs a visible reference to it.
- Open / half-open / closed interval: whether the endpoints are included in a range.
- Ordinal (day count): number of days from a chosen origin date.
- Code coverage (Clover): a tool reporting which statements the tests execute.
- Pull up / push down: moving a method toward the base class or toward a subclass.

### 5. Quotes
- "This is not an activity of malice... What I am about to do is nothing more and nothing less than a professional review."
- "Redundant comments are just places to collect lies and misinformation."
- "We've checked the code in a bit cleaner than when we checked it out."

### 6. Language-specific vs universal
- Java-specific: serialVersionUID, constants-interface inheritance, final keyword, enums with constant-specific bodies, Javadoc/HTML, java.util.Date/Calendar, static vs instance methods, wildcard imports (J1-J3).
- Universal / transfers to JavaScript/Node: get real coverage numbers and write your own tests before refactoring; use failing and un-covered code as a bug detector; test where bugs cluster; replace magic integers and string flags with named constants (object-frozen enums or string unions); keep parse/format/validate functions with the data type they belong to; do not let a base module know its variants (use a factory/registry); delete dead code and unused fields; remove history/obsolete comments; avoid boolean flag parameters; method names that signal "returns a new value" (immutability); explaining variables; replace switch on type/kind with a lookup table or per-case objects; make hidden logical dependencies explicit; move helpers into a utility module; check who really calls a function before polishing it. In JS the "static vs instance" and `final` points have only loose equivalents (module-level function vs method; const).
