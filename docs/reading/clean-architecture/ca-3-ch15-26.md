## Ch. 15 - What Is Architecture?

**1. Core argument.** Architecture is the shape a system's builders give it: how it is divided into components, how they are arranged, and how they talk. Its purpose is to support the system's whole life (development, deployment, operation, maintenance), not to make it behave correctly; plenty of badly structured systems run fine. The strategy is to keep as many options open for as long as possible, which means separating *policy* (business rules, where the value lives) from *details* (IO devices, databases, web, frameworks) so that the details can be decided late and changed cheaply. Two 1960s-70s war stories (device independence, relative disk addressing) show the principle in miniature.

**2. Rules / recommendations.**
1. An architect keeps programming. Reason: they cannot judge the pain they impose on others unless they feel it.
2. Judge architecture by the lifecycle cost it removes: easy to understand, develop, maintain, deploy. Goal: minimise lifetime cost and maximise programmer productivity.
3. Development: team structure drives architecture. A 5-person team can work in a monolith with no formal interfaces (and early structure can feel like an impediment, which is why so many systems start with none). Five teams of seven need well-defined components with stable interfaces, otherwise they trample each other; left to schedule pressure alone they gravitate to one component per team, which is poor for deployment/operation.
4. Deployment: aim for one-action deployment; the cost of deploying should be considered at the start. Example: a micro-service design that is easy to build but daunting to deploy (connection config and start-up timing become error sources); fewer services, or a hybrid of services and in-process components, might have been better.
5. Operation: architecture matters less here because hardware is cheap and people are expensive; throw servers at it. But architecture should *reveal* operation: use cases, features and required behaviours should be first-class, visible landmarks.
6. Maintenance is the costliest phase; cost = "spelunking" (digging for where to change) + risk (breaking something). Component separation behind stable interfaces illuminates the paths and reduces breakage.
7. Software has behaviour-value and structure-value; structure is the greater, because it is what keeps software soft (changeable).
8. Split every system into policy and details. Details = anything that lets humans, other systems and programmers communicate with the policy without changing it.
9. Defer decisions about details: no need to pick database, web server, REST, micro-service framework, or DI framework early, because policy should not know about them. Later decisions are better informed and allow experiments (try several databases against the same policy).
10. If someone already made the decision (company mandates a database/framework), pretend it hasn't been, and shape the system so it can still be changed. "A good architect maximizes the number of decisions not made."
11. Device independence story (1960s): code bound directly to card readers/printers had to be rewritten for tape. OS-level abstraction of unit-record devices let the same program run against cards, tape or printer unchanged (Martin calls this the birth of the Open-Closed Principle). Junk-mail story: because programs used the abstraction, the company redirected the expensive mainframe's output to tape and printed offline on cheap printers 24/7.
12. Physical addressing story (1970s): hard-wiring cylinder/head/sector into all business rules made a disk upgrade a data migration plus code rewrite everywhere. Fix: treat the disk as a linear array of sectors with sequential integer addresses and one small conversion routine that knows the geometry.

**3. Caveats.** Early structure is admitted to feel like an impediment for a small team. Operational performance does matter (it is "desirable"), just cheaper to fix with hardware. He says architecture's role in making a system *work* is "passive and cosmetic."

**4. Key terms.** Policy: business rules and procedures. Details: IO, databases, web, servers, frameworks, protocols. Spelunking: cost of digging through code to find where to change. Device independence: programs written against abstract devices.

**5. Quotes.**
- "The strategy behind that facilitation is to leave as many options open as possible, for as long as possible."
- "A good architect maximizes the number of decisions not made."
- "The primary purpose of architecture is to support the life cycle of the system."

**6. Applies to web SaaS (Node/Express + Postgres)?** Fully: the policy/detail split maps to business rules vs Express, Supabase/Postgres, mail providers, AI vendors. The deployment point (one action, few moving parts) and "hardware is cheap, people are expensive" transfer directly; the punch-card and disk examples are dated but the lesson (one conversion point for storage geometry or vendor specifics) is exactly the vendor-neutral-layer idea.

## Ch. 16 - Independence

**1. Core argument.** A good architecture must support four things: use cases, operation, development, deployment. The way to serve all of them while requirements stay unclear and keep changing is to decouple things that change for different reasons (layers) and things that are different use cases (vertical slices), and to leave open *how* the decoupled pieces are connected (source, deployable, or service level). Do not eliminate duplication reflexively; much of it is accidental.

**2. Rules.**
1. Use cases: the architecture should make the system's intent visible (a shopping cart system should look like one), with use cases as first-class named elements. (Forward reference to Ch. 21.)
2. Operation: the architecture must support the required throughput. Whether the system runs as a monolith, threads, processes or services is itself an option to keep open; a monolith that depends on being a monolith cannot be moved later, while well-isolated components that don't assume their communication mechanism can slide along the spectrum.
3. Development: Conway's law (system structure copies the organisation's communication structure). Partition into well-isolated, independently developable components so teams don't interfere.
4. Deployment: aim for "immediate deployment" after build; no piles of config scripts, hand-made directories or property-file tweaks. Achieved by clean partitioning plus well-built "master" components that start and supervise everything.
5. Requirements are indistinct and inconstant (you don't know all use cases, constraints, teams, or deploy needs, and they change), so rely on cheap principles that leave options open.
6. Decouple horizontally by reason for change (SRP + Common Closure): UI, application-specific business rules (e.g., input validation), application-independent/domain rules (interest calculation, inventory counting), and database/query language/schema.
7. Decouple vertically by use case: add-order and delete-order change at different rates and for different reasons; keep their UI, rules and data access separate so new use cases don't disturb old ones.
8. Decoupling mode matters for operation: to run on separate servers, components must not rely on a shared address space; they must be services communicating over a network. Services are one option, not the goal.
9. Independent develop-ability: if layers and use cases are decoupled, any team organisation (feature, component, layer) works.
10. Independent deployability: well-done decoupling allows hot-swapping layers/use cases; a new use case could be new jars/services added without touching the rest.
11. Duplication: distinguish true duplication (every change must be made in all copies) from accidental duplication (look alike now, will diverge). Two use cases with similar screens, or a DB record whose shape matches a screen view, are probably accidental; do not unify them and do not pass DB records straight to the UI, make a separate view model. Resist "knee-jerk elimination of duplication."
12. Decoupling modes: source level (one address space, function calls, monolith), deployment level (separately deployable units like jars/DLLs/gems, possibly other processes), service level (only data structures over the network). Choose the cheapest mode that works and push decoupling to the point where a service *could* be formed, but keep components in one address space as long as possible. Start as a monolith, move toward independent units/services as needs grow, and be able to slide back down when needs shrink.

**3. Caveats.** Martin says achieving the balance is "pretty hard" and the mode change should not be assumed trivial ("not saying ... a trivial configuration option (though sometimes ... appropriate)"). He explicitly declines to say SOA or micro-services are the best or the future. He says default-to-services is expensive in development time and encourages coarse-grained decoupling, and that the preference for staying in one address space is his own ("My preference").

**4. Key terms.** Conway's law. Common Closure Principle (things that change together live together). Horizontal layers vs vertical use-case slices. Decoupling modes: source / deployment / service. True vs accidental (false) duplication. View model.

**5. Quotes.**
- "A good architecture makes the system easy to change, in all the ways that it must change, by leaving options open."
- "Resist the temptation to commit the sin of knee-jerk elimination of duplication."
- "A good architecture will allow a system to be born as a monolith, deployed in a single file, but then to grow into a set of independently deployable units ..."

**6. Applies to web SaaS?** Very much: a Node/Express monolith with internal module boundaries is exactly his recommended starting mode, and the accidental-duplication warning applies to near-identical list screens, API shapes and queries; the passing-DB-rows-to-UI warning is directly relevant to routes returning raw Postgres rows. The jar/DLL/hot-swap vocabulary is Java/.NET specific (npm packages or separate deploys are the analogue).

## Ch. 17 - Boundaries: Drawing Lines

**1. Core argument.** Architecture is the art of drawing boundaries that stop one side from knowing about the other. Early boundaries exist to defer premature decisions (frameworks, databases, web servers, DI) and keep them out of the business rules. Boundaries go where there is an axis of change, and every dependency arrow across a boundary points toward the core business rules, making the volatile parts plugins. Two cautionary tales (P, W) and one success (FitNesse) illustrate it.

**2. Rules.**
1. People-power is sapped by coupling, especially coupling to premature decisions, i.e. those unrelated to the use cases.
2. Story P: a desktop product moved to the web with a three-tier, three-copies-of-every-object, serialize-and-marshal-everything design built for a server farm that never existed; every real deployment was one server. A simple new field required changes in three tiers, four message protocols, eight handlers. Lesson: three-tier is a topology, not an architecture, and committing to it early multiplied effort for nothing.
3. Story W: a fleet-management firm's imposed enterprise SOA with a service per domain object; adding a contact to a sales record meant looking up a service, creating a contact with dozens of required fields filled with fake data, then updating the sale via another service; testing needed all services plus a bus and a BPEL server. Lesson: nothing wrong with services; the error was premature adoption and enforcement of a massive service suite.
4. Story FitNesse (success): "Download and Go" rule drove decisions; they wrote their own tiny web server (deferring any web framework), and put all data access behind a WikiPage interface. They stubbed it (Mock), then an in-memory hash table, then flat files, and never needed MySQL; a customer later wrote a MySQL implementation in a day. 18 months with no database meant no schema, query, connection or password issues, and fast tests.
5. Draw lines between things that matter and things that don't: GUI vs business rules, database vs GUI, database vs business rules. The database is a tool the rules use indirectly through an interface; the interface is *owned by* the business-rules component and implemented in the database component, so the arrow points from Database to BusinessRules (Figures 17.1-17.3 described: BusinessRules uses DatabaseInterface; DatabaseAccess implements it; boundary drawn across the inheritance relationship just below the interface).
6. IO is irrelevant to the rules: the game model runs without the screen. GUI depends on BusinessRules (Figure 17.4), so GUI can be swapped.
7. Plugin architecture (Figure 17.5): treat GUI and DB (and any optional/variable component) as plugins to the core; it makes replacement practical even if not trivial (a client/server UI after a web UI may still need rework of communications).
8. Plugin argument: ReSharper depends on Visual Studio, so the ReSharper team cannot break Visual Studio but Microsoft could disable ReSharper; this asymmetry is desired between business rules and GUI/DB. Boundaries are firewalls against change propagation.
9. Where to draw: at an axis of change; sides change at different rates and for different reasons. This is the SRP again.
10. Method: partition into core and plugins, then point all arrows toward the core (Dependency Inversion + Stable Abstractions).

**3. Caveats.** Replacing plugins "might not be trivial." He says P is a "superposition" of many places (i.e. a composite, not one company). He notes SOA itself is fine.

**4. Key terms.** Boundary; axis of change; plugin architecture; premature decision; "Download and Go"; stub/mock/in-memory implementation of a data interface; asymmetric dependency.

**5. Quotes.**
- "Software architecture is the art of drawing lines that I call boundaries."
- "Boundaries are drawn where there is an axis of change."
- "The IO is irrelevant."

**6. Applies to web SaaS?** Strongly: models/ access layer behind which Postgres sits, a provider-neutral layer for email/AI/contact-data vendors, and in-memory fakes for fast tests are all his FitNesse pattern; the premature-microservices warning is directly relevant for a free-tier deployment. Figures 17.1-17.6 are present only as captions in the text (images not extracted); reconstructed above from prose.

## Ch. 18 - Boundary Anatomy

**1. Core argument.** A boundary crossing is, at runtime, just a function calling a function across a line with some data; the architectural work is managing *source code dependencies*, because that is what propagates change (recompile/redeploy). Boundaries take physical forms of increasing strength: source-level (monolith), deployable components, threads (not a boundary), local processes, and services. Whatever the form, the dependency rule is the same: arrows point toward the higher-level component, and lower-level pieces are plugins.

**2. Rules.**
1. Monolith (source-level boundary): no physical representation, just disciplined segregation inside one executable/address space. It is still valuable (independent development, assembly). It depends on dynamic polymorphism (OO or equivalent) to point dependencies the right way; without it you fall to risky function pointers and abandon partitioning.
2. Calling "downhill to uphill" (low-level client calls high-level service) needs nothing special (Figure 18.1, data structure defined on the called side). When a high-level client must call a low-level service, use dynamic polymorphism so the runtime dependency opposes the compile-time one: client calls an interface it owns, the low-level implementation implements it; data structure defined on the calling (high-level) side (Figure 18.2). Static polymorphism (generics) helps less because it does not spare recompilation/redeployment.
3. Monolith communication is cheap, so boundaries can be chatty; components shipped as source.
4. Deployment components (DLL, jar, gem, shared library): the simplest physical boundary, delivered as binaries, deployment = gathering them (WAR, directory). Same address space, same cheap function-call chattiness; same dependency strategy.
5. Threads are not boundaries or deployment units, only ordering/scheduling; may live inside or span components.
6. Local processes: separate address spaces on the same machine, talking via sockets/OS queues. Higher-level process source must not contain the names, physical addresses or registry keys of lower-level processes; lower-level ones plug in. Communication is moderately expensive (OS calls, marshalling, context switches): limit chattiness.
7. Services: strongest boundary; location-independent, all communication over the network, tens of milliseconds to seconds, so avoid chattiness and handle latency. Higher-level services must not hold specifics (e.g. a URI) of lower-level ones.
8. Real systems mix strategies; a service is often a facade over local processes, each of which is a monolith or set of deployables. Mix of chatty-local and latency-aware boundaries.

**3. Caveats.** Only that chattiness limits differ by boundary type; no admissions of debate.

**4. Key terms.** Boundary crossing; source-level/deployment-level/process/service boundaries; dynamic vs static polymorphism; chattiness; latency; facade (service as).

**5. Quotes.**
- "The trick to creating an appropriate boundary crossing is to manage the source code dependencies."
- "The strongest boundary is a service."
- "The remote process ... Lower-level services should 'plug in' to higher-level services." (paraphrase-close; the book says lower-level services should "plug in" to higher-level services.)

**6. Applies to web SaaS?** Yes: a Node/Express app is a monolith whose internal module boundaries matter; calls to Postgres, mail APIs and AI vendors are service boundaries where latency, timeouts and not hard-wiring URLs/vendor names in high-level code apply. Polymorphism specifics (jars, DLLs, function pointers) are language-specific; in JS the equivalent is passing an adapter/function in rather than importing the concrete module.

## Ch. 19 - Policy and Level

**1. Core argument.** A program is a statement of policy; split it into smaller policies and regroup them by how and when they change. "Level" is strictly the distance from inputs and outputs: the farther a policy is from IO, the higher its level. Source dependencies must follow level (low depends on high), not data flow, so volatile, IO-near code becomes a plugin to stable, important code.

**2. Rules.**
1. Group policies that change for the same reasons at the same times into one component (same level); separate others. Arrange components as a directed acyclic graph with edges between different levels, edges being compile-time dependencies (imports/requires).
2. Low-level components depend on high-level ones, always.
3. Level = distance from inputs/outputs; IO-handling policies are lowest.
4. Source dependencies should be decoupled from data flow and coupled to level. Example: an encryption program reads chars, translates through a table, writes chars; data flows in -> translate -> out, but the Translate component (highest level, "Central Transform" per Page-Jones) must not depend on reader/writer. The naive version with encrypt() calling readChar/writeChar is wrong because the high-level function depends on low-level ones; the better version has Encrypt owning CharReader/CharWriter interfaces, with Console implementations outside the boundary (Figure 19.2); at component level IODevices depends on Encryption (Figure 19.3).
5. Higher-level policies change less often and for more important reasons; lower-level ones change often and urgently but for less important reasons (IO devices change more than an algorithm). Pointing dependencies at high-level policy means trivial-but-urgent changes at the bottom don't ripple upward.

**3. Caveats.** None; ends with an exercise asking the reader to spot SRP, OCP, CCP, DIP, SDP, SAP in the discussion.

**4. Key terms.** Policy; level; Central Transform; directed acyclic graph of components; plugin (lower-level as plugin to higher).

**5. Quotes.**
- "Software systems are statements of policy."
- "The farther a policy is from both the inputs and the outputs of the system, the higher its level."
- "We want source code dependencies to be decoupled from data flow and coupled to level."

**6. Applies to web SaaS?** Transfers well: a request handler that reads a request, applies rules and writes SQL should have the rules not import the HTTP or SQL layer; the "who sits closest to IO" test is a handy audit of where a rule really lives. ## Ch. 20 - Business Rules

**1. Core argument.** Before splitting an app into business rules and plugins, define business rules. There are two kinds: Critical Business Rules (would exist and make/save money even done by hand, e.g. a bank's loan interest percent) bound with Critical Business Data into *Entities*, and application-specific rules (which only make sense in an automated system) captured as *Use Cases*. Use cases orchestrate entities, know nothing of UI or storage, and talk through plain request and response data structures. Dependencies point from use cases to entities, never the other way.

**2. Rules.**
1. Entity = object (or module of data structures + functions) bundling a small set of critical rules with the critical data they act on; pure business, free of database, UI or framework concerns, reusable by any system. You do not need an OO language; just bind the data and rules in one separate module. Example: Loan with balance, interest rate, schedule and three rules (Figure 20.1).
2. Use case = description of how an automated system is used: input from the user, output returned, processing steps; contains application-specific rules, e.g. a bank requiring contact info gathered and credit score at least 500 before payment estimates (Figure 20.2 mentions the Customer entity). Use cases "control the dance of the Entities."
3. A use case does not describe the UI; you can't tell from it whether it is web, console or service. How data gets in and out is irrelevant to it.
4. A use case is an object with functions, input data, output data, and references to entities.
5. Entities know nothing about use cases (DIP): entities are high level because they are generalisations usable by many applications; use cases are closer to IO because specific to one application.
6. Use cases take simple request structures and return simple response structures, independent of anything (not derived from HttpRequest/HttpResponse); no HTML or SQL. If the models carry dependencies, the use cases inherit them.
7. Do not put Entity references in request/response models. They look alike but change for different reasons; coupling them violates CCP/SRP and produces tramp data and many conditionals.
8. Business rules should be the pristine, most independent, reusable code, with lesser concerns plugged into them.

**3. Caveats.** Defines "very strictly speaking" business rules; offers that a class is not required for an Entity. Credits Jacobson for the names.

**4. Key terms.** Critical Business Rule; Critical Business Data; Entity; Use Case (interactor); request model; response model; application-specific business rule; tramp data.

**5. Quotes.**
- "Use cases control the dance of the Entities."
- "Entities have no knowledge of the use cases that control them."
- "They are the family jewels."

**6. Applies to web SaaS?** Directly: Express route handlers should call use-case functions that take plain objects and return plain objects (not req/res or raw DB rows), with domain rules (what counts as a submission, plan limits) living in pure modules. The banking examples are illustrative; the entity vs application-specific split is the part that carries over.

## Ch. 21 - Screaming Architecture

**1. Core argument.** Looking at a building's plans tells you whether it is a house or a library; the top-level folders of an application should likewise announce its purpose (health care, inventory) rather than its framework (Rails, Spring). Architecture is for use cases; frameworks are tools to be kept at arm's length. The web is a delivery mechanism/IO device, a detail to defer. If done well, use cases are testable without web server, database or framework.

**2. Rules.**
1. Top-level directory structure and highest-level packages should show the system's use cases, not "Rails" or "Spring/Hibernate".
2. Per Jacobson (use-case driven approach), architecture supports use cases; it should not be supplied by a framework. If architecture is framework-based it cannot be use-case-based.
3. A good architecture lets you defer framework/database/web server choices and change your mind (like choosing house cladding after the plan satisfies use cases).
4. The web is not an architecture; treat it as an IO device. The system should be deliverable as console, web, thick client or web service without undue change.
5. Treat frameworks skeptically ("jaded eye"): authors/disciples assume the framework does everything; ask how to use it and how to protect yourself from it; have a strategy to stop it taking over.
6. Testability test: unit-test all use cases without web server or database; entities are plain objects; use cases coordinate them; all together testable in situ without frameworks.
7. A new programmer opening the repo should see the domain and learn the use cases without knowing the delivery; if asked "where are the views and controllers?" the answer is "details we'll decide later."

**3. Caveats.** None stated; tone is deliberately provocative.

**4. Key terms.** Screaming architecture; use-case-driven architecture; delivery mechanism; framework as tool, not way of life; testable architecture.

**5. Quotes.**
- "So what does the architecture of your application scream?"
- "Frameworks are tools to be used, not architectures to be conformed to."
- "The web is a delivery mechanism - an IO device - and your application architecture should treat it as such." (hyphens replace dashes)

**6. Applies to web SaaS?** Yes: a repo with routes/, models/, services/ grouped by technical role screams "Express"; grouping by domain (candidates, submissions, outreach) screams "recruiting." Note the tension: the book prefers use-case-first folders, but a convention-based layout may be pragmatic for small teams; he gives no middle ground.

## Ch. 22 - The Clean Architecture

**1. Core argument.** Hexagonal (Ports and Adapters), DCI, BCE and similar schemes all separate concerns into layers with business rules apart from interfaces; Martin merges them into one diagram of concentric circles governed by a single Dependency Rule: source code dependencies point only inward, toward higher-level policy. The result is a system independent of frameworks, UI, database and external agencies, and testable without any of them. Where control flow must go outward, dynamic polymorphism (Dependency Inversion) is used to invert the source dependency.

**FIGURE 22.1 (not present in extracted text; reconstructed from prose).** Four concentric circles, innermost to outermost: (1) **Entities** (enterprise-wide Critical Business Rules); (2) **Use Cases** (application-specific rules; interactors); (3) **Interface Adapters** (controllers, presenters, gateways; convert data between the inner format and the outer format); (4) **Frameworks & Drivers** (web, UI, database, devices, external interfaces; mostly glue code). Arrows (dependencies) all point inward. In the lower-right of the diagram a small inset shows crossing a boundary: Controller -> Use Case Input Port -> Use Case Interactor -> Use Case Output Port (interface, inner) <- implemented by Presenter (outer); flow of control goes controller, use case, presenter while all source dependencies point toward the use case.
**FIGURE 22.2 (also missing; reconstructed):** typical Java web scenario: Web server -> Controller -> InputBoundary (interface) -> UseCaseInteractor -> uses Entities and DataAccessInterface (implemented by DataAccess in front of Database) -> builds OutputData -> OutputBoundary (interface) <- implemented by Presenter -> ViewModel -> View.

**2. Rules.**
1. Five properties: independent of frameworks (use them as tools), testable without UI/DB/web server, independent of UI, independent of database, independent of any external agency.
2. The Dependency Rule: nothing in an inner circle may know anything about something in an outer circle, including names of functions, classes, variables. Data formats declared outside (especially framework-generated) must not be used inside.
3. Entities: enterprise-wide critical rules, usable by many applications; for a single app, they are the business objects. Least likely to change; unaffected by navigation, security, or any app's operations.
4. Use cases: application-specific rules, orchestrate flow of data to and from entities. Changes to operation of the app affect this layer; changes to DB/UI/frameworks should not, and it should not affect entities.
5. Interface adapters: convert between formats; contains all of MVC (presenters, views, controllers; models are plain data structures). All SQL lives here, in the database-facing part; nothing inward knows about the database. Also adapters for external services.
6. Frameworks and drivers: web, database; little code beyond glue. "The web is a detail. The database is a detail." Keep them outside where they do little harm.
7. Four circles are schematic; use more if needed. The Dependency Rule is invariant; going inward the abstraction and policy level rise.
8. To cross a boundary against the flow of control: the use case calls an interface (the output port) declared in the inner circle; the outer presenter implements it.
9. Data crossing boundaries: simple, isolated structures (structs, DTOs, function args, hashmaps). Do not pass Entity objects or database row structures inward; data is passed in the form most convenient for the inner circle.
10. Scenario (Figure 22.2): controller packs input into a plain object; interactor drives entities and uses a data-access interface; builds output data; presenter converts it to a ViewModel of strings and flags (dates and currency already formatted, button/menu names, grey-out flags); view merely copies it into HTML.

**3. Caveats.** Circles are schematic; "you may find you need more than four." No stated debate beyond that.

**4. Key terms.** Dependency Rule; Entities; Use Cases / Interactors; Interface Adapters; Frameworks and Drivers; Input/Output Boundary (ports); Controller; Presenter; ViewModel; DTO; Ports and Adapters / Hexagonal; DCI; BCE.

**5. Quotes.**
- "Source code dependencies must point only inward, toward higher-level policies."
- "The web is a detail. The database is a detail."
- "We don't want to cheat and pass Entity objects or database rows."

**6. Applies to web SaaS?** The most directly transferable chapter: Express route = controller, a service/use-case function takes plain input and returns plain output, a data-access module hides SQL, and SQL/ORM row shapes should not leak into rule code. The Java interface/inheritance mechanics map in Node to passing an adapter object or function in (duck typing) rather than declared interfaces; the ceremony level is his, and chapter 25 admits it is often too much.

## Ch. 23 - Presenters and Humble Objects

**1. Core argument.** The Humble Object pattern splits behaviour into a tiny, hard-to-test part (the humble object) and a fully testable part holding the real logic. Presenter/View is the canonical example, but the same split recurs at every boundary (gateways, ORMs, service listeners), and the seam often marks an architectural boundary. Testability is an attribute of good architecture.

**2. Rules.**
1. Humble Object (originally from xUnit Patterns): put the hard-to-test behaviour (GUI drawing, SQL execution, network I/O) in a humble module stripped to the essentials; put everything testable elsewhere.
2. Presenter vs View: View only moves data to the screen, no processing. The Presenter takes application data and formats it into a View Model of strings, booleans and enums (formatted dates, currency with markers, negative-red flag, button names and disabled flags, menu text, table cells as formatted strings). Everything on screen the app controls is in the View Model.
3. Database gateways: between interactors and the database sit polymorphic gateway interfaces with a method per needed CRUD operation, named for the application's need (e.g. a method returning last names of users who logged in after a date). No SQL in the use case layer; the gateway implementation is the humble object holding SQL; interactors are not humble but are testable using stubs/test doubles for gateways.
4. Data mappers: "ORM" is a misnomer because objects are not data structures (their users see operations, not data); these tools are data mappers loading data into data structures. They live in the database layer and are another humble boundary between gateways and the database.
5. Service listeners: for external services, load simple data structures and pass them across; outbound modules format and send; inbound listeners parse into simple structures. Same humble pattern.

**3. Caveats.** None; the point about ORMs is his argument about naming, offered flatly.

**4. Key terms.** Humble Object; Presenter; View; View Model; Database Gateway; Data Mapper (his preferred name for ORM); Service Listener.

**5. Quotes.**
- "The View is the humble object that is hard to test."
- "Between the use case interactors and the database are the database gateways."
- "At each architectural boundary, we are likely to find the Humble Object pattern lurking somewhere nearby."

**6. Applies to web SaaS?** Yes: format dates/currency/labels on the server in a presenter so the front end only renders (valuable for plain-script frontends too), keep SQL inside named data-access functions (e.g. "list leads for owner") with in-memory fakes for tests. The Java class machinery is his; the ideas of view-model and gateway carry over unchanged.

## Ch. 24 - Partial Boundaries

**1. Core argument.** Full boundaries (reciprocal interfaces, input/output structures, separately compilable/deployable components) are expensive to build and maintain. When an architect suspects a boundary may be needed ("I might need it") but cannot justify the full cost, they can implement a partial boundary as a placeholder, accepting that it can degrade.

**2. Rules.**
1. Anticipatory design is frowned on by YAGNI advocates; architects sometimes do it anyway.
2. Skip the last step: do all the design and interface work for independent components, but compile and deploy them together as one. Cost = same code and design as a full boundary, minus version numbers and release management. FitNesse did this with its web server component (separable from the wiki) to keep "download and go"; over time, when it was clear a separate web component would never be needed, dependencies began to cross the line the wrong way and re-separating is now a chore.
3. One-dimensional boundary: a Strategy pattern (Figure 24.1): clients use a ServiceBoundary interface implemented by ServiceImpl; dependency inversion is in place but nothing stops a backchannel (the client bypassing the interface) except developer discipline, because there is no reciprocal interface.
4. Facade (Figure 24.2): even the dependency inversion is dropped; a Facade class lists services as methods and delegates to classes clients should not touch. Clients have a transitive dependency on all service classes (in static languages a change forces recompilation) and backchannels are easy.
5. These three are examples; architect decides where a boundary may one day exist and whether to implement it fully or partially.

**3. Caveats.** Each approach "can also be degraded if that boundary never materializes." Admits the FitNesse split eroded.

**4. Key terms.** Partial boundary; YAGNI; reciprocal boundary interfaces; one-dimensional boundary (Strategy); Facade; backchannel.

**5. Quotes.**
- "Full-fledged architectural boundaries are expensive."
- "Architects, however, sometimes look at the problem and think, 'Yeah, but I might.'"
- "Without reciprocal interfaces, nothing prevents this kind of backchannel other than the diligence and discipline of the developers and architects."

**6. Applies to web SaaS?** Useful for a solo or small team: a facade module in front of a vendor (email, AI, contact data) is a cheap one-sided boundary, but without a test or lint rule forbidding direct imports it will erode as he predicts. ## Ch. 25 - Layers and Boundaries

**1. Core argument.** The common three-component picture (UI, rules, database) is too coarse: using the Hunt the Wumpus text game as a deliberately trivial proxy, Martin shows that every axis of change (language, text delivery mechanism, persistence, networking, even separate levels of game policy) is a potential boundary, and that fully implementing all of them is expensive while retrofitting a missed one is also expensive. The architect must guess intelligently, watch for friction, and add boundaries at the inflection point where the cost of adding drops below the cost of ignoring.

**2. Rules.**
1. Axes of change define potential boundaries. In Wumpus: GameRules vs Language (English, Spanish) vs TextDelivery (shell, SMS, chat) vs DataStorage (flash, cloud, RAM). Figures 25.1-25.5 (missing; reconstructed): GameRules sits at the top; Language API and Persistence API are abstract components; Language, TextDelivery, DataStorage implementations depend on them; arrows follow source dependencies and point up.
2. The API at each boundary is defined and owned by the user (upstream/higher-level) component, not the implementer.
3. Dashed outlines = abstract API components. Inside each component are polymorphic Boundary interfaces used by one side and implemented by the other.
4. Data splits into streams that meet at the highest-level component (the "Central Transform"): a user-communication stream and a persistence stream; adding multiplayer adds a third (network) stream. Arrows show dependency direction, not data flow.
5. Within one component there may be further levels: GameRules splits into MoveManagement (map mechanics, declaring events like FoundFood, FellInPit) and a higher-level PlayerManagement (health, win/lose). Whether this is a boundary depends on context; in a massively multiplayer version with local move management and a server-hosted PlayerManagement exposed as a micro-service API, it becomes a full boundary (Figure 25.7).
6. Boundaries are everywhere; recognise them, know that full ones are costly and that ignored ones are very expensive to add later even with tests and refactoring discipline.
7. Do not decide once. Watch as the system evolves, note where boundaries may be needed, look for the first sign of friction from their absence, weigh cost, and revisit often. Implement at the inflection point.

**3. Caveats.** Footnote: he would not apply clean architecture to the trivial game (about 200 lines); it is a stand-in for a larger system. He admits the answer on YAGNI vs foresight is "dissatisfying": over-engineering is often worse than under-engineering, yet missing boundaries are costly. "You must guess - intelligently."

**4. Key terms.** Axis of change; abstract component (API); streams of data flow; Central Transform; MoveManagement/PlayerManagement (levels within the rules).

**5. Quotes.**
- "Architectural boundaries exist everywhere." (book wording: "architectural boundaries exist everywhere")
- "Your goal is to implement the boundaries right at the inflection point where the cost of implementing becomes less than the cost of ignoring."
- "It takes a watchful eye."

**6. Applies to web SaaS?** Strongly: it is a decision method rather than a recipe, matching a deferred, friction-driven approach to when to introduce per-tenant config, provider-neutral layers, or service splits. The game itself is a toy; his advice to revisit boundary decisions as friction appears is the transferable part.

## Ch. 26 - The Main Component

**1. Core argument.** Every system has a Main component that creates and wires everything and then hands control to the high-level abstract policy. It is the ultimate detail: the lowest-level, dirtiest component in the outermost circle; nothing but the OS depends on it. Treat it as a plugin, so you can have many (per environment, country, customer).

**2. Rules.**
1. Main creates factories, strategies and global facilities, then transfers control to high-level code.
2. Dependency injection frameworks, if used, belong here only; once injected into Main, distribute dependencies normally without the framework.
3. Main is dirty on purpose: in the Wumpus example it loads all the strings and tables (cavern names, adjectives), reads input, owns the loop, builds the map, creates the game via a factory given only a class *name* as a string (so the even-dirtier game facade class changing does not force Main to recompile), then defers all processing to higher-level components. (Code listing summarised, not reproduced.)
4. Because it is a plugin behind an architectural boundary, create multiple Mains: Dev, Test, Production, one per country/jurisdiction/customer. Configuration becomes a simple problem.

**3. Caveats.** None. (Main is just where the mess is allowed to live.)

**4. Key terms.** Main component; composition root (modern name, not his term); factory; dependency injection; ultimate detail.

**5. Quotes.**
- "The Main component is the ultimate detail - the lowest-level policy."
- "Think of Main as the dirtiest of all the dirty components."
- "Think of Main as a plugin to the application."

**6. Applies to web SaaS?** Yes: the process entry file (server start, env vars, selecting concrete adapters, per-environment or per-customer config) is Main; keep it thin and keep wiring there rather than in rule code. Per-customer Mains is an idea relevant to multi-tenant configuration, though in SaaS per-tenant data config is usually preferred over per-tenant builds.

## Cross-chapter synthesis (for the reader)
- One idea repeated: separate policy from detail; point every source dependency toward policy; let details be plugins decided late.
- Boundaries range from free (folders in a monolith) to costly (services); start cheap, add cost only at the point of friction (Ch. 16, 24, 25).
- Beware reflexive deduplication and passing storage shapes to the UI (Ch. 16, 22).
- Architecture should show the domain, not the framework (Ch. 21); keep tests free of the web and DB (Ch. 21, 22, 23).
