## Appendix A: Architecture Archaeology (1970 to early 1990s, autobiographical)

**1. Union Accounting System (1968-71, GE Datanet 30, then Varian 620/f).** A CRUD system for Agents, Employers and Members, plus dues posting and ledger changes, for a Teamsters local. It ran with no OS and no file system, so the team wrote their own disk drivers, supervisor and overlay swapper. The author, aged 18, rebuilt it on a cheaper minicomputer. Two boundaries emerged. Applications handed strings to the supervisor and never knew the output device (a "dependency normal" boundary). The supervisor started applications by jumping to one fixed address in the overlay area, so it had no compile-time dependency on them (a "dependency inverted" boundary, polymorphism by a single entry point). Lesson: device independence and a single start interface are the seeds of the Dependency Rule. [T] Keep business code ignorant of I/O devices, and let the framework call plugins through one stable interface.

**2. Laser Trim (Teradyne Applied Systems, 1973).** A system that measured resistors on ceramic substrates and trimmed them with a laser. It ran on an in-house M365 minicomputer, with tape-loop storage and a 30-minute, tape-error-prone assembly of about 20,000 lines. Its layers were an operating program (the "MOP"), a utility layer for hardware, an isolation layer, and a customer-programmable DSL. The boundaries were "soft at best", and the MOP was forked per division and merged by hand from marked-up listings. Lesson: typical early-1970s coupling. Even a layer meant to isolate was entangled with the layers below it, and forked shared code is painful. [T] Forks of shared code and "layers" that call back into each other are not boundaries.

**3. Aluminum Die-Cast Monitoring (Outboard Marine, mid-1970s).** An IBM System/7 counted and timed die-cast machine cycles in raw interrupt-driven assembler and fed a CICS-COBOL mainframe display. The author was fired from this job and says the culture was the cause. The only architectural point is the SPI instruction, which lets lower-priority interrupts run (analogous to `Thread.yield()`). [H]

**4. 4-TEL (Teradyne, 1976-88).** A system that tested every phone line in a service area nightly and reported lines needing repair. Originally monolithic, with each central-office tester (COLT) doing everything over slow 300-baud links. The team split it, so dialing and measuring stayed in the COLT while analysis and reports moved to the service-area computer (SAC). The boundary was clean, and the two sides exchanged tiny DSL-like packets ("DIAL xxxx", "MEASURE"). Result: fast screens and smaller COLTs. Lesson: a boundary driven by a real constraint (bandwidth and memory) paid off at once. [T] A thin command protocol between a front tier and a worker is a sound split.

**4a. The "Vectorization" project (4-TEL firmware).** The 30K program was burned onto 30 EPROM chips. Any change shifted every address, so field engineers had to swap and carry all 30 chips. The fix, which took three months, was 32 independently compilable files, each with a fixed 40-byte table of its routine addresses. At boot the tables were loaded into RAM "vectors", and every call went indirectly through them. Only changed chips needed shipping. The author says "We had invented polymorphic dispatch. We had invented objects." The same mechanism gave literal plugins (a feature chip in an open socket added its own menu) and allowed live patching over a dial-up modem by repointing a RAM vector. Lesson: independent deployability comes from indirection through a stable table, which is also the root of plugin architecture. [T] Feature flags, versioned interfaces and independently deployable modules all rely on the same indirection.

**5. Service Area Computer (SAC, 1976 on).** A 60,000-line, single-program M365 assembler system with a home-grown polling task switcher (MPS), constant race conditions, and modem and terminal logic smeared through the business rules. Two stories drive the lessons.
- *The dispatch-determination code:* this was the economic core of the product (deciding which craft to dispatch). It was written by a brilliant person who communicated badly and then quit, and nobody could change it without breaking it. Management finally ordered it locked down, so it became "officially rigid". Lesson: the value of clean, understandable code.
- *The modem hack:* the hardware engineer ignored the plea to make the new modem look like the old one, and the new modem's control bits were completely different. Rewriting hundreds of call sites was judged infeasible, so the team patched one low-level bus-write routine to translate old-modem bit patterns into new-modem ones. It worked, and it was a "worst hack imaginable". Lesson: isolate hardware from business rules and abstract interfaces. [T] The same applies to payment, email and AI vendors.

**6. The Grand Redesign in the Sky (SAC rewrite in C/UNIX, about 1982 to 1988).** The first "Tiger Team" burned two or three man-years and delivered nothing. A second attempt ("Deep Thought", 80286) took years and may never have shipped. Reason: a redesign team cannot catch up with a large staff still maintaining the old system.

**6a. Europe fork.** Sales to Europe could not wait, so a UK team forked the US M365 code. Bugs found on one side could not be mapped to the other, and three attempts to merge the forks back into configuration all failed. The rewrite team also had to handle the US/Europe split. Lesson: forking for a market makes the differences expensive for good, and the target of a rewrite keeps moving. [T] Per-tenant or per-region forks of code are costly. Use configuration instead (this matches PACE's per-org config rule).

**7. C language and the PDP-11/60 (about 1980).** The author pushed for a real development computer (PDP-11/60, two 25 MB disks) and built cross-compilation to the 8085. He then found C via Kernighan and Ritchie and bought the Whitesmiths compiler, which could emit assembly for the 8085 target. The hard part was convincing assembly programmers to adopt it. Lesson: tooling and language choice change productivity, and adoption is a people problem. [H, mild T]

**8. BOSS (Basic Operating System and Scheduler).** A small non-preemptive task switcher in C for the 8085. It was cooperative: `block(eventCheckFunction)` suspended the task and put a polling function in a list. It became the base for many later projects. Lesson: a small reusable core, built after seeing the pain of MPS and the System/7. [T, loosely] It is a cooperative scheduler, an ancestor of the Node event loop (blocking the loop is the cardinal sin).

**9. pCCU.** Digital switches meant dialing (at the central office) and measuring (out at distribution points) had to be separated. The author notes the boundary was obvious and a few years earlier would have "saved a fortune". The team kept postponing the CCU/CMU architecture, because customers' schedules kept slipping. Then one customer announced deployment in a month. His boss saw that this tiny customer needed only a small relay computer that decoded the phone number and forwarded commands to two standard COLTs, which the author built in about a week in C on BOSS. Lessons: **the schedule trap** (delay because deadlines seem far off, then face a crisis), and a minimal solution can satisfy the real requirement. [T] Do not defer a needed boundary, and look for the narrowest design that fits the one customer in front of you.

**10. DLU/DRU (Display Local/Remote Unit, early 1980s Texas customer).** A board that multiplexed terminal traffic over one 9600 bps conditioned modem link to a remote demultiplexer box. The author built the DLU as a dataflow or pipes-and-filters design (small tasks joined by queues, like an assembly line). Mike Carew built the DRU as one big task per terminal (many expert builders, each making a whole product, no queues). Both worked well. Lesson: very different architectures can be equally effective, and debates over "superior" ones are often tribal. [T] Queue-based pipelines versus per-request handlers is a real choice, and both are fine.

**11. VRS (Voice Response System; second-hand account).** Craftsmen controlled fault location by phone with touch tones and heard results spoken back. The team chose the UNIFY database and spread embedded SQL and vendor API calls everywhere in the C code. When UNIFY was cancelled, three months of trying to switch to another vendor failed, so they paid UNIFY's third-party maintainer, with rates rising yearly. Lesson: **the database is a detail**, to be isolated from the business purpose, and avoid strong coupling to third-party software. [T] Strong fit (data-access layer, vendor-neutral providers).

**12. The Electronic Receptionist (ER, 1983).** Callers spelled a name on touch tones. The system connected them, followed a list of alternate numbers, and took messages, in effect the first voice mail system. The three-person team built all the hardware and software. One listener process per phone line started handler processes for each call state, and processes passed state through disk files and exited. The author calls it service-oriented, with signs of true boundaries and independently deployable services, though not a plugin architecture. Failure: the company, a test-equipment seller, could not market it, and the CEO dropped the patent application, which a competitor filed three months later and won. Lesson: good architecture does not rescue a product with no market path. The author notes he can't be blamed for today's voice-mail systems.

**13. Craft Dispatch System (CDS, mid-1980s).** ER's technology retargeted to read trouble tickets to field repairmen. The author pushed the service idea further, in what he calls a micro-service architecture. Every state transition started a new service, and the state machine was externalized in a text file. Behaviour could be changed without changing code (Open-Closed Principle) and while the system ran ("hot-swapping", a BPEL analogue). Disk files were too slow, so they built a named shared-memory store (the "3DBB", Three-Dimensional Black Board), which held only strings because MP/M processes had separate address spaces. To cope with messy hand-typed ticket text (`/pno 8475551212 /noise ...`), the author invented FLD (Field Labeled Data), a recursive named-data format with a string form, a precursor of XML and JSON. Lesson: "There is nothing new under the Sun." An externalized state machine, services and a serialization format are old ideas. [T] Workflow state machines as data, and parsing messy human input at the edge into a clean structure.

**14. Clear Communications (startup, 1988 on).** The goal was monitoring T1 line quality on a US map. The team worked 70 to 80 hours a week, wrote a full seven-layer ISO communications stack and a 3000-line C function `gi()` ("Graphic Interpreter", pure "goo"), and had no time for architecture ("Just code, dammit!"). After three years they had failed to sell. Lesson: building grand structures without selling or validating the market is a trap, and no architecture at all was no better. Positive thread: during the same two years the author got on Usenet and email, switched to C++ when Sun shipped a compiler, and read widely (Stroustrup, Wirfs-Brock, Coad, Goldberg, Coplien, Booch). Debates on Netnews laid the foundations of the SOLID principles, and this got him noticed. A coworker's nickname "Uncle Bob" was later adopted on purpose as a brand. [T] Public debate and reading as a way to refine design principles.

**15. ROSE (Rational, 1990).** A C++ tool for drawing Booch diagrams. It had a real layered architecture (GUI → representation → manipulation rules → database), with strictly controlled dependencies that pointed along the flow of control and not toward high-level policy. The author says this contributed to its demise. Two big mistakes: an object-oriented database (a "big, slow, intrusive, expensive third-party framework") and over-architecture (too many layers, each with communication overhead). After many man-years and two tepid releases it was scrapped and replaced by a small team's simple app. Lesson: **architecture must be sized to the problem**. Enterprise-grade layering for a desktop tool is a recipe for failure. [T] Do not adopt fashionable infrastructure (the OO database of the day) or extra layers beyond what the problem needs, and again treat the database as a detail.

**16. Architects Registry Exam (ETS/NCARB, early 1990s).** Software to give architect candidates CAD-like exam problems (18 vignettes) and score them automatically (18 scoring apps, 36 applications in all). The author and Jim Newkirk promised a reusable framework so later apps would "pop out every few weeks". After a year, the first app (Vignette Grande) came with 45,000 lines of framework and 6,000 of application code, and the framework did not fit the next vignettes. They rewrote it by building four vignettes at once (another year, another 45,000-line framework, vignettes of 3,000 to 6,000 lines). The vignettes became plugins to the framework, in line with the Dependency Rule even though they were statically linked. The next four apps then came out every few weeks. Lesson: "You can't make a reusable framework until you first make a usable framework." Reusable frameworks must be built in concert with several reusing applications. [T] Extract shared modules from at least two or three real users, not from guesses (strong fit for a multi-tenant product).

**Conclusion of the appendix.** A partial history that stops in the early 1990s, with the late-1990s events saved for another book.

## Lessons stated in the appendix, consolidated

1. Isolate I/O devices and hardware from business rules, and abstract the interface, because hardware will change underneath you (SAC modems). [T]
2. Treat the database as a detail, and do not smear vendor SQL or API calls through the code or couple strongly to third-party software (VRS/UNIFY, ROSE). [T]
3. Do not adopt a fashionable framework or data technology just because it is exciting (the object-oriented database in ROSE). [T]
4. Size the architecture to the problem. Over-architecture (too many layers, each with overhead) can kill a product (ROSE). [T]
5. A reusable framework must be built from several real users, so build a usable one first (ETS vignettes). [T]
6. Indirection through a stable table or interface gives independent deployability, plugins and live patching (4-TEL vectorization). [T]
7. Point dependencies at high-level policy, not along the flow of control. ROSE's flow-based layering aided its demise. [T]
8. Clean, understandable code is itself economic value. Unreadable core logic ("officially rigid" dispatch code) becomes a business liability. [T]
9. A redesign or rewrite team can rarely catch up with a large team still maintaining the live system (SAC "Deep Thought"). [T]
10. Forking code for a new market makes later reintegration extremely hard. Prefer configuration (SAC Europe). [T]
11. Do not defer an obvious architectural boundary (dial versus measure in 4-TEL/pCCU), and watch for the schedule trap. [T]
12. Sometimes the narrowest solution that meets the real customer's need (pCCU) beats the grand design. [T]
13. Very different architectures (dataflow versus task-per-terminal) can both work well, so avoid dogmatism (DLU/DRU). [T]
14. Externalizing a state machine and splitting work into services supports change without recoding (CDS). Everything "new" (microservices, JSON/XML) has precedents. [T]
15. Splitting a system along a real constraint (bandwidth, memory) gave large gains with a very thin command protocol (4-TEL SAC/COLT). [T]
16. Great technology does not guarantee a product. Marketing and market fit matter (ER lost the voice-mail market, Clear never sold). [T, business]
17. Speed-of-coding without any architecture (Clear's "just code") also fails, with no sales to carry it. [T]
18. Soft boundaries and coupled layers (Laser Trim, MOP) were typical of the early era and cost later (forked shared code merged by hand). [T]
