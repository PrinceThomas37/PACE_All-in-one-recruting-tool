## Ch. 27 Services: Great and Small

**1. Core argument.** Service/micro-service designs are popular because services seem strongly decoupled and independently developable and deployable. Martin says both beliefs are only partly true. A service is just a function call across a process or platform boundary, so being a service does not make something architecturally significant. The "kitty problem" shows a cross-cutting feature touching every service in a functional decomposition. The fix is the same as in a monolith: give each service an internal component design that follows the Dependency Rule, so the architectural boundaries run through services.

**2. Rules / recommendations.**
1. Services are not architecture. Architecture is boundaries that separate high-level policy from low-level detail along the Dependency Rule. Services that only split up behaviours are "expensive function calls". Analogy: most functions in a monolith are not architecturally significant either.
2. Do not assume services are decoupled. They still share processor and network resources and, above all, share data. Adding a field to a shared record forces every service that uses it to change and to agree on its meaning. Service interfaces are no more formal than function interfaces.
3. Do not assume services can be developed, deployed and operated independently. To the extent they are coupled by data or behaviour, they must be coordinated. Large systems have also been built successfully from monoliths and component-based systems.
4. Beware cross-cutting concerns (kitty problem). A taxi aggregator split into TaxiUI, TaxiFinder, TaxiSelector and TaxiDispatcher services needs all of them changed to add kitten delivery (driver and customer allergies, 3-day vehicle history). Functional decompositions are vulnerable to features that cut across all the functions.
5. Handle cross-cutting features with SOLID and polymorphism. Extract the ride-specific logic into a Rides component and put kittens into a Kittens component. Both extend abstract base classes (Template Method or Strategy), objects are created by factories under UI control, and only the UI changes. The new feature ships as a new jar/gem/DLL loaded at runtime.
6. Apply the same to services: each service is a set of abstract classes plus extension components. A new feature is added as a new component, which follows the Open-Closed Principle.
7. Conclusion: a service may be one component, several components separated by architectural boundaries, or (rarely, "we hope", Martin says experience suggests otherwise) so coupled to clients that it has no architectural significance.

**3. Caveats.** Martin does not say services are bad. He says they are useful for scalability and developability, and "substantial benefits" exist in separating functionality across processes and platforms, whether or not they obey the Dependency Rule. He only denies that they define the architecture.

**4. Key terms.** Decoupling fallacy: the belief that process isolation means real decoupling. Kitty problem: a cross-cutting feature that forces change in every service. Cross-cutting concern: a requirement that spans several functional modules. Architecturally significant: crosses a boundary following the Dependency Rule.

**5. Quotes.**
- "Services that simply separate application behaviors are little more than expensive function calls, and are not necessarily architecturally significant."
- "architectural boundaries do not fall between services. Rather, those boundaries run through the services, dividing them into components."
- "Services are, after all, just function calls across process and/or platform boundaries."

**6. PACE applicability.** Strongly transfers: the lesson that a deployment unit is not the architecture applies to a Node/Express monolith, and the cross-cutting-feature test (how many modules change?) is language-neutral. In Node, "extension components" are modules or plugins behind an interface. The jar/gem/DLL loading is Java-specific.

## Ch. 28 The Test Boundary

**1. Core argument.** Tests are part of the system and an architectural component, the outermost circle. They depend inward on the code, nothing depends on them, and they are independently deployable. Because they are isolated, developers wrongly treat them as outside the design, and tests not designed into the system become fragile and make the system rigid. The remedy is a dedicated testing API that decouples the structure of the tests from the structure of the application.

**2. Rules.**
1. All tests are architecturally the same: unit, TDD, BDD, Cucumber, FitNesse and so on. They follow the Dependency Rule, are concrete and detailed, and depend inward.
2. Design for testability. Treat tests as a real component. The first rule of design is not to depend on volatile things, and the GUI is volatile, so do not test business rules through the GUI.
3. Fragile Tests Problem: strongly coupled tests break in the hundreds or thousands when a common component changes. Example: GUI tests that log in and navigate to reach a rule break on any login or navigation change. Fragile tests also make the system rigid, because developers resist changes that break 1000 tests (marketing's "simple" navigation change).
4. Create a Testing API. It is a superset of the interactors and interface adapters the UI uses. It has "superpowers": bypass security, skip expensive resources such as databases, and force the system into testable states.
5. Avoid structural coupling, where there is one test class per production class and one test method per production method. The testing API hides the application's structure so production code and tests can be refactored independently. Tests tend to become more concrete over time while production code becomes more abstract, so strong coupling blocks both.
6. Security: the superpowers are dangerous in production. If that is a concern, keep the testing API and its dangerous parts in a separate, independently deployable component.

**3. Caveats.** He explicitly declines to enter the debate over test categories. The security caveat is the only stated limit.

**4. Key terms.** Fragile Tests Problem. Structural coupling (tests mirror production class and method structure). Testing API (a test-only interface with elevated powers).

**5. Quotes.**
- "Tests that are not well integrated into the design of the system tend to be fragile, and they make the system rigid and difficult to change."
- "The purpose of the testing API is to decouple the tests from the application."
- "Such tests often wind up on the maintenance room floor—discarded because they are too difficult to maintain."

**6. PACE applicability.** Transfers directly: do not drive business rules through the browser, and expose a service-level seam that tests call. The caveat for the "superpowers" API is that it must not ship enabled in production, and any test-only back door (auth bypass, state forcing) needs deliberate gating or separation. Examples are Java-flavoured, but the idea is language-neutral.

## Ch. 29 Clean Embedded Architecture (James Grenning)

**1. Core argument.** Software does not wear out, but firmware and hardware become obsolete. Code becomes "firmware" (hard to change as hardware evolves) not because of where it is stored but because of what it depends on. Embedded developers (and non-embedded ones who bury SQL or platform APIs everywhere) too often only pass the "App-titude test" (it works) and so write firmware rather than software. A clean embedded architecture separates software from firmware and hardware through abstraction layers (HAL, PAL, OSAL) so that the code is testable off the target and has a long life.

**2. Rules.**
1. "Software" vs "firmware": firmware is defined by dependency on hardware and difficulty of change, not by ROM. Write less firmware and more software. Examples: a TDM/VOIP phone product where the old code was the spec because business logic was tangled with TDM, and a message dispatcher in the same file as UART code.
2. Do not stop at "make it work". Follow Beck's order: make it work, make it right, then make it fast. Brooks: plan to throw one away. The App-titude test is merely getting an app to work. Example: one file mixing domain logic, hardware setup, button handling, A/D reads, flash storage and a misnamed function, with no way to test off-target.
3. Avoid the target-hardware bottleneck, where code can be tested only on the target. Hardware is developed in parallel and has its own defects.
4. Layer: hardware, firmware, software. Software and firmware intermingling is an anti-pattern, with risky changes and full manual regression.
5. Firm up the software/firmware line with a hardware abstraction layer (HAL). Its API is shaped by the software's needs (name/value pairs, not byte arrays to flash) and does not reveal hardware details. The example raises the level from `Led_TurnOn(5)` to `Indicate_LowBattery()`. Layers contain layers (a fractal pattern). The HAL is the seam for off-target testing.
6. The processor is a detail. Vendor header files and C extensions (register-like variables, non-standard binary literals) make code no longer portable C. Confine them to a few firmware files. Use the standard `stdint.h` types, and write your own `stdint.h` that wraps the vendor types for target builds. Anything that touches device registers becomes firmware, so isolate it behind a processor abstraction layer (PAL).
7. The OS is a detail. Insulate software from an RTOS or embedded Linux/Windows with an operating system abstraction layer (OSAL), to survive supplier changes and capability changes. The OSAL isolates duplication, encourages a common concurrency structure (message passing) and gives test points.
8. Program to interfaces and substitutability. Use header files as interface definitions and put only declarations, constants and struct names needed by the interface in them, with implementation details out. Expect implementation details to change.
9. DRY the conditional compilation. Thousands of `#ifdef BOARD_V2` occurrences violate DRY. Hide the hardware type under the HAL and bind via linker or runtime binding.

**3. Caveats.** Embedded is special (memory, real-time, no hardware yet), but "not so special" that the principles do not apply. He does not claim all firmware can be processor independent. He grants that vendors may be helpful and not cynical.

**4. Key terms.** Firmware (code defined by hardware dependency). App-titude test (it merely works). Target-hardware bottleneck. HAL, PAL, OSAL (abstraction layers for hardware, processor, OS). Seam (substitution point for testing).

**5. Quotes.**
- "Although software does not wear out, it can be destroyed from within by unmanaged dependencies on firmware and hardware."
- "Firmware does not mean code lives in ROM."
- "You non-embedded developers essentially write firmware whenever you bury SQL in your code or when you spread platform dependencies throughout your code."

**6. PACE applicability.** The principle transfers: a thin domain-shaped wrapper over each platform, vendor or SDK (email providers, Supabase, AI vendors) with the API tailored to the app's needs, plus use of standard types and one place that knows vendor specifics. The C, ISR, RTOS and `#ifdef` details are specific to embedded. The "SQL in your code is firmware" remark is directly relevant to Postgres.

## Ch. 30 The Database Is a Detail

**1. Core argument.** The data model is architecturally significant, but the database (the software that moves data to and from disk) is a low-level mechanism, like a doorknob to a house. Relational databases are excellent technology, but still technology. The business rules should not know about tables and rows. Databases are prevalent because disks are slow, and the data is reorganised in RAM into lists, trees and so on anyway. Performance is real but is a low-level concern that can be encapsulated.

**2. Rules.**
1. Distinguish the data model (significant) from the database (a detail).
2. Restrict knowledge of the tabular structure to the lowest-level utility functions in the outer circles. Do not pass database rows or tables as objects through the system (data access frameworks encourage it). This is an architectural error that couples use cases, business rules and sometimes the UI to the relational structure.
3. Reasoning: databases exist because of slow rotating disks (indexes, caches, query optimisation), splitting into file systems (document based) and RDBMSs (content based). With RAM storage you would use native data structures, and you already do that after loading the data, so the on-disk form is not an architectural concern.
4. Performance can be encapsulated in low-level data access mechanisms.
5. Anecdote: in the late 1980s his T1-line network-management startup used random-access files with trees and linked lists. He fought marketing and a hardware engineer who wanted an RDBMS. Customers expected one, as a check-box item created by vendor marketing, so he was wrong commercially though right technically. He should have bolted an RDBMS on the side behind a narrow, safe data channel and kept the files in the core. (He quit and became a consultant.)

**3. Caveats.** He admits these are "fighting words" and that he lost the real-world argument, because customer expectation is a real (if irrational) requirement. He also dismisses "enterprise" and SOA as marketing.

**4. Key terms.** Data model (structure of the data in the application). Database (a utility giving access to data). RDBMS vs file system (content-based vs document-based stores).

**5. Quotes.**
- "The data is significant. The database is a detail."
- "Allowing this is an architectural error."
- "the database is a non-entity—it is a detail that does not rise to the level of an architectural element."

**6. PACE applicability.** The principle (business rules call a data-access layer that returns domain objects, not raw rows) transfers to Node/Postgres. Caveats: his disk-vs-RAM argument is dated, and with a SaaS built on Postgres/RLS the database also carries tenancy, security and transactions, so treating it as fully swappable is a trade-off rather than free. The anecdote's lesson (customers may demand a specific technology as a product requirement) is relevant to a product sold to others.

## Ch. 31 The Web Is a Detail

**1. Core argument.** The web is one swing of an industry pendulum between centralising and distributing computing power (mainframes, terminals, client-server, web, Ajax, Node). Architects should look at the long term and keep these short-term oscillations away from business rules. The GUI is a detail, the web is a GUI, so the web is a detail: an I/O device. Use cases can be modelled as input data, processing and output data, which makes the business logic device independent even if the UI/application "dance" is device specific.

**2. Rules.**
1. Decouple business rules from the UI, because "marketing geniuses" will change the UI (company Q's personal finance app went browser-like and then reverted; company A's phone OS changed the look of all apps).
2. Treat the web as an I/O device; device independence has been valued since the 1960s.
3. Do not try to abstract the chatty browser/app interaction, which is specific to the GUI type. Abstract at the use-case boundary instead: complete input data structure in, output data structure out, executed by a process independent of the UI.
4. Expect it to take several iterations to get right.

**3. Caveats.** Admits that GUIs such as the web are rich enough that full device independence is impractical, and that the abstraction "is not easy".

**4. Key terms.** Endless pendulum (central vs distributed oscillation). Web as IO device. Use-case input/output data structures.

**5. Quotes.**
- "The GUI is a detail. The web is a GUI. So the web is a detail."
- "The WEB is an IO device."
- "because you never know what the marketing geniuses will do next."

**6. PACE applicability.** Directly relevant: server-side use-case functions (input object in, result object out) that Express routes and the front-end merely call. Written in 2017, his pendulum list ends at Node, and today's SPA/SSR/edge debates are the next swing. Examples are not language-bound.

## Ch. 32 Frameworks Are Details

**1. Core argument.** Frameworks are useful but are not architectures. Their authors solve their own problems, not yours, and the relationship is an asymmetric marriage: you commit deeply, they commit to nothing. Frameworks ask you to inherit from their base classes and to bring their types into your business objects. The solution is not to marry the framework: keep it in the outer circles and integrate it through components that plug into the core.

**2. Rules.**
1. Do not couple your business objects (Entities) to a framework. Say no to deriving them from framework base classes; derive proxies in plugin components instead.
2. Use frameworks at arm's length in the outer circles, integrated by plugins that follow the Dependency Rule.
3. Example: use Spring's dependency injection in Main (the dirtiest, lowest-level component), not `@Autowired` throughout business objects.
4. Risks: frameworks often violate the Dependency Rule; the product may outgrow the framework and it fights back; the framework may evolve in unhelpful directions or drop features you use; a better framework may appear.
5. Some marriages are unavoidable (STL in C++, the Java standard library), but make it a conscious decision.
6. "Date" the framework, keep it behind a boundary as long as possible, and "get the milk without buying the cow".

**3. Caveats.** Framework authors act in good faith and overlap with your problems is the reason frameworks are valuable. Some frameworks must be adopted.

**4. Key terms.** Asymmetric marriage (one-way commitment to a framework). Proxy (a framework-facing class in a plugin that stands in for a business object). Main component (the lowest-level place that wires frameworks).

**5. Quotes.**
- "Don't marry the framework!"
- "It's a one-directional marriage."
- "Perhaps you can find a way to get the milk without buying the cow."

**6. PACE applicability.** Transfers well: keep Express, Supabase and AI vendor SDK types out of domain code, and wire them at the entry point (`index.js`/routes). Java specifics (Spring, annotations) do not apply, but the advice about keeping vendor/framework types out of core logic does. He doesn't price the cost of the indirection, which matters for a small team.

## Ch. 33 Case Study: Video Sales

**1. Core argument.** A worked example of the process: identify actors, derive use cases, then partition components by actor (Single Responsibility Principle) and by dependency direction (Dependency Rule), with the aim of separating things that change for different reasons and at different rates. The product is a site selling programming tutorial videos to individuals and businesses.

**2. Rules / steps.**
1. Start from actors and use cases. Four actors (viewer, purchaser, author, administrator) are the four sources of change. Partition so a change for one actor does not affect another. The use-case list is deliberately incomplete (no login/logout).
2. Use abstract use cases to unify near-duplicates. "View Catalog" is a dashed abstract use case shared by "View Catalog as Viewer" and "as Purchaser". It is not strictly required but wise.
3. Component architecture: views, presenters, interactors and controllers split per actor, with special Catalog View and Catalog Presenter components holding abstract classes that inheriting components extend.
4. Components are potential jars/DLLs, but build them independently and reserve the right to combine them (for example into five jars by role, or views and presenters together, or two jars). This keeps deployment options open as the system changes.
5. Dependency management: control flow is right to left (controllers, interactors, presenters, views). Dependencies mostly point left to right, always toward higher-level policy. Using relationships follow control flow while inheritance runs against it (OCP).
6. Two dimensions of separation: actors (SRP, different reasons) and policy level (Dependency Rule, different rates).

**3. Caveats.** Simplified, and he says he would not necessarily deploy as many jars as components. The notation for abstract use cases is his own, not standard UML.

**4. Key terms.** Actor (a source of change). Abstract use case (general policy fleshed out by other use cases). Component = deployable unit (jar/DLL).

**5. Quotes.**
- "The goal of both is to separate components that change for different reasons, and at different rates."
- "Therefore we want to partition the system such that a change to one actor does not affect any of the other actors."
- "You can group the components into deployable deliverables in any way that makes sense, and easily change that grouping when conditions change."

**6. PACE applicability.** Strong parallel for a recruiting ATS: the actors (recruiter, bench manager, candidate, admin, customer-org owner) are separate sources of change and could drive the partition. Specific to his example are the view/presenter/interactor/controller split and the jar granularity; the figures are missing, so the exact component layout is inferred from prose.

## Ch. 34 The Missing Chapter (Simon Brown)

**1. Core argument.** Good design intent is destroyed by implementation details: how code is packaged, which access modifiers are used, and what the compiler can enforce. Brown compares four ways to organise one use case ("view order status" in a Java book store): package by layer, package by feature, ports and adapters, and his own package by component. He argues that if every type is public, all four collapse into the same layered picture, so encapsulation, not folder organisation, makes an architecture real. He prefers the compiler (access modifiers, module/source-tree boundaries) to discipline or post-build tools for enforcing the rules.

**2. Rules / options.**
1. Package by layer (horizontal: web, business logic, persistence). It is a quick start and Fowler says good for starting, but it scales poorly, "screams" nothing about the domain (two different domains look alike), and has a hidden problem (below).
2. Package by feature (vertical, one package per domain concept or aggregate). It shows the domain at the top level and makes the code for a use case easier to find, which matters less with modern IDEs. Brown calls both suboptimal. Teams often swap one for the other after layering hurts.
3. Ports and adapters (hexagonal, boundaries/controllers/entities): an "inside" (domain) and an "outside" (UI, DB, third parties), with the outside depending on the inside only. Names inside use the ubiquitous domain language (`Orders`, not `OrdersRepository`). The diagram is simplified (no interactors or data marshalling objects).
4. Package by component (his preference): bundle the business logic and persistence for one coarse-grained component behind a single clean interface, with the UI kept separate as a delivery mechanism. Consumers see only the component interface (`OrdersComponent`), and internal separation of concerns remains hidden. His definition: a grouping of related functionality behind a clean interface inside an execution environment (C4 model: containers, components, classes). Whether a component is a separate jar is orthogonal. Well-defined components in a monolith are a stepping stone to micro-services.
5. Strict layers can be cheated. A newcomer injects the repository into the controller, skipping the service, giving a "relaxed layered architecture" with arrows still pointing downward and a nice acyclic graph. This bypass may be fine (CQRS) but bad if the business layer enforces authorisation. Enforcement by discipline and code review is fallible. Static analysis (NDepend, Structure101, Checkstyle rules such as "web must not access data") is crude, runs post-compile and gives slow feedback. Unchecked, this becomes a "big ball of mud".
6. Prefer compiler enforcement. Overuse of `public` makes packages mere folders, so the four approaches become identical. Apply the most restrictive access modifier: public only for types with inbound dependencies from other packages, with implementation classes package-private. Per approach: by layer (services and repository interfaces public), by feature (only the controller public, but nothing else can reach order data), ports and adapters (domain interfaces public, implementations package-private and injected), by component (only the component interface public, so nothing outside can use the repository). .NET: `internal` plus one assembly per component.
7. Other decoupling modes: module systems (OSGi, Java 9) distinguish public from published types. Separate source trees/build modules (domain, web, persistence), ideally one per component, but idealistic given performance, complexity and maintenance costs. A simpler two-tree split (domain vs infrastructure) risks the "Périphérique anti-pattern", where infrastructure code in different areas can call one another without passing through the domain, especially if access modifiers were forgotten.
8. Final advice: map the design onto code structures, choose decoupling modes for runtime and compile time, leave options open but be pragmatic about team size, skill, complexity, time and budget, use the compiler, and watch coupling in other places such as data models.

**3. Caveats.** Admits that Java access modifiers are imperfect (no package/subpackage access hierarchy) and that reflection can cheat. Package by feature has the downside that nothing outside the package can reach order data except via the controller. Separate source trees are idealistic. He openly disagrees slightly with Martin's component and organisation advice ("I come to a slightly different conclusion"), and says his definition of component differs from Martin's (a deployable unit).

**4. Key terms.** Package by layer / feature / component. Ports and adapters (hexagonal): inside/outside with dependencies inward. Relaxed layered architecture (layers allowed to skip). CQRS (separate update and read paths). Big ball of mud. C4 model (containers, components, classes). Périphérique anti-pattern. Ubiquitous domain language (DDD naming). Public vs published (module systems).

**5. Quotes.**
- "The devil is in the implementation details."
- "The fewer public types you have, the smaller the number of potential dependencies."
- "I'd personally like to use the compiler to enforce my architecture if at all possible."

**6. PACE applicability.** The folder-organisation debate (by layer vs by feature/component) applies directly to deciding how `routes/`, `services/` and `models/` are grouped, and the point that a route reaching around the service to the table breaks a rule (for example tenant scoping or authorisation) matches PACE's existing `db.forRequest` rule. The mechanism does not transfer: Node/JS has no `package-private`, so the compiler cannot enforce it. The substitutes are ES-module exports (export only the component interface), a `package.json` "exports" map or lint/import-restriction rules, and tests (PACE already has route-shadowing and guard tests). The Java/.NET details are specific.
