## Ch 7 - SRP: Single Responsibility Principle

**1. Core argument.** SRP is the most misunderstood SOLID principle because the name suggests "do one thing" (that is a different rule, for functions). The real rule: a module should have one reason to change, which Martin restates as "responsible to one, and only one, actor", where an actor is the group of people who want a change in the same way. When code serving different actors lives together, a change for one actor breaks another. The fix is to separate code by who it serves, then optionally tie it back together with a thin Facade.

**2. Rules / recommendations.**
1. A module (usually a source file, or a cohesive set of functions and data) answers to one actor only. Reason: cohesion is the force binding code that serves one actor.
2. Watch for Symptom 1, accidental duplication: in his Employee payroll class, calculatePay (CFO/accounting), reportHours (COO/HR), save (CTO/DBAs) share a helper regularHours(). A change requested by accounting silently corrupts HR's report, costing millions. Separate code that different actors depend on.
3. Watch for Symptom 2, merges: many people changing one file for different reasons collide; merges are always risky and can hit several stakeholders. Separate code that supports different actors.
4. Solution A: split data from functions. Three classes (pay, hours, save) share a plain data structure (EmployeeData) and do not know each other. Downside: the caller must instantiate and track three classes.
5. Solution B: add a Facade that instantiates and delegates to them (very little code).
6. Solution C: keep the most important business method in the original Employee class and make it the Facade for the lesser ones, for those who like rules near data.
7. Splitting does not mean one function per class: each class owns a family of private methods, a scope hidden from outside.

**3. Caveats.** None strongly stated; Martin notes the class-per-actor objection and answers it (families of private methods). Says SRP reappears at component level as CCP and at architecture level as the Axis of Change creating boundaries.

**4. Key terms.** Actor: group of people who require the same kind of change. Module: a source file or cohesive set of code/data. Facade: small class delegating to the separated classes. Accidental duplication: code that looks the same but serves different actors.

**5. Quotes.**
- "A module should be responsible to one, and only one, actor."
- "A function should do one, and only one, thing." (he says this is NOT the SRP)

**6. Web SaaS applicability.** Fully transfers; the actor idea maps well to roles like sales, finance, admin and DBAs/ops in a multi-tenant app. Employee/Facade is Java-style but the point is language-neutral: do not share a helper between code owned by different stakeholders.

## Ch 8 - OCP: Open-Closed Principle

**1. Core argument.** Coined by Bertrand Meyer (1988): software should be open for extension, closed for modification. If small new requirements force big changes, the architecture has failed. Martin shows it at architecture level with a financial-summary example: separate things that change for different reasons (SRP) and then point dependencies so that higher-level components are protected from lower-level ones (DIP).

**2. Rules.**
1. Extend behaviour without modifying existing artifacts; ideally a new requirement changes zero old code.
2. Thought experiment: a web page showing financial data must also become a paginated black-and-white printed report with negatives in parentheses. Separate (a) calculating the reportable data from (b) presenting it (web vs print). Then split into classes and components: Controller, Interactor, Database, Presenters and Views.
3. All dependencies are source-code dependencies; arrow A to B means A names B and B knows nothing of A. Every component boundary is crossed in one direction only.
4. "If component A should be protected from changes in component B, then B should depend on A." Protection runs by "level": Interactor (business rules, highest-level policy) is most protected; Views least; Presenters in between; Controller above Presenters.
5. Directional control: much of the diagram's complexity (interfaces such as FinancialDataGateway, the presenter and view interfaces) exists purely to invert dependencies so they point the right way.
6. Information hiding: FinancialReportRequester interface keeps the Controller from knowing the Interactor's internals, avoiding transitive dependencies (software should not depend on things it does not directly use; forward link to ISP and CRP).

**3. Caveats.** None explicit here; the class diagram is admittedly complex ("if you recoiled in horror, look again"). (The CCP chapter later says 100% closure is unattainable; closure must be strategic.)

**4. Key terms.** Open for extension / closed for modification. Interactor: component holding business rules. Level: distance from I/O, the basis of protection hierarchy. Transitive dependency. Unidirectional component relationships.

**5. Quotes.**
- "A software artifact should be open for extension but closed for modification."
- "If component A should be protected from changes in component B, then component B should depend on component A."

**6. Web SaaS applicability.** Transfers strongly: keep business rules from depending on HTTP handlers, templates, or the DB driver. The Java interface mechanics are specific; in Node you can get the same inversion with injected functions/modules. Figures 8.1-8.3 are diagrams (not in text); worked from prose.

## Ch 9 - LSP: Liskov Substitution Principle

**1. Core argument.** Liskov (1988): S is a subtype of T if programs written against T behave unchanged when given S. Originally a guide for inheritance, it has grown into a rule about any interface and its implementations, including REST services. A substitutability violation forces special-case mechanisms into the architecture.

**2. Rules.**
1. Subtypes must be substitutable for their base type without callers needing to know which one they have. Good example: License with PersonalLicense and BusinessLicense, both implementing calcFee; Billing does not care which.
2. Classic violation: Square derived from Rectangle. Width and height are independently settable on Rectangle but tied together in Square, so code that sets width 5, height 2 and expects area 10 fails. Defending requires an if/type check in the caller, which proves non-substitutability.
3. Applies to any interface form: Java interfaces, duck-typed Ruby classes, or services sharing a REST contract.
4. Architectural example: a taxi-aggregator dispatches by PUT to a URI stored per driver record, appending pickupAddress/pickupTime/destination. One company (Acme) abbreviates the field to "dest". The naive fix, an if on URI starting with "acme.com", is dangerous (what if Acme buys Purple Taxi?). The architect ends up building a configuration-driven dispatch-format module keyed by URI. Cost of the one violation: a significant extra mechanism.

**3. Caveats.** Humorous aside on office politics (Acme CEO's relationships) to say you cannot just refuse the special case. No stated exceptions.

**4. Key terms.** Subtype / substitution property. Substitutability. Dispatch URI config table.

**5. Quotes.**
- "The LSP can, and should, be extended to the level of architecture."

**6. Web SaaS applicability.** Highly relevant: third-party APIs, webhooks, and per-vendor integrations that nominally share an interface but differ in details (email providers, job boards). The lesson: normalise differences behind an adapter/config rather than scattering `if (vendor === ...)`. Inheritance details are Java/C++-specific.

## Ch 10 - ISP: Interface Segregation Principle

**1. Core argument.** Do not make clients depend on operations they do not use. In statically typed languages, a user of a fat class (OPS with op1-3) is dragged into recompilation/redeployment when unrelated ops change; segregating into per-user interfaces fixes it. The deeper point (architectural) is that depending on something carrying baggage you do not need invites unexpected trouble.

**2. Rules.**
1. Split fat interfaces so each user depends only on the operations it uses (User1 sees U1Ops, not OPS).
2. Language caveat: the recompile/redeploy argument is strongest in static languages (Java) because declarations create source dependencies; in dynamic languages (Ruby, Python) those declarations don't exist, which makes them looser and more flexible. This could make ISP look like a language issue.
3. But the root concern is architectural: System S uses framework F that is bound to database D; unused features of D can force redeployment of F and S, and a failure in D's features can break F and S.
4. Forward reference: Common Reuse Principle (Ch 13) generalises this.

**3. Caveats.** Explicitly says the original motivation is language-dependent; argues it nevertheless holds at architecture level.

**4. Key terms.** Fat interface. Segregated interfaces (U1Ops etc.). Baggage (unneeded dependencies).

**5. Quotes.**
- "Depending on something that carries baggage that you don't need can cause you troubles that you didn't expect."

**6. Web SaaS applicability.** The compile-time argument mostly does not apply to Node; the architectural argument does: avoid pulling a heavy framework or SDK (and its failure modes, upgrades, security patches) for a small need. Figures 10.1-10.3 not in text.

## Ch 11 - DIP: Dependency Inversion Principle

**1. Core argument.** The most flexible systems have source-code dependencies pointing only at abstractions, not concrete implementations. You cannot do this absolutely (e.g., Java String is concrete and stable), so focus on volatile concretions, the things under active development. Control flow and source dependencies point in opposite directions at the boundary, hence "inversion".

**2. Rules.**
1. Don't refer to volatile concrete classes; refer to abstract interfaces. This constrains object creation and pushes you to Abstract Factories.
2. Don't derive from volatile concrete classes: inheritance is the strongest, most rigid source relationship (less so in dynamic languages, still a dependency).
3. Don't override concrete functions: overriding inherits their dependencies; make the function abstract and give it several implementations.
4. Never mention the name of anything concrete and volatile (restatement).
5. Reasoning for stable abstractions: changing an interface forces changes in implementations, but not vice versa; so interfaces are less volatile, and good designers work to keep them stable ("Software Design 101").
6. Factories: creating an object requires depending on its concrete type, so use an Abstract Factory (Application calls ServiceFactory.makeSvc; ServiceFactoryImpl instantiates ConcreteImpl). A curved architectural boundary separates abstract side from concrete side; all dependencies cross it toward the abstract side while control flows the other way.
7. Some concrete component must violate DIP; gather violations into a small number of concrete components, typically `main`, which creates the factory and places it in a global of the abstract type.
8. Previews the Dependency Rule of later chapters.

**3. Caveats.** Treating the rule absolutely is "unrealistic"; stable platform/OS facilities are tolerated. In dynamic languages "concrete" means any module where the called functions are implemented.

**4. Key terms.** Abstract Factory. Volatile concretion vs stable background. Architectural boundary (curved line). `main` as the dirty/concrete component. Dependency Rule (forward ref).

**5. Quotes.**
- "The most flexible systems are those in which source code dependencies refer only to abstractions, not to concretions."

**6. Web SaaS applicability.** Transfers: keep business logic from importing the DB client, email vendor or payment SDK directly; wire concrete choices in a composition root (index.js/main). In JS the interface is by convention (shape), and factories are often just injected functions or module-level wiring; no inheritance needed.

## Ch 12 - Components

**1. Core argument.** Components are the smallest deployable units (jar, gem, DLL, a set of source files in interpreted languages). Well-designed components remain independently deployable and developable. Martin gives a history showing how component plugin architecture became possible once linking got fast.

**2. Content (history; few rules).**
1. Early programs fixed memory addresses (e.g., PDP-8 `*200` origin); libraries were included as source, so compile time grew with library size.
2. Libraries were compiled separately and loaded at a fixed address; applications outgrew their space and had to be split around the library: unsustainable.
3. Relocatable binaries and a smart loader solved placement; compilers emitted external references and definitions, giving the linking loader.
4. Linking loaders became too slow (tapes, slow disks, huge libraries); linking was split into a separate linker producing something quick to load.
5. 1980s C programs grew; compile-and-link time stayed around an hour: Murphy's law of program size ("programs grow to fill all available compile and link time").
6. Moore's law won by mid-1990s: link time fell to seconds, load-time linking returned (ActiveX, shared libraries, .jar), giving the plugin architecture (Minecraft mods, Resharper in Visual Studio).

**3. Caveats.** None; purely historical and framing.

**4. Key terms.** Component. Relocatable binary. Linking loader / linker. Plugin architecture. Murphy's law of program size.

**5. Quotes.**
- "Components are the units of deployment."

**6. Web SaaS applicability.** Mostly historical colour. The concept transfers if you read "component" as an npm package/module or deployable service; in a single-process Express app the independently deployable unit is often just the whole app, so component boundaries are a discipline of modules and folders rather than literal artifacts. PDP-8 listing and figures 12.1-12.2 are illustrative only.

## Ch 13 - Component Cohesion

**1. Core argument.** Which classes go into which component has historically been ad hoc. Three principles guide it: REP, CCP, CRP. REP and CCP push components bigger (inclusive); CRP pushes smaller (exclusive). Good architects balance them, and the balance shifts over time.

**2. Rules.**
1. **REP (Reuse/Release Equivalence)**: the granule of reuse is the granule of release. Reusable code must be tracked through releases with version numbers and release notes so users can decide when to adopt (they may stay on an old release). Grouped classes must form a cohesive whole releasable together. Martin admits this is weak, hand-waving advice, but violations are easy to notice, and CCP/CRP define it more strongly in a negative sense.
2. **CCP (Common Closure)**: gather classes that change for the same reasons and at the same times; separate those that change at different times/for different reasons. It is SRP for components. For most apps maintainability beats reusability: confine a change to one component so only it is redeployed and revalidated. Tied to OCP: since 100% closure is unattainable, closure must be strategic, closed against the most common anticipated or experienced changes.
3. **CRP (Common Reuse)**: don't force users of a component to depend on things they don't need. Classes reused together belong together (container and its iterators); classes not tightly bound should not share a component. Reason: any dependency on a component means redeploying/revalidating when it changes, even if the used class is untouched. It is the generic form of ISP (ISP: don't depend on unused methods; CRP: don't depend on components with unused classes). Sound bite: "Don't depend on things you don't need."
4. **Tension diagram** (triangle, credited to Tim Ottinger): the edges show the cost of abandoning the opposite vertex principle. REP+CRP focus: too many components affected by simple changes. CCP+REP focus: too many unneeded releases. Projects start near the side where only reuse is sacrificed (CCP favoured: developability over reuse) and slide toward the REP side as other projects begin to consume them. The structure depends on how the project is developed and used, not on what it does.

**3. Caveats.** REP admitted as weak; balance is dynamic ("jitter and evolve"); the old notion of cohesion as "does one function" is too simple.

**4. Key terms.** REP, CCP, CRP. Granule of release. Inclusive vs exclusive principles. Tension diagram. Strategic closure.

**5. Quotes.**
- "The granule of reuse is the granule of release."
- "Gather into components those classes that change for the same reasons and at the same times."
- "Don't depend on things you don't need."

**6. Web SaaS applicability.** CCP is the most useful for a product team: group code by what changes together (a feature/domain area), which matches how a SaaS evolves and is released. REP/CRP matter mainly when publishing internal packages or consuming npm libraries; for a single deployed app, early on favour CCP. Figure 13.1 not in text; worked from prose.

## Ch 14 - Component Coupling

**1. Core argument.** Three principles govern relationships between components: ADP (no cycles), SDP (depend toward stability), SAP (stable components must be abstract). Together with metrics (I, A, D) they let you quantify design health. The component graph is a map of buildability and maintainability, not of function, so it evolves rather than being designed upfront.

**2. Rules.**
1. **ADP (Acyclic Dependencies)**: allow no cycles in the component dependency graph.
   - Problem: "morning after syndrome" (someone changed what you depend on overnight); scales badly with team size.
   - Weekly build as the old remedy: private work four days, integrate Friday; integration then creeps earlier (Thursday, biweekly), efficiency and feedback fall.
   - Better remedy: partition into releasable components; teams release numbered versions and others adopt when ready; integration happens in small increments. This only works if the dependency graph is a DAG.
   - Benefits of a DAG: impact of a release found by following arrows backward; a leaf (Main) releasing affects no one; a component can be tested with only the versions it depends on; build and release order proceeds bottom-up (Entities, Database/Interactors, Presenters, View, Controllers, Authorizer, Main).
   - Effect of a cycle: example where User in Entities uses Permissions in Authorizer; Entities, Authorizer and Interactors become effectively one big component, release and unit tests drag in unrelated stuff, build issues grow geometrically, and build order may have no correct answer.
   - Breaking a cycle: (1) apply DIP, put an interface in Entities that Authorizer implements, inverting the arrow; (2) create a new component both depend on and move the shared classes there.
   - "Jitters": the structure grows and shifts with requirements, so keep monitoring for cycles.
2. **Top-down design is wrong for components**: the component structure cannot be designed first. It is a buildability/maintainability map, so it emerges as classes accumulate; first SRP/CCP localise change and isolate volatility (GUI cosmetics or reports must not affect business rules), then CRP as reuse appears, then ADP as cycles arise. Designing it before classes exist leads to wrong closure, unseen reuse and cycles.
3. **SDP (Stable Dependencies)**: depend in the direction of stability. Components meant to change should not be depended on by components hard to change; hanging a dependency on a volatile module makes it hard to change without editing it.
   - Stability defined as "not easily moved" (penny on edge vs table), i.e. work required to change, not frequency of change. A major cause: many dependents.
   - Stable X: three components depend on it (responsible), depends on nothing (independent). Unstable Y: no dependents (irresponsible), depends on three (dependent).
   - Metrics: Fan-in = classes outside that depend on classes inside; Fan-out = classes inside that depend on classes outside. **Instability I = Fan-out / (Fan-in + Fan-out)**, range [0,1]; I=0 maximally stable (responsible and independent), I=1 maximally unstable (irresponsible, dependent). Example: Cc has Fan-in 3, Fan-out 1, so I = 1/4. (Earlier books named these Ca/Ce, afferent/efferent.) Count is easy via #include or Java imports.
   - SDP statement: a component's I should be larger than the I of components it depends on; I decreases in the direction of dependency.
   - Not everything should be stable: a fully stable system could not change. Draw unstable components on top; any arrow pointing up violates SDP (and ADP).
   - Violation example: Stable depends on Flexible. Fix with DIP: introduce interface US in a new component UServer (I=0), have C in Flexible implement it, so both depend on UServer and arrows flow toward lower I.
   - Abstract components (interface-only) are common in static languages, nonexistent in dynamic ones (Ruby, Python), where dependency structure is simpler.
3. **SAP (Stable Abstractions)**: a component should be as abstract as it is stable. High-level policy belongs in stable components (I=0), but stable code is hard to change, so make it extensible via OCP, i.e. abstract classes/interfaces; unstable components are concrete so their code is easy to change. SDP plus SAP equals DIP for components (dependencies run toward abstraction); unlike class-level DIP, components can be partly abstract and partly stable.
   - **Abstractness A = Na / Nc** (Na = abstract classes and interfaces, Nc = total classes); range [0,1].
   - **Main Sequence**: on a graph with I on the horizontal and A on the vertical axis, ideal points are (0,1) (stable and abstract) and (1,0) (unstable and concrete); the line joining them is the Main Sequence. Mid components are fine on or near it. Abstract classes deriving from abstract classes make a maximally abstract but not maximally stable component.
   - **Zone of Pain** near (0,0): stable and concrete, rigid; only matters if volatile (volatility as a third axis). Examples: database schemas (volatile, concrete, heavily depended on, hence painful schema updates); a concrete utility library like String is harmless because it is non-volatile.
   - **Zone of Uselessness** near (1,1): maximally abstract with no dependents; leftover abstract classes nobody implemented.
   - **Distance D = |A + I - 1|**, range [0,1]; 0 = on the Main Sequence, 1 = furthest. Use: compute D for each component and re-examine ones not near zero; compute mean and variance across the design (expect near zero), use control limits (e.g., more than one standard deviation, Z=1) to flag outliers on a scatterplot; plot D over releases (e.g., Payroll component with a control threshold at 0.1; release R2.1 exceeded it, so investigate).

**3. Caveats.** Conclusion (cut off at end of slice) begins: metrics measure conformance to a "good" pattern from experience, but "a metric is not a god; it is merely a measurement against an arbitrary [standard]" (sentence truncated). Martin also admits the two-endpoint ideal cannot always hold, naming the Main Sequence as the fallback. Footnote: he apologises for borrowing "Main Sequence" from astronomy and dropped his earlier D-prime notation.

**4. Key terms.** Morning-after syndrome; DAG; weekly build; jitters; Fan-in/Fan-out (Ca/Ce); Instability I; Abstractness A; stable/unstable (responsible/irresponsible, independent/dependent); abstract component; Main Sequence; Zone of Pain; Zone of Uselessness; Distance D.

**5. Quotes.**
- "Allow no cycles in the component dependency graph."
- "Depend in the direction of stability."
- "A component should be as abstract as it is stable."

**6. Web SaaS applicability.** ADP and SDP transfer directly to module/package structure in Node (circular `require`/`import` chains are a real hazard; stable shared libraries at the bottom, volatile UI/route code on top). The I/A/D metrics assume classes and interfaces; JS has no interface declarations, so A is hard to measure (A tends to 0), and tools like madge/dependency-cruiser are practical for cycles and fan-in/out. Database schema as Zone of Pain is a very relevant point for Postgres. Jar/DLL release mechanics are less relevant to a single deployed app. Figures 14.1-14.15 not in text.
