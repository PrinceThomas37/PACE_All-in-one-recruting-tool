# CH 13 - Service-Based Architecture Style (lines 1-362)

## 1. Core argument
Service-based architecture is a pragmatic hybrid of microservices: a few (4-12, average ~7) coarse-grained, separately deployed "domain services", usually behind a separately deployed UI and sharing ONE monolithic database. You get much of the agility, testability, deployability and fault isolation of distributed systems without the cost and complexity of microservices, EDA or space-based. Because services are big, ordinary ACID transactions still work inside a service, and orchestration/choreography problems mostly vanish. The main price is coarse change scope (a change retests a whole service) and database-schema coupling, which must be managed by logically partitioning the DB and its shared entity libraries. The book calls it one of the most pragmatic styles and the cheapest/easiest distributed architecture.

## 2. Concepts, section by section
**Topology.** Distributed macro-layered: separate UI, separate remote coarse-grained domain services, one shared DB. Services deployed like a normal monolith artifact (WAR/EAR/assembly); containers optional. Usually one instance per service; multiple instances need a load balancer. UI reaches services via REST (or messaging/RPC/SOAP), commonly directly via a service locator in the UI, API gateway or proxy. Shared DB means normal SQL joins; connection counts are not a problem at 4-12 services; schema change is the problem.
**Topology variants** (very flexible style): split the UI into domain UIs (down to one per service); split the DB into several (even per domain service) - only if one service does not need another's data (avoid inter-service calls and data duplication); add an API layer (reverse proxy/gateway) between UI and services - good for exposing services to external systems and consolidating cross-cutting concerns (metrics, security, auditing, service discovery).
**Service design and granularity.** Each domain service is internally layered (API facade, business, persistence) or domain-partitioned into sub-domains like a modular monolith. Each needs an API access facade that orchestrates the request internally (example: PlaceOrder = create order, generate id, apply payment, update inventory, all as class-level calls inside OrderService). In microservices the same would be external orchestration of many remote services. Inside a service you use real ACID commit/rollback; fine-grained microservices use BASE (eventual consistency). Example: expired card - monolith-style service just rolls back; microservices leave order half-inserted and raise questions (is inventory reserved? can another buyer take the last unit?). Trade-off: a change to order placement means retesting and redeploying the whole OrderService (including payment) - more code deployed, more risk - whereas microservices change one small service.
**Database partitioning.** Shared DB couples all services to schema changes. A single shared library of entity objects (JAR/DLL, maybe with SQL) is the "least effective" way: any table change forces a change and redeploy of every service. Better: logically partition the DB into domains (example: common, customer, invoicing, order, tracking) and mirror it with one federated shared library per domain, so an invoicing-table change only hits the invoicing service. A "common" domain used by all services remains; mitigate by locking those common entity objects in version control and restricting changes to the database team. Rule: make logical partitions as fine-grained as possible while keeping well-defined data domains.
**Example architecture: electronics recycling.** Domains: quoting, receiving, assessment, accounting, item status, recycling, reporting - each a separate domain service. Only customer-facing Quoting and Item Status need scaling; others single instance. UIs federated (Customer Facing; Receiving; Recycling and Accounting) for fault tolerance, scalability, security. Two physical databases (external vs internal network zone), one-way firewall access (internal can update external, not reverse), or table mirroring/sync. Assessment service changes constantly (new rules per product) and that churn is isolated to one service -> agility, testability, deployability.

**Characteristics ratings (Figure 13-9, image; values from prose).** Domain-partitioned (not technically partitioned). Quanta: one or more (1 if services share DB/UI; recycling example has 2). No five-star ratings; four stars on: agility (faster change), testability, deployability, fault tolerance, availability (and the book says "reliability" is better than other distributed styles - larger services, less network traffic, fewer distributed transactions). Three stars: scalability. Two stars: elasticity. Simplicity and cost are favourable (relatively simple/cheap for a distributed style). Modularity/evolvability high (domain-scoped), performance not stated in the prose (assume moderate; my inference). The book notes the trade-off: higher cost/complexity styles score better on the four-star characteristics.
Why scalability 3 / elasticity 2: coarse services replicate more code than fine-grained ones, so less efficient; usually single instances.
Why fault tolerance 4: services are self-contained, little inter-service communication; if Receiving goes down the other six continue.

**When to use:** pragmatic default for business apps that want distributed benefits without the price ("a Ferrari for rush-hour driving" analogy for over-powered styles); natural fit for domain-driven design; best at preserving ACID among distributed styles (only if UI/API gateway orchestrates 2+ services do you need sagas/BASE); good modularity without the granularity pitfalls (orchestration = central mediator conducts; choreography = services talk to each other, no mediator; both needed as services get finer, much less so with coarse services).
**When not to use** (implied): when you need extreme elasticity/scalability/per-function fine-grained deployability (microservices/space-based), or when many services must be constantly coordinated.

## 3. Pitfalls / anti-patterns
- Single shared library of all entity objects (every schema change redeploys everything).
- Inter-service calls between domain services when splitting databases (and data duplication).
- Letting the "common" tables be changed by anyone.
- Too-coarse service that couples unrelated functionality so one change retests everything.
- Using a distributed-transaction (saga) across services when you could have kept the transaction inside one service.

## 4. Key terms
- Domain service: coarse-grained, independently deployed portion of an application scoped to a business domain.
- API access facade: entry point of a domain service that orchestrates the request internally.
- Federated shared libraries: one entity library per logical DB domain.
- ACID vs BASE: strong transactional integrity vs basic availability/soft state/eventual consistency.
- Orchestration vs choreography: central mediator vs peer-to-peer coordination.
- Quantum (here): independently deployable unit with high functional cohesion incl. its DB/UI.

## 5. Quotes
- "Service-based architecture ... is considered one of the most pragmatic architecture styles, mostly due to its architectural flexibility."
- "Make the logical partitioning in the database as fine-grained as possible while still maintaining well-defined data domains."

## 6. Relevance to PACE (my analysis)
PACE is today a layered/modular monolith with one Postgres - and CLAUDE.md already enforces a logical partition (`models/`, `models/tables.js`, territories, "one home" per rule), which is exactly the book's cure for shared-DB coupling, done inside one deployable. Service-based is the natural FIRST step if PACE ever has to split: candidate domain services would be (1) the email send/sweep engine (index.js leads engine, mailbox sweeps, follow-ups), (2) the ATS API (routes/recruiting), (3) AI/parse workers (resume parsing, ai-provider). Keep the shared DB (multi-tenancy via org_id/RLS and ACID transactions are valuable) and the single frontend. Signals that would justify: the daily send/sweep jobs starving user-facing requests on the single free-tier instance (latency spikes), need to deploy email engine changes without touching the ATS, a second engineer/team owning a domain, or different scaling profile for public pages (/apply, /i) vs internal. Do NOT split for fashion; solo owner + AI builder, free tier, makes microservices a poor fit. The book's "avoid inter-service calls" and "coarse + ACID" rules match CLAUDE.md's "three pipelines stay three, share nothing for sending".

# CH 14 - Event-Driven Architecture Style (lines 363-1207)
(Note: text lines ~390-432 duplicate a page - Figure 14-1 and "Topology" intro appear twice; extraction artefact, nothing missing.)

## 1. Core argument
EDA is a distributed, asynchronous style of decoupled event processors, giving very high scalability, performance and evolvability; it can stand alone or be embedded in other styles (microservices, space-based, microkernel, pipeline). It contrasts with the request-based model (deterministic, synchronous: "get my order history") by modelling things that happen to which the system must react (a bid placed). Two topologies: broker (no central coordinator, a relay race; max decoupling and speed, but weak workflow control, error handling and recoverability) and mediator (central orchestrator; control, error handling and restart, but more coupling and lower scale/performance). The big gains (responsiveness, scale) come with big costs: eventual consistency only, hard testing/debugging, and hard error handling - which the chapter addresses with the workflow event pattern and data-loss prevention techniques.

## 2. Concepts
**Request-based vs event-based.** Request-based: a request orchestrator (UI, API layer or ESB) synchronously and deterministically routes to request processors that read/update the DB. Event-based: reacts to a situation and takes action.
**Broker topology.** No central mediator; message flow chained across event processors via a lightweight broker (RabbitMQ, ActiveMQ, HornetQ). Four components: initiating event (starts the flow), event broker (usually federated: multiple domain-based clustered instances, each with the channels of its domain; usually topics/pub-sub; topic exchanges in AMQP), event processor, processing event. A processor does its task then asynchronously advertises what it did via a new processing event; others react; continues until nobody is interested. Good practice: every processor advertises what it did even if nobody listens - that is architectural extensibility (e.g. an email-sent event ignored today; a later email-analyser just subscribes, no changes elsewhere).
 - Example retail order: PlaceOrder -> OrderPlacement inserts order, returns order id, publishes order-created -> in parallel Notification (emails; emits email-sent), Payment (emits payment-applied or payment-denied), Inventory (decrements; emits inventory-updated -> Warehouse reorders). payment-denied -> Notification emails customer to fix card. payment-applied -> OrderFulfillment (pick/pack, order-fulfilled) -> Notification + Shipping in parallel -> order-shipped -> Notification.
 - Relay-race analogy: once a processor hands off the event it is done and free; each processor scales independently; topics are the back-pressure point if a processor is down or slow.
 - Table 14-1 broker trade-offs. Advantages: highly decoupled processors, high scalability, high responsiveness, high performance, high fault tolerance. Disadvantages: no workflow control, error handling, recoverability, restart capabilities, data inconsistency.
 - Negatives explained: nobody knows when the business transaction is complete; if Payment crashes nobody notices, the others carry on (inventory still decremented); the initiating event cannot be resubmitted because other actions already happened and nobody owns the request's state.
**Mediator topology.** Components: initiating event, initiating event queue, event mediator, event channels (usually queues, point-to-point), event processors. The mediator knows the steps, generates processing events (commands) to dedicated queues; processors do work and acknowledge to the mediator; processors do NOT advertise to the rest of the system. Usually multiple mediators per domain/event grouping (customer mediator, order mediator) to reduce single point of failure and raise throughput.
 - Implementation choices by complexity: simple error handling/orchestration -> Apache Camel, Mule ESB, Spring Integration (flows custom-coded). Complex conditional flows with dynamic paths and elaborate error handling -> BPEL engines (Apache ODE, Oracle BPEL; XML-like, graphical tools; powerful but complex). Long-running with human intervention (e.g. trade needs senior-trader approval) -> BPM engine such as jBPM. Wrong fit is costly: Camel for human-in-the-loop is miserable; BPM for simple flows wastes months.
 - Recommendation: classify events as simple, hard, or complex; send every event through a simple mediator that handles simple ones and forwards hard/complex ones to a BPEL/BPM mediator (mediator delegation model; the simple mediator may track completion or fully delegate).
 - Example order flow, 5 steps: (1) create-order -> OrderPlacement acks with order id; (2) concurrent email-customer, apply-payment, adjust-inventory - mediator waits for all three acks; (3) concurrent fulfill-order and order-stock; (4) email-customer (ready to ship) and ship-order; (5) email-customer (shipped); mediator marks flow complete and deletes its state. Steps serial, tasks inside a step parallel.
 - Because mediator holds state it can handle errors, recoverability and restart: expired card -> mediator stops, persists request state in its own datastore, resumes from step 3 when payment eventually applied.
 - Commands vs events: mediator messages are commands (things that must happen, must be processed); broker messages are events (things that happened, may be ignored).
 - Negatives: hard to model dynamic complex flows declaratively (often a hybrid of mediator for the general flow + broker for nontypical cases such as out-of-stock); mediator must scale too and can bottleneck; processors less decoupled; lower performance.
 - Table 14-2 mediator trade-offs. Advantages: workflow control, error handling, recoverability, restart capabilities, better data consistency. Disadvantages: more coupling of processors, lower scalability, lower performance, lower fault tolerance, difficulty modelling complex workflows.
 - Choice summary: workflow control and error handling vs raw performance/scale.
**Asynchronous capabilities.** EDA relies only on async comms, for both fire-and-forget and request/reply. Example: posting a product comment takes 3,000 ms of checking (bad-word, grammar, context). Sync REST: 50+3000+50 = 3,100 ms felt by the user; async messaging: ~25 ms felt (still 3,025 ms real work). Lesson: responsiveness (acknowledge fast) is different from performance (make the work faster; would mean parallelising the checkers, caching). Caveat: user only gets an acknowledgement, not a guarantee; if the comment is later rejected you must reach back (e.g. message to the registered user); a stock trade with no way back is harder. Main issue of async = error handling.
**Error handling: workflow event pattern** (reactive architecture; resiliency + responsiveness via delegation, containment and repair). The consumer that hits an error immediately delegates it to a workflow processor and moves on to the next message (so the queue is not blocked). The workflow processor tries to diagnose and programmatically repair the message (deterministic rules or even ML) and resubmits it to the originating queue as a new message. If it cannot work out the fault, it routes it to a "dashboard" queue - an Outlook-like app on a person's desktop - where a human fixes it manually and resubmits (via reply-to header). Example: a trading advisor sends a basket of orders as `ACCOUNT,SIDE,SYMBOL,SHARES`; one row says "8756 SHARES" (parse error). Without handling it just logs; with the pattern, the Trade Placement service delegates to Trade Placement Error service, which strips the word SHARES and resubmits; the trade then places successfully. Consequence: repaired messages are processed OUT OF ORDER; if order within a context matters (trades per brokerage account), hold later messages for that account in a temporary FIFO queue until the failed one is fixed, then drain in order - possible but complex.
**Preventing data loss.** Data loss = message dropped or never reaching its final destination. Three loss points: (1) message never reaches the queue from Processor A, or broker dies before B fetches it; (2) Processor B dequeues and crashes before processing; (3) B cannot persist to the DB due to a data error. Fixes: (1) persistent queues (guaranteed delivery - broker persists to disk/db as well as memory) plus synchronous send (producer blocks until broker acknowledges persistence) - the message is always either still with the producer or persisted in the queue; (2) client acknowledge mode - the message stays in the queue (tagged with the client ID so others cannot take it) until the consumer acks, instead of default auto-acknowledge which removes at dequeue; (3) ACID transaction with a DB commit, and last participant support (LPS): the message is acked/removed from the persistent queue only after the commit succeeds. Together they guarantee no loss from A to the database.
**Broadcast capabilities.** A producer publishes a message that multiple subscribers receive, without knowing who or what they do; the highest decoupling; essential to eventual-consistency patterns and complex event processing (CEP); example stock-price tickers.
**Request-reply.** When you need an answer (an order ID, a flight confirmation number) - pseudo-synchronous. Each channel is two queues: request and reply. Producer sends async to request queue then blocks waiting on the reply queue. Technique 1 (recommended, most common): correlation ID - reply message's CID header = original message ID; producer waits with a message selector on CID; unrelated replies in the queue are skipped (example ID 124; replies with CIDs 120/122 ignored; reply 857 with CID 124 accepted). Technique 2: temporary queue per request, named in the reply-to header, deleted afterward - simpler but the broker must create/delete a queue per request and volume slows it, hence not recommended at scale.
**Choosing request-based vs event-based.** Request-based for well-structured, data-driven requests where certainty and control over the workflow are needed (retrieve customer profile). Event-based for flexible, action-based events needing high responsiveness and scale, with complex dynamic processing. Table 14-3. Advantages of event-based: better response to dynamic user content, better scalability and elasticity, better agility and change management, better adaptability and extensibility, better responsiveness and performance, better real-time decision making, better reaction to situational awareness. Trade-offs: only supports eventual consistency, less control over processing flow, less certainty of outcome of event flow, difficult to test and debug.
**Hybrid EDA.** Often combined: microservices and space-based architectures both use messaging for data pumps and for programmatic scalability/inter-service comms; also event-driven microkernel and event-driven pipeline. Adding EDA to any style removes bottlenecks, gives a back-pressure point when requests pile up, and improves user responsiveness.

**Characteristics ratings (Figure 14-22 is an image; from prose).** Technically partitioned (a domain is spread across processors/mediators/queues/topics; a domain change touches many parts). Quanta: one to many - shared DB or request-reply coupling puts processors in the same quantum even though comms are async (example: if the order-placing processor is down, the requester cannot continue -> same quantum). Five stars: performance, scalability, fault tolerance, evolvability (evolutionary - adding features/processors is easy, especially broker hooks). Low: simplicity and testability (nondeterministic dynamic flows; event tree diagrams can generate hundreds to thousands of scenarios, hard to govern and test). Elasticity high (programmatic competing consumers; my reading of the prose - exact star not stated in the text), cost/overall moderate-to-high (not stated). Reasons: performance from async + parallel; scalability via competing consumers; fault tolerance via decoupled async with eventual processing (promises/futures when downstream is down).

**When to use** (from the chapter's guidance): async fire-and-forget workloads, high responsiveness/scale, complex dynamic processing, extensibility needs, reacting to situations. **Avoid** for deterministic, data-driven request flows needing strict consistency and workflow certainty.

## 3. Pitfalls / anti-patterns
- Broker topology when you need to know a business transaction is complete or restartable (stuck processes nobody notices).
- Choosing the wrong mediator class for the event complexity (Camel for human workflow; BPM for trivial flows).
- Consumer spending time diagnosing an error instead of delegating (blocks the queue).
- Repairing/replaying out of order when order matters.
- Auto-acknowledge on dequeue, non-persistent queues, fire-and-forget producer send - all lose data.
- Temporary reply queues at high volume.
- Treating "accepted" as "done" (async acknowledgement is a promise, not a guarantee); confusing responsiveness with performance.
- Not advertising events in broker topology (loses extensibility).

## 4. Key terms
- Initiating event / processing event: first event of a flow / event emitted by a processor.
- Event broker / event mediator: message infrastructure with no control / orchestrator that owns workflow state.
- Command vs event: must-happen vs already-happened.
- Workflow event pattern / workflow delegate: delegate-contain-repair error handling.
- Guaranteed delivery, synchronous send, client acknowledge mode, last participant support (LPS): the data-loss defences.
- Correlation ID, message selector, temporary queue: request-reply techniques.
- Competing consumers: multiple instances reading one queue for scale.
- Back pressure point: queue/topic that absorbs overload.
- Responsiveness vs performance.

## 5. Quotes
- "The main issue with asynchronous communications is error handling."
- "Responsiveness is all about notifying the user that the action has been accepted and will be processed momentarily, whereas performance is about making the end-to-end process faster."
- "The choice between the broker and mediator topology essentially comes down to a trade-off between workflow control and error handling capability versus high performance and scalability."

## 6. Relevance to PACE (my analysis, not the book's)
**Should PACE move to EDA?** Not wholesale: PACE's core is request-based (ATS CRUD, pipelines, scoping by org/owner) where the book itself recommends request/response and strong consistency. But PACE already contains an EDA-shaped subsystem - the email send queue, reply sweeps, follow-up timers, candidate outreach batches - where async + mediator-like control is right. Of the two topologies, PACE's send loop is a mediator/queue-with-owner model (one process owns state), which the book says gives the error handling and restart PACE needs; a broker (free-for-all events) would be a regression for "who owns this send". Signals that would justify a real queue/broker (e.g. a Postgres-backed job table with SKIP LOCKED, or later a managed queue): sends/sweeps competing with web requests on one free-tier instance; multiple instances needing to share work (competing consumers); need to fan out one event (reply received) to several reactions (conversation intel, notifications, activity log) without editing the send loop; a second customer with heavy volume. Until then, a durable table in Postgres IS the persistent queue - keep it.
**Applied now to the email queue (the big takeaway):**
 - Guaranteed delivery / persisted queue = the pending rows live in Postgres, not memory. Keep it that way; never hold a send only in a process variable.
 - Client acknowledge mode = do not delete or mark a row "sent" at dequeue; mark it 'sending' (claim with owner + timestamp) and only mark 'sent' after the provider confirms. PACE already moves rows left at 'sending' by a dead process to "Didn't send" at boot - that is the book's crash-before-ack case (issue 2); note the book's answer is redelivery, PACE's answer is deliberately NOT to redeliver an uncertain send (double-send is worse than a missed send) - correct for email since send is not idempotent.
 - LPS / ACID commit = acknowledge only after the DB write: write the sent-state and thread/message id in the same step as confirming the send, so a crash cannot leave a sent mail that is recorded as pending (issue 3). Record the provider message id as the idempotency key (my suggestion).
 - Workflow event pattern = PACE's failure classification (`recordSendFailure`, retry only temporary errors, bad merge fields refused with a 400, "Didn't send" with reason): delegate the failed row out of the main loop so one bad recipient never blocks the queue (the book's "do not stall the queue" point), auto-repair only deterministic things (the rules writer / validators), and route the rest to a human-visible queue (needs-you-today). The book's out-of-order caveat applies: a retried or repaired send must not overtake a later follow-up to the same lead (keep per-lead ordering, like the trading per-account queue).
 - Dead-letter / dashboard: every failed row needs an exit a person can see and resubmit - already in PACE's "every row has an exit" rule.
 - Responsiveness vs performance: returning "queued" instantly to the user and sending later is the right pattern for the UI; but be honest that queued != delivered (PACE's rule "never report an unsaved write as saved").
 - Request-reply: avoid blocking a web request waiting on a send/AI call; the AI provider already returns null rather than blocking.

# CH 15 - Space-Based Architecture Style (lines 1208-1912)
(Chapter 14 tail at 1198-1206 covered above. Figures 15-1..15-15 are images, missing; worked from prose. Hazelcast member-list log listings at ~1343-1401 are illustrative code, summarised.)

## 1. Core argument
Normal web apps scale as a triangle: web tier is easy to scale, app tier harder, database hardest, so the DB is the final limit on concurrent transactions. Space-based architecture (named for "tuple space": parallel processors sharing memory) removes the central database from the synchronous path: each processing unit holds the data it needs in a replicated in-memory data grid, and updates are sent asynchronously to the database through data pumps (persistent queues). Processing units start and stop dynamically, so the system handles extreme, variable and unpredictable load (ticketing, auctions). The cost: great complexity, eventual consistency, risk of data collisions and loss, very hard testing, and expensive caching products/infrastructure.

## 2. Concepts
**Components:** processing unit (application code + in-memory data grid + replication engine; small apps = one unit; large = split by functional area; may contain microservice-like services), virtualized middleware, data pumps, data writers, data readers.
**Virtualized middleware** (custom or third-party): messaging grid, data grid, processing grid (optional), deployment manager.
 - Messaging grid: receives requests and session state, picks an available processing unit (round-robin up to next-available tracking); typically a web server/load balancer (HAProxy, Nginx).
 - Data grid: the most crucial; usually implemented inside the processing units as a replicated cache (Hazelcast, Apache Ignite, Oracle Coherence); every unit must hold identical data because any unit can receive any request. Replication is async, usually under 100 ms. Units sharing the same named cache (e.g. "CustomerProfile") sync automatically; each knows others via a member list (IPs/ports) which updates as instances start/stop (Hazelcast logs illustrate sizes 1->2->3->2). A new instance loads the named cache from a running peer, so units can come and go without reading the DB if at least one instance holds the cache. A unit may hold many caches; it can also call another unit (choreography) or use the processing grid.
 - Processing grid (optional): mediates/orchestrates a request spanning several unit types (order unit + payment unit).
 - Deployment manager: watches response times/user load, starts and stops units; essential for elasticity.
**Data pumps:** always asynchronous, how updates reach the DB (eventual consistency). The unit that took the update owns sending it. Implemented with messaging (async, guaranteed delivery, FIFO order, decouples unit from data writer so units keep working when the writer is down). Usually one per domain/sub-domain or per cache type; have a contract (add/delete/update action + data; JSON/XML schema, object, or map message); updates usually carry only changed values (+ id).
**Data writers:** read pumps and update DB; implemented as services, applications or data hubs (Ab Initio). Two styles: domain-based writer (one writer for the whole customer domain listening to Profile, WishList, Wallet, Preferences pumps) vs dedicated writer per pump/processing unit (too many components but better scalability and agility).
**Data readers:** read DB and feed units via a reverse data pump; invoked only in three cases: all instances of a named cache crashed, all redeployed, or archive data not in the cache is needed. On cold start instances grab a lock; the first becomes temporary cache owner, requests data via queue, the reader queries and sends via the reverse pump, owner loads the cache, releases lock, the others sync.
**Data abstraction layer vs data access layer.** Writers + readers form one. Access layer = units coupled to table structures; abstraction layer = units decoupled through contracts, so cache schema can differ from DB tables; readers/writers contain transformation logic and buffer DB changes (column type changed, column/table dropped) until caches catch up. Space-based generally uses the abstraction model.
**Data collisions.** With active/active replicated caches, replication latency lets two instances update the same item and then overwrite each other with stale values. Example: blue widgets 500; A sets 490 (10 sold), B sets 495 (5 sold) during replication; end result A=495, B=490, correct is 485. Estimation formula (presented as): CollisionRate = N * (UR^2 / S) * RL, where N = instances sharing the cache, UR = update rate (per ms, squared), S = cache size in rows, RL = replication latency. Worked numbers: UR 20/s, N 5, S 50,000, RL 100 ms => 72,000 updates/hour, 14.4 collisions/hour (0.02%) -> replication viable. RL 1 ms => 0.1/hour (0.0002%). N 2 => 5.8/hour (0.008%). S 10,000 => 72/hour (0.1%). Collisions are proportional to instances, update rate squared and latency, inversely to cache size. Latency is rarely published, measure in production; 100 ms is the planning figure. Calculate minimum, normal and peak update rates rather than one average.
**Cloud versus on-premises.** Whole topology can run in cloud, on-prem, or split: processing units + middleware in elastic managed cloud while the physical database/data stay on-prem (async pumps + eventual consistency make this synchronisation workable); keeps reporting/analytics/data management local and secure.
**Replicated vs distributed caching.** Replicated (standard): each unit has its own in-memory grid kept in sync; very fast, no single point of failure (some products need an external controller). Not usable when caches exceed ~100 MB (memory per VM limits scale/elasticity) or update rates are too high for the replication engine. Distributed: central cache server/service accessed remotely; better consistency (one copy), but slower (network) and a fault-tolerance risk (cache down = all units down; mirroring risks inconsistency on failover). Table 15-1: Replicated: optimises performance, small (<100 MB), relatively static data, relatively low update frequency, high fault tolerance. Distributed: optimises consistency, large (>500 MB), highly dynamic data, high update rate, low fault tolerance. Use both in one system (inventory = distributed for consistency; customer profile = replicated for speed/fault tolerance); do not force one model.
**Near-cache.** Hybrid: a distributed full backing cache plus a smaller front cache in each unit with an eviction policy (most recently used, most frequently used, or random replacement when no analysis). Front caches stay in sync with the backing cache but NOT with each other, so units sharing context hold different data and behave inconsistently -> the book does NOT recommend near-cache for space-based.
**Implementation examples.** Suited to high spikes and >10,000 concurrent users. Concert ticketing: traffic jumps from hundreds to tens of thousands when sales open; limited seats, seat availability updated fast; a central DB cannot take that synchronous load; the deployment manager can pre-start units shortly before on-sale. Online auction: unpredictable bidders and concurrent bids; start/destroy units with load; a unit per auction keeps bidding data consistent; async pumps feed bid history, analytics, auditing with little latency.

**Star ratings (Figure 15-15 is an image; from prose).** Five stars: elasticity, scalability, performance (the driving characteristics; millions of concurrent users possible). Testability: 1 star (simulating huge scale is complex and costly; testing often done in production with real extreme load). Simplicity: low (very complicated: caching, eventual consistency, many moving parts). Cost: relatively expensive (caching licences, high resource use). Fault tolerance and others not stated in the prose (my recollection: moderate-to-high fault tolerance, low deployability/evolvability - unverifiable here, treat as unconfirmed). Partitioning: both domain and technical (processing units can act as domain services; but the cache / pump / writer / DB layering is technical). Quanta: varies; DB is not part of the quantum equation (no synchronous DB comms); quanta follow UI-to-processing-unit association; units communicating synchronously (incl. via processing grid) share a quantum.
**When to use:** extreme, variable, unpredictable concurrent load needing elasticity (ticketing, auctions, flash sales). **When not:** conventional relational/data-heavy, strongly consistent systems; small budget; small teams.

## 3. Pitfalls
- Assuming scaling web servers fixes the DB bottleneck (triangle topology).
- Replicated cache with large/high-update data; ignoring collision maths.
- Using near-cache.
- Losing data across the many moving parts (refer to Ch.14 techniques).
- Testing only at low scale.
- Cost surprise from caching licences / always-on capacity.

Tuple space; processing unit; virtualized middleware; messaging grid; data grid; processing grid; deployment manager; data pump / reverse data pump; data writer / reader; replicated vs distributed cache; near-cache (front/backing); member list; data collision; replication latency; data abstraction layer.

# CH 16 - Orchestration-Driven Service-Oriented Architecture (lines 1913-2118)

## 1. Core argument
A late-1990s/2000s enterprise style, born when compute, OS and DB licences were expensive, so the dominating value was reuse. It layered services by technical taxonomy (business, enterprise, application, infrastructure) tied together by a central orchestration engine/service bus. It is the most technically partitioned general-purpose architecture ever tried; it failed because reuse created enormous coupling, domain concepts were smeared across tiers, the central engine became a bureaucratic bottleneck, and the architecture combined the downsides of monolith and distributed systems. Its main legacy is the lessons: distributed transactions are hard and technical partitioning has practical limits; it motivated microservices.

## 2. Concepts
**History/philosophy.** Enterprises merging and growing fast; scarce, commercial computing; licensing wars between app-server and DB vendors; so architects were told to reuse as much as possible.
**Taxonomy (Fig 16-1).** Business services (top, entry points like ExecuteTrade/PlaceOrder; defined by business users with no code, only input/output/schema; test: "are we in the business of...?"). Enterprise services (fine-grained shared building blocks like CreateCustomer, CalculateQuote, built by a dedicated team aiming at the right granularity to be reusable forever - defeated by reality: markets, technology, practices change). Application services (one-off, single-application, e.g. geo-location nobody wants to make reusable; owned by an app team). Infrastructure services (monitoring, logging, authn/z; owned by a shared infrastructure/ops team).
**Orchestration engine.** The heart: stitches business services from enterprise services; handles transactional coordination, message transformation; integration hub for custom, packaged and legacy software; typically tied to one or few relational DBs so transactions are declared in the engine rather than the database. Conway's law: the integration team that owns it becomes a political force and a bottleneck. In practice a disaster: picking the right transaction granularity got ever harder.
**Message flow.** Everything, even internal calls, goes through the engine/service bus (example CreateQuote -> bus -> CreateCustomer + CalculateQuote -> application services).
**Reuse...and coupling.** Example: insurance divisions each have a notion of Customer; extract a canonical Customer service. Consequences: huge coupling - a change to Customer ripples everywhere, needing coordinated deployments and holistic testing; the shared Customer carries everyone's fields (driver's licence irrelevant to disability insurance); a domain concept like CatalogCheckout is ground to dust across tiers - adding an address line touches dozens of services across tiers plus one DB schema; if the transaction granularity is wrong you build a near-identical service - "so much for reuse".
**Ratings (Fig 16-5 image; from prose).** Technically partitioned. Single quantum (shared DB(s) plus the orchestration engine is a giant coupling point - no part can have different characteristics than the mediator). Deployability and testability: disastrous (1 star-ish; also not goals in that era). Elasticity and scalability: supported (vendors invested in session replication etc.), modest. Performance: extremely poor (each request split across so much architecture). Simplicity and cost: inverse of what architects want (complex and costly). Agile movement had barely started.
**When to use:** the book effectively gives none - historical/legacy; encountered in big enterprise integration estates.

## 3. Pitfalls
Reuse as primary goal; canonical enterprise-wide models (Customer); central orchestration/ESB owning all logic; technical partitioning to the extreme; declarative distributed transactions; a gatekeeper integration team.

## 4. Key terms
Business/enterprise/application/infrastructure service; orchestration engine; service bus; canonical representation; Conway's law; technical partitioning.

## 5. Quote
- "...this architecture manages to find the disadvantages of both monolithic and distributed architectures."

## 6. Relevance to PACE (my analysis)
A warning more than an option. PACE's own temptation to avoid: one canonical "Person" model for candidate + lead + contact + user + applicant. CLAUDE.md already keeps them apart (applicants never land in `candidates`; three email tables stay three) - that is the bounded-context lesson the book draws. Also: do not put workflow logic in a central engine that every feature must pass through; PACE's `index.js` being "the engine" is the closest analogue and is why ARCHITECTURE.md's one-home rules and territories matter. Heavy reuse (shared helpers) is fine only where the rule truly is one rule (e.g. submission-stages, outreach-dedup), not as a default goal.

# CH 17 - Microservices Architecture (lines 2119-2604)

## 1. Core argument
Microservices (named in Fowler and Lewis's March 2014 blog post) is the physical embodiment of domain-driven design's bounded context: each small, single-purpose service owns everything it needs - code, data schema, often its own database - and is coupled to nothing outside. Its guiding trade-off: it prefers duplication over coupling/reuse, the opposite of orchestration-driven SOA. This yields extreme scalability, elasticity, deployability, testability and evolvability, but at the cost of performance (network calls, per-endpoint security checks), operational complexity, loss of cross-service transactions and single source of truth. The key skill is finding the right service granularity (not too small), avoiding cross-service transactions, and choosing choreography vs orchestration deliberately.

## 2. Concepts
**History.** Most styles are named after the fact; microservices was named early. Inspired by DDD, especially bounded context (a decoupling style: internals coupled, nothing coupled outside). Reuse = coupling (First Law: everything is a trade-off); to get decoupling you favour duplication.
**Topology.** Services far smaller than other distributed styles; each includes everything to run independently, including its database.
**Distributed.** Each service in its own process (once physical machine, now VM/container). Solves shared multi-tenant infrastructure problems (resource contention, poor isolation among apps on a shared application server). Enabled by open-source OSes, automated provisioning, cloud and containers. Negative: performance (network calls slower than method calls; security verification per endpoint). Experts advise against transactions across service boundaries, so granularity is the key to success.
**Bounded context.** Each service models a domain or workflow; prefer duplicating a shared class like Address to coupling. Domain partitioning taken to the extreme.
**Granularity.** Common mistake: too small, so services need chatty links to do useful work. "Microservice" is a label not a description (Fowler); it was chosen against SOA's "gigantic services". Guidelines for boundaries: (a) Purpose - each service functionally cohesive, one significant behaviour; (b) Transactions - entities that must change together in a transaction suggest the boundary (avoid transactions across services); (c) Choreography - if services with great isolation need extensive communication to function, consider bundling them back into one larger service. Iteration is the only way to good granularity.
**Data isolation.** No shared schemas/databases as integration points. Beware the entity trap (a service per DB entity). Lose the single relational source of truth: either one domain is the source of truth for a fact and others ask it, or use replication/caching. Upside: each service picks the best data tool (cost, type) and can change it without affecting other teams.
**API layer.** Optional (proxy, naming/service discovery, operational hooks). Must NOT be a mediator/orchestrator: all interesting logic belongs inside a bounded context; mediators belong to technically partitioned styles.
**Operational reuse and sidecar.** Split domain from operational concerns: duplicate domain, couple operations (monitoring, logging, circuit breakers). Sidecar pattern: common operational component deployed with each service, owned by a shared infrastructure team; upgrading the sidecar upgrades everyone. Connect sidecars via a service plane into a service mesh = a console for global control of monitoring/logging levels. Service discovery builds elasticity (requests go via a discovery tool that tracks request volume and spins up instances); often part of the mesh/API layer.
**Frontends.** Original vision included the UI in the bounded context. Two common styles: monolithic frontend calling through the API layer (rich desktop/mobile/web app, e.g. a JS framework), or microfrontends - each service emits its UI component and the frontend assembles them, giving a team ownership from UI to backend (via component frameworks like React or microfrontend frameworks).
**Communication.** Protocol-aware heterogeneous interoperability: no central integration hub, so services know how to call each other (standardised REST level, message queues...); heterogeneous = polyglot stacks allowed; interoperability = services call over the network. Enforced heterogeneity story: a startup architect forced each team to use a different tech stack so they could not accidentally share classes - contrasting with enterprise standardisation; the goal is the right-scale technology for the narrow problem, not maximum complexity. Async uses events/messages i.e. EDA internally: broker pattern = choreography, mediator = orchestration.
**Choreography and orchestration.** Domain/architecture isomorphism: the shape of the architecture maps to the shape of the problem; microservices (decoupling) resembles broker EDA, so they are symbiotic. Choreography: no mediator, services call each other (e.g. CustomerWishList calls CustomerDemographics for missing data). Orchestration: build a localised mediator service for a coordination (e.g. ReportCustomerInformation calls others). Trade-off: choreography keeps decoupling but error handling and coordination get harder; for complex workflows the first service becomes a mediator by default ("front controller pattern" - added complexity); a dedicated orchestrator concentrates coordination in one service and leaves others less affected but adds coupling. Domain workflows are often inherently coupled; the architect's job is to represent that coupling well.
**Transactions and sagas.** Cross-service transactions violate decoupling and create connascence of value. Advice: "don't! Fix the granularity instead"; transaction boundaries are an indicator of granularity. Exceptions (services needing very different characteristics but still transactional): saga pattern - a mediator service calls each part, records success/failure, coordinates results; on a failure it sends compensating requests to previously successful parts to undo (compensating transaction framework). Implementations: each request enters a pending state until overall success (complex with async, new requests contingent on pending state, lots of network traffic); or each operation has do and undo (undo is much harder than do, more than doubling design/implementation/debugging). Use sparingly: "a few transactions across services is sometimes necessary; if it's the dominant feature of the architecture, mistakes were made".
**Ratings (Figure 17-13 image; prose-supported).** Extremes on the scale. High: scalability, elasticity, evolutionary (some of the most scalable systems built this way), modern engineering practices - automated deployment, testability (not listed in the chart text; depends on DevOps). Fault tolerance/reliability high for independent single-purpose services, but harmed by too much inter-service communication; mitigated by redundancy and discovery. Performance is poor-ish (network calls, per-endpoint security; mitigate with caching/replication; one reason for choreography over orchestration). Domain partitioned; the most distinct quanta of any modern style (exemplifies the quantum measure). My recollection of the chart (not in the text; verify against the book figure): scalability 5, elasticity 5, evolutionary 5, deployability 5, testability 5, fault tolerance 4, performance 2, simplicity 1, cost 1.
**Additional references:** Building Microservices (Newman); Microservices vs. Service-Oriented Architecture and Microservices AntiPatterns and Pitfalls (Richards).
**When to use** (implied): need independent scale/deploy/evolve per domain, large organisation with several teams, mature DevOps, different characteristics per service. **Avoid** when domain is highly semantically coupled (multi-page forms depending on earlier pages - Ch. 18), team/DevOps immature, or transactions dominate.

## 3. Pitfalls
- Services too fine-grained / "microservice" taken as commandment / entity trap.
- Chatty services needing constant communication.
- Transactions across services; saga as dominant feature.
- API layer used as orchestrator.
- Shared database or schema as integration point.
- Choreography with no coordinator for complex flows (hidden front controller).
- Sharing classes across services (coupling).
- Expecting the performance of a monolith.

## 4. Key terms
Bounded context; domain-driven design; entity trap; sidecar; service plane; service mesh; service discovery; microfrontends; protocol-aware heterogeneous interoperability; choreography; orchestration; front controller pattern; saga; compensating transaction; connascence of value; domain/architecture isomorphism.

## 5. Quotes
- "The term 'microservice' is a label, not a description." (Fowler, quoted)
- "Don't do transactions in microservices - fix granularity instead!"
- "A few transactions across services is sometimes necessary; if it's the dominant feature of the architecture, mistakes were made!"

## 6. Relevance to PACE (my analysis)
Microservices is wrong for PACE today (solo owner + AI builder, free tier, no DevOps team, tightly coupled domain: lead -> candidate -> submission -> email -> reply intelligence). The book's own list of fit conditions fails. What PACE should borrow is the mindset, which it already follows: bounded contexts inside the monolith (territories, models/, three email pipelines kept separate, applicants vs candidates), "duplication over coupling" where domains differ, and "transaction boundaries indicate granularity" (a Postgres transaction across candidate+submission+activity is fine because it stays in one service). Trigger signals to even consider extracting a service: (1) a component with genuinely different operational characteristics (the bulk email/sweep engine vs interactive UI; the resume parser/AI worker that is CPU- or latency-heavy), (2) separate team ownership, (3) separate scaling or deploy cadence causing release risk to the rest, (4) a customer demanding data/infra isolation (per-tenant dedicated deployments). Even then the book would say extract one coarse service (service-based), not many. Also: every customer bringing its own keys (D-0055) is a sidecar-like cross-cutting concern - keep it in one home (provider-neutral layer), not duplicated across modules.

# CH 18 - Choosing the Appropriate Architecture Style (lines 2605-2917)
(Slice ends at line ~2917 with the end of the GGG case study; nothing garbled. No summary table of all styles is in this slice - the chapter has none in the text provided; the book's per-style star charts are images.)

## 1. Core argument
There is no universal answer ("it depends"): the choice culminates analysis of architecture characteristics, domain, data, organisation, process and trade-offs. Architecture fashion shifts for identifiable reasons, and architects should know the trends, then decide when to follow or deviate. The decision starts from understanding the domain, the characteristics that shape structure, data architecture, organisational factors, team/process maturity, and domain/architecture isomorphism; it resolves into three determinations (monolith vs distributed; where data lives; sync vs async communication) and yields a topology, ADRs and fitness functions. Two case studies (Silicon Sandwiches monolith; Going, Going, Gone distributed) show the reasoning.

## 2. Concepts
**Shifting fashion.** Drivers: observations from the past (new styles fix pain points of old ones, e.g. rethinking reuse); ecosystem changes (Kubernetes unknown a few years earlier, may be replaced); new capabilities (containers/Docker changed paradigms - look for nuance, not just "one more of what we have"); acceleration (rate of change rising); domain changes (business evolution, mergers); technology changes; external factors (licensing cost forcing migration).
**Decision criteria - things to be comfortable with:** the domain (good general understanding, especially what affects operational characteristics); architecture characteristics that impact structure; data architecture (collaborate with DBAs; interplay with existing data); organisational factors (cloud vendor cost, planned mergers and acquisitions favouring open/integration architectures); knowledge of process, teams, operations (Agile maturity, ops interaction, QA - styles that depend on practices you lack will hurt); domain/architecture isomorphism (microkernel for customizability via plug-ins; space-based for genome analysis with many discrete operations; poor matches: highly scalable systems on big coupled monoliths; a highly semantically coupled domain such as an insurance app of multipage forms each depending on earlier pages is poor for microservices, better for less-decoupled service-based).
**Determinations:**
 1. Monolith vs distributed - via quanta: one set of characteristics suffices => monolith (other factors may still push distributed); differing characteristics => distributed.
 2. Where should data live - monolith: one or few relational DBs; distributed: which services persist data and how data flows for workflows; iterate on structure and behaviour.
 3. Sync vs async - sync is convenient and has fewer design/implementation/debugging problems; async gives performance/scale but brings data synchronisation, deadlocks, race conditions, debugging pain. Rule: "Use synchronous by default, asynchronous when necessary."
 Output: architecture topology, ADRs for the hardest decisions, and fitness functions protecting key principles and operational characteristics.
**Monolith case study: Silicon Sandwiches** (small, no big budget, single quantum). Modular monolith: domain-centric components, single relational DB, single web UI (mobile-friendly) to hold cost down; if resources allow, separate tables and DB assets by domain component so a later migration to distributed is easier. Customization is not inherent, so design an Override endpoint and require each domain component to reference it for customizable characteristics - a perfect fitness function. Microkernel alternative (domain/architecture isomorphism with customizability): core = domain components + one relational DB (synchronised domains/data for future migration); customizations as plug-ins (common set with own DB, local ones with their own data, decoupled); the API layer uses Backends for Frontends (BFF) - thin microkernel adaptors translate generic backend output into device-specific form (e.g. iOS format, pagination, latency); eases supporting future devices. Communication in either design can be synchronous (no extreme performance/elasticity, short operations).
**Distributed case study: Going, Going, Gone (auction).** Different parts need different characteristics (auctioneer vs bidder availability/scalability); ambitious scale, elasticity, performance. Candidates: low-level event-driven or microservices; microservices chosen because it better supports differing operational characteristics per piece (pure EDA partitions by communication style not by operational needs). Performance is the challenge; mitigate by designing around the weak points (too much orchestration, too aggressive data separation). Design: UIs - Bidder, Auctioneer, Streamer (read-only stream allows optimisation). Services: BidCapture (captures bids, asynchronously forwards to BidTracker, no persistence - a conduit); BidStreamer (high-performance read-only stream back to bidders); BidTracker (unifies auctioneer and online bid streams, ordering them as close to real time as possible; both inbound links async so queues buffer different rates); Auctioneer Capture (separate from Bid Capture because quanta analysis found different characteristics); Auction Session (workflow of individual auctions); Payment (third-party provider after the auction); Video Capture; Video Streamer. Async mainly to accommodate different operational characteristics: e.g. if Payment can do one payment per 500 ms and many auctions end together, sync calls time out; message queues add reliability to a fragile part. Result: five quanta (Payment, Auctioneer, Bidder, Bidder Streams, Bid Tracker). Authors: not the "correct" design, just the "least worst set of trade-offs"; microservices plus intelligent events/messages gives a foundation for expansion.

## 3. Pitfalls
- Following fashion without context; picking a style before knowing characteristics and quanta.
- Ignoring team/process maturity.
- Defaulting to async everywhere.
- Mismatched domain/architecture (high semantic coupling in microservices).
- Skipping ADRs and fitness functions.

## 4. Key terms
Architecture fashion; domain/architecture isomorphism; quantum; modular monolith; microkernel; plug-in; BFF (Backends for Frontends); ADR; fitness function; "least worst" trade-off.

## 5. Quotes
- "Use synchronous by default, asynchronous when necessary."
- "It depends!" (opening)
- (paraphrase of the closing) not the best design, only the one with the least worst trade-offs.

## 6. Relevance to PACE (my analysis)
Run PACE through the chapter: (1) one quantum? Mostly yes - same availability/security profile across ATS, leads, outreach, so a monolith fits; the only candidate for a different quantum is the bulk email/sweep engine and public candidate-facing pages (/apply, /i), which have different availability and burst needs. (2) Data: one Postgres with RLS and org_id; keep it, and keep the domain-aligned table partition (models/tables.js) - this is exactly the book's "separate tables by domain component so migration is easier". (3) Sync by default, async only where necessary: PACE does this already (HTTP sync for user actions, queue/timers for sends and sweeps). Use the book's explicit modular monolith as PACE's target pattern; the microkernel angle matches "per-org configuration/plug-in" demands (per-customer templates, providers, roles) - customizability could be modelled as per-org config/plug-ins (provider-neutral contact-data layer, per-org mail identity) rather than forks. Add fitness functions (PACE's smoke tests are already these: route shadowing, admin-numbers, tenant scoping) and write ADRs (DECISIONS.md is that). Decision triggers table (mine): move to service-based when (a) sweep/send jobs hurt interactive latency or exceed one free-tier instance, (b) deploy risk of email engine blocks ATS releases, (c) a second team/owner appears, (d) enterprise customer needs isolation; consider a real queue when multiple instances must share send work; never go microservices/space-based without a team and budget.
