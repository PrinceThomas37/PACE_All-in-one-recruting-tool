# A Philosophy of Software Design (2nd ed., Ousterhout) - Chapters 8-13 notes

## Chapter 8 - Pull Complexity Downwards
1. **Core argument.** When a module faces unavoidable complexity, the module's developer should absorb it rather than push it to users. Modules have more users than developers, so a simple interface matters more than a simple implementation. Throwing an exception or adding a config knob is the easy way out for the developer and multiplies the burden across every caller or administrator. The tool for this is giving the module a richer, more complete job.
2. **Rules / principles.**
   1. Prefer a simple interface over a simple implementation; take extra suffering on yourself to spare users. Example: a line-oriented editor text class is easy to build but forces the UI to split and join lines; a character/range-oriented interface keeps that inside the class.
   2. Avoid configuration parameters. Each is a way of moving complexity up to every admin of every install. Before exporting one ask "can users determine a better value than we can here?" Example: a transport protocol can measure response times and derive the retry interval itself, adapting dynamically, whereas a configured value goes stale.
   3. When a parameter is truly needed, give a sensible default so users only set it in exceptional cases. Each module should solve its problem completely.
   4. Pulling down is justified only if (a) the complexity is closely related to the class's existing function, (b) it simplifies the rest of the app, (c) it simplifies the class's interface.
3. **Caveats.** Can be overdone (pulling the whole app into one class). Counter-example: putting a backspace-key method in the text class leaked UI knowledge into it without really simplifying callers. Config parameters are legitimate where users genuinely know more (e.g. request priority).
4. **Key terms.** Pull complexity downward: handle it inside the module. Configuration parameter: a knob that exports a policy decision to users.
5. **Quotes.** "it is more important for a module to have a simple interface than a simple implementation." / "look for opportunities to take a little bit of extra suffering upon yourself in order to reduce the suffering of your users."
6. **Clean Code.** Not named in this chapter.
7. **Web SaaS applicability.** Strongly: prefer computed/sane defaults in the service layer over per-customer settings and over letting every route handler cope with the same condition. (Tension to note for the owner's team: a rule that every customer limit be an admin setting pushes complexity up; this chapter says be sparing and default well.)

## Chapter 9 - Better Together Or Better Apart?
1. **Core argument.** Whether to combine or split code is decided by whether it reduces total complexity, not by size. Splitting adds interfaces, management code, separation (flipping between files) and duplication. Things that share information, are always used together, overlap conceptually, or can't be understood alone belong together; unrelated or general-vs-special things belong apart. The same logic applies to methods: length alone is rarely a reason to split; depth is what matters.
2. **Rules.**
   1. Bring together if information is shared. Example: HTTP request reading and parsing in two classes both needed knowledge of the format; merged, the code got shorter.
   2. Bring together if it simplifies the interface (interfaces between the pieces vanish; defaults can be automatic). Example: Java FileInputStream plus BufferedInputStream; buffering should be default and hidden.
   3. Bring together to eliminate duplication, via a helper method (best for long snippets with a simple signature) or by restructuring so the snippet runs in one place (e.g. goto to one cleanup/log point in C-like code). One or two line repeats are not worth extracting; complex environment access makes a poor signature.
   4. Separate general-purpose from special-purpose code: a general mechanism should not contain use-specific code; put the specialisation in the module for that use. Example: text class stays general; "delete selection" lives in the UI.
   5. Selection and insertion cursor looked related but combining them was worse: callers still treated them separately, and the implementation needed a boolean to say which end was the cursor. Separate objects built from a general Position class were simpler.
   6. Do not split off shallow, single-use helper classes that are tightly coupled to their call site. Example: a NetworkErrorLogger class with one-line methods each called once; inlining the log statements was better.
   7. Methods: don't split on length alone ("split anything over 20 lines" is wrong). A long method with a simple signature that reads easily is deep and fine. Split only if cleaner abstractions result: (b) extract a cleanly separable, ideally general-purpose subtask (reader of the child needn't know the parent and vice versa), or (c) divide a method doing unrelated things into separate methods each callable alone with simpler interfaces. Avoid splits where callers must call both or pass state between them (shallow methods). Joining methods can also help (replace two shallow with one deep, remove duplication, intermediate data, dependencies).
   8. Each method should do one thing completely, with a simple interface.
   - **RED FLAG: Repetition** - same or near-same code over and over means the right abstraction is missing.
   - **RED FLAG: Special-General Mixture** - a general mechanism also holding code specialised for one use; causes leakage and coupled changes.
   - **RED FLAG: Conjoined Methods** - you cannot understand one method without reading another (or two physically separate pieces each only understood via the other).
3. **Caveats.** Bidirectional "used together" is the only compelling form (a block cache uses a hash table, but hash tables are used everywhere, so separate). Goto is normally bad but acceptable for escaping nested code to shared cleanup. Subdividing is good when pieces are truly independent.
4. **Key terms.** Deep method: much functionality behind a simple interface. Shallow method: little functionality, interface nearly as complex. Conjoined methods: split pieces that can't be understood separately.
5. **Quotes.** "Depth is more important than length: first make functions deep, then try to make them short enough to be easily read." / "length by itself is rarely a good reason for splitting up a method."
6. **Clean Code.** Section 9.8 names Robert Martin directly. Martin: functions should be tiny, blocks one line (a function call), indent level one or two, even 10 lines is too long. Ousterhout agrees shorter is generally easier, but past a few dozen lines further shrinking barely helps readability; too-small functions become conjoined, add interfaces to learn, and hide how pieces cooperate. He says keep the larger function when the related code belongs together. Direct disagreement.
7. **Web SaaS applicability.** Directly relevant to route handlers and services in Express: do not shred a 100-line handler into many tiny one-use helpers; do extract genuinely reusable, self-contained steps. Keep one home for each rule (shared-information principle) and keep generic mechanisms free of customer-specific logic.

## Chapter 10 - Define Errors Out Of Existence
1. **Core argument.** Exception handling is a disproportionate source of complexity: it is hard to write, creates secondary errors, is verbose, hard to test, and rarely runs (so often broken). Programmers add too many exceptions in an over-defensive style. The fix is to reduce the number of places exceptions must be handled: define the error away, mask it low down, aggregate handlers, or just crash. Expose an exception only if callers truly need it.
2. **Rules / techniques.**
   1. Exceptions are part of the interface; a class with many is shallow. Throwing is easy, handling is hard. Don't punt a hard case to callers: if you don't know what to do, they probably don't either.
   2. **Define errors out of existence.** Redefine semantics so the normal behaviour covers the case. Examples: Tcl `unset` should ensure a variable does not exist (no error if absent) rather than delete it; Unix file delete succeeds while the file is open (name removed, data lives until last close) versus Windows refusing; Java `substring` should return the overlapping characters for out-of-range indices (as Python slices do), turning 5-10 lines of clamping into one call. Likewise the Buffer.copy in ch13 returns fewer bytes instead of erroring.
   3. Answer to "won't that hide bugs?": errors add complexity which causes other bugs; the best way to reduce bugs is to make software simpler.
   4. **Mask exceptions.** Handle at a low level so higher layers never see it. Examples: TCP resending lost packets; NFS retrying forever and hanging (controversial) rather than raising errors that every app would have to handle or collapse on. Masking is pulling complexity downward and gives deeper classes.
   5. **Aggregate exceptions.** One handler for many exceptions, placed high so many propagate to it (opposite placement from masking). Example: web server getParameter missing-parameter errors caught once in the top-level dispatcher, with the error message carried in the exception; new error kinds plug in by sharing a base type. General pattern: an exception that aborts the current request, cleans up and moves to the next, caught in one place in the request loop, distinct from system-fatal errors.
   6. Promote small errors into large ones to reuse one recovery path. Example: RAMCloud crashes a server on a corrupted object so the existing crash-recovery code handles it (and gets exercised more); not sensible for frequent errors.
   7. **Just crash** for errors that are rare and unrecoverable: out of memory (a wrapper ckalloc that aborts), unrecoverable I/O or socket errors, internal inconsistency. Abort with a clear diagnostic.
3. **Caveats.** Don't define away information callers need: a student network module that swallowed all network errors made robust apps impossible. Crashing is wrong for replicated storage that must recover from I/O errors. Aggregation is for per-request handling, not fatal errors. Promotion is bad for frequent errors. Hide the unimportant, expose the important.
4. **Key terms.** Exception: any uncommon condition altering normal flow (not just the language mechanism; includes special return values). Masking: handle it in a low layer. Aggregation: one handler for many. Error promotion: escalate small failures to a bigger existing recovery.
5. **Quotes.** "Throwing exceptions is easy; handling them is hard." / "Overall, the best way to reduce bugs is to make software simpler." / "code that hasn't been executed doesn't work".
6. **Clean Code.** Not named. (Martin advocates exceptions over error codes; this chapter instead wants fewer exceptions overall. Implied tension only; the author does not say so.)
7. **Web SaaS applicability.** Very direct: one Express error-handling middleware that turns a typed "abort this request" error into a response; idempotent deletes/upserts (delete of something already gone succeeds); crash-and-restart for truly unrecoverable boot errors; mask transient retries in a single HTTP client layer, but never swallow errors callers must see (e.g. an uncertain email send).

## Chapter 11 - Design it Twice
1. **Core argument.** First ideas are rarely best for hard design problems, so sketch at least two radically different designs for each major decision, list pros and cons, and pick or combine. It costs little (an hour or two for a class) against days or weeks of implementation, and it also trains your design judgement.
2. **Rules.**
   1. Consider multiple options per major decision, as different from each other as possible; even if you "know" the answer, force a second one and study the weaknesses of the bad one.
   2. Compare on: ease of use for higher-level code (most important for interfaces), simplicity of interface, generality, efficiency of implementation. Example: line vs character vs string/range-oriented text interfaces.
   3. The best may be a combination, or a new design driven by the problems you found. Example: both line and character APIs force callers to do extra text manipulation (a red flag that the text class isn't doing all the text work), leading to a range-oriented API.
   4. Apply at many levels: interface first, then implementation (linked list of lines, fixed blocks, gap buffer; goals differ: simplicity and performance), UI features, system decomposition.
   5. Beware the "smart people get it right first time" belief; the problems are simply hard.
3. **Caveats.** Needs only sketches of key methods, not full designs; no explicit exception beyond scaling time to module size.
4. **Key terms.** Design it twice: compare multiple radically different designs before committing.
5. **Quotes.** "no-one is good enough to get it right with their first try." (large systems) / "It isn't that you aren't smart; it's that the problems are really hard!"
6. **Clean Code.** Not named.
7. **Web SaaS applicability.** Good for schema, API shape and module boundaries (cheap to sketch, costly to migrate); worth a short written comparison before a migration or public API.

## Chapter 12 - Why Write Comments? The Four Excuses
1. **Core argument.** Comments capture design information that code cannot express, are what make abstractions possible (without them the only abstraction is the bare signature), and writing them improves design. The four common excuses all fail. Good comments reduce cognitive load and unknown unknowns and clarify dependencies and obscurity.
2. **Excuses and rebuttals.**
   1. "Good code is self-documenting": a myth. Signatures hold only a sliver of an interface; rationale, meaning of results, and when to call something are informal. Expecting readers to read bodies pushes you to many small shallow methods and exposes all complexity, so no abstraction. Example: a substring method's signature can't say whether end is inclusive or what start > end does.
   2. "No time": investment mindset; typing code is perhaps 10% of dev time, so even doubling it adds about 10%. Interface comments written during design pay back immediately.
   3. "Comments go stale": keep docs close to code and avoid duplication (ch16); code review catches stale comments; big doc edits only follow big code changes.
   4. "Existing comments are worthless": the most valid excuse, but solvable by learning to write good ones (ch13).
   - Benefits: faster, more accurate changes by future developers (including yourself after a few weeks); helps with cognitive load and unknown unknowns (not change amplification).
3. **Caveats.** Good design reduces the need for comments, particularly inside method bodies.
4. **Key terms.** Abstraction: simplified view preserving essential information. Cognitive load, unknown unknowns, change amplification (from ch2). Obscurity.
5. **Quotes.** "Without comments, you can't hide complexity" (paraphrase of: documentation plays an important role in abstraction; without comments, you can't hide complexity). / "Well-written comments are not failures."
6. **Clean Code.** Section 12.6 names Martin: comments are "at best a necessary evil" and "always failures" compensating for inexpressive code, replace with well-named extracted functions. Ousterhout disagrees: comments carry different information than code, make reading the code unnecessary, and Martin's approach yields cryptic long names that retype documentation at every call and breeds a bad attitude where good designers are criticised for having comments. Agrees that good design reduces the need for comments, especially in method bodies.
7. **Web SaaS applicability.** Argues for interface comments on service functions and API routes (units, nullability, side effects, errors) rather than relying on names; fits a team where non-authors must maintain code.

## Chapter 13 - Comments Should Describe Things that Aren't Obvious from the Code
1. **Core argument.** The guiding rule: comment what is not obvious to a first-time reader, at a different level of detail than the code, either lower (precision) or higher (intuition/abstraction). Interface comments let people use a module without reading its code and must not leak implementation. Implementation comments say what and why, not how. Cross-module decisions need a findable home.
2. **Rules.**
   1. Pick conventions (use Javadoc/Doxygen/godoc style if available); they give consistency and make you actually write comments. Categories: interface, data-structure member, implementation, cross-module. Every class, class variable and method should have an interface comment; commenting everything is easier than deciding case by case.
   2. Don't repeat the code: ask if someone who had never seen the code could write the comment from the adjacent code; if so it's worthless. Examples: line-by-line "Get pointer copy" comments; "Add a horizontal scroll bar".
      - **RED FLAG: Comment Repeats Code** - the comment is obvious from the adjacent code, e.g. reuses the words of the name. Use different words that add information (units, which sides) - e.g. padding "in pixels, on left and right".
   3. Lower-level comments add precision: units, inclusive/exclusive bounds, meaning of null, who frees/closes a resource, invariants. Vague words like "current" or "width" mislead. Rename (width to length) and document missing-entry meaning. Describe variables as nouns (what it represents), not verbs (how it's toggled). Example: heartbeat flag documented by meaning rather than the places that set it.
   4. Higher-level comments add intuition: say what the code is trying to do and why it is reached ("how we get here"), not restate the conditions. Example: "try to append the key hash to an existing unsent RPC" beats a paraphrase of the loop's conditions. Harder to write; requires stepping back to the essential idea.
   5. Interface documentation defines abstractions. Separate interface from implementation comments; if the interface comment must describe the implementation, the thing is shallow. Class comment: what each instance represents, capabilities, limitations (e.g. single-threaded). Method comment: caller-visible behaviour, each argument (constraints, dependencies), return value, side effects, exceptions, preconditions. Example: Buffer.copy documents the short-copy and zero-overlap cases (errors defined away). IndexLookup exercise: users need the comparison function (and maybe concurrency for performance) but not message formats, server data structures, RPC names, private config constants, or crash recovery that is invisible.
      - **RED FLAG: Implementation Documentation Contaminates Interface** - interface comments describing internals not needed to use the thing. Move such text inside the method. Also explain what "ready" really means and what the caller must do (e.g. must be invoked for progress).
   6. Implementation comments: explain what and why. Label major blocks ("Phase 1: ..."), describe each iteration of complex loops abstractly, explain non-obvious reasons (bug fixes, may cite a bug ticket id instead of copying details). Most short methods need none; comment only long-lived local variables.
   7. Cross-module decisions: they cause many bugs; put the note where developers will necessarily look (e.g. a comment in the Status enum listing the 7 other files to update), or keep a central designNotes file with named sections and short "See X in designNotes" pointers in the code. Downside: central doc is far from the code and may go stale.
   8. "Obvious" is judged from a first-time reader's view; if a reviewer says it's not obvious, accept it and fix with comments or code.
3. **Caveats.** Getters/setters occasionally need no comment (rare). Loop comments only for long or complex loops. Class-level usage examples are optional but helpful for deep classes. Cross-module docs are rare and hard to keep current.
4. **Key terms.** Interface comment, data-structure member comment, implementation comment, cross-module comment; side effect (consequence affecting future behaviour but not the result); precondition; invariant.
5. **Quotes.** "comments should describe things that aren't obvious from the code." / "if a reader thinks it's not obvious, then it's not obvious."
6. **Clean Code.** Not named in this chapter; consistent with the chapter-12 stance (comments carry information code cannot).
7. **Web SaaS applicability.** Highly applicable: document units, nullability, tenant-scoping, idempotency and side effects on service functions and routes; use a designNotes-style central file with pointers for rules that span modules (e.g. a business rule enforced in route, job and UI).
