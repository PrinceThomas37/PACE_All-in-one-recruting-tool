## Chapter 1 - Introduction (It's All About Complexity)
1. **Core argument.** Software is limited only by our ability to understand it, so the biggest enemy is complexity, which accrues inevitably as features and people are added. Tools help but are not enough; the systems themselves must be made simpler. Two attacks: make code simpler and more obvious (remove special cases, use names consistently), and encapsulate complexity via modular design so a programmer need not hold it all at once. Waterfall fails for software because you cannot foresee a large design; incremental/agile development works because software is malleable, which means design is never done and continuous redesign is expected.
2. **Rules/recommendations.**
 1. Think about complexity all the time; it is the guide for every design choice. (Reason: it is the main limit on building bigger systems cheaply.)
 2. Design continuously, not up-front; budget some fraction of time for design improvement. (Reason: first designs are almost never the best; waterfall causes patching and "an explosion of complexity".)
 3. Learn to spot **red flags** (signs code is more complicated than needed); when you see one, stop and try alternative designs, and keep trying several before settling. Use code review to practise, since others' design problems are easier to see than your own.
 4. Use moderation: every principle has limits; chapters have "Taking it too far" sections.
 No named Red Flag in this chapter.
3. **Caveats.** Book is not sufficient alone (examples too small); examples are Java/C++ but ideas apply to functions, subsystems, network services. No simple recipe exists; the concepts are for comparing alternatives.
4. **Key terms.** Complexity (see ch 2); modular design (split into relatively independent modules); waterfall (phases frozen in sequence); red flag (symptom of avoidable complexity).
5. **Quotes.** "Incremental development means that software design is never done."
6. **Clean Code.** Not named here.
7. **Web SaaS?** Very applicable; the incremental-design and "plan on redesign time" stance fits a product that grows feature by feature.

## Chapter 2 - The Nature of Complexity
1. **Core argument.** Complexity is anything in a system's structure that makes it hard to understand and modify, judged by the developer experience, not by size or sophistication. It is weighted by how often a part is touched, so hidden-away complexity matters little. It shows up as three symptoms and has two causes, dependencies and obscurity, and it accumulates through many small lapses rather than one big error, so it needs a zero-tolerance attitude.
2. **Rules/principles.**
 1. Definition: complexity = structure that makes the system hard to understand and modify; equivalently cost/benefit of change. Simple = easy to understand and modify. A large system that is easy to work on is not complex; a small one can be.
 2. Overall complexity is the sum of each part's complexity weighted by the time developers spend in it. So isolating complexity where nobody looks is nearly as good as removing it.
 3. Complexity is more apparent to readers than writers: if others find your code complex, it is complex. Probe the disagreement.
 4. Three symptoms: **Change amplification** (a simple change needs edits in many places; example: banner colour hard-coded per web page vs one shared variable). **Cognitive load** (how much you must know; example: a C function returns allocated memory and expects the caller to free it; fewer lines of code is not necessarily simpler, e.g. a framework with tiny apps but hard-to-discover lines). **Unknown unknowns** (not obvious what must change or what you must know; example: darker "emphasis" colour derived from the banner colour but written separately in some pages, so changing the central variable silently breaks them). Unknown unknowns are the worst, since you cannot even find what to look for.
 5. Goal: an **obvious** system, where a developer can make a quick guess and be confident it is right.
 6. Two causes: **dependencies** (code that cannot be understood/changed in isolation; e.g. method signatures, network protocol sender/receiver) and **obscurity** (important information not obvious; vague names like "time", undocumented units, a hidden message table that needs a new entry for each new error status, inconsistent reuse of a name). Dependencies cannot be eliminated; reduce their number and make the remaining ones simple and obvious (the shared colour variable replaced hidden page-to-page coupling with one findable API dependency).
 7. Needing lots of documentation is itself a red flag that the design is off; simplifying the design is the best cure for obscurity.
 8. Complexity is incremental ("death by a thousand cuts"); adopt zero tolerance, because once built up it is hard to remove.
 No named Red Flag box in this chapter (the "lots of documentation needed" remark is red-flag-like but unlabeled).
3. **Caveats.** Dependencies are intentionally introduced (every new class creates some); the aim is fewer and clearer, not zero.
4. **Key terms.** Change amplification; cognitive load; unknown unknowns; dependency; obscurity; obvious.
5. **Quotes.** "Complexity is anything related to the structure of a software system that makes it hard to understand and modify the system." / "Of the three manifestations of complexity, unknown unknowns are the worst."
6. **Clean Code.** Not named. Implicit tension: line-count/shortness is not a measure of simplicity here.
7. **Web SaaS?** Directly: the colour-variable example maps to any business rule (e.g. a limit or label) duplicated across routes and UI; "single home for a rule" fights change amplification and unknown unknowns.

## Chapter 3 - Working Code Isn't Enough (Strategic vs Tactical)
1. **Core argument.** A tactical mindset (get the feature working fast, accept small kludges) produces accumulating complexity and eventual slowdown. A strategic mindset treats good design as the primary goal (code must of course work) and invests continually in it. The investment is about 10-20% of development time, pays back in the author's opinion in roughly 6-18 months, and is a trap to postpone even in startups.
2. **Rules/principles.**
 1. Working code is not enough; the primary goal is a great design that also works, since most future code extends existing code.
 2. Beware the **tactical tornado**: a prolific, fast, shortcut-taking programmer whom management treats as a hero while others clean up the wreckage and look slower.
 3. Invest proactively (try two or three designs for each new class and pick the cleanest; imagine likely future changes; write good documentation) and reactively (when a design problem surfaces, fix it rather than patch around it).
 4. Invest small amounts continually, about 10-20% of time; do not try a big up-front design (that is waterfall).
 5. Technical debt: tactical programming borrows time from the future, and unlike financial debt most is never fully repaid.
 6. Do the cleanup today, not after the next crunch ("slippery slope"); delays become permanent, problems grow, and the culture slides tactical.
 7. Startups should not use pressure as an excuse: spaghetti code is nearly impossible to fix later, the payoff of good design comes fast, and the best engineers (cheap relative to productivity) care about design and will avoid a wrecked code base. Examples: Facebook's early "Move fast and break things" (later "Move fast with solid infrastructure"), contrasted with Google and VMware who stayed strategic.
 No named Red Flag.
3. **Caveats.** The 10-20% and 6-18 months figures are the author's opinion with no data; Figure 3.1 (tactical vs strategic progress curves, tactical ahead at first then falling behind) is qualitative only. A company can succeed either way (Facebook), but it is more pleasant and cheaper long-term with clean code.
4. **Key terms.** Tactical programming; strategic programming; tactical tornado; technical debt; investment mindset.
5. **Quotes.** "Your primary goal must be to produce a great design, which also happens to work." / "Unlike financial debt, most technical debt is never fully repaid: you'll keep paying and paying forever."
6. **Clean Code.** Not named; broadly aligned in spirit (continual cleanup).
7. **Web SaaS?** Highly relevant to an early product sold to other companies: small, steady design investment and fixing problems when found beats "ship now, clean later"; the 10-20% budget is a usable planning number.

## Chapter 4 - Modules Should Be Deep
1. **Core argument.** Modular design splits a system into modules, each with an interface (what outsiders must know) and an implementation. The best modules are deep: lots of functionality behind a small, simple interface. Depth is cost vs benefit: benefit is functionality, cost is interface complexity. Shallow modules (complex interface for little function) and the "classes should be small" convention (classitis) add system complexity.
2. **Rules/principles.**
 1. Minimise dependencies between modules; the ideal (full independence) is unreachable. In an ideal system complexity equals that of the worst module.
 2. A developer should need the interface and implementation of their own module plus only the interfaces of modules it calls. "Module" includes classes, methods/functions, subsystems and services (interface may be kernel calls or HTTP requests).
 3. The best modules have interfaces much simpler than implementations: (a) lower burden on the rest of the system; (b) implementation can change without touching others.
 4. An interface has formal parts (signatures, types, exceptions: language-checkable) and informal parts (behaviour, usage-order constraints: only comments can express them). Anything a developer must know to use the module is part of the interface; the informal part is usually bigger. A clear interface removes unknown unknowns.
 5. An abstraction is a simplified view that omits unimportant details. It fails by including unimportant details (extra load) or omitting important ones (a **false abstraction**, causing obscurity). Example: file system hides block allocation but must expose rules about when data reaches storage, because databases need it.
 6. Make modules deep. Examples: Unix file I/O (five calls, open/read/write/lseek/close, hiding hundreds of thousands of lines and unchanged for decades); garbage collection (no interface at all, and it shrinks the system's interface by removing explicit freeing).
 7. **Red Flag: Shallow Module** - interface is complicated relative to the functionality it provides; the benefit of not learning internals is cancelled by the cost of learning the interface. "Small modules tend to be shallow." Example: a one-line wrapper method that just puts a null value into a map, which is longer to document and call than the direct line.
 8. Avoid **classitis**: "classes are good, so more classes are better." Splitting every class or every method longer than N lines (N maybe 10) yields many shallow pieces whose interfaces add up system-wide complexity and boilerplate.
 9. Make the common case simple, with defaults. Example: Java needed three stacked stream objects (file, buffered, object) to read serialised objects, and forgetting the buffering object silently makes I/O slow; Unix made sequential access the default with lseek optional. If an interface has many features but most users need few, its effective complexity is that of the common ones; keep rarely used controls cleanly separated.
3. **Caveats.** Shallow classes (e.g. a linked list) are sometimes unavoidable and still useful, just give little leverage. Footnote: formal specification languages could in theory replace informal interface description, but the author thinks English is more understandable.
4. **Key terms.** Module; interface (formal/informal); implementation; abstraction; false abstraction; deep/shallow module; classitis. Figure 4.1 (not reproduced in text): rectangles, area = functionality, top edge = interface complexity.
5. **Quotes.** "The best modules are those whose interfaces are much simpler than their implementations." / "Interfaces are good, but more, or larger, interfaces are not necessarily better!"
6. **Clean Code.** The chapter does not name it, but it directly opposes the common advice that classes and methods should be small and methods split once beyond a handful of lines ("Any method longer than N lines should be divided", N as low as 10); the author calls this classitis. (Section 9.8 explicitly discusses Clean Code; outside this slice.)
7. **Web SaaS?** Strong fit: prefer a few service modules with narrow, defaulted APIs (e.g. one "send email" function that handles retries, rendering, limits internally) over many thin helpers; HTTP APIs and DB access layers are modules too.

## Chapter 5 - Information Hiding (and Leakage)
1. **Core argument.** Information hiding (Parnas) is the main route to deep modules: each module encapsulates a few design decisions (data structures, algorithms, formats, assumptions) in its implementation and keeps them out of its interface. It lowers complexity twice: simpler interfaces, and changes to a hidden decision touch one module only. The opposite, information leakage, is when one design decision shows up in several modules, and the commonest cause is temporal decomposition (structuring by order of execution). Fixes often mean making a class slightly larger so all knowledge of one thing lives together.
2. **Rules/principles.**
 1. Each module hides a few design decisions; when you can hide more, you can simplify the interface and so deepen the module. Making a field `private` is not information hiding if getters/setters expose its nature just as publicly.
 2. Total hiding is best; partial hiding still helps (a rarely needed feature offered through separate methods, so common users never see it).
 3. **Red Flag: Information Leakage** - the same knowledge (e.g. a file format) used in more than one place. Back-door leakage (not visible in any interface, e.g. one class reads and another writes a format) is worse than interface leakage because it is not obvious. Response: ask how to reorganise so the knowledge affects one class; options are to merge small tightly-bound classes, or extract a new class that encapsulates just that knowledge, but only if it has a simple interface (otherwise you just moved the leak into an interface).
 4. **Red Flag: Temporal Decomposition** - code structure mirrors execution order (read class, modify class, write class), so knowledge needed at several times is encoded in several places. Design around the knowledge needed for tasks, not the order of operations. Order will still show up in code but not necessarily in module boundaries.
 5. Example (HTTP server, from student projects): one team split reading a request from parsing it; but Content-Length requires parsing headers to know how much to read, so both classes needed the format and the caller had to call two methods in order. Merge into one class: better hiding and a one-method interface. General theme: information hiding often improves by making a class slightly larger, either to gather all code for one capability or to raise the interface level (one method for a three-step computation). The merged class is deeper.
 6. Hide distinctions callers do not care about: students merged parameters from URL and body, and decoded URL encoding inside the parser. Do not expose internal data structures: a `getParams()` that returns the internal map is shallow, leaks the representation, forces two-step access and risks callers mutating internal state. Prefer `getParameter(name)` and typed variants such as `getIntParameter(name)`, which also hide string-to-int conversion.
 7. Provide good defaults: one team made callers specify the HTTP version for a response, though it must match the request and the library can supply it (likewise the Date header). Defaults are partial information hiding and make the common case simple; classes should "do the right thing" without being asked (Java's explicit buffering is the negative example). "The best features are the ones you get without even knowing they exist."
 8. **Red Flag: Overexposure** - an API for a common feature forces users to learn about rarely used features, raising cognitive load.
 9. Apply hiding inside a class too: private methods should each encapsulate something, and minimise how many places use each instance variable.
3. **Caveats / taking it too far.** Only hide what is not needed outside; if callers really need it (e.g. performance-tuning configuration parameters) it must be exposed. Prefer self-adjusting modules over exposing tunables, but recognise what must be visible. Larger classes can go too far (one class for the whole app); chapter 9 covers when to split.
4. **Key terms.** Information hiding; information leakage (interface vs back-door); temporal decomposition; overexposure; partial information hiding.
5. **Quotes.** "Information leakage is one of the most important red flags in software design." / "The best features are the ones you get without even knowing they exist."
6. **Clean Code.** Not named. Implicitly opposes decomposition into many small steps-in-order classes; favours larger, deeper classes.
7. **Web SaaS?** Very applicable: a stored format or business rule (e.g. how an email body is rendered, how stages are counted) should be owned by one module that both reading and writing code call; do not leak DB row shapes through route handlers; sensible defaults on service functions.

## Chapter 6 - General-Purpose Modules are Deeper
1. **Core argument.** Over-specialisation is possibly the single biggest cause of complexity; "somewhat general-purpose" modules (functionality for today's needs, interface general enough for several uses) are simpler, deeper, hide more information and often need less code. Specialised code is unavoidable but should be pushed up (into the application/feature layer) or down (into plug-in-like drivers) away from general mechanisms. The same thinking applies inside method bodies: design the normal case so special cases disappear.
2. **Rules/principles.**
 1. Build new modules "somewhat general-purpose": implementation reflects current needs, interface does not tie itself to them. "Somewhat" matters: do not build something too general to use easily today. Author reversed his earlier preference for special-purpose after reviewing student work; even single-use classes were less work when general.
 2. Example (GUI text editor text class): students gave the text class UI-shaped methods (backspace, delete, deleteSelection taking Cursor/Selection types). Result: many shallow, once-used methods, UI abstractions leaking into the text class, and every new UI feature requiring a text-class change. Better API: generic `insert(position, string)`, `delete(start, end)`, `changePosition(position, n)`; backspace and delete keys become one line each in UI code. It is slightly longer at the call site but more obvious (UI developers see exactly which characters go), and less code overall; it could also serve a find-and-replace tool by adding just `findNext`.
 3. Generality gives better information hiding, and spares reading. The old `backspace` method was a **false abstraction**: UI developers had to read it anyway. When details matter to the caller, make them explicit and obvious rather than hiding them. "Determine who needs to know what, and when."
 4. Three questions: (a) What is the simplest interface covering all current needs? (fewer methods without piling on parameters). (b) In how many situations will this method be used? A method built for one use is a red flag that it is too special-purpose. (c) Is the API easy to use for my current needs? If callers must write much extra code, you have over-generalised (example: single-character insert/delete is general but forces loops and is inefficient, so range operations are better).
 5. Push specialisation upwards (editor UI behaviour lives in the UI layer, text class stays generic) or downwards (device drivers implement generic read-block/write-block interfaces so the OS core knows no device specifics, and new devices need no OS change).
 6. Example (undo): students put the whole undo mechanism in the text class including callbacks for selection/cursor; it leaked and was awkward. Better: separate `History` class that manages a list of `Action` objects (each with undo/redo) plus "fences" for grouping, knowing nothing about what actions do; specific action classes (UndoableInsert, UndoableSelection) live with the modules that understand them; grouping policy lives in high-level UI code. Splitting one general mechanism from its special-purpose parts "made the rest fall out naturally".
 7. Separate special from general only within the same mechanism; special-purpose undo code for text can sensibly live in the text class (related to text functions) even though text is general-purpose for text management.
 8. Eliminate special cases in code: design the normal case so edge conditions are handled with no extra code. Example: editor selection. Most students kept a boolean for "selection exists" and sprinkled checks everywhere; better to always have a selection and represent "none" as an empty selection (start == end). Copying zero bytes, or deleting by joining the text before and after the selection, then work unchanged with no special branch. (Chapter 10 returns to this for exceptions.) Special cases make code if-ridden and bug-prone.
 9. Prose-level red flag (unboxed): a method designed for exactly one use, like backspace, may be too special-purpose. No formal Red Flag box appears in this chapter's text (the 'General-Specific Mixture' box of the book's summary is not in this extract).
3. **Caveats.** Specialisation cannot be eliminated; do not over-generalise (the "somewhat" qualifier and question (c)). The general-purpose-first stance contradicts the cautious "build only what you need now" incremental view; the author argues general interfaces cost no more.
4. **Key terms.** General-purpose vs special-purpose; false abstraction; push specialisation up/down; fence (in the History class); somewhat general-purpose.
5. **Quotes.** "I now think that over-specialization may be the single greatest cause of complexity in software." / "One of the most important elements of software design is determining who needs to know what, and when."
6. **Clean Code.** Not named. Tension with YAGNI-flavoured advice to build only today's feature; the author says general interface, current-need implementation.
7. **Web SaaS?** Yes: avoid endpoints/service functions shaped around one screen's button (e.g. `markCandidateSubmittedFromBoardDrag`); expose general operations and put UI-specific policy in the route/frontend layer; push vendor-specific logic down into adapters (relevant to provider-neutral integrations).

## Chapter 7 - Different Layer, Different Abstraction
1. **Core argument.** Systems are layered, and each layer should offer a different abstraction from the one above and below (file -> block cache -> device driver; TCP byte stream -> best-effort packets). Adjacent layers with similar abstractions signal a bad class decomposition. It shows up as pass-through methods, decorators that duplicate APIs, interfaces mirroring their own implementation, and pass-through variables. Every piece of design infrastructure adds complexity, so it must remove more than it adds.
2. **Rules/principles.**
 1. **Red Flag: Pass-Through Method** - a method that only forwards its arguments to another method, usually with the same signature. Reasoning: it enlarges the interface without adding function (shallower), couples the two classes' signatures, and signals fuzzy division of responsibility. Example: a student TextDocument class where 13 of 15 public methods just called TextArea. Rule: the interface to a feature should live in the class that implements it. Fixes (Figure 7.1): let callers use the lower class directly; redistribute functionality between the classes; or merge them (the student collapsed three classes into two).
 2. Same-signature methods are fine when each adds real function: a **dispatcher** (selects among handlers, e.g. a web server routing a URL to a file or script) and multiple implementations of one interface (disk drivers), which reduces cognitive load since you learn the interface once; such methods sit in one layer and do not call each other.
 3. **Decorators** (wrappers) encourage cross-layer API duplication; they tend to be shallow, full of pass-throughs, and overused to make a new class per small feature (Java I/O: BufferedInputStream over InputStream; ScrollableWindow over Window). Before writing one: (a) add the function to the underlying class if general-purpose, logically related, or used by most users (buffering should have been built in); (b) merge it into the specialised use case; (c) merge into an existing decorator for one deeper wrapper; (d) consider a stand-alone class that does not wrap (scrollbars need not wrap the window). Wrappers make sense mainly to adapt an unmodifiable external class to a different interface, and that is rare.
 4. Interface should differ from implementation: if they share the same abstraction the class is probably shallow. Example: text module stored as lines internally but also exposed `getLine`/`putLine`, forcing UI code to split and join lines in many places; a character-oriented `insert`/`delete` (allowing newlines) hides the line handling, making the class deeper.
 5. **Pass-through variables** (a value, such as certificate settings parsed from a command line, threaded through many intermediate methods that do not use it) force every intermediate signature to know about it and make adding new ones expensive. Options: store it in an object already shared by top and bottom (but that object may itself be pass-through); a global variable (avoid: prevents two independent instances in one process, which hurts tests); or, the author's most-used solution, a **context object** holding all global state (config, shared subsystems, counters), one per system instance, whose reference is saved in major objects and passed explicitly only to constructors. Benefits: new state added in one place, easy testing by changing fields. Drawbacks: has most downsides of globals, can become a grab-bag creating non-obvious dependencies, thread-safety concerns (prefer immutable values); author admits he has found no better solution.
 6. Conclusion rule: any interface, argument, function, class or definition adds complexity and is justified only if it removes more complexity than it introduces.
 Named Red Flags in this chapter: Pass-Through Method. (The chapter also frames "adjacent layers with similar abstractions" as a red flag in prose.)
3. **Caveats.** Duplicated signatures are acceptable for dispatchers and interface implementations; wrappers are acceptable for adapting external classes; contexts are an imperfect, not ideal, remedy.
4. **Key terms.** Layer; abstraction per layer; pass-through method; dispatcher; decorator/wrapper; pass-through variable; context object.
5. **Quotes.** "Pass-through methods indicate that there is confusion over the division of responsibility between classes." / "Contexts are far from an ideal solution."
6. **Clean Code.** Not named. Implicitly critiques extra wrapper/decorator classes and tiny delegating layers that small-class styles can produce.
7. **Web SaaS?** Very applicable: route -> service -> model -> db wrapper layers that only forward arguments are pass-through methods; request-scoped context (org, user, config) is the book's "context object" and avoids threading `orgId` through every function, with the book's warning about grab-bags and immutability; middleware and DB helper wrappers should each add real function.
