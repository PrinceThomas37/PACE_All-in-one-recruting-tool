## 1. What the owner asked at the start

  sub-agent workers → tools verify*. Asked: can this chat switch between Opus / Sonnet / Haiku agents; create or edit those agents;

## 2. The cost answer (prices from Anthropic's price table, per 1M tokens)
| Model | Fresh input | Re-read (cached) input | Output (incl. thinking) |
|---|---|---|---|
| Opus 5.5 | $4.00 | $0.20 | $20 |
| Sonnet 5.5 | $2.00 | $0.20 | $10 |
| Haiku 5.5 | $0.10 | (lower still) | $0.50 |

- **Agent work is ~90% re-reading** (every step re-sends the conversation) and re-reads cost the same on Opus and Sonnet, so Opus vs
  Sonnet is ~1.5–2×, not more. "High effort" costs more because more thinking = more output tokens.
- **Haiku is ~10–20× cheaper per run**, but the cost that matters is per *finished* task: a wrong change to email-sending code means a
  redo on a bigger model plus possible wrong emails to real clients. **Haiku belongs on read-only look-ups, not on building.**
- **One agent's start-up cost** (files it must read first): CLAUDE.md 21 KB + territory README 7 KB + its agent file + its memory —
  the surface memory alone was 176 KB (~44k tokens) and was trimmed to ~38 KB (archive kept in `docs/territories/surface-archive.md`).
- **Rough per-task estimate, a medium screen change (~25 steps):** directly in the chat ≈ $1 · Sonnet agent ≈ $1 + ~$0.15 to brief and
  check it · Haiku agent ≈ $0.05–0.10 (not safe for this code) · Opus agent at high effort ≈ $2–3. [Guess on totals; per-token prices
  are firm.] On the claude.ai plan this shows as usage-limit consumption, not a bill — the ratios are the same.
- **Conclusion: agents do not save money on small fixes; they save the chat's memory space and allow parallel work.** Use them for big
  features and batches only — and only with the owner's yes (D-0060).

### Agent changes made (R-308)
- New **`scout`** agent on Haiku (`.claude/agents/scout.md`): Read/Grep/Glob only, cannot edit; answers "where is X" with file:line.
- `effort: medium` on the Sonnet builders (surface, gateway, guild, foundry). Opus stays on harbour (email), rampart (security),
  deep (data), observatory (AI), ledger, dispatch — where a mistake reaches customers.

## 5. How the work was run (lessons worth keeping)
- One PR at a time on the session branch; the next piece is stashed until the open one merges, so a merge carries exactly what was tested.
- Full suite on BOTH Node 22 and Node 26 from a **clean `git worktree` of the exact PR head** — a run from the tree being edited tests a mix,
  and an old log file once read as a new pass (said to the owner and corrected).
- A flake that will not reproduce is found by reading the interleaving and then FORCED in a test (R-322), never retried until green.
- Screenshots catch what tests miss (the invisible tile numbers in the dark theme) — then a test is added for it (contrast check).
- Continue in a **new chat** after the hand-off is written: CONTEXT_WINDOW.md + this file + ROADMAP/DECISIONS carry the state; compaction is lossy.
